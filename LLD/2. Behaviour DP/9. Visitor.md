# Pattern 9: Visitor

> **TL;DR:** **Visitor** lets you add **new operations** to a stable family of classes **without modifying them**: each element "accepts" a visitor and calls back the visitor method for its own type (**double dispatch**). Great when the **class structure is fixed** but **operations keep growing** (e.g., AST: type-check, optimize, pretty-print).

---

## 1. Problem it solves

**Without the pattern:** every new operation invades every class — or type-checks pile up.

```python
# Option A: keep adding methods to every shape class
class Circle:
    def area(self): ...
    def to_svg(self): ...        # new feature -> edit Circle
    def to_json(self): ...       # another -> edit Circle AGAIN (and Square, and Line...)

# Option B: external function with isinstance ladder
def export_svg(shape):
    if isinstance(shape, Circle): ...
    elif isinstance(shape, Square): ...
    elif isinstance(shape, Line): ...     # forget one -> silent bug
```

Problems:

- Option A: classes **bloat** with unrelated responsibilities (geometry + SVG + JSON + ...), and may be unmodifiable (library code).
- Option B: fragile **isinstance ladders** duplicated per operation; no error if a type is forgotten.

**With the pattern:** each operation = **one visitor class** with a method per element type; elements only need a tiny `accept()`.

---

## 2. Real-world analogy

An **insurance agent** visiting buildings: at a *house* he sells home insurance, at a *bank* he sells theft insurance, at a *café* fire insurance. The buildings don't change — the agent (visitor) carries type-specific behavior. Next week a **tax inspector** (new visitor) visits the same buildings doing something entirely different — still zero changes to the buildings.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Element** (interface) | `accept(visitor)` | `Shape.accept()` |
| **Concrete Elements** | `accept` calls the visitor method **for their type** | `Circle`, `Square` |
| **Visitor** (interface) | One `visit_X()` per element type | `ShapeVisitor` |
| **Concrete Visitors** | One class per **operation** | `AreaCalculator`, `SVGExporter` |

```text
client ──> element.accept(visitor) ──> visitor.visit_circle(self)
                 (1st dispatch:               (2nd dispatch:
                  which element?)              which operation?)
            = DOUBLE DISPATCH: behavior picked by BOTH types
```

---

## 4. Python implementation

```python
from abc import ABC, abstractmethod
import math


# ----- Elements: stable hierarchy, touched ONCE (to add accept) -----
class Shape(ABC):
    @abstractmethod
    def accept(self, visitor: "ShapeVisitor"): ...


class Circle(Shape):
    def __init__(self, radius: float):
        self.radius = radius

    def accept(self, visitor: "ShapeVisitor"):
        return visitor.visit_circle(self)        # "I am a Circle" — no isinstance needed


class Square(Shape):
    def __init__(self, side: float):
        self.side = side

    def accept(self, visitor: "ShapeVisitor"):
        return visitor.visit_square(self)


# ----- Visitor interface: one method per element type -----
class ShapeVisitor(ABC):
    @abstractmethod
    def visit_circle(self, circle: Circle): ...

    @abstractmethod
    def visit_square(self, square: Square): ...


# ----- Each OPERATION = one visitor class (classes above stay untouched) -----
class AreaCalculator(ShapeVisitor):
    def visit_circle(self, circle):
        return math.pi * circle.radius ** 2

    def visit_square(self, square):
        return square.side ** 2


class SVGExporter(ShapeVisitor):
    def visit_circle(self, circle):
        return f'<circle r="{circle.radius}"/>'

    def visit_square(self, square):
        return f'<rect width="{square.side}" height="{square.side}"/>'


shapes: list[Shape] = [Circle(2), Square(3)]

area, svg = AreaCalculator(), SVGExporter()
for shape in shapes:
    print(f"{shape.accept(svg):30} area={shape.accept(area):.2f}")
```

```text
<circle r="2"/>                 area=12.57
<rect width="3" height="3"/>    area=9.00
```

- New operation (`JSONExporter`, `PerimeterCalculator`) = **one new visitor class**; shapes untouched.
- Forgetting a type = **abstract method error**, not a silent isinstance fall-through.
- Why not just `visitor.visit(shape)`? Python picks methods by **one** type (single dispatch). `accept` lets the *element* route to its own `visit_X` — that's **double dispatch**.

### Pythonic alternative — `functools.singledispatch`

```python
from functools import singledispatch

@singledispatch
def to_svg(shape) -> str:
    raise NotImplementedError(f"no SVG export for {type(shape)}")

@to_svg.register
def _(circle: Circle) -> str:
    return f'<circle r="{circle.radius}"/>'

@to_svg.register
def _(square: Square) -> str:
    return f'<rect width="{square.side}" height="{square.side}"/>'


print(to_svg(Circle(5)))
```

```text
<circle r="5"/>
```

- Dispatch-by-type **without touching the classes at all** (no `accept` needed) — Python's native half of Visitor.

## 5. When to use / when NOT to use

**Use when:**

- The element hierarchy is **stable**, but you keep adding **operations** (compilers/ASTs: type-check, optimize, codegen, pretty-print — `ast.NodeVisitor` in the stdlib!).
- Operations need type-specific behavior across a **Composite** tree (file trees: size, search, export).
- You want related behavior **gathered in one class** instead of smeared over 20 element classes.

**Avoid when:**

- The **element hierarchy changes often** — every new element type forces a new `visit_X` in *every* visitor (the pattern's Achilles heel).
- Operations are few and natural members of the classes — keep them as plain methods.
- Visitors need deep access to element internals — may force breaking encapsulation.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| New operations without touching element classes (OCP) | New **element type** → update every visitor |
| Related behavior in one visitor class (SRP) | Elements may need to expose internals to visitors |
| Visitors accumulate state while traversing (e.g., totals) | Indirection of double dispatch is hard to read at first |
| Type-safe: missing visit method = loud error | `accept()` boilerplate in every element |

---

## 7. Visitor vs. similar patterns

| Compared with | Difference |
|---|---|
| **Iterator** | Iterator hands elements **out** for external processing; Visitor sends an operation **in**, with per-type behavior. They combine well (iterate + visit). |
| **Composite** | Natural partners: Visitor is *the* way to run type-aware operations over a Composite tree. |
| **Strategy** | Strategy = one algorithm family, swap per context. Visitor = one operation spread across **many types** at once. |
| **singledispatch** | Single dispatch (by one argument's type) covers most Python needs; classic Visitor exists for **double** dispatch in languages without it. |

---

## 8. Quick recap

- `element.accept(visitor)` → `visitor.visit_<type>(element)` = **double dispatch**.
- One visitor class per **operation**; one visit method per **element type**.
- Trade-off axis: easy to add **operations**, painful to add **element types** (exact opposite of plain inheritance).
- Stdlib proof it matters: `ast.NodeVisitor`.
- Pythonic lite: `functools.singledispatch`.

---

## 9. Interview Q&A

**Q1. What is the Visitor pattern?**
A way to define new operations over a fixed set of element classes without modifying them: elements implement `accept(visitor)` which calls the visitor method matching their concrete type, so each operation lives in its own visitor class.

**Q2. Explain double dispatch and why Visitor needs it.**
The executed behavior depends on **two** runtime types: the element and the visitor. Most OO languages dispatch on one (the receiver). Visitor simulates the second dispatch via `accept`: the element (knowing its own type) calls the matching `visit_X`.

**Q3. The classic trade-off question: Visitor vs adding methods to classes?**
Plain methods: easy to add **element types**, hard to add operations (edit all classes). Visitor: easy to add **operations**, hard to add element types (edit all visitors). Pick by which axis of your design changes more often.

**Q4. Where is Visitor used in real tooling?**
Compilers and interpreters over ASTs — Python's `ast.NodeVisitor`/`NodeTransformer`, linters (pylint/flake8 checkers are visitors), serializers walking document trees, static analyzers.

**Q5. How does Python reduce the need for full Visitor?**
`functools.singledispatch` registers type-specific implementations of a function without touching the classes; duck typing and `match` statements (3.10+) also cover simple cases. Classic Visitor remains useful for strict completeness and stateful traversals.
