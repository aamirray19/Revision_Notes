# Pattern 5: Mediator

> **TL;DR:** **Mediator** replaces tangled **many-to-many** communication between objects with a central **hub**: colleagues talk only to the mediator, which contains the interaction logic. n² pairwise links collapse into n links. Think air-traffic control: planes never coordinate with each other directly.

---

## 1. Problem it solves

**Without the pattern:** every component knows and pokes every other component.

```python
class CheckoutForm:
    def on_country_changed(self):
        self.state_dropdown.reload(self.country.value)
        self.zip_field.set_format(self.country.value)
        self.shipping_options.refresh(self.country.value)
        self.submit_button.set_enabled(self.validate_all())
        # every widget updates every other widget — n² spaghetti
```

Problems:

- Components are **coupled to each other** — none is reusable alone (`state_dropdown` drags along the whole form).
- Interaction logic is **smeared across all components**.
- n components → up to **n(n−1)/2 connections** to maintain.

**With the pattern:** each widget only reports "I changed" to the **mediator (the form/dialog)**, which alone decides who must react.

---

## 2. Real-world analogy

**Air traffic control**: planes never negotiate landing order with each other ("hey 747, you go first?") — that would be chaos. Every pilot talks **only to the tower**, which knows the whole picture and coordinates everyone. New plane in the airspace? Nobody else's procedures change.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Mediator** (interface) | Receives notifications from colleagues | `notify(sender, event)` |
| **Concrete Mediator** | Contains ALL coordination logic | `SignupDialog` |
| **Colleagues** | Do their own job; report events to mediator only | `Checkbox`, `TextBox`, `Button` |

```text
WITHOUT:  A ↔ B, A ↔ C, A ↔ D, B ↔ C, B ↔ D, C ↔ D     (n² links)

WITH:         A ──┐
              B ──┼──> Mediator (owns the interaction rules)
              C ──┤        │
              D ──┘        └──> tells exactly who must react
```

## 4. Python implementation

```python
from abc import ABC, abstractmethod


# ----- Mediator interface -----
class Mediator(ABC):
    @abstractmethod
    def notify(self, sender: object, event: str) -> None: ...


# ----- Colleagues: dumb components, reusable anywhere -----
class Component:
    def __init__(self, mediator: Mediator | None = None):
        self.mediator = mediator


class Checkbox(Component):
    def __init__(self, mediator=None):
        super().__init__(mediator)
        self.checked = False

    def toggle(self) -> None:
        self.checked = not self.checked
        self.mediator.notify(self, "toggled")        # just report; no peer-poking


class TextBox(Component):
    def __init__(self, mediator=None):
        super().__init__(mediator)
        self.text = ""
        self.visible = False

    def type(self, text: str) -> None:
        self.text = text
        self.mediator.notify(self, "typed")


class Button(Component):
    def __init__(self, mediator=None):
        super().__init__(mediator)
        self.enabled = False

    def click(self) -> None:
        if self.enabled:
            self.mediator.notify(self, "clicked")
        else:
            print("[Button] disabled — ignoring click")


# ----- Concrete Mediator: ALL the wiring lives HERE -----
class SignupDialog(Mediator):
    def __init__(self):
        self.has_coupon = Checkbox(self)
        self.coupon_code = TextBox(self)
        self.submit = Button(self)

    def notify(self, sender: object, event: str) -> None:
        if sender is self.has_coupon and event == "toggled":
            self.coupon_code.visible = self.has_coupon.checked
            print(f"[Dialog] coupon field visible: {self.coupon_code.visible}")
            self._update_submit()
        elif sender is self.coupon_code and event == "typed":
            self._update_submit()
        elif sender is self.submit and event == "clicked":
            print(f"[Dialog] submitting with coupon: {self.coupon_code.text or 'none'}")

    def _update_submit(self) -> None:
        ok = (not self.has_coupon.checked) or bool(self.coupon_code.text)
        self.submit.enabled = ok
        print(f"[Dialog] submit enabled: {ok}")


dialog = SignupDialog()
dialog.submit.enabled = True

dialog.has_coupon.toggle()          # coupon required now → submit disabled
dialog.submit.click()               # blocked
dialog.coupon_code.type("SAVE20")   # typing re-enables submit
dialog.submit.click()
```

```text
[Dialog] coupon field visible: True
[Dialog] submit enabled: False
[Button] disabled — ignoring click
[Dialog] submit enabled: True
[Dialog] submitting with coupon: SAVE20
```

- `Checkbox`, `TextBox`, `Button` know **nothing about each other** — fully reusable in any dialog.
- All interaction rules are **in one readable place** (`SignupDialog.notify`).

### Classic second example — chat room

```python
class ChatRoom:                                   # mediator
    def __init__(self):
        self._users: list["User"] = []

    def join(self, user: "User") -> None:
        self._users.append(user)
        user.room = self

    def broadcast(self, sender: "User", message: str) -> None:
        for user in self._users:
            if user is not sender:                # routing logic lives here
                user.receive(sender.name, message)


class User:                                       # colleague
    def __init__(self, name: str):
        self.name, self.room = name, None

    def send(self, message: str) -> None:
        self.room.broadcast(self, message)        # users never message each other directly

    def receive(self, sender: str, message: str) -> None:
        print(f"{self.name} got from {sender}: {message}")


room = ChatRoom()
alice, bob, carol = User("Alice"), User("Bob"), User("Carol")
for u in (alice, bob, carol):
    room.join(u)

alice.send("Hi all!")
```

```text
Bob got from Alice: Hi all!
Carol got from Alice: Hi all!
```

## 5. When to use / when NOT to use

**Use when:**

- A set of objects communicate in **complex many-to-many** ways (form widgets, chat participants, aircraft, game entities in a scene).
- You can't **reuse a component** because it drags its peers along.
- Interaction rules change often — better to edit **one mediator** than n components.

**Avoid when:**

- Only two objects interact, or interactions are trivial — direct calls are clearer.
- The mediator is absorbing **business logic that belongs in components** — watch for the **god object** smell.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| n² peer links → n links to one hub | Mediator can grow into a **god object** |
| Components decoupled → individually reusable & testable | Single point of complexity (and failure) |
| Interaction logic centralized in one place (SRP) | Extra indirection for simple interactions |
| New interaction rules → edit mediator only (OCP-ish) | |

---

## 7. Mediator vs. similar patterns

| Compared with | Difference |
|---|---|
| **Observer** | Observer: subject **broadcasts blindly** to whoever subscribed (one-to-many). Mediator: hub **knows the colleagues** and applies routing/coordination **logic** (many-to-many). Mediators are often built *using* observer internally. |
| **Facade** | Facade: one-way simplification of a subsystem that doesn't know the facade exists. Mediator: colleagues **actively participate**, sending events to the hub (two-way protocol). |
| **Controller (MVC)** | The controller coordinating views/models is mediator-ish — centralizing interaction is the same instinct. |
| **Message broker** | A broker (RabbitMQ/Kafka) is a distributed mediator: endpoints know only the broker, never each other. |

---

## 8. Quick recap

- Colleagues never reference each other — only `mediator.notify(self, event)`.
- **All interaction logic in one class** → components stay dumb & reusable.
- Turns n² coupling into n.
- Watch the one risk: mediator becoming a **god object**.
- Real examples: dialog controllers, chat rooms, ATC, event buses.

---

## 9. Interview Q&A

**Q1. What is the Mediator pattern?**
It centralizes many-to-many communication: components send events only to a mediator object, which contains the coordination logic and decides who reacts — removing direct peer-to-peer coupling.

**Q2. Mediator vs Observer — the classic?**
Observer is an unaware broadcast: the subject notifies subscribers without knowing them or containing routing logic. Mediator is an aware coordinator: it knows its colleagues and encodes *rules* about how they interact. (A mediator may use observer as its delivery mechanism.)

**Q3. What's the main risk of Mediator and how do you mitigate it?**
The mediator becoming a **god object** hoarding logic. Mitigate by keeping colleague-specific behavior in colleagues, splitting large mediators per use-case, and keeping the mediator to pure *coordination*.

**Q4. Where does Mediator appear in real systems?**
UI dialog/form controllers, chat servers, air-traffic control, event buses, message brokers, game engines coordinating entities, Django's `Form` clean/validation coordinating fields.

**Q5. How does Mediator improve testability?**
Colleagues can be unit-tested with a mock mediator (just assert `notify` calls), and interaction rules can be tested in the mediator with stub colleagues — instead of wiring up the whole object web.
