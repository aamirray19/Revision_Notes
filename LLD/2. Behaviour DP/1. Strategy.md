# Pattern 1: Strategy

> **TL;DR:** **Strategy** encapsulates a family of **interchangeable algorithms** behind one interface so the client can pick/swap one at **runtime** — replacing `if/elif` chains with pluggable objects. In Python, strategies are often just **functions** passed as arguments (e.g., `sorted(key=...)`).

---

## 1. Problem it solves

**Without the pattern:** algorithm choice buried in conditionals.

```python
class ShippingCalculator:
    def cost(self, order, method):
        if method == "standard":
            return order.weight * 5
        elif method == "express":
            return order.weight * 10 + 50
        elif method == "overnight":
            return order.weight * 20 + 150
        # new method? edit this class AGAIN
```

Problems:

- Every new algorithm **modifies** the class (violates Open/Closed).
- The class accumulates **unrelated algorithm details** and their imports/helpers.
- Can't easily unit-test one algorithm or swap it per customer/config.

**With the pattern:** each algorithm is its own class/function; the calculator just **uses whichever it's given**.

---

## 2. Real-world analogy

Getting to the **airport**: you can drive, take a cab, or ride a bus. The goal is fixed (reach the airport); the **strategy** is interchangeable, chosen at the moment based on budget/time. You don't rebuild the trip — you swap the transport.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Strategy** (interface) | Common interface for all algorithms | `ShippingStrategy.calculate()` |
| **Concrete Strategies** | One class per algorithm | `Standard`, `Express`, `Overnight` |
| **Context** | Holds a strategy reference; delegates to it | `ShippingCalculator` |
| **Client** | Picks the strategy and gives it to the context | checkout code |

```text
Client ──picks──> Strategy ──injected into──> Context
                     ▲                        calculate() ──delegates──> strategy.calculate()
        ┌────────────┼────────────┐
    Standard      Express     Overnight
```

## 4. Python implementation

### 4a. Classic class-based strategies

```python
from abc import ABC, abstractmethod


# ----- Strategy interface -----
class ShippingStrategy(ABC):
    @abstractmethod
    def calculate(self, weight: float) -> float: ...


# ----- Concrete Strategies -----
class Standard(ShippingStrategy):
    def calculate(self, weight: float) -> float:
        return weight * 5


class Express(ShippingStrategy):
    def calculate(self, weight: float) -> float:
        return weight * 10 + 50


class Overnight(ShippingStrategy):
    def calculate(self, weight: float) -> float:
        return weight * 20 + 150


# ----- Context -----
class ShippingCalculator:
    def __init__(self, strategy: ShippingStrategy):
        self.strategy = strategy                 # swappable at any time

    def cost(self, weight: float) -> float:
        return self.strategy.calculate(weight)   # delegate — no if/elif!


calc = ShippingCalculator(Standard())
print("Standard:", calc.cost(10))

calc.strategy = Overnight()                      # runtime swap
print("Overnight:", calc.cost(10))
```

```text
Standard: 50
Overnight: 350.0
```

### 4b. Pythonic — functions ARE strategies

First-class functions make the pattern nearly invisible in Python:

```python
def standard(weight): return weight * 5
def express(weight): return weight * 10 + 50
def overnight(weight): return weight * 20 + 150

def shipping_cost(weight, strategy):             # strategy = any callable
    return strategy(weight)

print(shipping_cost(10, express))

# You already use Strategy daily:
words = ["banana", "fig", "apple"]
print(sorted(words, key=len))                    # `key` is a sorting strategy!
```

```text
150
['fig', 'apple', 'banana']
```

- `sorted(key=...)`, `max(key=...)`, `list.sort(key=...)`, callbacks, `json.dumps(default=...)` — all Strategy.

## 5. When to use / when NOT to use

**Use when:**

- Several **interchangeable ways** to perform one task exist (payment, compression, routing, pricing, validation).
- You want to choose/switch the algorithm **at runtime** (config, user choice, A/B tests).
- A class is bloated with a **conditional selecting behaviors** — extract each branch into a strategy.
- You want to **test algorithms in isolation** or add new ones without touching existing code.

**Avoid when:**

- Only one or two **stable** algorithms — a simple `if` is more readable than extra classes.
- Clients shouldn't have to know the differences between strategies (picking becomes their burden — consider pairing with a Factory).

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Swap algorithms at runtime | Client must know the strategies to choose one |
| Open/Closed: new algorithm = new class/function only | More objects/classes for simple cases |
| Isolates algorithm code (easy testing) | Extra indirection |
| Removes fat conditionals | In Python, often over-engineering vs plain functions |

---

## 7. Strategy vs. similar patterns

| Compared with | Difference |
|---|---|
| **State** | Structurally twins! Strategy: client picks it; strategies are independent & unaware of each other. State: transitions happen **internally**; states often know the next state. |
| **Template Method** | Template Method varies **steps** via inheritance (static, class-level); Strategy varies the **whole algorithm** via composition (dynamic, object-level). |
| **Command** | Command encapsulates a **request** (verb + receiver + args, undoable/queueable); Strategy encapsulates **how** something is computed. |
| **Bridge** | Same composition shape; Bridge is a **structural** split of abstraction/implementation hierarchies, Strategy swaps one behavior. |

---

## 8. Quick recap

- Family of algorithms, one interface, chosen at **runtime**.
- Context **delegates**, never `if/elif`s.
- New algorithm = new class/function; context untouched (**OCP**).
- Pythonic form: **pass a function** (`sorted(key=...)`).

---

## 9. Interview Q&A

**Q1. What is the Strategy pattern?**
Encapsulating interchangeable algorithms behind a common interface so the context can delegate to whichever it's configured with, enabling runtime swapping and eliminating conditional chains.

**Q2. Strategy vs State — the classic?**
Same structure (context + delegated objects). Strategy: the **client** selects the algorithm; strategies don't know each other and rarely change mid-flow. State: the **object/states themselves** drive transitions, and behavior change over time is the whole point.

**Q3. How does Python simplify Strategy?**
Functions are first-class — a strategy can be a plain function/lambda passed as a parameter (`sorted(key=...)`). No interface or class hierarchy needed unless strategies carry state/config.

**Q4. How does Strategy support SOLID?**
**OCP**: add algorithms without modifying the context. **SRP**: each algorithm lives in its own unit. **DIP**: context depends on the strategy abstraction.

**Q5. How do you avoid the client knowing all strategies?**
Combine with a **Factory** (map config/name → strategy) so selection logic lives in one place; the client passes a key, not a class.
