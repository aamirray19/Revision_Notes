# Pattern 3: Iterator

> **TL;DR:** **Iterator** provides a way to access elements of a collection **sequentially without exposing its internal structure** (array? tree? graph?). Python has this pattern **built into the language**: the iterator protocol (`__iter__`/`__next__`), `for` loops, and **generators** are all Iterator.

---

## 1. Problem it solves

**Without the pattern:** clients must know each collection's internals to traverse it.

```python
# list → index loop; dict → .items(); tree → manual stack; linked list → .next hops
i = 0
while i < len(my_list):
    process(my_list[i]); i += 1

node = linked_list.head
while node:                      # completely different traversal code!
    process(node.value); node = node.next
```

Problems:

- **Different traversal code per structure** — clients coupled to internals.
- Changing the underlying structure **breaks every loop** written against it.
- Multiple simultaneous traversals need separate cursor bookkeeping.
- Collection classes get bloated with traversal logic (SRP violation).

**With the pattern:** every collection hands out an **iterator object** with a uniform `next()` interface; clients write **one kind of loop** for everything.

---

## 2. Real-world analogy

A **TV remote's "next channel" button**: you don't need to know how channels are stored or ordered inside the TV — you just press *next* repeatedly until you've seen them all. Each remote (iterator) also remembers *its own* current position, so two people with two remotes... okay, don't try that at home.

---

## 3. Structure

| Role | Responsibility | Python equivalent |
|---|---|---|
| **Iterable** (collection) | Can produce an iterator | has `__iter__()` → iterator |
| **Iterator** | Tracks position; returns next element | has `__next__()` (+ `__iter__` returning self) |
| **Client** | Loops using the uniform protocol | `for x in collection:` |

```text
for x in collection  ≡  it = iter(collection)        # collection.__iter__()
                        while True:
                            x = next(it)             # it.__next__()
                            ... until StopIteration
```

---

## 4. Python implementation

### 4a. Custom iterable + iterator (the full protocol)

```python
class Playlist:
    """Iterable collection — hides HOW songs are stored."""
    def __init__(self):
        self._songs: list[str] = []

    def add(self, song: str) -> "Playlist":
        self._songs.append(song)
        return self

    def __iter__(self) -> "PlaylistIterator":
        return PlaylistIterator(self._songs)         # fresh iterator per loop


class PlaylistIterator:
    """Iterator — owns its OWN position; many can run at once."""
    def __init__(self, songs: list[str]):
        self._songs = songs
        self._index = 0

    def __iter__(self):
        return self                                  # iterators are also iterable

    def __next__(self) -> str:
        if self._index >= len(self._songs):
            raise StopIteration                      # the protocol's "no more items"
        song = self._songs[self._index]
        self._index += 1
        return song


playlist = Playlist().add("Song A").add("Song B").add("Song C")

for song in playlist:                                # uniform client code
    print("Playing:", song)

# Two independent traversals at once — each iterator has its own cursor:
it1, it2 = iter(playlist), iter(playlist)
print(next(it1), next(it1), "|", next(it2))
```

```text
Playing: Song A
Playing: Song B
Playing: Song C
Song A Song B | Song A
```

### 4b. Generators — iterators without the boilerplate

```python
class Playlist2:
    def __init__(self, songs):
        self._songs = list(songs)

    def __iter__(self):
        yield from self._songs                   # generator = auto-built iterator

    def shuffled(self):
        import random
        order = self._songs[:]
        random.shuffle(order)
        yield from order                         # alternative traversal strategy!


p = Playlist2(["A", "B", "C"])
print(list(p))
print(sorted(p.shuffled()))
```

```text
['A', 'B', 'C']
['A', 'B', 'C']
```

- `yield` makes Python **write the iterator class for you** (state machine included).
- Generators are **lazy** — perfect for huge/infinite sequences:

```python
def naturals():
    n = 0
    while True:                                  # infinite — impossible with a list!
        yield n
        n += 1

import itertools
print(list(itertools.islice(naturals(), 5)))
```

```text
[0, 1, 2, 3, 4]
```

### 4c. Tree traversal — hiding a complex structure

```python
class TreeNode:
    def __init__(self, value, left=None, right=None):
        self.value, self.left, self.right = value, left, right

    def __iter__(self):                          # in-order traversal, recursively
        if self.left:
            yield from self.left
        yield self.value
        if self.right:
            yield from self.right


tree = TreeNode(2, TreeNode(1), TreeNode(3))
print(list(tree))                                # client has NO idea it's a tree
```

```text
[1, 2, 3]
```

## 5. When to use / when NOT to use

**Use when:**

- You want clients to traverse a collection **without knowing its structure** (list/tree/graph/network stream).
- You need **multiple simultaneous** or **multiple kinds** of traversal (in-order, reverse, filtered).
- Sequences are **huge or infinite** — lazy generators avoid materializing them.

**Avoid when:**

- (Rare in Python!) The collection is a plain list used locally — just loop it.
- You need **random access** by index or to mutate while traversing — iterators fit forward, read-mostly scans.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Uniform traversal — clients decoupled from structure | Mutating a collection during iteration is dangerous (`RuntimeError` for dicts) |
| Many concurrent traversals (own cursors) | Iterators are one-shot — must re-create to re-traverse |
| Lazy evaluation → memory-efficient, infinite sequences | Can be slower than direct indexed access for simple arrays |
| SRP: traversal logic out of the collection class | |

---

## 7. Iterator vs. similar patterns

| Compared with | Difference |
|---|---|
| **Composite** | Natural partners: Iterator **walks** the Composite tree so clients don't recurse manually. |
| **Visitor** | Iterator exposes elements one by one for the client to process; Visitor sends an **operation into** the structure. |
| **Generator vs iterator class** | Same pattern; generator is Python's concise implementation (compiler builds `__next__` state machine from `yield`). |
| **Cursor (DB)** | A database cursor is an Iterator over a result set — same idea across the industry. |

---

## 8. Quick recap

- Protocol: `__iter__` returns an iterator; iterator's `__next__` yields items, then raises **`StopIteration`**.
- `for` loops = syntactic sugar over the protocol.
- **Generators (`yield`)** auto-generate iterators — lazy, memory-light, can be infinite.
- Each iterator holds **its own position** → multiple concurrent traversals.
- Collections can expose **several traversals** (in-order, shuffled, reversed).

## 9. Interview Q&A

**Q1. What is the Iterator pattern and how does Python embody it?**
Sequential access to a collection's elements without exposing internals. Python bakes it into the language: `iter()`/`next()`, the `__iter__`/`__next__` protocol, `for` loops, generators, and comprehensions all rely on it.

**Q2. Difference between an *iterable* and an *iterator*?**
Iterable = can produce an iterator (`__iter__`). Iterator = the stateful cursor itself (`__next__`, plus `__iter__` returning self). Every iterator is iterable; a list is iterable but not an iterator.

**Q3. Why do iterators raise `StopIteration` instead of returning None?**
`None` can be a legitimate element. A dedicated exception unambiguously signals exhaustion, letting `for` terminate cleanly.

**Q4. What are generators and why are they preferred?**
Functions using `yield`; Python builds the iterator state machine automatically. They're lazy (compute on demand), memory-efficient, support infinite sequences, and are far less boilerplate than hand-written iterator classes.

**Q5. What happens if you modify a collection while iterating?**
Risky: dicts/sets raise `RuntimeError: changed size during iteration`; lists silently skip/repeat elements. Iterate over a copy (`list(d)`), or collect changes and apply after.
