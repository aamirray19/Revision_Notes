# Pattern 10: Memento

> **TL;DR:** **Memento** captures an object's internal state in a **snapshot object** so it can be **restored later** — without exposing the object's internals to anyone else. The originator makes and consumes mementos; a caretaker only **stores** them. This is the pattern behind undo, save-games, and checkpoints.

---

## 1. Problem it solves

**Without the pattern:** outsiders rummage through an object's fields to save/restore it.

```python
# Caretaker code manually copying "private" internals:
backup = {
    "text": editor._text,          # reaching into privates!
    "cursor": editor._cursor,
    "selection": editor._selection,
}
# ...later...
editor._text = backup["text"]      # breaks encapsulation; misses new fields
```

Problems:

- **Encapsulation broken** — external code depends on private internals.
- Add a field to `Editor` → every snapshot site silently becomes **incomplete**.
- No clean way to keep a **history** of states for multi-level undo.

**With the pattern:** only the **originator** reads/writes its own state; outsiders handle mementos as **opaque tokens**.

---

## 2. Real-world analogy

A **video game save file**: the game (originator) serializes its full state into a save slot. You (caretaker) just see "Save 3 — Level 7, 14:32" — you can store it, label it, load it, but you can't (and shouldn't) edit its internals. Restoring puts the game back *exactly* where it was.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Originator** | Owns real state; `save() -> Memento`, `restore(memento)` | `Editor` |
| **Memento** | Immutable snapshot; internals visible **only** to originator | `_EditorState` |
| **Caretaker** | Stores mementos (stack/list); never inspects them | `History` |

```text
Editor ──save()──> Memento ──stored by──> History [m1, m2, m3]
Editor <─restore(m2)──────────────────── History.pop()
        (only Editor reads a memento's contents)
```

---

## 4. Python implementation

```python
from dataclasses import dataclass, field


# ----- Memento: immutable snapshot (frozen dataclass) -----
@dataclass(frozen=True)
class _EditorState:
    """Opaque to everyone except Editor (leading _ signals: don't touch)."""
    text: str
    cursor: int


# ----- Originator -----
class Editor:
    def __init__(self):
        self._text = ""
        self._cursor = 0

    def type(self, chars: str) -> None:
        self._text = self._text[: self._cursor] + chars + self._text[self._cursor:]
        self._cursor += len(chars)

    def save(self) -> _EditorState:
        return _EditorState(self._text, self._cursor)     # originator makes snapshot

    def restore(self, memento: _EditorState) -> None:
        self._text = memento.text                         # ...and consumes it
        self._cursor = memento.cursor

    def __str__(self) -> str:
        return f"'{self._text}' (cursor at {self._cursor})"


# ----- Caretaker: stores snapshots, NEVER looks inside -----
class History:
    def __init__(self):
        self._stack: list[_EditorState] = []

    def backup(self, memento: _EditorState) -> None:
        self._stack.append(memento)

    def undo(self) -> _EditorState | None:
        return self._stack.pop() if self._stack else None


editor = Editor()
history = History()

history.backup(editor.save())          # checkpoint BEFORE each change
editor.type("Hello")

history.backup(editor.save())
editor.type(" World")
print("Now:   ", editor)

editor.restore(history.undo())
print("Undo 1:", editor)

editor.restore(history.undo())
print("Undo 2:", editor)
```

```text
Now:    'Hello World' (cursor at 11)
Undo 1: 'Hello' (cursor at 5)
Undo 2: '' (cursor at 0)
```

- `History` manages snapshots without knowing an editor has text or a cursor.
- The memento is **frozen** (immutable) — a snapshot that could be mutated is worthless.
- Adding an `Editor` field = update `_EditorState`, `save`, `restore` — all in **one file**, callers unaffected.

### Practical notes

```python
# Deep-copy mutable state when snapshotting, or share immutables:
import copy
def save(self):
    return _State(copy.deepcopy(self._layers))   # otherwise snapshot mutates with you!

# Pickle = generic memento for whole objects (persistable):
import pickle
blob = pickle.dumps(editor.__dict__)             # save
# editor.__dict__.update(pickle.loads(blob))     # restore
```

- **Memory tip:** full snapshots can be big. Options: cap history length, store **diffs/deltas**, or mix with Command (commands reverse small steps; mementos checkpoint occasionally).

## 5. When to use / when NOT to use

**Use when:**

- You need **undo/rollback/checkpoints**: editors, games, wizards with a back button, transactions (savepoints!), exploratory algorithms (backtracking).
- Direct access to the object's state for copying would **violate encapsulation**.

**Avoid when:**

- Snapshots are **huge and frequent** — memory explodes; consider deltas or Command-based undo.
- State references **external resources** (sockets, file handles) that can't be meaningfully restored.
- A simple value field is enough — just keep the old value in a variable.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Undo/restore **without** breaking encapsulation | Memory cost of snapshots (especially frequent/deep ones) |
| Snapshot logic lives with the owner of the state | Caretaker can't know how expensive a memento is |
| Caretakers stay simple (store/pop) | Mutable-state snapshots need careful deep-copying |
| Combines cleanly with Command for robust undo | In dynamic languages, "only originator sees internals" is by convention |

---

## 7. Memento vs. similar patterns

| Compared with | Difference |
|---|---|
| **Command (undo)** | Command undo **reverses operations** step by step (cheap, but each command must know its inverse). Memento undo **restores snapshots** (simple, but memory-heavy). Real editors combine both. |
| **Prototype** | Both copy state! Prototype's copy becomes a **new independent object**; a memento is a frozen snapshot used to **restore the original**. |
| **State** | State pattern = *behavior* organized by mode; Memento = *data* captured for time-travel. Unrelated jobs, often confused by name. |
| **Serialization (pickle)** | Serialization is a memento that can leave the process (disk/network); classic memento usually stays in memory with stricter encapsulation. |

---

## 8. Quick recap

- Three roles: **Originator** (makes/consumes), **Memento** (immutable snapshot), **Caretaker** (stores blindly).
- Only the originator touches a memento's internals.
- Deep-copy mutable state; keep mementos **immutable**.
- Watch memory: cap history, use deltas, or combine with **Command**.
- Uses: undo, save-games, DB savepoints, backtracking.

---

## 9. Interview Q&A

**Q1. What is the Memento pattern?**
Capturing an object's internal state as an immutable snapshot (memento) that only the object itself can create and consume, so state can be restored later — enabling undo/checkpoints without exposing internals.

**Q2. Who are the three participants and what may each do?**
Originator: creates mementos from its state and restores from them. Memento: passive immutable snapshot. Caretaker: stores and returns mementos but never inspects or modifies their contents.

**Q3. Memento vs Command for implementing undo?**
Command replays inverse **operations** — memory-light but every command needs correct inverse logic. Memento restores **whole states** — trivially correct but memory-heavy. Production editors mix them: commands for steps, periodic memento checkpoints.

**Q4. How do you keep memento history from eating all memory?**
Bound the stack (last N states), snapshot on coarse boundaries only, store structural **diffs** instead of full copies, share immutable sub-structures, or compress old snapshots.

**Q5. How does Python's lack of true privates affect Memento?**
Encapsulation is by convention (`_underscore`); nothing stops a caretaker from peeking. Discipline + frozen dataclasses get you the spirit of the pattern; for hard guarantees you'd need closures or C extensions — rarely worth it.
