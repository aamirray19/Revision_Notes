# Pattern 6: State

> **TL;DR:** **State** lets an object change its behavior when its **internal state changes** — by delegating to a current **state object** instead of branching on a status flag. Each state is a class implementing the same actions differently; states themselves trigger transitions. The object "appears to change its class."

---

## 1. Problem it solves

**Without the pattern:** every method branches on the status flag.

```python
class Document:
    def __init__(self):
        self.status = "draft"

    def publish(self):
        if self.status == "draft":
            self.status = "moderation"
        elif self.status == "moderation":
            self.status = "published"      # (should also check admin rights...)
        elif self.status == "published":
            pass                           # already published

    def edit(self):
        if self.status == "draft": ...
        elif self.status == "moderation": ...   # SAME branching in EVERY method
        elif self.status == "published": ...
```

Problems:

- The **same `if/elif` ladder** repeats in every method — add a state, touch everything.
- Transition rules are **scattered**; illegal transitions slip through.
- Methods mix behavior of **all states** — hard to read and test.

**With the pattern:** one class per state; `Document` delegates to `self.state`, and states hand over to the next state.

---

## 2. Real-world analogy

A **vending machine**: the same "press button" action behaves differently depending on its mood — *no coin* ("insert coin first"), *has coin* (dispense), *sold out* ("empty"). The machine physically transitions between these modes; the button doesn't check flags, the **current mode defines the behavior**.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Context** | Holds current state object; delegates actions to it | `Document` |
| **State** (interface) | One method per action | `State.publish/edit` |
| **Concrete States** | Implement actions for one state; **trigger transitions** | `Draft`, `Moderation`, `Published` |

```text
Document ──publish()──> current State ──behavior + transition──> Document.state = NextState
   │
   └── holds exactly ONE state object at a time; swapping it swaps ALL behavior
```

---

## 4. Python implementation

```python
from abc import ABC, abstractmethod


# ----- State interface -----
class State(ABC):
    @abstractmethod
    def publish(self, doc: "Document") -> None: ...

    @abstractmethod
    def edit(self, doc: "Document") -> None: ...


# ----- Concrete States: behavior of ONE state each -----
class Draft(State):
    def publish(self, doc: "Document") -> None:
        print("Draft -> sent to moderation")
        doc.state = Moderation()                    # state triggers the transition

    def edit(self, doc: "Document") -> None:
        print("Editing draft")


class Moderation(State):
    def publish(self, doc: "Document") -> None:
        if doc.user_is_admin:
            print("Moderation -> published!")
            doc.state = Published()
        else:
            print("Only admins can approve publication")

    def edit(self, doc: "Document") -> None:
        print("Rejected: cannot edit while under moderation")


class Published(State):
    def publish(self, doc: "Document") -> None:
        print("Already published — nothing to do")

    def edit(self, doc: "Document") -> None:
        print("Published -> back to draft for editing")
        doc.state = Draft()


# ----- Context: no if/elif anywhere -----
class Document:
    def __init__(self, user_is_admin: bool = False):
        self.state: State = Draft()                 # start state
        self.user_is_admin = user_is_admin

    def publish(self) -> None:
        self.state.publish(self)                    # pure delegation

    def edit(self) -> None:
        self.state.edit(self)


doc = Document(user_is_admin=True)
doc.edit()          # draft: editable
doc.publish()       # draft -> moderation
doc.edit()          # moderation: blocked
doc.publish()       # moderation -> published (admin)
doc.publish()       # published: no-op
doc.edit()          # published -> draft
```

```text
Editing draft
Draft -> sent to moderation
Rejected: cannot edit while under moderation
Moderation -> published!
Already published — nothing to do
Published -> back to draft for editing
```

- Zero conditionals in `Document`; each state class reads like a **spec of that state**.
- Adding a `Scheduled` state = **one new class** + transitions into it; existing classes barely change.
- (Micro-optimization: stateless state objects can be shared singletons/flyweights instead of `Moderation()` each time.)

---

## 5. When to use / when NOT to use

**Use when:**

- An object's behavior genuinely depends on a **mode/status** and it has **several operations** affected by it (orders: placed→paid→shipped→delivered; TCP connections; game characters: idle/running/jumping; media players; workflow engines).
- You see **duplicate `if self.status == ...` ladders** across methods.
- Transition rules deserve to be **explicit and enforced** (illegal transitions impossible).

**Avoid when:**

- Only 2 simple states or one affected method — a boolean/flag is fine.
- States rarely change and conditionals are shallow — classes add ceremony.
- You need the full picture of transitions in one place → consider a **table-driven FSM** (dict of `(state, event) → next_state`) instead.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Removes repeated state conditionals (SRP) | A class per state — overkill for tiny machines |
| Each state's behavior isolated & testable | Transition logic distributed across state classes (harder to see the whole graph) |
| New states added with minimal changes (OCP) | Context and states are mutually coupled |
| Illegal transitions become impossible to express | |

---

## 7. State vs. similar patterns

| Compared with | Difference |
|---|---|
| **Strategy** | The twins! Same structure. Strategy: **client** picks the algorithm; strategies are independent, swap is rare. State: the **state objects themselves** drive transitions; change over time is the point; states may know each other. |
| **Finite State Machine (table)** | Same concept, different encoding: FSM tables map `(state, event) → next`; State pattern encodes it in polymorphic classes. Tables show the graph; classes show the behavior. |
| **Memento** | Memento snapshots state **data** for restore; State pattern organizes state-dependent **behavior**. |
| **Chain of Responsibility** | CoR: request travels until someone handles it. State: ONE current handler (the state) handles everything, and gets replaced over time. |

---

## 8. Quick recap

- One **class per state**; context holds the current one and **delegates**.
- **States trigger transitions**: `doc.state = NextState()`.
- Kills repeated `if self.status == ...` ladders.
- vs Strategy: who changes the object — **client (Strategy)** vs **the states themselves (State)**.
- Real uses: order lifecycles, TCP, players, game characters, workflows.

---

## 9. Interview Q&A

**Q1. What is the State pattern?**
Behavior-per-mode encapsulated in state classes: the context delegates its operations to a current state object and the states transition the context between them — so behavior changes at runtime without conditionals, as if the object changed its class.

**Q2. State vs Strategy — the inevitable question?**
Identical structure, different intent. Strategy: interchangeable algorithms, chosen by the client, unaware of each other, usually fixed for the context's lifetime. State: behavior modes that the object cycles through **by itself**; states know about and create their successors.

**Q3. Who should trigger transitions — context or states?**
Either works. States triggering transitions (our example) keeps rules local and context clean; context-driven transitions centralize the graph. For complex machines, a transition **table** may beat both.

**Q4. Real-world examples?**
Order/booking lifecycles, TCP connection states (LISTEN/ESTABLISHED/CLOSED — the GoF original), media player (playing/paused/stopped), game character states, document workflows, traffic lights.

**Q5. How would you implement a lightweight state machine in Python without classes?**
A dict-based FSM: `transitions = {("draft", "publish"): "moderation", ...}` plus per-state handler functions — great when behavior is small but the transition graph matters. Mention `enum.Enum` for state constants.
