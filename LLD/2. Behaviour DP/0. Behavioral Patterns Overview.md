# Behavioral Design Patterns — Overview

> **TL;DR:** Behavioral patterns deal with **communication and responsibility between objects** — who talks to whom, who decides what, and how algorithms/requests/state flow through the system. They turn rigid `if/else` logic and tight coupling into flexible, swappable collaborations.

---

## 1. What problems do behavioral patterns address?

- Swapping **algorithms** at runtime without `if/else` chains.
- Notifying many objects about **events** without hard-coding them.
- **Decoupling senders from receivers** of requests.
- Managing objects whose behavior changes with **state**.
- Traversing, operating on, and snapshotting **object structures** cleanly.

Common theme: **encapsulate what varies** — the algorithm, the request, the state, the traversal — as an object.

---

## 2. The 11 Behavioral Patterns at a Glance

| # | Pattern | One-line intent | Classic example |
|---|---------|-----------------|-----------------|
| 1 | **Strategy** | Swap interchangeable **algorithms** at runtime | Payment methods; sort key functions |
| 2 | **Observer** | Notify many subscribers when a subject's **state changes** | YouTube channel → subscribers; event listeners |
| 3 | **Iterator** | Traverse a collection **without exposing its internals** | Python's `for` loop / `__iter__` / generators |
| 4 | **Command** | Turn a **request into an object** (queue, log, undo) | Text editor undo/redo; task queues |
| 5 | **Mediator** | Centralize **many-to-many communication** in one hub | Air traffic control; chat room; UI dialog |
| 6 | **State** | Object changes behavior when its **internal state** changes | Vending machine; order lifecycle; TCP connection |
| 7 | **Template Method** | Fixed algorithm **skeleton**; subclasses fill in steps | Data pipeline: load→process→save; unittest setUp/test/tearDown |
| 8 | **Chain of Responsibility** | Pass request along a **chain** until someone handles it | Support ticket escalation; middleware |
| 9 | **Visitor** | Add **new operations** to an object structure without changing it | AST operations: type-check, print, compile |
| 10 | **Memento** | **Snapshot & restore** object state without breaking encapsulation | Undo; save games; checkpoints |
| 11 | **Interpreter** | Define a mini-**language** and evaluate its sentences | Expression evaluators; rule engines; regex |

---

## 3. How to pick the right one (decision cheat-sheet)

- Multiple interchangeable **ways to do one thing** → **Strategy**
- One event, **many interested parties** → **Observer**
- Need to walk a collection/tree uniformly → **Iterator**
- Requests must be **queued / undone / logged** → **Command**
- Objects talk to each other in a **tangled web** → **Mediator**
- Behavior depends on **which mode/state** the object is in → **State**
- Same algorithm outline, **different step details** → **Template Method**
- **Several possible handlers**, decided at runtime, maybe in sequence → **Chain of Responsibility**
- Stable object structure, **ever-growing operations** → **Visitor**
- Need to **save/restore** state privately → **Memento**
- Input is a **grammar/mini-language** → **Interpreter**

---

## 4. Classic confusions (interview favorites)

| Pair | Key difference |
|---|---|
| **Strategy vs State** | Strategy: *client* picks the algorithm; strategies don't know each other. State: the *object itself* transitions between states; states know/trigger transitions. |
| **Strategy vs Template Method** | Strategy = composition (swap whole algorithm object); Template Method = inheritance (override steps of a fixed skeleton). |
| **Observer vs Mediator** | Observer: one-to-many broadcast, subject doesn't know subscribers' types. Mediator: many-to-many hub containing the interaction logic. |
| **Command vs Strategy** | Command wraps *a request + its receiver* (what to do, to whom — supports undo/queue); Strategy wraps *an algorithm* (how to do it). |
| **Chain of Responsibility vs Decorator** | Same linked structure, but CoR handlers may **stop** the chain; decorators always delegate onward. |
