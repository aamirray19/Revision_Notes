# Pattern 8: Chain of Responsibility

> **TL;DR:** **Chain of Responsibility** passes a request along a **chain of handlers**; each handler either **handles it** or **forwards it** to the next. The sender knows only the first link — not who will ultimately respond (maybe nobody). Think support-ticket escalation or web middleware.

---

## 1. Problem it solves

**Without the pattern:** one monolithic dispatcher knows every possible handler.

```python
def handle_request(request):
    if request.level == "basic":
        bot.answer(request)
    elif request.level == "technical":
        if engineer.available:
            engineer.answer(request)
        else:
            senior_engineer.answer(request)      # fallback logic tangled in
    elif request.level == "billing":
        billing_team.answer(request)
    elif request.level == "legal":
        ...                                       # grows forever
```

Problems:

- Sender is **coupled to every receiver** and to the escalation order.
- Adding/removing/reordering handlers means **editing this dispatcher**.
- Can't build the processing sequence **dynamically** (per config/tenant).

**With the pattern:** handlers are links in a chain; each decides *handle or pass on*. Sender just drops the request into link #1.

---

## 2. Real-world analogy

**Customer support escalation**: your call hits the **bot** first; can't fix it → **L1 agent**; still stuck → **L2 engineer**; worst case → **manager**. You dialed one number; you don't know (or care) who finally solves it. Each tier handles what it can and escalates the rest.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Handler** (interface/base) | `set_next()` + `handle()`; default = forward to next | `Handler` |
| **Concrete Handlers** | Handle what they can; else delegate | `BotSupport`, `L1Support`, `L2Support` |
| **Client** | Builds the chain; sends request to the first link | setup code |

```text
request ──> [Bot] ──can't──> [L1] ──can't──> [L2] ──can't──> None (unhandled)
              │ handles "password reset"etc.   └ handles hard stuff
              └──> response (chain stops as soon as someone handles it)
```

---

## 4. Python implementation

### 4a. Classic chain — stop at first handler

```python
from abc import ABC, abstractmethod


class Handler(ABC):
    def __init__(self):
        self._next: Handler | None = None

    def set_next(self, handler: "Handler") -> "Handler":
        self._next = handler
        return handler                              # return next => fluent chaining

    def handle(self, issue: str, difficulty: int) -> str | None:
        if self._next:
            return self._next.handle(issue, difficulty)
        return None                                 # end of chain: unhandled


class BotSupport(Handler):
    def handle(self, issue, difficulty):
        if difficulty <= 1:
            return f"Bot solved: {issue}"
        print(f"Bot: escalating '{issue}'")
        return super().handle(issue, difficulty)    # pass along


class L1Support(Handler):
    def handle(self, issue, difficulty):
        if difficulty <= 2:
            return f"L1 agent solved: {issue}"
        print(f"L1: escalating '{issue}'")
        return super().handle(issue, difficulty)


class L2Support(Handler):
    def handle(self, issue, difficulty):
        if difficulty <= 3:
            return f"L2 engineer solved: {issue}"
        return super().handle(issue, difficulty)


# ----- Client builds the chain (order is data, not code!) -----
bot = BotSupport()
bot.set_next(L1Support()).set_next(L2Support())

print(bot.handle("reset password", 1))
print(bot.handle("app crashes on login", 2))
print(bot.handle("data corruption", 3))
print(bot.handle("alien invasion", 9))
```

```text
Bot solved: reset password
Bot: escalating 'app crashes on login'
L1 agent solved: app crashes on login
Bot: escalating 'data corruption'
L1: escalating 'data corruption'
L2 engineer solved: data corruption
Bot: escalating 'alien invasion'
L1: escalating 'alien invasion'
None
```

- Reordering/removing tiers = change the **wiring**, not the classes.
- An unhandled request falls off the end (`None`) — decide explicitly what that means.

### 4b. Middleware-style chain — every link processes, any link can abort

```python
class Middleware(ABC):
    def __init__(self):
        self._next = None

    def set_next(self, mw): self._next = mw; return mw

    def process(self, request: dict) -> dict | None:
        result = self.check(request)
        if result is not None:                      # link produced a response: STOP
            return result
        return self._next.process(request) if self._next else {"status": 200}

    @abstractmethod
    def check(self, request: dict) -> dict | None: ...


class AuthMiddleware(Middleware):
    def check(self, request):
        if not request.get("user"):
            return {"status": 401, "error": "not logged in"}
        print("  auth ok")


class RateLimitMiddleware(Middleware):
    def check(self, request):
        if request.get("requests_this_minute", 0) > 100:
            return {"status": 429, "error": "slow down"}
        print("  rate ok")


chain = AuthMiddleware()
chain.set_next(RateLimitMiddleware())

print(chain.process({"user": "alice", "requests_this_minute": 3}))
print(chain.process({}))                            # fails at the first link
```

```text
  auth ok
  rate ok
{'status': 200}
{'status': 401, 'error': 'not logged in'}
```

- Two classic flavors: **"first handler wins"** (support desk) vs **"all links filter, any can abort"** (middleware/validation). Django/Flask middleware, logging handler chains, and `try/except` lookup up the call stack are all CoR-flavored.

---

## 5. When to use / when NOT to use

**Use when:**

- **Several handlers** could process a request and the right one is known only at **runtime** (support tiers, approval workflows: team lead → manager → director by amount).
- You want processing steps to be **composable and reorderable** (middleware pipelines, validators, event bubbling in GUIs/DOM).
- The sender **shouldn't know** receivers.

**Avoid when:**

- Exactly one fixed handler → call it directly.
- **Every** request must be guaranteed handling — a chain allows fall-through; add a catch-all terminal handler if needed.
- The chain gets long and hot — each hop costs a call; debugging "who swallowed my request" is painful.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Sender decoupled from receivers (knows only link #1) | No guarantee anyone handles the request |
| Chain built/reordered at **runtime** from config | Hard to debug/trace a request through many links |
| Each handler has single responsibility | Long chains add latency |
| Open/Closed: insert new handlers freely | Order mistakes cause subtle bugs |

---

## 7. Chain of Responsibility vs. similar patterns

| Compared with | Difference |
|---|---|
| **Decorator** | Same linked-wrapper shape! Decorator **always delegates** and adds behavior on the way; a CoR handler may **stop the chain** and is about *who handles*. |
| **Command** | Complementary: CoR decides **who** processes; Command packages **what** is processed. Chains often pass command objects. |
| **Mediator** | Mediator routes via a **central hub** with global knowledge; CoR routes **linearly**, each link knowing only its successor. |
| **Observer** | Observer notifies **all** subscribers unconditionally; CoR goes link-by-link and typically **stops** when handled. |

---

## 8. Quick recap

- Linked handlers: each **handles or forwards**; sender sees only the first.
- Two flavors: **first-wins** (escalation) and **filter-pipeline** (middleware).
- Chain order is **data** — build it from config at runtime.
- Add a **catch-all** at the end if unhandled requests are unacceptable.
- Real uses: middleware, approval workflows, logging handlers, event bubbling.

---

## 9. Interview Q&A

**Q1. What is the Chain of Responsibility pattern?**
A chain of handler objects where each either processes a request or forwards it to its successor — decoupling senders from receivers and letting the handler set/order be composed at runtime.

**Q2. What happens if no handler processes the request?**
It falls off the end (returns None / does nothing). If that's unacceptable, terminate the chain with a default/catch-all handler or raise explicitly — an interview-worthy design decision.

**Q3. CoR vs Decorator — both are chains of wrappers?**
Decorator always passes through, each layer **adding behavior**; the full stack runs every time. CoR is about **finding the handler** — links may short-circuit and stop propagation.

**Q4. Where does CoR appear in real systems?**
Web middleware (Django/Express), servlet filters, Python `logging` (record travels logger→parent loggers→handlers), GUI/DOM event bubbling, approval workflows, exception propagation up the call stack (conceptually).

**Q5. How do you keep long chains debuggable?**
Log entry/exit per handler, give handlers names, keep the chain definition in one visible place (config/list), and prefer a flat list iteration (`for h in handlers: if h.try_handle(r): break`) — same pattern, easier to inspect.
