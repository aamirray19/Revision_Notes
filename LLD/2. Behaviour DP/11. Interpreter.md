# Pattern 11: Interpreter

> **TL;DR:** **Interpreter** defines a **grammar for a small language** and represents each grammar rule as a **class**; sentences become **trees of these objects** (ASTs) that evaluate themselves via a recursive `interpret()`. Use for mini-languages: filter expressions, rule engines, formulas. For anything big — use a real parser generator.

---

## 1. Problem it solves

**Without the pattern:** evaluating user-defined expressions with ad-hoc string hacking.

```python
rule = "age > 18 AND country == 'IN'"

# Ad-hoc parsing: splits, regexes, index juggling...
parts = rule.split(" AND ")          # breaks on OR, parentheses, nesting, quotes...
# ...50 lines of brittle special cases later, still wrong.

# Or worse:
eval(rule)                           # SECURITY NIGHTMARE — never eval user input
```

Problems:

- String munging **can't handle nesting/precedence** (`(a OR b) AND c`).
- Each new operator makes the hack **exponentially messier**.
- `eval()` on user input = **arbitrary code execution**.

**With the pattern:** grammar rules become classes; any sentence becomes a **tree** that evaluates itself safely.

---

## 2. Real-world analogy

A **music performer reading sheet music**: the notation is a formal language (notes, rests, tempo marks). Each symbol class has a fixed meaning ("interpret rule"); the musician walks the score symbol by symbol, *interpreting* each in context, producing the performance. Different sheets (sentences), same grammar.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Abstract Expression** | Declares `interpret(context)` | `Expression` |
| **Terminal Expressions** | Leaves: literals/variables (no sub-expressions) | `Number`, `Variable` |
| **Non-terminal Expressions** | Composites: operators holding sub-expressions | `Add`, `Sub`, `Mul` |
| **Context** | External info for evaluation (variable values) | `dict` of variables |
| **Client/Parser** | Builds the expression tree, calls `interpret` | parser function |

```text
"x + 2 * y"  ──parse──>        Add                 ← non-terminal
                              /   \
                       Variable(x)  Mul            ← non-terminal
                                   /   \
                            Number(2)  Variable(y) ← terminals
tree.interpret({"x": 1, "y": 5})  =  11
```

Note the shape: an Interpreter AST **is a Composite tree** — each node interprets itself recursively.

## 4. Python implementation

```python
from abc import ABC, abstractmethod


# ----- Abstract Expression -----
class Expression(ABC):
    @abstractmethod
    def interpret(self, context: dict) -> float: ...


# ----- Terminal expressions (leaves) -----
class Number(Expression):
    def __init__(self, value: float):
        self.value = value

    def interpret(self, context: dict) -> float:
        return self.value


class Variable(Expression):
    def __init__(self, name: str):
        self.name = name

    def interpret(self, context: dict) -> float:
        return context[self.name]                 # context supplies the value


# ----- Non-terminal expressions (operators) -----
class Add(Expression):
    def __init__(self, left: Expression, right: Expression):
        self.left, self.right = left, right

    def interpret(self, context: dict) -> float:
        return self.left.interpret(context) + self.right.interpret(context)


class Sub(Expression):
    def __init__(self, left: Expression, right: Expression):
        self.left, self.right = left, right

    def interpret(self, context: dict) -> float:
        return self.left.interpret(context) - self.right.interpret(context)


class Mul(Expression):
    def __init__(self, left: Expression, right: Expression):
        self.left, self.right = left, right

    def interpret(self, context: dict) -> float:
        return self.left.interpret(context) * self.right.interpret(context)


# ----- Build the tree for:  x + 2 * y   (usually a parser does this) -----
expr = Add(Variable("x"), Mul(Number(2), Variable("y")))

print(expr.interpret({"x": 1, "y": 5}))      # 1 + 2*5
print(expr.interpret({"x": 10, "y": 0}))     # same tree, new context — reusable!
```

```text
11
10
```

### Boolean rule-engine flavor (the practical one)

```python
class Rule(ABC):
    @abstractmethod
    def interpret(self, user: dict) -> bool: ...

class GreaterThan(Rule):
    def __init__(self, key, value): self.key, self.value = key, value
    def interpret(self, user): return user[self.key] > self.value

class Equals(Rule):
    def __init__(self, key, value): self.key, self.value = key, value
    def interpret(self, user): return user[self.key] == self.value

class And(Rule):
    def __init__(self, *rules): self.rules = rules
    def interpret(self, user): return all(r.interpret(user) for r in self.rules)

class Or(Rule):
    def __init__(self, *rules): self.rules = rules
    def interpret(self, user): return any(r.interpret(user) for r in self.rules)


# "age > 18 AND (country == IN OR country == US)"
rule = And(GreaterThan("age", 18),
           Or(Equals("country", "IN"), Equals("country", "US")))

print(rule.interpret({"age": 25, "country": "IN"}))
print(rule.interpret({"age": 15, "country": "US"}))
```

```text
True
False
```

- Nesting, precedence, new operators — all **compose naturally**; no string hacks, no `eval`.
- Rules can be **built from JSON/config** at runtime → safe user-defined filters.

## 5. When to use / when NOT to use

**Use when:**

- You have a **small, stable grammar**: search filters, pricing/discount rules, feature-flag conditions, spreadsheet-like formulas, simple query languages.
- Sentences must be **safely** evaluated (user input — never `eval`).
- Expressions arrive as **data** (JSON/DB/config) and must become executable logic.

**Avoid when:**

- The grammar is **large or evolving** — class-per-rule explodes; use parser generators (ANTLR, Lark, PLY) or an embedded language.
- Performance is critical — recursive object interpretation is slow (real engines compile instead).
- A plain function, dict lookup, or `operator` module composition already does the job.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Each grammar rule isolated in one class — easy to extend | Class explosion as the grammar grows |
| Nesting/precedence handled by tree structure for free | Slow for complex grammars (deep recursion) |
| Safe alternative to `eval` for user expressions | You still need a **parser** to build trees from text |
| Trees built from data/config at runtime | Rarely the right tool beyond mini-languages |

---

## 7. Interpreter vs. similar patterns

| Compared with | Difference |
|---|---|
| **Composite** | The AST **is** a Composite; Interpreter adds *meaning* — a recursive `interpret()` over that tree. |
| **Visitor** | Alternative evaluation style: keep nodes dumb and put `interpret`/`print`/`optimize` logic into **visitors** — better when many operations run over the same AST. |
| **Strategy** | Strategy = choose among **whole algorithms**; Interpreter = **compose** behavior from grammar pieces. |
| **Parser generators** | Lark/ANTLR/PLY generate the parsing machinery for serious grammars; Interpreter pattern suits tiny hand-built ones. |

**Real examples:** regex engines (`re.compile` builds an internal program), SQLAlchemy/Django ORM filter expressions (`Q(age__gt=18) & Q(country="IN")` — an interpreter tree!), spreadsheet formulas, feature-flag rule engines.

---

## 8. Quick recap

- Grammar rule → class; sentence → **tree of expression objects**; evaluation → recursive `interpret(context)`.
- **Terminals** = leaves (numbers, variables); **non-terminals** = operators holding children.
- Context carries external data (variable values).
- Safe replacement for `eval` on user expressions.
- Grammar getting big? Switch to a real parser (Lark/ANTLR).

---

## 9. Interview Q&A

**Q1. What is the Interpreter pattern?**
Representing each rule of a small language's grammar as a class, so any sentence becomes a tree of expression objects that evaluates itself via recursive `interpret(context)` calls — terminals return values, non-terminals combine their children's results.

**Q2. Terminal vs non-terminal expressions?**
Terminals are leaves with no sub-expressions (literals, variables) — recursion ends there. Non-terminals contain sub-expressions (AND/OR, +, ×) and combine their interpreted results.

**Q3. Why is Interpreter better than `eval()` for user-defined rules?**
`eval` executes arbitrary Python — a critical security hole. An interpreter tree supports exactly the operations you define, nothing more, and can be built safely from untrusted input/config.

**Q4. How does Interpreter relate to Composite and Visitor?**
The expression tree is structurally a Composite. When you need many operations over the same tree (evaluate, pretty-print, optimize), move them into Visitors instead of adding methods to every node class.

**Q5. When would you abandon this pattern?**
When the grammar grows beyond a handful of rules, needs real tokenizing/precedence handling, or performance matters — switch to parser generators (Lark, ANTLR, PLY) or compile to Python functions instead of interpreting node-by-node.
