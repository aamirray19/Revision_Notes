# Pattern 7: Template Method

> **TL;DR:** **Template Method** defines the **skeleton of an algorithm** in a base-class method, with some steps left as **abstract/hook methods** for subclasses to fill in. The outline (order of steps) is fixed and reused; only the details vary. "Don't call us, we'll call you" — the **Hollywood Principle**.

---

## 1. Problem it solves

**Without the pattern:** near-identical algorithms copy-pasted with small variations.

```python
class CSVReport:
    def generate(self):
        data = open("data.csv").read()       # 1. load (CSV-specific)
        rows = parse_csv(data)               # 2. parse (CSV-specific)
        rows = [r for r in rows if r.valid]  # 3. validate   ─┐
        summary = aggregate(rows)            # 4. aggregate   ├ IDENTICAL in
        print(format_table(summary))         # 5. output      ┘ JSONReport, XMLReport...

class JSONReport:
    def generate(self):
        ...same 5 steps, only 1–2 differ...   # copy-paste!
```

Problems:

- Steps 3–5 **duplicated** in every variant — fix a bug in one, forget the others.
- The **algorithm's order** isn't enforced anywhere; a variant may skip validation.
- Clients see N unrelated classes instead of one family.

**With the pattern:** the base class owns the **invariant skeleton**; subclasses override only the differing steps.

---

## 2. Real-world analogy

A **recipe template** for any cake: 1) preheat oven, 2) mix ingredients, 3) bake, 4) decorate. Steps 1 and 3 are identical for every cake; steps 2 and 4 vary (chocolate vs vanilla). The cookbook (base class) fixes the order; each specific recipe fills in its own blanks — nobody re-invents "preheat the oven".

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Abstract Class** | `template_method()` fixing step order; implements common steps; declares abstract steps + optional hooks | `DataPipeline.run()` |
| **Concrete Classes** | Implement the abstract steps (and override hooks) | `CSVPipeline`, `APIPipeline` |

```text
BaseClass.template_method():      # FINAL skeleton — subclasses don't override this
    step1()      ← common (implemented in base)
    step2()      ← abstract (subclass MUST implement)
    hook()       ← hook (optional override, has default)
    step3()      ← common
```

---

## 4. Python implementation

```python
from abc import ABC, abstractmethod


class DataPipeline(ABC):
    """Abstract class: owns the algorithm skeleton."""

    def run(self) -> None:                      # <-- THE template method
        raw = self.extract()                    # varies     (abstract)
        data = self.transform(raw)              # varies     (abstract)
        data = self.validate(data)              # common     (implemented here)
        if self.should_notify():                # hook       (optional override)
            print("  Notifying stakeholders...")
        self.load(data)                         # common

    # ----- common steps: written ONCE -----
    def validate(self, data: list) -> list:
        print(f"  Validating {len(data)} records")
        return [d for d in data if d is not None]

    def load(self, data: list) -> None:
        print(f"  Loaded {len(data)} records into warehouse")

    # ----- hook: default behavior, subclasses MAY override -----
    def should_notify(self) -> bool:
        return False

    # ----- abstract steps: subclasses MUST implement -----
    @abstractmethod
    def extract(self) -> str: ...

    @abstractmethod
    def transform(self, raw: str) -> list: ...


class CSVPipeline(DataPipeline):
    def extract(self) -> str:
        print("  Reading CSV file")
        return "a,b,,c"

    def transform(self, raw: str) -> list:
        print("  Parsing CSV")
        return [x if x else None for x in raw.split(",")]


class APIPipeline(DataPipeline):
    def extract(self) -> str:
        print("  Calling REST API")
        return '["x", "y"]'

    def transform(self, raw: str) -> list:
        print("  Parsing JSON")
        import json
        return json.loads(raw)

    def should_notify(self) -> bool:            # opt in via the hook
        return True


print("CSV run:")
CSVPipeline().run()
print("API run:")
APIPipeline().run()
```

```text
CSV run:
  Reading CSV file
  Parsing CSV
  Validating 4 records
  Loaded 3 records into warehouse
API run:
  Calling REST API
  Parsing JSON
  Validating 2 records
  Notifying stakeholders...
  Loaded 2 records into warehouse
```

- The **order** (extract → transform → validate → load) is enforced in exactly one place.
- `validate`/`load` written **once**; subclasses provide only their 1–2 unique steps.
- **Hooks** (`should_notify`) = optional extension points with safe defaults.

### You already use it daily

```python
import unittest

class MyTest(unittest.TestCase):       # unittest's template: setUp -> test_* -> tearDown
    def setUp(self): ...               # you fill in the steps;
    def test_something(self): ...      # the framework calls them in ITS fixed order
    def tearDown(self): ...
```

Other examples: Django class-based views (`get`/`post` steps inside a fixed `dispatch` flow), `asyncio.Protocol` callbacks, ABCs with partial implementations.

## 5. When to use / when NOT to use

**Use when:**

- Several classes share an algorithm that is **identical in outline** but differs in a few steps (parsers, pipelines, report generators, game AI turns).
- You want to **enforce the order** of steps and stop copy-paste drift.
- Building a **framework**: you own the flow, users plug in the steps (Hollywood Principle).

**Avoid when:**

- Steps vary **per object at runtime** or you need to swap the whole algorithm → **Strategy** (composition beats inheritance there).
- The skeleton needs frequent changes — every change ripples into all subclasses.
- In Python, if only **one step** varies, just pass a function argument instead of subclassing.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Removes duplication: common steps written once | Locked into **inheritance** (static, single-parent) |
| Algorithm order enforced centrally | Skeleton changes affect every subclass (fragile base class) |
| Controlled extension points (abstract steps + hooks) | Harder to follow: logic split across base and subclasses |
| Framework-friendly: inversion of control | Subclass may violate LSP if it breaks step expectations |

---

## 7. Template Method vs. similar patterns

| Compared with | Difference |
|---|---|
| **Strategy** | The classic duel: Template Method varies **parts** of an algorithm via **inheritance** (fixed at class level); Strategy swaps the **whole** algorithm via **composition** (changeable at runtime). |
| **Factory Method** | Factory Method IS a specialization: a template step whose job is "create the object". |
| **Hook vs abstract step** | Abstract step: subclass **must** implement. Hook: has a default (often no-op); subclass **may** override. |
| **Callbacks (Pythonic)** | Passing functions as parameters achieves the same variation without inheritance — prefer it for single varying steps. |

---

## 8. Quick recap

- Base class method = **fixed skeleton**; calls abstract steps + hooks.
- Subclasses fill in **only what differs**; never override the template itself.
- **Hollywood Principle**: the framework calls *your* code.
- Hooks = optional steps with defaults.
- vs Strategy: inheritance & partial variation vs composition & whole-algorithm swap.

---

## 9. Interview Q&A

**Q1. What is the Template Method pattern?**
A base-class method that defines an algorithm's invariant step sequence, implementing shared steps and deferring variable ones to subclass overrides — reusing the outline while customizing details.

**Q2. Template Method vs Strategy?**
Both vary behavior. Template Method: **inheritance**, varies *some steps*, variation chosen at class-definition time. Strategy: **composition**, swaps the *entire algorithm object*, switchable at runtime. Rule of thumb: "fill in the blanks" → Template; "swap the engine" → Strategy.

**Q3. What's a hook method?**
An optional step with a default (often empty) implementation that subclasses *may* override to inject behavior — unlike abstract steps, which they *must* implement. Hooks let the base class offer extension points without forcing work on every subclass.

**Q4. What is the Hollywood Principle?**
"Don't call us, we'll call you" — inversion of control: the high-level template calls the subclass's low-level steps, not the other way round. It's how frameworks (unittest, Django CBVs) integrate your code.

**Q5. Why might Python developers skip this pattern?**
First-class functions: if only a step or two vary, passing callables as parameters (or using decorators) is lighter than an inheritance hierarchy. Template Method earns its keep when several steps, shared state, and enforced ordering are involved.
