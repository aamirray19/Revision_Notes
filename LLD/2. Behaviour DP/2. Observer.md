# Pattern 2: Observer

> **TL;DR:** **Observer** defines a **one-to-many** dependency: when a **Subject's** state changes, all registered **Observers** are notified automatically. The subject knows only that observers implement `update()` — not who they are. This is the pattern behind event systems, pub/sub, and reactive UIs.

---

## 1. Problem it solves

**Without the pattern:** the subject hard-codes everyone who must react.

```python
class Stock:
    def set_price(self, price):
        self.price = price
        mobile_app.refresh(price)        # hard-coded dependency
        email_service.send_alert(price)  # another one
        dashboard.redraw(price)          # and another...
        # new consumer? edit Stock AGAIN. remove one? edit Stock again.
```

Problems:

- Subject is **tightly coupled** to every consumer — it must import and know them all.
- Adding/removing consumers means **editing the subject**.
- Alternative (consumers **polling** for changes) wastes cycles and reacts late.

**With the pattern:** consumers **subscribe themselves**; the subject just broadcasts "I changed" to its list.

---

## 2. Real-world analogy

A **YouTube channel**: the creator uploads a video and *all subscribers* get notified. The creator doesn't know subscribers personally, and people can subscribe/unsubscribe anytime without the creator changing anything. (Contrast with polling: checking the channel page every hour.)

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Subject / Publisher** | Keeps observer list; `attach/detach/notify` | `Stock` |
| **Observer** (interface) | `update()` called on changes | `Investor`-like objects |
| **Concrete Observers** | React to the notification | `MobileApp`, `EmailAlert` |
| **Client** | Wires subscriptions | setup code |

```text
                 ┌──> ObserverA.update(data)
Subject.notify() ┼──> ObserverB.update(data)
   (on change)   └──> ObserverC.update(data)
Subject holds: [ObserverA, ObserverB, ObserverC]   ← attach()/detach() at runtime
```

---

## 4. Python implementation

```python
from abc import ABC, abstractmethod


# ----- Observer interface -----
class Observer(ABC):
    @abstractmethod
    def update(self, symbol: str, price: float) -> None: ...


# ----- Subject -----
class Stock:
    def __init__(self, symbol: str, price: float):
        self.symbol = symbol
        self._price = price
        self._observers: list[Observer] = []

    def attach(self, observer: Observer) -> None:
        self._observers.append(observer)

    def detach(self, observer: Observer) -> None:
        self._observers.remove(observer)

    def _notify(self) -> None:
        for observer in self._observers:        # subject knows ONLY the interface
            observer.update(self.symbol, self._price)

    @property
    def price(self) -> float:
        return self._price

    @price.setter
    def price(self, value: float) -> None:
        self._price = value
        self._notify()                          # state change triggers broadcast


# ----- Concrete Observers -----
class MobileApp(Observer):
    def update(self, symbol: str, price: float) -> None:
        print(f"[App] {symbol} is now {price}")


class EmailAlert(Observer):
    def __init__(self, threshold: float):
        self.threshold = threshold

    def update(self, symbol: str, price: float) -> None:
        if price > self.threshold:
            print(f"[Email] ALERT: {symbol} crossed {self.threshold}: {price}")


# ----- Client wires it up -----
apple = Stock("AAPL", 180.0)
app = MobileApp()
alert = EmailAlert(threshold=200)

apple.attach(app)
apple.attach(alert)

apple.price = 195.0
apple.price = 205.0

apple.detach(app)                               # unsubscribe at runtime
apple.price = 210.0
```

```text
[App] AAPL is now 195.0
[App] AAPL is now 205.0
[Email] ALERT: AAPL crossed 200: 205.0
[Email] ALERT: AAPL crossed 200: 210.0
```

- `Stock` never imports `MobileApp` or `EmailAlert` — new observers plug in with **zero subject changes**.

### Pythonic variant — callbacks as observers

```python
class Event:
    """Tiny pub/sub: observers are plain callables."""
    def __init__(self):
        self._subscribers = []

    def subscribe(self, fn):
        self._subscribers.append(fn)
        return fn                                 # usable as a decorator

    def emit(self, *args, **kwargs):
        for fn in self._subscribers:
            fn(*args, **kwargs)


on_order_placed = Event()

@on_order_placed.subscribe
def send_receipt(order_id):
    print(f"Receipt for order {order_id}")

on_order_placed.emit(42)
```

```text
Receipt for order 42
```

### Push vs pull

- **Push** (above): subject sends the data in `update(symbol, price)` — simple, but may send more than needed.
- **Pull**: subject sends itself — `update(subject)` — and observers query what they want. More flexible, more coupling to the subject's API.

---

## 5. When to use / when NOT to use

**Use when:**

- A change in one object requires reactions in an **unknown/changing set** of others (events, notifications, live UIs, model→view sync, domain events).
- You want **loose coupling**: the subject shouldn't depend on concrete consumers.

**Avoid when:**

- There's exactly **one, fixed** consumer — a direct call is clearer.
- Update **order matters** or updates **cascade** (observer triggers subject again) — risk of subtle bugs and infinite loops.
- You need guaranteed delivery/backpressure — use a real message queue, not in-process observer.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Loose coupling: subject knows only the interface | Notification order is unspecified — don't rely on it |
| Subscribe/unsubscribe at **runtime** | Cascading updates can cause loops/perf issues |
| Open/Closed: new observers, no subject changes | Forgotten unsubscribes → memory leaks (**lapsed listener**) |
| Basis of event-driven architecture | Debugging "who reacted and why" gets harder |

---

## 7. Observer vs. similar patterns

| Compared with | Difference |
|---|---|
| **Mediator** | Observer: one-to-many **broadcast** from a subject. Mediator: many-to-many hub that **contains interaction logic** between colleagues. A mediator may be *implemented* with observers. |
| **Pub/Sub (message broker)** | Observer is in-process & synchronous with direct references; pub/sub adds a **broker + topics**, fully decoupling and often async (Kafka, Redis). |
| **Command** | Command packages a request to execute (possibly later); Observer reacts to **state changes** as they happen. |
| **Callbacks** | A single callback is the degenerate (1-observer) case; Observer manages a **list** of them. |

---

## 8. Quick recap

- Subject keeps a **list of observers**; state change → `notify()` → each `update()`.
- Subject depends only on the **Observer interface** — plug in/out at runtime.
- Know **push vs pull**, and the **lapsed listener** (unsubscribe!) pitfall.
- Pythonic: observers can be plain **callables**.

---

## 9. Interview Q&A

**Q1. What is the Observer pattern?**
A one-to-many dependency where a subject maintains a list of observers and automatically notifies them (via a common `update` interface) whenever its state changes — the push alternative to wasteful polling.

**Q2. Observer vs Pub/Sub?**
Observer: subject and observers hold direct references, same process, usually synchronous. Pub/Sub: a **broker** sits between publishers and subscribers (topics/queues) so they don't know each other at all — enables async and cross-process messaging.

**Q3. Push vs pull notification?**
Push: subject passes changed data into `update(data)` — simple, possibly oversharing. Pull: subject passes itself, observers query only what they need — flexible, but observers become coupled to the subject's getters.

**Q4. What is the lapsed listener problem?**
Observers that never detach remain referenced by the subject — they can't be garbage-collected (memory leak) and keep receiving irrelevant updates. Fixes: explicit `detach`, weak references (`weakref`), or context-managed subscriptions.

**Q5. Where is Observer used in the wild?**
GUI event listeners (Tkinter/Qt signals-slots), `django.dispatch` signals, RxPy/reactive streams, model-view binding, webhooks (conceptually), `logging` handlers fan-out.
