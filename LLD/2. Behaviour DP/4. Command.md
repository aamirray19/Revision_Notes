# Pattern 4: Command

> **TL;DR:** **Command** turns a request into a **stand-alone object** carrying everything needed to perform it (receiver + action + args). Once requests are objects, you can **queue, log, schedule, retry, and UNDO** them. The invoker (button/queue) doesn't know what the command does — it just calls `execute()`.

---

## 1. Problem it solves

**Without the pattern:** the UI (or scheduler) is hard-wired to business logic.

```python
class Button:
    def __init__(self, action_name, editor):
        self.action_name, self.editor = action_name, editor

    def click(self):
        if self.action_name == "copy":
            self.editor.copy()
        elif self.action_name == "paste":
            self.editor.paste()
        # toolbar button, menu item, shortcut ALL duplicate this mapping
        # and UNDO? no record of what happened — impossible.
```

Problems:

- Invokers (button, menu, shortcut) are **coupled** to receivers and duplicated mapping logic.
- No way to **queue, log, or undo** — the request vanishes after execution.
- Can't pass "an action" around as data (assign to key bindings, send to a worker).

**With the pattern:** `Button(PasteCommand(editor))` — button just calls `execute()`; the same command object serves menus, shortcuts, macros, and the undo stack.

---

## 2. Real-world analogy

A **restaurant order slip**: you don't shout instructions at the chef. The waiter writes an **order** (a command object: table, dishes, notes), pins it in the kitchen **queue**; any chef (receiver) executes it; the slip also serves as a **log**, and can be cancelled (undo) before cooking. Requester and executor never meet.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Command** (interface) | `execute()` (+ `undo()`) | `Command` ABC |
| **Concrete Commands** | Bind a receiver to an action + args | `TypeCommand`, `DeleteCommand` |
| **Receiver** | Knows how to actually do the work | `TextEditor` |
| **Invoker** | Triggers commands; may keep history | `Button`, `CommandHistory` |
| **Client** | Creates commands, wires them to invokers | setup code |

```text
Client ──creates──> Command(receiver, args)
Invoker ──execute()──> Command ──delegates──> Receiver does the work
History [cmd1, cmd2, cmd3] ──undo()──> last command reverses itself
```

## 4. Python implementation

### 4a. Text editor with undo

```python
from abc import ABC, abstractmethod


# ----- Receiver: the real logic -----
class TextEditor:
    def __init__(self):
        self.text = ""


# ----- Command interface -----
class Command(ABC):
    @abstractmethod
    def execute(self) -> None: ...

    @abstractmethod
    def undo(self) -> None: ...


# ----- Concrete Commands (each knows how to reverse itself) -----
class TypeCommand(Command):
    def __init__(self, editor: TextEditor, chars: str):
        self.editor, self.chars = editor, chars

    def execute(self) -> None:
        self.editor.text += self.chars

    def undo(self) -> None:
        self.editor.text = self.editor.text[: -len(self.chars)]


class DeleteCommand(Command):
    def __init__(self, editor: TextEditor, count: int):
        self.editor, self.count = editor, count
        self._deleted = ""                            # remember state for undo

    def execute(self) -> None:
        self._deleted = self.editor.text[-self.count:]
        self.editor.text = self.editor.text[: -self.count]

    def undo(self) -> None:
        self.editor.text += self._deleted


# ----- Invoker with history -----
class CommandHistory:
    def __init__(self):
        self._history: list[Command] = []

    def run(self, command: Command) -> None:
        command.execute()
        self._history.append(command)                 # log everything that ran

    def undo_last(self) -> None:
        if self._history:
            self._history.pop().undo()


editor = TextEditor()
history = CommandHistory()

history.run(TypeCommand(editor, "Hello "))
history.run(TypeCommand(editor, "World"))
print(repr(editor.text))

history.run(DeleteCommand(editor, 5))
print(repr(editor.text))

history.undo_last()                                   # un-delete
print(repr(editor.text))
history.undo_last()                                   # un-type "World"
print(repr(editor.text))
```

```text
'Hello World'
'Hello '
'Hello World'
'Hello '
```

- The history/invoker has **no idea** what the commands do — yet gives us full undo.
- Redo = keep a second stack of undone commands and re-`execute()`.

### 4b. Invoker decoupling — same command, many triggers

```python
class Button:
    def __init__(self, command: Command):
        self.command = command                        # ANY command fits

    def click(self):
        self.command.run() if hasattr(self.command, "run") else self.command.execute()


save_cmd = TypeCommand(editor, "!")
toolbar_btn = Button(save_cmd)
# menu_item = MenuItem(save_cmd); shortcut = Hotkey("Ctrl+S", save_cmd)
toolbar_btn.click()
print(repr(editor.text))
```

```text
'Hello !'
```

### 4c. Pythonic lightweight commands

Callables + `functools.partial` cover the no-undo cases:

```python
from functools import partial

task_queue = []
task_queue.append(partial(print, "send email to alice"))   # request as object
task_queue.append(partial(print, "generate report"))

for task in task_queue:                                    # invoker
    task()
```

```text
send email to alice
generate report
```

Use full command classes when you need **undo, serialization, or metadata**; use callables when you just need "code as data".

---

## 5. When to use / when NOT to use

**Use when:**

- You need **undo/redo** (commands remember how to reverse themselves).
- Requests must be **queued, scheduled, logged, retried, or sent across a network** (job queues like Celery, transaction logs, macros).
- Many invokers trigger the **same operation** (button + menu + shortcut) — one command object serves all.
- You want to decouple "**when/who triggers**" from "**what happens**".

**Avoid when:**

- Simple, immediate, never-undone calls — a direct method call or callback is clearer.
- Undo state would be huge — consider **Memento** snapshots instead of per-command reversal.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Decouples invoker from receiver | A class per operation → lots of small classes |
| Undo/redo, queuing, logging, macros for free | Undo logic per command can be tricky (state capture) |
| Commands are first-class: store, pass, serialize | Indirection: harder to trace "what does this button do" |
| Open/Closed: new commands without touching invokers | |

---

## 7. Command vs. similar patterns

| Compared with | Difference |
|---|---|
| **Strategy** | Strategy = *how* to do one task (interchangeable algorithms). Command = *a request itself* (verb + receiver + args), often queued/undone. |
| **Memento** | Both support undo: Command replays/reverses **operations**; Memento restores **snapshots** of state. Often combined. |
| **Observer** | Observer broadcasts "something changed" to subscribers; Command hands a specific executable request to an invoker. |
| **Chain of Responsibility** | CoR finds *who* handles a request; Command packages *what* the request is. A chain can pass command objects along. |

---

## 8. Quick recap

- Request = object with `execute()` (+ `undo()`).
- **Invoker** triggers; **Receiver** works; command binds them.
- History stack of executed commands → **undo/redo, logs, macros**.
- Queueable, schedulable, serializable — "code as data".
- Pythonic lightweight form: **callables / `functools.partial`**.

---

## 9. Interview Q&A

**Q1. What is the Command pattern?**
Encapsulating a request as an object containing the receiver, the action, and its parameters — so requests can be passed around, queued, logged, and undone, while invokers stay decoupled from the work.

**Q2. How does Command enable undo/redo?**
Each command implements `undo()` (storing whatever state it needs at execute-time). An invoker keeps a history stack: undo pops and reverses; redo re-executes from a second stack.

**Q3. Command vs Strategy?**
Strategy varies **how** something is computed and is chosen by the context. Command represents **a thing to do** (with its target baked in) and is handed to invokers who neither know nor care what it does.

**Q4. Real-world examples?**
GUI actions (Qt's QAction), undo stacks in editors, job/task queues (Celery tasks are serialized commands), database transaction logs & replay, HTTP request objects, game input replay systems.

**Q5. How does Python slim this pattern down?**
Any callable is a zero-boilerplate command; `functools.partial`/closures bake in the receiver and args. Full classes are only needed for undo, serialization, or rich metadata.
