# Pattern 7: Flyweight

> **TL;DR:** **Flyweight** supports **huge numbers of objects** cheaply by **sharing** the heavy, unchanging part of their state. Split state into **intrinsic** (shared, immutable — stored in the flyweight) and **extrinsic** (unique per use — passed in by the caller). A factory caches flyweights so each distinct one exists **once**.

---

## 1. Problem it solves

**Without the pattern:** a forest game creates 1,000,000 trees; each stores its own copy of heavy data.

```python
class Tree:
    def __init__(self, x, y, species, texture, mesh):
        self.x, self.y = x, y                 # 16 bytes — unique per tree
        self.species = species
        self.texture = texture                # 2 MB  — identical for every Oak!
        self.mesh = mesh                      # 5 MB  — identical for every Oak!

# 1,000,000 trees × ~7MB  =  ~7 TB of RAM. Game over (literally).
```

Problems:

- **Massive duplication**: identical textures/meshes copied into every instance.
- RAM becomes the bottleneck long before CPU does.

**With the pattern:** one shared `TreeType("Oak", texture, mesh)` object + per-tree `(x, y)` → 1M trees ≈ a few shared objects + 1M tiny coordinate pairs.

---

## 2. Real-world analogy

A **library**: 500 students studying the same textbook don't get 500 personal copies printed — the library holds a few **shared copies** (intrinsic: the book's content), and each student brings their own bookmark and notes (extrinsic: personal context).

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Flyweight** | Stores **intrinsic** (shared, immutable) state; methods accept extrinsic state as parameters | `TreeType` |
| **Flyweight Factory** | Caches flyweights; returns existing one if present | `TreeTypeFactory` |
| **Context** | Stores **extrinsic** (unique) state + reference to flyweight | `Tree(x, y, type)` |
| **Client** | Creates contexts via the factory | `Forest` |

```text
Forest ──> Tree(x=3, y=7) ─────ref────┐
           Tree(x=9, y=2) ─────ref────┼──> TreeType("Oak", texture, mesh)   ← ONE shared object
           Tree(x=5, y=5) ─────ref────┘         (from TreeTypeFactory cache)
           (extrinsic: cheap, many)              (intrinsic: heavy, few)
```

---

## 4. Python implementation

```python
# ----- Flyweight: heavy INTRINSIC state, shared & immutable -----
class TreeType:
    def __init__(self, species: str, texture: str, mesh: str):
        self.species = species
        self.texture = texture       # imagine megabytes of data
        self.mesh = mesh
        print(f"  (loaded heavy assets for {species})")

    def draw(self, x: int, y: int) -> str:          # EXTRINSIC state passed in
        return f"{self.species} at ({x},{y})"


# ----- Flyweight Factory: one instance per distinct type -----
class TreeTypeFactory:
    _cache: dict[str, TreeType] = {}

    @classmethod
    def get(cls, species: str) -> TreeType:
        if species not in cls._cache:
            cls._cache[species] = TreeType(species, f"{species}.png", f"{species}.obj")
        return cls._cache[species]                   # reuse existing flyweight


# ----- Context: tiny, per-object EXTRINSIC state -----
class Tree:
    __slots__ = ("x", "y", "type")                   # keep per-object cost minimal

    def __init__(self, x: int, y: int, tree_type: TreeType):
        self.x, self.y, self.type = x, y, tree_type

    def draw(self) -> str:
        return self.type.draw(self.x, self.y)        # delegate, passing extrinsic state


# ----- Client -----
import random

forest = [
    Tree(random.randint(0, 100), random.randint(0, 100),
         TreeTypeFactory.get(random.choice(["Oak", "Pine"])))
    for _ in range(10_000)
]

print(f"{len(forest)} trees, but only {len(TreeTypeFactory._cache)} TreeType objects!")
print(forest[0].draw())
print(forest[1].draw())
print(forest[0].type is TreeTypeFactory.get(forest[0].type.species))   # shared!
```

```text
  (loaded heavy assets for Pine)
  (loaded heavy assets for Oak)
10000 trees, but only 2 TreeType objects!
Pine at (57,12)
Oak at (3,88)
True
```

- 10,000 trees share **2** heavy objects; each tree holds only coordinates + a reference.
- Flyweights must be **immutable** — changing a shared `TreeType` would change *every* tree using it.

### Python already uses Flyweight internally

```python
a = 100
b = 100
print(a is b)            # True  — small ints (-5..256) are cached flyweights

s1 = "hello"
s2 = "hello"
print(s1 is s2)          # True  — string interning (sys.intern for explicit control)
```

```text
True
True
```

Other real examples: `functools.lru_cache` factories, pygame sprite sheets, character glyphs in text editors (the GoF original: a document has millions of characters but ~100 distinct glyph objects).

## 5. When to use / when NOT to use

**Use when:**

- The app must support **huge numbers of objects** and RAM is the bottleneck.
- Much of each object's state is **duplicated** across objects and can be made **immutable + shared** (textures, glyphs, styles, config blocks).
- Extrinsic state can be cheaply computed/stored by the caller.

**Avoid when:**

- Object count is modest — the split adds complexity for no gain.
- The "shared" state actually **varies or mutates** per object — sharing mutable state is a bug factory.
- CPU trade-off hurts: recomputing/passing extrinsic state each call costs time to save space.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Massive RAM savings when duplication is high | Code complexity: splitting intrinsic/extrinsic state |
| Fewer allocations → faster object creation | Trades CPU (passing/computing extrinsic state) for RAM |
| Centralized cache → consistent shared data | Shared flyweights **must be immutable** — subtle bugs otherwise |
| | Cache management (eviction, threading) adds work |

---

## 7. Flyweight vs. similar patterns

| Compared with | Difference |
|---|---|
| **Singleton** | Singleton = exactly **one** instance of a class; Flyweight = **one instance per distinct value**, many flyweights coexist. Also flyweights are immutable; singletons often (sadly) mutable. |
| **Prototype** | Prototype **copies** objects to create more; Flyweight **shares** objects to create fewer. Opposite directions! |
| **Object pool** | Pool lends out objects **exclusively** and takes them back; flyweights are **shared simultaneously** by everyone, forever. |
| **Caching/memoization** | Flyweight is essentially caching applied to **object identity** — `lru_cache` on a factory is a flyweight factory. |

---

## 8. Quick recap

- Split state: **intrinsic** (shared, immutable, in flyweight) vs **extrinsic** (unique, passed in).
- **Factory with a cache** guarantees one flyweight per distinct value.
- Flyweights **must be immutable**.
- Python does it natively: small-int cache, string interning.
- Use only under real **memory pressure** with real duplication.

---

## 9. Interview Q&A

**Q1. What is the Flyweight pattern?**
A memory optimization: share the common immutable part of state (intrinsic) among many objects via a caching factory, while callers supply the unique part (extrinsic) per use — supporting huge object counts cheaply.

**Q2. Intrinsic vs extrinsic state?**
Intrinsic = context-independent, immutable, stored inside the flyweight and shared (texture, glyph shape). Extrinsic = context-specific, varies per use, passed in by the caller (position, color, font size at a location).

**Q3. Why must flyweights be immutable?**
They're shared by many contexts simultaneously — mutating one would silently change every object that references it.

**Q4. Where does Python use Flyweight internally?**
Small integers (−5..256) are pre-created and reused; string literals are interned (`sys.intern`); `True`/`False`/`None` are shared singletons of their values.

**Q5. Flyweight vs Singleton?**
Singleton: one instance per **class**, globally accessible. Flyweight: one instance per **distinct intrinsic value**, obtained via a factory cache — potentially thousands of different flyweights.
