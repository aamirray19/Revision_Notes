# Pattern 1: Adapter

> **TL;DR:** **Adapter** converts the interface of an existing class into the interface a client expects, letting **incompatible classes work together without modifying either**. It's a translator sitting between client and service. Use it to integrate legacy code or third-party libraries whose interfaces don't match yours.

---

## 1. Problem it solves

**Without the pattern:** your app expects `get_data() -> dict`, but a third-party analytics library only offers `fetch_xml() -> str`.

```python
# Your code everywhere assumes:
data = source.get_data()            # returns dict

# Third-party lib offers only:
xml_string = legacy_lib.fetch_xml() # returns XML string — incompatible!
```

Bad options:

- **Rewrite your client code** to handle XML → pollutes clean code with conversion logic everywhere.
- **Modify the library** → impossible (3rd-party) or risky (legacy).

**With the pattern:** write one Adapter that *implements your interface* and *translates calls* to the library.

---

## 2. Real-world analogy

A **travel power adapter**: your laptop has an EU plug, the wall socket is US. You change **neither** the laptop nor the wall — you insert an adapter that converts one interface to the other.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Target** (interface) | What the client expects | `DataSource.get_data() -> dict` |
| **Adaptee** | Existing/incompatible class | `LegacyXMLService.fetch_xml()` |
| **Adapter** | Implements Target, wraps and translates to Adaptee | `XMLAdapter` |
| **Client** | Works only with Target | report code |

```text
Client ──expects──> Target.get_data()
                       ▲
                   Adapter ──translates──> Adaptee.fetch_xml()
                   (wraps adaptee, converts data/calls)
```

---

## 4. Python implementation

### 4a. Object adapter (composition — preferred)

```python
from abc import ABC, abstractmethod


# ----- Target: the interface OUR code expects -----
class DataSource(ABC):
    @abstractmethod
    def get_data(self) -> dict: ...


# ----- Adaptee: third-party/legacy class we CANNOT change -----
class LegacyXMLService:
    def fetch_xml(self) -> str:
        return "<user><name>Alice</name><age>30</age></user>"


# ----- Adapter: implements Target, wraps Adaptee -----
class XMLAdapter(DataSource):
    def __init__(self, service: LegacyXMLService):
        self._service = service                      # composition: HAS the adaptee

    def get_data(self) -> dict:
        xml = self._service.fetch_xml()              # call the incompatible API
        return self._parse(xml)                      # translate to what clients expect

    @staticmethod
    def _parse(xml: str) -> dict:
        import re
        return dict(re.findall(r"<(\w+)>([^<]+)</\1>", xml))


# ----- Client: knows ONLY the Target interface -----
def print_report(source: DataSource) -> None:
    data = source.get_data()
    print(f"Report -> name: {data['name']}, age: {data['age']}")


print_report(XMLAdapter(LegacyXMLService()))
```

```text
Report -> name: Alice, age: 30
```

- Neither `LegacyXMLService` nor `print_report` changed — only the adapter knows both worlds.

### 4b. Class adapter (multiple inheritance — rarer)

```python
class XMLClassAdapter(DataSource, LegacyXMLService):
    """Inherits the adaptee instead of wrapping it."""
    def get_data(self) -> dict:
        return XMLAdapter._parse(self.fetch_xml())   # self IS the adaptee


print_report(XMLClassAdapter())
```

```text
Report -> name: Alice, age: 30
```

Prefer the **object adapter**: composition is looser coupling, works even if the adaptee is a final/complex class, and can adapt an instance received from elsewhere.

### 4c. Pythonic note — duck typing

Since Python checks behavior, not declared types, an adapter often doesn't need a formal ABC — any object with a `get_data()` method works. The pattern is the same; the ceremony is lighter.

---

## 5. When to use / when NOT to use

**Use when:**

- Integrating a **third-party or legacy class** whose interface doesn't match yours.
- You want to reuse existing classes in a new system **without modifying them**.
- You're writing tests and need to wrap a real service in your own interface.

**Avoid when:**

- You control both sides → just **change the interface** at the source; an adapter would be needless indirection.
- The "adaptation" involves heavy business logic → that's not an adapter anymore; put logic in its own layer.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Reuse existing/legacy code without touching it | Extra layer of indirection |
| Single Responsibility: conversion isolated in one class | Many adapters can clutter a codebase |
| Client stays clean, coded to one interface | Two-way adaptation (both directions) gets complex |

---

## 7. Adapter vs. similar patterns

| Compared with | Difference |
|---|---|
| **Decorator** | Decorator keeps the **same** interface and adds behavior; Adapter **changes** the interface and adds nothing. |
| **Proxy** | Proxy keeps the same interface and controls **access**; Adapter converts interfaces. |
| **Facade** | Facade defines a **new simplified** interface over a whole subsystem; Adapter makes an existing interface **match another existing one**, usually 1-to-1. |
| **Bridge** | Bridge is designed **up-front** to let two hierarchies vary; Adapter is applied **after the fact** to fix incompatibility. |

---

## 8. Quick recap

- Translator between the client's **Target** interface and an incompatible **Adaptee**.
- Prefer **object adapter** (wraps instance) over class adapter (inheritance).
- Changes **interface shape only** — no new behavior (that's Decorator's job).
- Perfect for **legacy / third-party integration**.

---

## 9. Interview Q&A

**Q1. What does the Adapter pattern do?**
It wraps an existing class with a new interface so incompatible classes can collaborate — translating method names, parameters, and data formats, without modifying either side.

**Q2. Object adapter vs class adapter?**
Object adapter uses **composition** (holds an adaptee instance) — flexible, works with subclasses of the adaptee. Class adapter uses **(multiple) inheritance** — can override adaptee behavior but is tightly coupled. Python supports both; composition is preferred.

**Q3. Adapter vs Decorator vs Proxy — the wrapper question?**
All wrap an object. Adapter → **different** interface (compatibility). Decorator → **same** interface + **added behavior**. Proxy → **same** interface + **access control**.

**Q4. Where do you see adapters in real Python code?**
`socket.makefile()` (adapts a socket to a file-like interface), DB-API drivers adapting different databases to one interface, `pathlib.Path` vs `os.path` wrappers, ORM adapters over REST clients.

**Q5. When is an adapter a code smell?**
When you own both interfaces (just align them), or when the adapter starts holding business logic — it should be a thin translation layer.
