# Pattern 5: Bridge

> **TL;DR:** **Bridge** splits one big class hierarchy into **two independent hierarchies** — an **Abstraction** (high-level control, e.g., Remote) and an **Implementation** (low-level work, e.g., Device) — connected by composition. Each side can grow independently, turning an m×n subclass explosion into m+n classes. "Prefer composition over inheritance", formalized.

---

## 1. Problem it solves

**Without the pattern:** two dimensions of variation multiply into one inheritance tree.

```python
# Dimension 1: shape type     Dimension 2: rendering method
class VectorCircle: ...
class RasterCircle: ...
class VectorSquare: ...
class RasterSquare: ...
# Add Triangle  -> +2 classes. Add OpenGLRenderer -> +3 classes. m shapes × n renderers!
```

Problems:

- **m × n class explosion** — every new shape needs a version per renderer and vice versa.
- Both concerns (geometry + rendering) are **tangled in each class**.
- Can't **switch renderer at runtime** — it's baked into the class.

**With the pattern:** `Shape` *has a* `Renderer`. m shapes + n renderers = **m + n classes**, combined freely at runtime.

---

## 2. Real-world analogy

**Remote controls and devices**: a basic remote or an advanced remote (abstraction hierarchy) can operate a TV or a radio (implementation hierarchy). Remotes and devices evolve **independently** — a new remote model works with all devices; a new device works with all remotes. The "bridge" is the remote **holding a reference** to a device.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Abstraction** | High-level interface; **holds a reference** to Implementation | `Shape` |
| **Refined Abstractions** | Variants of the abstraction | `Circle`, `Square` |
| **Implementation** (interface) | Low-level operations interface | `Renderer.render_shape()` |
| **Concrete Implementations** | Actual low-level work | `VectorRenderer`, `RasterRenderer` |

```text
      Abstraction  ── has-a (THE BRIDGE) ──>  Implementation
        Shape                                   Renderer
       ▲      ▲                                ▲        ▲
    Circle  Square                  VectorRenderer  RasterRenderer

   (hierarchy 1: WHAT it is)        (hierarchy 2: HOW it's drawn)
```

---

## 4. Python implementation

```python
from abc import ABC, abstractmethod


# ----- Implementation hierarchy: HOW to draw -----
class Renderer(ABC):
    @abstractmethod
    def render_shape(self, name: str, size: float) -> str: ...


class VectorRenderer(Renderer):
    def render_shape(self, name: str, size: float) -> str:
        return f"Drawing {name} (size {size}) as crisp vector lines"


class RasterRenderer(Renderer):
    def render_shape(self, name: str, size: float) -> str:
        return f"Drawing {name} (size {size}) as pixels"


# ----- Abstraction hierarchy: WHAT to draw -----
class Shape(ABC):
    def __init__(self, renderer: Renderer):
        self.renderer = renderer               # <-- THE BRIDGE (composition)

    @abstractmethod
    def draw(self) -> str: ...


class Circle(Shape):
    def __init__(self, renderer: Renderer, radius: float):
        super().__init__(renderer)
        self.radius = radius

    def draw(self) -> str:
        return self.renderer.render_shape("circle", self.radius)   # delegate HOW


class Square(Shape):
    def __init__(self, renderer: Renderer, side: float):
        super().__init__(renderer)
        self.side = side

    def draw(self) -> str:
        return self.renderer.render_shape("square", self.side)


# ----- Client: mix & match freely -----
print(Circle(VectorRenderer(), 5).draw())
print(Circle(RasterRenderer(), 5).draw())
print(Square(VectorRenderer(), 3).draw())

# Even switch implementation at RUNTIME:
shape = Square(RasterRenderer(), 4)
print(shape.draw())
shape.renderer = VectorRenderer()
print(shape.draw())
```

```text
Drawing circle (size 5) as crisp vector lines
Drawing circle (size 5) as pixels
Drawing square (size 3) as crisp vector lines
Drawing square (size 4) as pixels
Drawing square (size 4) as crisp vector lines
```

- Adding `Triangle` = **1 class** (works with every renderer). Adding `OpenGLRenderer` = **1 class** (works with every shape).
- The renderer can even be **swapped at runtime** — impossible with inheritance.

---

## 5. When to use / when NOT to use

**Use when:**

- A class varies along **two (or more) independent dimensions** (shape×renderer, remote×device, GUI×OS, notification-type×delivery-channel).
- You want to pick/switch the implementation **at runtime**.
- You're seeing names like `VectorCircle`, `RasterSquare` — a multiplying hierarchy is the tell-tale smell.
- Frontend/backend style splits: one API abstraction over several platform implementations.

**Avoid when:**

- There's only **one dimension** of variation — plain polymorphism suffices.
- Highly cohesive single class — splitting adds indirection without benefit.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| m+n classes instead of m×n | More indirection; slightly harder to follow |
| Both hierarchies evolve independently (OCP) | Up-front design needed to find the right split |
| Implementation switchable at runtime | Overkill for a single, stable dimension |
| Hides platform details from high-level code | |

---

## 7. Bridge vs. similar patterns

| Compared with | Difference |
|---|---|
| **Adapter** | Adapter is a **retrofit** to make existing incompatible classes work together; Bridge is **designed up-front** to let two hierarchies vary independently. |
| **Strategy** | Structurally similar (composition + delegation)! Strategy swaps an **algorithm** (one behavior method); Bridge separates an entire **implementation platform** from an abstraction hierarchy — a structural, architecture-level split. |
| **Abstract Factory** | Can **team up**: a factory creates the right Implementation for a platform, which is then handed to the Abstraction. |
| **State** | Also composition-based, but the wrapped object (state) **changes itself** over time; a bridge implementation is picked and mostly stays. |

---

## 8. Quick recap

- Two hierarchies: **Abstraction (what)** has-a **Implementation (how)**.
- The "bridge" = the **composition link** between them.
- Kills m×n subclass explosion → m+n.
- Implementation can be **swapped at runtime**.
- Smell that calls for it: class names combining two concerns (`RasterCircle`).

---

## 9. Interview Q&A

**Q1. What is the Bridge pattern in one line?**
Decouple an abstraction from its implementation (via composition) so the two can vary independently.

**Q2. How does Bridge prevent class explosion?**
With inheritance, m variants × n platforms = m×n subclasses. Bridge keeps them in two separate hierarchies connected by a has-a reference, giving m+n classes and free mix-and-match.

**Q3. Bridge vs Adapter?**
Intent + timing: Adapter is applied **after** classes exist, to fix interface mismatch. Bridge is planned **before**, to keep two dimensions of a design independent.

**Q4. Bridge vs Strategy — both are composition + delegation?**
Strategy is behavioral: swap one interchangeable **algorithm** behind a method. Bridge is structural: split an entire class into abstraction and implementation **hierarchies** that both grow. Strategy = tactical, Bridge = architectural.

**Q5. Give real software examples.**
GUI toolkits (widget abstraction over per-OS implementations), JDBC/DB-API (API abstraction over per-database drivers), device drivers, messaging (Notification types over delivery channels: email/SMS/push).
