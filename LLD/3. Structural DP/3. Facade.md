# Pattern 3: Facade

> **TL;DR:** **Facade** provides a **single, simplified interface** to a complex subsystem. It doesn't add functionality — it **orchestrates** existing classes so clients make one call instead of ten. Use it to shield client code from a subsystem's complexity and coupling.

---

## 1. Problem it solves

**Without the pattern:** to convert a video, every client must know the whole pipeline.

```python
# EVERY place that converts a video repeats this dance:
file = VideoFile("birthday.mp4")
codec = CodecFactory.extract(file)
buffer = BitrateReader.read(file, codec)
result = BitrateReader.convert(buffer, MPEG4Codec())
audio = AudioMixer().fix(result)
save(audio, "birthday.avi")
```

Problems:

- Clients are **coupled to many subsystem classes** — any internal change breaks all callers.
- The correct **sequence of calls** is duplicated everywhere.
- Hard to learn: new developers must understand the full pipeline to do one simple thing.

**With the pattern:** clients call `converter.convert("birthday.mp4", "avi")` — one line, zero subsystem knowledge.

---

## 2. Real-world analogy

A **hotel front desk**: you want extra towels, a taxi, and a dinner reservation. You don't call housekeeping, the taxi company and the restaurant yourself — you make **one call to reception**, which coordinates all departments. The departments still exist and can be contacted directly if needed.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Facade** | Knows which subsystem classes to use and in what order; exposes simple methods | `VideoConverter.convert()` |
| **Subsystem classes** | Do the real work; unaware of the facade | `VideoFile`, `CodecFactory`, `BitrateReader`, `AudioMixer` |
| **Client** | Calls only the facade (but *may* bypass it for advanced needs) | app code |

```text
Client ──convert()──> Facade ──orchestrates──> [SubsystemA, SubsystemB, SubsystemC, ...]
   (one simple call)              (knows the sequence & wiring)
```

---

## 4. Python implementation

```python
# ----- Complex subsystem (clients shouldn't need to know all this) -----
class VideoFile:
    def __init__(self, filename: str):
        self.filename = filename
        self.codec = filename.rsplit(".", 1)[-1]


class CodecFactory:
    @staticmethod
    def extract(file: VideoFile) -> str:
        print(f"  Extracting codec: {file.codec}")
        return file.codec


class BitrateReader:
    @staticmethod
    def read(file: VideoFile, codec: str) -> str:
        print(f"  Reading bitrate for {file.filename}")
        return f"raw({file.filename})"

    @staticmethod
    def convert(buffer: str, target_codec: str) -> str:
        print(f"  Converting buffer to {target_codec}")
        return f"{buffer}->{target_codec}"


class AudioMixer:
    def fix(self, result: str) -> str:
        print("  Fixing audio sync")
        return f"fixed({result})"


# ----- Facade: ONE simple entry point -----
class VideoConverter:
    def convert(self, filename: str, target_format: str) -> str:
        print(f"Converting {filename} -> {target_format}")
        file = VideoFile(filename)
        codec = CodecFactory.extract(file)
        buffer = BitrateReader.read(file, codec)
        result = BitrateReader.convert(buffer, target_format)
        result = AudioMixer().fix(result)
        print("Done!")
        return f"{filename.rsplit('.', 1)[0]}.{target_format}"


# ----- Client: blissfully ignorant of the pipeline -----
converter = VideoConverter()
output = converter.convert("birthday.mp4", "avi")
print("Saved as:", output)
```

```text
Converting birthday.mp4 -> avi
  Extracting codec: mp4
  Reading bitrate for birthday.mp4
  Converting buffer to avi
  Fixing audio sync
Done!
Saved as: birthday.avi
```

- The client shrank from ~6 coupled lines to **one call**.
- The pipeline's order/wiring now lives in exactly **one place** — easy to change.
- Power users can still use `BitrateReader` directly; a facade **doesn't forbid** direct access.

### Real Python examples you already use

```python
import requests
requests.get("https://example.com")   # facade over sockets, SSL, redirects, pooling, cookies

import shutil
shutil.make_archive("backup", "zip", "my_folder")  # facade over zipfile/os walking

# json.dumps(), pathlib.Path.read_text() — all facades over lower-level machinery
```

## 5. When to use / when NOT to use

**Use when:**

- Clients need a **simple view** of a complex subsystem (common operations, sensible defaults).
- You want to **decouple** client code from subsystem internals so internals can evolve freely.
- Layering a system: each layer exposes a facade as its entry point.
- Wrapping a messy legacy system before refactoring it.

**Avoid when:**

- The subsystem is already simple — a facade just adds a pass-through layer.
- The facade starts accumulating logic of its own and becomes a **god object** doing everything — split it.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Shields clients from subsystem complexity | Risk of becoming a **god object** coupled to everything |
| Call sequence/wiring lives in one place | Can hide capabilities power-users need (mitigate: allow direct access) |
| Loosens client↔subsystem coupling; internals can change | Another layer to maintain |
| Great seam for testing (mock the facade) | |

---

## 7. Facade vs. similar patterns

| Compared with | Difference |
|---|---|
| **Adapter** | Adapter makes an interface **match another existing interface** (usually wraps one class); Facade invents a **new simpler** interface over **many** classes. |
| **Mediator** | Both centralize communication, but subsystem classes **don't know** the Facade (one-way); colleagues **know and talk through** the Mediator (two-way). |
| **Proxy** | Proxy has the **same** interface as the real object; Facade's interface is different (simpler) and covers a subsystem. |
| **Abstract Factory** | Abstract Factory simplifies **creation** of families; Facade simplifies **usage** of a subsystem. |

---

## 8. Quick recap

- One class exposing **simple methods** that orchestrate a complex subsystem.
- Adds **no new behavior** — just coordination + defaults.
- Subsystem stays accessible for advanced use.
- You use facades daily: `requests.get`, `shutil.make_archive`, `json.dumps`.

---

## 9. Interview Q&A

**Q1. What is the Facade pattern?**
A single simplified entry point to a complex subsystem: it wires together the right classes in the right order so clients make one call instead of learning the whole subsystem.

**Q2. Facade vs Adapter?**
Different intents: Adapter **converts** an interface to match what a client already expects (compatibility); Facade **defines a new, simpler** interface to reduce complexity. Adapter usually wraps one object; Facade orchestrates many.

**Q3. Does a Facade forbid direct subsystem access?**
No — it's a convenience, not a wall. Clients with advanced needs can still use subsystem classes directly.

**Q4. What's the main danger with Facades?**
Becoming a **god object**: as teams funnel every feature through it, it grows huge and coupled to everything. Keep facades thin — orchestration only — and split by use-case when they grow.

**Q5. Facade vs Mediator?**
Facade: one-way simplification; subsystem classes are unaware of it. Mediator: colleagues deliberately communicate **through** the mediator to avoid knowing each other; communication is two-way and the mediator contains interaction logic.
