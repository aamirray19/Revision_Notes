# Pattern 6: Proxy

> **TL;DR:** **Proxy** provides a **stand-in** object with the **same interface** as the real object, so it can **control access** to it — lazy creation (virtual proxy), permissions (protection proxy), caching, logging, or remote communication. The client can't tell (and shouldn't care) whether it's talking to the proxy or the real thing.

---

## 1. Problem it solves

**Without the pattern:** a heavyweight object is created even when it may never be used, or access-control/caching logic pollutes the client or the service.

```python
class HighResImage:
    def __init__(self, path):
        print(f"Loading {path} from disk... (takes 3s, 500MB RAM)")
    def display(self): ...

gallery = [HighResImage(f"photo{i}.png") for i in range(1000)]   # loads ALL 1000 now!
# ...user scrolls and views only 3 of them.
```

Problems:

- **Eager, expensive initialization** for objects that may never be used.
- Cross-cutting concerns (auth checks, caching, logging) end up **inside the service** or **in every client**.
- Clients of a **remote** service would need networking code everywhere.

**With the pattern:** the proxy implements the same interface, defers/guards the real object, and clients don't change at all.

---

## 2. Real-world analogy

A **credit card** is a proxy for your bank account: same "interface" (pay money), but it adds access control (PIN), logging (statements), and you never hand over the actual cash vault. A celebrity's **assistant** is a protection proxy: same requests go in, but only approved ones reach the celebrity.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Subject** (interface) | Common interface for real object & proxy | `Image.display()` |
| **Real Subject** | The actual heavyweight/sensitive object | `HighResImage` |
| **Proxy** | Same interface; holds/creates the real subject; adds control logic | `ImageProxy` |
| **Client** | Uses Subject, unaware which one it has | gallery code |

```text
Client ──display()──> Proxy ──(only when needed / allowed)──> RealSubject
                      same interface as RealSubject
                      [lazy init | access check | cache | log | remote call]
```

## 4. Python implementation

### 4a. Virtual proxy (lazy loading)

```python
from abc import ABC, abstractmethod


# ----- Subject -----
class Image(ABC):
    @abstractmethod
    def display(self) -> None: ...


# ----- Real Subject: expensive -----
class HighResImage(Image):
    def __init__(self, path: str):
        self.path = path
        print(f"Loading {path} from disk... (expensive!)")

    def display(self) -> None:
        print(f"Displaying {self.path}")


# ----- Proxy: same interface, lazy creation -----
class ImageProxy(Image):
    def __init__(self, path: str):
        self.path = path
        self._real: HighResImage | None = None     # NOT loaded yet

    def display(self) -> None:
        if self._real is None:                     # create only on first use
            self._real = HighResImage(self.path)
        self._real.display()


# ----- Client: identical code for proxy or real image -----
gallery = [ImageProxy(f"photo{i}.png") for i in range(3)]
print("Gallery created (instant — nothing loaded)")

gallery[1].display()        # loads ONLY this one
gallery[1].display()        # already loaded — no second load
```

```text
Gallery created (instant — nothing loaded)
Loading photo1.png from disk... (expensive!)
Displaying photo1.png
Displaying photo1.png
```

### 4b. Protection + logging proxy

```python
class DocumentService:
    def read(self, doc: str) -> str:
        return f"contents of {doc}"

    def delete(self, doc: str) -> str:
        return f"{doc} deleted"


class SecureDocumentService:
    """Same interface as DocumentService + access control + audit log."""

    def __init__(self, service: DocumentService, role: str):
        self._service = service
        self._role = role

    def read(self, doc: str) -> str:
        print(f"[AUDIT] {self._role} reads {doc}")
        return self._service.read(doc)

    def delete(self, doc: str) -> str:
        if self._role != "admin":
            raise PermissionError("Only admins can delete")
        print(f"[AUDIT] {self._role} deletes {doc}")
        return self._service.delete(doc)


svc = SecureDocumentService(DocumentService(), role="viewer")
print(svc.read("report.pdf"))
try:
    svc.delete("report.pdf")
except PermissionError as e:
    print("Blocked:", e)
```

```text
[AUDIT] viewer reads report.pdf
contents of report.pdf
Blocked: Only admins can delete
```

### 4c. The main proxy types (know these!)

| Type | Controls | Example |
|---|---|---|
| **Virtual proxy** | Lazy creation of expensive objects | image galleries, ORM lazy relations |
| **Protection proxy** | Permissions / access rights | role-checked service wrappers |
| **Remote proxy** | Communication with an object in another process/machine | gRPC/RPC client stubs |
| **Caching proxy** | Reuse of results | `functools.lru_cache`, HTTP caches |
| **Smart reference** | Extra bookkeeping (ref-counting, locking, logging) | audit wrappers |

Python hooks that enable "invisible" proxies: `__getattr__` (forward unknown attributes to the real object), descriptors, `unittest.mock.Mock` (a universal proxy), weakref proxies.

---

## 5. When to use / when NOT to use

**Use when:**

- The real object is **expensive** and often unused → virtual proxy.
- You need **access control / auditing** without touching the service or clients.
- The object lives **remotely** and you want local-call syntax → remote proxy.
- Results are worth **caching** transparently.

**Avoid when:**

- The object is cheap and access is unrestricted — a proxy is pure overhead.
- The added latency/indirection matters on a hot path.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Control object lifecycle (lazy init) transparently | Extra indirection/latency per call |
| Add security/caching/logging without changing service or client | Response may be stale (caching) or delayed (lazy) |
| Works even when the real object isn't ready/local | Duplicate interface to keep in sync (less an issue with `__getattr__`) |
| Open/Closed: new control logic without touching the service | Code becomes harder to trace/debug |

---

## 7. Proxy vs. similar patterns

| Compared with | Difference |
|---|---|
| **Decorator** | Same structure, different intent: Decorator **adds features** and the client stacks wrappers; Proxy **controls access** and usually manages its subject's lifecycle itself. |
| **Adapter** | Adapter **changes** the interface; Proxy keeps it **identical**. |
| **Facade** | Facade simplifies a **subsystem** with a new interface; Proxy mirrors **one object's** interface. |
| **Singleton-ish lazy init** | A virtual proxy gives per-object lazy init without making anything global. |

---

## 8. Quick recap

- Stand-in with the **same interface**; client can't tell the difference.
- Five flavors: **virtual, protection, remote, caching, smart reference**.
- Adds control **around** the real call: check → delegate → extra work.
- Python: `__getattr__` forwarding, `lru_cache`, mock objects, RPC stubs.

---

## 9. Interview Q&A

**Q1. What is the Proxy pattern?**
An object with the same interface as a real subject that intercepts calls to control access — creating the subject lazily, checking permissions, caching results, logging, or forwarding to a remote object.

**Q2. Proxy vs Decorator?**
Identical structure; different **intent**. Decorator adds behavior and clients compose stacks explicitly; Proxy controls access and typically creates/owns the real subject internally (client may not even know it has a proxy).

**Q3. Name the common proxy types.**
Virtual (lazy init), protection (permissions), remote (network stub), caching, and smart reference (extra bookkeeping like locking/refcounting).

**Q4. How can Python make a proxy without re-declaring every method?**
Implement `__getattr__` to forward unhandled attribute lookups to the wrapped object — unknown methods/attributes automatically reach the real subject.

**Q5. Where do proxies appear in real systems?**
ORM lazy-loaded relations (SQLAlchemy/Django), RPC/gRPC client stubs, `functools.lru_cache`, reverse proxies (nginx) conceptually, `unittest.mock.Mock`, weakref.proxy.
