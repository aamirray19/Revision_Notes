# Pattern 4: Decorator

> **TL;DR:** **Decorator** attaches new behavior to an object by **wrapping** it in another object with the **same interface**. Wrappers can be **stacked** in any combination at **runtime** — avoiding the subclass explosion of `CoffeeWithMilkAndSugarAndCream`. Python's `@decorator` syntax is the function-level version of the same idea.

---

## 1. Problem it solves

**Without the pattern:** every feature combination becomes a subclass.

```python
class Coffee: ...
class CoffeeWithMilk(Coffee): ...
class CoffeeWithSugar(Coffee): ...
class CoffeeWithMilkAndSugar(Coffee): ...
class CoffeeWithMilkAndSugarAndCream(Coffee): ...   # combinatorial explosion!
```

Problems:

- **Class explosion**: n add-ons → up to 2ⁿ subclasses.
- Combinations fixed at **compile time** — can't add milk *at runtime* based on user's order.
- Inheritance is **static**; you can't remove or reorder features later.

**With the pattern:** each add-on is a small wrapper; stack them freely: `Cream(Sugar(Milk(Espresso())))`.

---

## 2. Real-world analogy

**Wearing clothes**: you (the core object) put on a shirt, then a sweater, then a raincoat. Each layer adds a feature (warmth, waterproofing) while you remain "a person" (same interface). Layers stack in any order and can be added/removed at will.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Component** (interface) | Common interface for core & wrappers | `Beverage.cost()`, `description()` |
| **Concrete Component** | The plain object being decorated | `Espresso` |
| **Base Decorator** | Implements Component; holds a wrapped Component; delegates | `AddonDecorator` |
| **Concrete Decorators** | Add behavior **before/after delegating** | `Milk`, `Sugar`, `Cream` |

```text
Client ──> Cream( Sugar( Milk( Espresso ) ) )      all share the Beverage interface
             │      │      │       └── does base work
             └──────┴──────┴── each adds its bit, then delegates inward
```

---

## 4. Python implementation

### 4a. Classic object decorator

```python
from abc import ABC, abstractmethod


# ----- Component -----
class Beverage(ABC):
    @abstractmethod
    def cost(self) -> float: ...

    @abstractmethod
    def description(self) -> str: ...


# ----- Concrete Component -----
class Espresso(Beverage):
    def cost(self) -> float:
        return 80.0

    def description(self) -> str:
        return "Espresso"


# ----- Base Decorator -----
class AddonDecorator(Beverage):
    def __init__(self, beverage: Beverage):
        self._beverage = beverage              # wraps ANY Beverage (core or decorated)

    def cost(self) -> float:
        return self._beverage.cost()           # default: pure delegation

    def description(self) -> str:
        return self._beverage.description()


# ----- Concrete Decorators -----
class Milk(AddonDecorator):
    def cost(self) -> float:
        return self._beverage.cost() + 20      # add own cost AFTER delegating

    def description(self) -> str:
        return self._beverage.description() + " + Milk"


class Sugar(AddonDecorator):
    def cost(self) -> float:
        return self._beverage.cost() + 10

    def description(self) -> str:
        return self._beverage.description() + " + Sugar"


class Cream(AddonDecorator):
    def cost(self) -> float:
        return self._beverage.cost() + 30

    def description(self) -> str:
        return self._beverage.description() + " + Cream"


# ----- Client: compose at RUNTIME -----
order = Cream(Sugar(Milk(Espresso())))         # any combination, any order
print(order.description(), "=", order.cost())

simple = Sugar(Espresso())
print(simple.description(), "=", simple.cost())
```

```text
Espresso + Milk + Sugar + Cream = 140.0
Espresso + Sugar = 90.0
```

- 3 add-ons = **3 small classes**, not 2³ subclasses — combinations are free.
- A decorator doesn't care if it wraps the core or another decorator — everything is a `Beverage`.

### 4b. Python's `@decorator` — same idea for functions

```python
import functools
import time


def timed(func):
    @functools.wraps(func)                     # preserves name/docstring of wrapped func
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)         # delegate to the wrapped function
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper


def logged(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print(f"Calling {func.__name__}{args}")
        return func(*args, **kwargs)
    return wrapper


@logged          # stacking decorators — just like Cream(Sugar(...))
@timed
def add(a, b):
    return a + b


print(add(2, 3))
```

```text
Calling add(2, 3)
add took 0.0000s
5
```

- Same principle: wrap a callable, add behavior, delegate, same "interface" (callable).
- Real examples: `@functools.lru_cache`, `@staticmethod`, Flask's `@app.route`, `@pytest.fixture`.

## 5. When to use / when NOT to use

**Use when:**

- You need to add responsibilities **per-object, at runtime**, in arbitrary combinations (streams: buffering + compression + encryption; UI: borders + scrollbars; services: logging + caching + retry).
- Extending via subclassing would cause **class explosion** or is impossible (final classes).

**Avoid when:**

- There's only **one fixed extension** — simple inheritance or a flag is clearer.
- Object **identity matters**: `decorated is original` is False; `isinstance` can also surprise you.
- Many stacked layers make **debugging painful** (deep delegation chains).

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Add/remove behavior at **runtime** | Many small classes/wrappers to track |
| Combine features freely (no subclass explosion) | Order of stacking can matter (encrypt-then-compress ≠ compress-then-encrypt) |
| Single Responsibility: one feature per decorator | Hard to remove a specific wrapper from the middle of a stack |
| Open/Closed: new features without touching existing code | Identity/type checks on decorated objects break |

---

## 7. Decorator vs. similar patterns

| Compared with | Difference |
|---|---|
| **Adapter** | Adapter **changes** the interface; Decorator **keeps** it and adds behavior. |
| **Proxy** | Same shape! Difference is **intent & control**: Proxy manages **access** (lazy/auth/cache) and usually creates/owns its subject; Decorator **enhances** and is stacked by the client. |
| **Composite** | Decorator = recursive composition with **one** child (adds behavior); Composite = **many** children (aggregates). |
| **Strategy** | Strategy changes the **guts** (swaps the algorithm inside); Decorator changes the **skin** (wraps outside). |
| **Chain of Responsibility** | CoR handlers can **stop** the chain; decorators **always delegate** inward. |

---

## 8. Quick recap

- Wrapper with the **same interface**; adds its bit, then **delegates**.
- Stack wrappers at runtime: `Cream(Sugar(Milk(Espresso())))`.
- Kills subclass explosion: n features = n decorators, all combinations free.
- Python `@decorators` = the same pattern for functions (`functools.wraps`!).

---

## 9. Interview Q&A

**Q1. What problem does Decorator solve over inheritance?**
Inheritance is static and per-class; combinations of features explode into 2ⁿ subclasses. Decorator composes features per-**object** at **runtime**, with one small class per feature.

**Q2. Decorator vs Proxy — they look identical?**
Structurally yes (same interface, wraps subject, delegates). Intent differs: Decorator **adds behavior** and the client composes the stack; Proxy **controls access** (lazy init, permissions, caching, remoting) and often instantiates/owns the real subject itself.

**Q3. Is Python's `@decorator` syntax the GoF Decorator pattern?**
Conceptually yes — it wraps a callable with another callable of the same "interface" to add behavior. GoF describes it for objects; Python applies it to functions/classes with syntactic sugar. Mention `functools.wraps` for preserving metadata.

**Q4. Does stacking order matter?**
Yes. Each decorator runs before/after delegating, so `logged(timed(f))` logs the timing call, while `timed(logged(f))` times the logging. For streams, compress-then-encrypt differs from encrypt-then-compress.

**Q5. Real-world examples?**
Java I/O streams (`BufferedInputStream(GzipInputStream(FileInputStream))`), Python `functools.lru_cache`, middleware in web frameworks (each wraps the next handler), `gzip.open` over file objects.
