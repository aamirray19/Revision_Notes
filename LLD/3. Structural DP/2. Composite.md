# Pattern 2: Composite

> **TL;DR:** **Composite** composes objects into **tree structures** (part–whole hierarchies) and lets clients treat a **single object and a group of objects uniformly** — both expose the same interface. Think files vs folders: `size()` works on both; a folder just sums its children.

---

## 1. Problem it solves

**Without the pattern:** client code must constantly distinguish single items from groups.

```python
def total_size(item):
    if isinstance(item, File):
        return item.size
    elif isinstance(item, Folder):
        total = 0
        for child in item.children:
            total += total_size(child)       # type checks + recursion in CLIENT code
        return total
```

Problems:

- `isinstance` checks **everywhere** a tree is processed (size, delete, search, display...).
- Adding a new node type (e.g., `Shortcut`) means editing **every** such function.
- Client is coupled to the tree's internal structure.

**With the pattern:** `File` and `Folder` share one interface; the recursion lives **inside** `Folder`, and clients call `item.size()` without caring what it is.

---

## 2. Real-world analogy

A **company org chart**: asking a manager "what's your team's total headcount?" works whether you ask an individual contributor (returns 1) or a VP (recursively sums all sub-teams). The question (interface) is identical; the structure handles the recursion.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Component** (interface) | Common operations for both leaf & composite | `FSNode.size()`, `show()` |
| **Leaf** | End node — does the actual work | `File` |
| **Composite** | Holds children; delegates/aggregates over them | `Folder` (add/remove/iterate children) |
| **Client** | Works with everything via Component | `print(node.size())` |

```text
            FSNode (Component)
            size() / show()
            ▲            ▲
          File        Folder ──children──> [FSNode, FSNode, ...]
         (Leaf)      (Composite: recursion lives here)
```

---

## 4. Python implementation

```python
from abc import ABC, abstractmethod


# ----- Component -----
class FSNode(ABC):
    def __init__(self, name: str):
        self.name = name

    @abstractmethod
    def size(self) -> int: ...

    @abstractmethod
    def show(self, indent: int = 0) -> None: ...


# ----- Leaf -----
class File(FSNode):
    def __init__(self, name: str, size_kb: int):
        super().__init__(name)
        self._size = size_kb

    def size(self) -> int:
        return self._size

    def show(self, indent: int = 0) -> None:
        print(" " * indent + f"- {self.name} ({self._size} KB)")


# ----- Composite -----
class Folder(FSNode):
    def __init__(self, name: str):
        super().__init__(name)
        self._children: list[FSNode] = []

    def add(self, node: FSNode) -> "Folder":
        self._children.append(node)
        return self                                  # chaining convenience

    def remove(self, node: FSNode) -> None:
        self._children.remove(node)

    def size(self) -> int:
        return sum(child.size() for child in self._children)   # recursion hidden here

    def show(self, indent: int = 0) -> None:
        print(" " * indent + f"+ {self.name}/ ({self.size()} KB)")
        for child in self._children:
            child.show(indent + 2)


# ----- Client: treats File and Folder IDENTICALLY -----
root = Folder("project")
src = Folder("src")
src.add(File("main.py", 4)).add(File("utils.py", 2))
root.add(src)
root.add(File("README.md", 1))

root.show()
print("Total:", root.size(), "KB")          # same call works on File too
print("One file:", File("a.txt", 5).size(), "KB")
```

```text
+ project/ (7 KB)
  + src/ (6 KB)
    - main.py (4 KB)
    - utils.py (2 KB)
  - README.md (1 KB)
Total: 7 KB
One file: 5 KB
```

- Client never asks "is this a file or folder?" — **zero `isinstance` checks**.
- New node types (e.g., `SymLink`) plug in by implementing `FSNode`; no client changes.

---

## 5. When to use / when NOT to use

**Use when:**

- Your domain is naturally a **tree / part–whole hierarchy**: file systems, UI widget trees (a panel contains buttons and other panels), org charts, menus with submenus, arithmetic expression trees, product bundles containing products or other bundles.
- You want clients to **ignore the difference** between single items and groups.

**Avoid when:**

- The structure is **flat** — a plain list is simpler.
- Leaves and composites have **almost nothing in common** — forcing one interface makes it too general (e.g., `add_child()` on a leaf is meaningless; you must decide whether leaves raise an error or the methods live only on Composite).

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Uniform treatment of items & groups (no type checks) | Interface can become **over-general** (child ops on leaves?) |
| Arbitrary-depth nesting for free (recursion built in) | Harder to restrict *which* components a composite may contain |
| Open/Closed: new node types without client changes | Deep trees → recursive calls can be a performance concern |

---

## 7. Composite vs. similar patterns

| Compared with | Difference |
|---|---|
| **Decorator** | Both delegate recursively, but Decorator has exactly **one** child and **adds behavior**; Composite has **many** children and **aggregates** them. |
| **Iterator** | Iterator traverses a collection externally; Composite typically operates **internally** (each node processes itself). They're often combined to walk the tree. |
| **Visitor** | Visitor adds **new operations** to an existing Composite tree without changing node classes. |
| **Chain of Responsibility** | CoR passes a request **along a line** until one handles it; Composite fans out to **all** children. |

---

## 8. Quick recap

- Tree structure: **Leaf** does work, **Composite** aggregates children.
- One **Component interface** → client code has no `isinstance` checks.
- Recursion lives **inside the composite**, not in clients.
- Great for file systems, UIs, org charts, expressions, bundles/menus.

---

## 9. Interview Q&A

**Q1. What problem does Composite solve?**
It removes the client-side distinction between individual objects and groups: both implement one Component interface, so operations like `size()`/`render()` work uniformly and recursion is encapsulated inside composites.

**Q2. Where do child-management methods (`add`/`remove`) belong — Component or Composite?**
Design trade-off. On Component → full uniformity ("transparency") but leaves get meaningless methods. On Composite only → type safety but clients must know the difference to build trees. Most Python code puts them on Composite only (as in our example).

**Q3. Give real-world examples of Composite.**
File systems, GUI widget trees (Tkinter/Qt containers holding widgets or other containers), HTML/XML DOM, org hierarchies, menu systems, arithmetic expression trees (used later by Interpreter).

**Q4. How do Composite and Decorator relate structurally?**
Both are recursive composition with a shared interface; Decorator is essentially a composite with **one child** whose purpose is to add behavior rather than aggregate many children.

**Q5. How would you traverse a Composite tree without bloating the node classes?**
Combine with **Iterator** (expose traversal) or **Visitor** (move operations out of nodes), keeping the tree structure and the operations decoupled.
