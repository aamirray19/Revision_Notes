# Structural Design Patterns — Overview

> **TL;DR:** Structural patterns deal with **how classes and objects are composed** into larger structures while keeping those structures flexible and efficient. They answer: "how do I connect/wrap/organize objects so the overall system stays simple?"

---

## 1. What problems do structural patterns address?

- Incompatible interfaces that must work together (legacy code, 3rd-party libs).
- Adding behavior to objects **without subclass explosion**.
- Treating single objects and groups of objects **uniformly**.
- Hiding the complexity of a subsystem behind a simple entry point.
- Controlling access to an object, or sharing objects to **save memory**.

The common theme: **composition over inheritance** — build behavior by combining objects.

---

## 2. The 7 Structural Patterns at a Glance

| # | Pattern | One-line intent | Classic example |
|---|---------|-----------------|-----------------|
| 1 | **Adapter** | Convert one interface into another that clients expect | Card reader adapting SD card to USB; wrapping a legacy API |
| 2 | **Composite** | Treat individual objects and compositions **uniformly** (tree) | File system: files & folders both support `size()` |
| 3 | **Facade** | One simple interface over a complex subsystem | `compiler.compile()` hiding lexer/parser/codegen |
| 4 | **Decorator** | Attach responsibilities to an object **dynamically** by wrapping | Coffee + milk + sugar; Python `@decorators` |
| 5 | **Bridge** | Split a class into **abstraction** and **implementation** hierarchies that vary independently | Shapes × Renderers; Remotes × Devices |
| 6 | **Proxy** | A stand-in object that **controls access** to the real one | Lazy loading, access control, caching, remote objects |
| 7 | **Flyweight** | **Share** common immutable state to support huge numbers of objects | Text editor sharing character/glyph objects; game trees |

---

## 3. How to pick the right one (decision cheat-sheet)

- Interfaces **don't match** → **Adapter**
- Need a **part-whole tree** treated uniformly → **Composite**
- Subsystem too complex for clients → **Facade**
- Add features **per-object at runtime** → **Decorator**
- Two dimensions of variation (abstraction × implementation) → **Bridge**
- Control / delay / guard access to an object → **Proxy**
- Millions of similar objects, RAM pressure → **Flyweight**

---

## 4. The wrapper confusion (interview favorite!)

Adapter, Decorator, Proxy and Facade all "wrap" something — the difference is **intent**:

| Pattern | Interface vs wrapped object | Intent |
|---|---|---|
| **Adapter** | **Different** interface | Make incompatible interfaces fit |
| **Decorator** | **Same** interface | Add behavior/features |
| **Proxy** | **Same** interface | Control access (lazy, auth, cache) |
| **Facade** | **New, simpler** interface | Simplify a whole subsystem |
