# Pattern 1: Factory Method

> **TL;DR:** **Factory Method** moves object creation out of the client and into a dedicated **creator method**, so the client asks "give me a notifier" instead of writing `EmailNotifier()` itself. Subclasses (or a simple factory function) decide **which concrete class** to instantiate. Use it when the exact class to create is decided at runtime.

---

## 1. Problem it solves

**Without the pattern:** the client code decides the concrete class itself with `if/elif` chains.

```python
def send_notification(channel, message):
    if channel == "email":
        notifier = EmailNotifier()
    elif channel == "sms":
        notifier = SMSNotifier()
    elif channel == "push":
        notifier = PushNotifier()
    notifier.send(message)
```

Problems:

- Every **new channel** (e.g., WhatsApp) means editing this function → violates **Open/Closed Principle**.
- This `if/elif` creation logic gets **duplicated** everywhere a notifier is needed.
- The client is **tightly coupled** to every concrete notifier class.

**With the pattern:** creation is centralized in a factory; the client only knows the abstract `Notifier` interface.

---

## 2. Real-world analogy

A **logistics company**: you call `plan_delivery()`. The *road logistics* branch creates a **Truck**, the *sea logistics* branch creates a **Ship**. The head office (client) never says "build me a truck" — each branch's *factory method* decides the transport, and all transports share one interface: `deliver()`.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Product** (interface) | Common interface all products implement | `Notifier` |
| **Concrete Products** | Actual implementations | `EmailNotifier`, `SMSNotifier`, `PushNotifier` |
| **Creator** | Declares the factory method returning a Product | `NotificationCreator.create_notifier()` |
| **Concrete Creators** | Override the factory method to return a specific product | `EmailCreator`, `SMSCreator` |

```text
Client ──> Creator.create_notifier() ──returns──> Notifier (interface)
                   ▲                                  ▲
        ┌──────────┴──────────┐            ┌──────────┼──────────┐
   EmailCreator          SMSCreator   EmailNotifier SMSNotifier PushNotifier
```

## 4. Python implementation

### 4a. Classic (subclass-based) Factory Method

```python
from abc import ABC, abstractmethod


# ----- Product interface -----
class Notifier(ABC):
    @abstractmethod
    def send(self, message: str) -> None: ...


# ----- Concrete Products -----
class EmailNotifier(Notifier):
    def send(self, message: str) -> None:
        print(f"[EMAIL] {message}")


class SMSNotifier(Notifier):
    def send(self, message: str) -> None:
        print(f"[SMS] {message}")


class PushNotifier(Notifier):
    def send(self, message: str) -> None:
        print(f"[PUSH] {message}")


# ----- Creator -----
class NotificationCreator(ABC):
    @abstractmethod
    def create_notifier(self) -> Notifier:          # <-- THE factory method
        ...

    def notify(self, message: str) -> None:
        notifier = self.create_notifier()           # creator uses its own factory
        notifier.send(message)


# ----- Concrete Creators -----
class EmailCreator(NotificationCreator):
    def create_notifier(self) -> Notifier:
        return EmailNotifier()


class SMSCreator(NotificationCreator):
    def create_notifier(self) -> Notifier:
        return SMSNotifier()


# ----- Client -----
def client_code(creator: NotificationCreator) -> None:
    creator.notify("Your order has shipped!")       # client never names a concrete class


client_code(EmailCreator())
client_code(SMSCreator())
```

```text
[EMAIL] Your order has shipped!
[SMS] Your order has shipped!
```

### 4b. Pythonic shortcut — simple factory function

In Python you often don't need the full subclass hierarchy; a **factory function + registry** is idiomatic:

```python
NOTIFIER_REGISTRY = {
    "email": EmailNotifier,
    "sms": SMSNotifier,
    "push": PushNotifier,
}

def create_notifier(channel: str) -> Notifier:
    try:
        return NOTIFIER_REGISTRY[channel]()         # classes are objects — store & call them
    except KeyError:
        raise ValueError(f"Unknown channel: {channel}")


create_notifier("push").send("Hello!")
```

```text
[PUSH] Hello!
```

- Adding a new channel = **one new class + one registry entry**. No `if/elif` edits anywhere.
- Note: this simplified version is usually called **Simple Factory** — interviews may ask the difference (see §8).

---

## 5. When to use / when NOT to use

**Use when:**

- The **exact concrete class is known only at runtime** (config, user input, environment).
- You want to **add new product types without touching client code**.
- Creation involves logic you don't want duplicated (caching, pooling, validation).

**Avoid when:**

- There's only **one concrete class** and no variation is expected → just call the constructor.
- The subclass-per-product hierarchy adds more code than it saves (in Python, prefer the registry version).

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Decouples client from concrete classes | More classes/indirection than direct instantiation |
| Open/Closed: add products without editing clients | Classic form needs a creator subclass per product |
| Centralizes creation logic (single place to change) | Overkill for simple, stable object creation |

---

## 7. Factory Method vs. similar patterns

| Compared with | Difference |
|---|---|
| **Simple Factory** | Simple Factory = one function/`if-else` or registry choosing the class. Factory Method = creation deferred to **subclasses** via an overridable method. |
| **Abstract Factory** | Factory Method creates **one product**; Abstract Factory creates a **family of related products** (and is often implemented *using* factory methods). |
| **Builder** | Factory returns the product in **one call**; Builder constructs it **step by step**. |

---

## 8. Quick recap

- One **overridable method** whose job is to create and return a Product.
- Client codes against the **Product interface**, never a concrete class.
- New product = new subclass (or registry entry), **zero client changes**.
- Pythonic version: **factory function + dict registry**.

---

## 9. Interview Q&A

**Q1. What problem does Factory Method solve?**
It removes direct instantiation (`ConcreteClass()`) and type-checking `if/elif` chains from client code, decoupling clients from concrete classes and keeping creation logic in one place (supports Open/Closed Principle).

**Q2. Factory Method vs Simple Factory?**
Simple Factory is one static function/registry that picks a class — it's a coding idiom, not a GoF pattern. Factory Method is a GoF pattern where a **base creator defines an abstract creation method** and subclasses override it to pick the product.

**Q3. Factory Method vs Abstract Factory?**
Factory Method = one method creating **one product type**. Abstract Factory = an object with **multiple factory methods** creating a **consistent family** of products.

**Q4. How is Factory Method naturally simpler in Python?**
Classes are first-class objects — you can store them in a dict and call them (`REGISTRY[key]()`), and duck typing often removes the need for a formal ABC.

**Q5. Which SOLID principles does it support?**
**OCP** (add products without modifying clients) and **DIP** (clients depend on the Product abstraction, not concretions).
