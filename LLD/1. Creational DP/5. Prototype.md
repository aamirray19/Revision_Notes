# Pattern 5: Prototype

> **TL;DR:** **Prototype** creates new objects by **cloning an existing, pre-configured object** instead of constructing from scratch. Use it when object creation is **expensive** (DB/network/heavy computation) or when you need many variations of a base configuration. In Python the `copy` module (`copy.copy` / `copy.deepcopy`) does the heavy lifting.

---

## 1. Problem it solves

**Without the pattern:** rebuilding an expensive object every time.

```python
enemy1 = Enemy("Orc")    # loads 3D model, textures, AI config... takes 2s
enemy2 = Enemy("Orc")    # loads EVERYTHING again... another 2s
enemy3 = Enemy("Orc")    # and again...
```

Also, copying manually is fragile:

```python
clone = Enemy("Orc")
clone.health = original.health      # must remember EVERY field
clone.weapons = original.weapons    # BUG: both now share the same list!
```

Problems:

- **Expensive initialization repeated** for each identical object.
- Manual field-by-field copying is **error-prone** (missed fields, shared mutable state).
- Sometimes you only hold a reference to an **interface** and don't even know the concrete class to re-construct.

**With the pattern:** build/configure **one prototype**, then `clone()` it cheaply and tweak the copies.

---

## 2. Real-world analogy

**Cell division (mitosis)** — a cell doesn't build a new cell from raw atoms; it **clones itself**, and the copy can then differentiate. Or simpler: a **photocopier** — design the document once, photocopy it for everyone, and each person can annotate their own copy.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Prototype** (interface) | Declares `clone()` | `clone()` method |
| **Concrete Prototype** | Implements cloning of itself | `Enemy` |
| **Prototype Registry** *(optional)* | Stores ready-made prototypes by name | `EnemySpawner` |
| **Client** | Gets new objects by cloning, never by `new`/constructor | game code |

```text
Client ──clone()──> Prototype (pre-configured) ──returns──> independent copy
            (optionally via a Registry: "orc" → orc prototype)
```

## 4. Python implementation

### 4a. Cloning with `copy.deepcopy`

```python
import copy
import time


class Enemy:
    def __init__(self, kind: str):
        print(f"Loading assets for {kind}... (expensive)")
        time.sleep(1)                      # simulate heavy load (model, AI, textures)
        self.kind = kind
        self.health = 100
        self.weapons = ["claws"]

    def clone(self) -> "Enemy":
        return copy.deepcopy(self)         # copies EVERY field, including nested ones

    def __str__(self) -> str:
        return f"{self.kind}(health={self.health}, weapons={self.weapons})"


# Build ONE expensive prototype...
orc_prototype = Enemy("Orc")

# ...then clone cheaply and customize each copy
orc1 = orc_prototype.clone()
orc2 = orc_prototype.clone()
orc2.health = 150
orc2.weapons.append("axe")

print(orc1)
print(orc2)
print(orc1.weapons is orc2.weapons)        # deepcopy => independent nested objects
```

```text
Loading assets for Orc... (expensive)
Orc(health=100, weapons=['claws'])
Orc(health=150, weapons=['claws', 'axe'])
False
```

- The 1-second load happened **once**; clones are near-instant.
- `deepcopy` means `orc2.weapons.append()` does **not** affect `orc1`.

### 4b. Shallow vs deep copy — the crucial distinction

```python
import copy

original = Enemy.__new__(Enemy)            # (skipping load for demo)
original.kind, original.health, original.weapons = "Orc", 100, ["claws"]

shallow = copy.copy(original)              # copies object, SHARES nested objects
deep = copy.deepcopy(original)             # copies object AND nested objects

shallow.weapons.append("club")
print(original.weapons)                    # ['claws', 'club']  <-- affected!
deep.weapons.append("axe")
print(original.weapons)                    # ['claws', 'club']  <-- NOT affected by deep
```

```text
['claws', 'club']
['claws', 'club']
```

| | `copy.copy` (shallow) | `copy.deepcopy` (deep) |
|---|---|---|
| Top-level object | new | new |
| Nested mutable objects (lists, dicts) | **shared** | copied recursively |
| Speed | fast | slower |
| Customize via | `__copy__` | `__deepcopy__` |

### 4c. Prototype Registry

```python
class EnemySpawner:
    """Registry of ready-made prototypes — clients clone by name."""

    def __init__(self) -> None:
        self._prototypes: dict[str, Enemy] = {}

    def register(self, name: str, prototype: Enemy) -> None:
        self._prototypes[name] = prototype

    def spawn(self, name: str) -> Enemy:
        return self._prototypes[name].clone()


spawner = EnemySpawner()
spawner.register("orc", orc_prototype)

wave = [spawner.spawn("orc") for _ in range(3)]   # 3 orcs, zero loading cost
print(len(wave), "orcs spawned")
```

```text
3 orcs spawned
```

## 5. When to use / when NOT to use

**Use when:**

- Object creation is **expensive** (network/DB/disk/compute) and copies are acceptable.
- You need many objects that are **variations of a base configuration** (templates: documents, game entities, test fixtures).
- Code holds objects via an interface and **can't know the concrete class** to construct — but can ask the object to clone itself.

**Avoid when:**

- Objects are **cheap to construct** — just call the constructor.
- Objects hold **non-copyable resources** (open sockets, file handles, locks) — cloning them is ambiguous or wrong.
- Deep object graphs with **circular references** make deepcopy slow/tricky (though `deepcopy` does handle cycles via its memo dict).

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Avoids repeating expensive initialization | Deep-copying complex graphs can be slow/subtle |
| Clone without knowing the concrete class | Objects with external resources clone badly |
| Add/remove prototypes at **runtime** (registry) | Shallow-vs-deep mistakes cause shared-state bugs |
| Reduces subclass count (configure + clone instead of subclassing) | `clone()` semantics must be kept up to date as fields change |

---

## 7. Prototype vs. similar patterns

| Compared with | Difference |
|---|---|
| **Factory Method** | Factory **constructs fresh** objects via constructors; Prototype **copies** a configured instance. Factories can even be implemented by cloning prototypes internally. |
| **Builder** | Builder assembles step-by-step from nothing; Prototype starts from a **finished example** and duplicates it. |
| **Singleton** | Opposite intents: Singleton = exactly **one** instance; Prototype = cheap **many** instances. |
| **Memento** | Memento snapshots an object's state to **restore it later**; Prototype copies to make a **new independent object**. |

---

## 8. Quick recap

- Clone a **pre-configured prototype** instead of re-running expensive construction.
- Python: `copy.copy` = shallow (nested objects **shared**), `copy.deepcopy` = fully independent.
- Customize cloning with `__copy__` / `__deepcopy__`.
- Add a **registry** to spawn clones by name.
- Watch out: resources (sockets/files/locks) don't clone well.

---

## 9. Interview Q&A

**Q1. What is the Prototype pattern and when is it useful?**
Creating objects by cloning an existing instance rather than constructing from scratch — useful when construction is expensive or when you need many variants of a pre-configured object.

**Q2. Shallow copy vs deep copy?**
Shallow copy (`copy.copy`) duplicates the top-level object but **shares** nested mutable objects — mutating a nested list in the copy affects the original. Deep copy (`copy.deepcopy`) recursively copies everything, producing a fully independent object.

**Q3. How does Python support Prototype natively?**
Through the `copy` module, and the `__copy__`/`__deepcopy__` hooks that let a class customize exactly how it clones (e.g., re-open a connection instead of copying it).

**Q4. What is a prototype registry?**
A store of named, ready-made prototypes (`"orc" → configured Enemy`); clients request clones by name, decoupling them from both concrete classes and configuration details.

**Q5. What are the pitfalls of cloning?**
Accidentally shared mutable state (shallow copy), objects owning external resources (file handles, sockets, DB connections), and `deepcopy` cost on large object graphs. `deepcopy` handles circular references via its memo dictionary, but it's still expensive.
