# Pattern 2: Abstract Factory

> **TL;DR:** **Abstract Factory** creates **families of related objects** (e.g., Button + Checkbox for the *same* OS theme) without naming concrete classes. The client picks a factory once; every product it creates is guaranteed to be **compatible** with the others. Think "factory of factories" / "one factory per product family".

---

## 1. Problem it solves

**Without the pattern:** a cross-platform UI app creates widgets directly — and nothing stops it from mixing families:

```python
if os_name == "mac":
    button = MacButton()
    checkbox = WinCheckbox()     # BUG: mixed Mac button with Windows checkbox!
```

Problems:

- **Nothing enforces consistency** — you can accidentally mix products from different families.
- `if os_name == ...` checks get **duplicated** at every creation site.
- Adding a new family (Linux) means hunting down **every** such `if`.

**With the pattern:** choose the family **once** (pick the factory), then every product automatically matches.

---

## 2. Real-world analogy

A **furniture showroom**: you pick a style — *Modern* or *Victorian*. Once chosen, the showroom gives you a matching **chair, sofa, and table** of that style. You never pick individual items from different styles; the *style factory* guarantees everything matches.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Abstract Products** | Interfaces, one per product kind | `Button`, `Checkbox` |
| **Concrete Products** | Implementations, grouped by family | `MacButton`+`MacCheckbox`, `WinButton`+`WinCheckbox` |
| **Abstract Factory** | Interface with one create-method **per product kind** | `GUIFactory` |
| **Concrete Factories** | One per family; create matching products | `MacFactory`, `WinFactory` |

```text
                 GUIFactory (abstract)
                 create_button() / create_checkbox()
                   ▲                    ▲
             MacFactory             WinFactory
             │ MacButton            │ WinButton
             └ MacCheckbox          └ WinCheckbox
            (family: Mac)          (family: Windows)
```

- Rows = product kinds (Button, Checkbox). Columns = families (Mac, Win). Each concrete factory builds **one whole column**.

---

## 4. Python implementation

```python
from abc import ABC, abstractmethod


# ----- Abstract Products -----
class Button(ABC):
    @abstractmethod
    def render(self) -> str: ...


class Checkbox(ABC):
    @abstractmethod
    def render(self) -> str: ...


# ----- Concrete Products: Mac family -----
class MacButton(Button):
    def render(self) -> str:
        return "Mac-style button"


class MacCheckbox(Checkbox):
    def render(self) -> str:
        return "Mac-style checkbox"


# ----- Concrete Products: Windows family -----
class WinButton(Button):
    def render(self) -> str:
        return "Windows-style button"


class WinCheckbox(Checkbox):
    def render(self) -> str:
        return "Windows-style checkbox"


# ----- Abstract Factory -----
class GUIFactory(ABC):
    @abstractmethod
    def create_button(self) -> Button: ...

    @abstractmethod
    def create_checkbox(self) -> Checkbox: ...


# ----- Concrete Factories (one per family) -----
class MacFactory(GUIFactory):
    def create_button(self) -> Button:
        return MacButton()

    def create_checkbox(self) -> Checkbox:
        return MacCheckbox()


class WinFactory(GUIFactory):
    def create_button(self) -> Button:
        return WinButton()

    def create_checkbox(self) -> Checkbox:
        return WinCheckbox()


# ----- Client -----
class Application:
    def __init__(self, factory: GUIFactory):     # family chosen ONCE, here
        self.button = factory.create_button()
        self.checkbox = factory.create_checkbox()

    def render(self) -> None:
        print(self.button.render())
        print(self.checkbox.render())


def get_factory(os_name: str) -> GUIFactory:     # the ONLY place that knows families
    factories = {"mac": MacFactory, "windows": WinFactory}
    return factories[os_name]()


app = Application(get_factory("mac"))
app.render()

app = Application(get_factory("windows"))
app.render()
```

```text
Mac-style button
Mac-style checkbox
Windows-style button
Windows-style checkbox
```

- `Application` never names `MacButton` or `WinCheckbox` — it can't accidentally mix families.
- Adding a **Linux family** = new products + one `LinuxFactory` + one registry entry. `Application` is untouched.

---

## 5. When to use / when NOT to use

**Use when:**

- Your code works with **multiple families of related products** that must be used **together consistently** (themes, OS widgets, DB driver + cursor + connection, cloud provider SDKs).
- You want to be able to **swap an entire family at once** (e.g., testing with a `FakeFactory`).

**Avoid when:**

- There's only **one product kind** → Factory Method is enough.
- Families change rarely, but **product kinds change often** — adding a new kind (e.g., `Slider`) forces editing the abstract factory **and every** concrete factory. This is the pattern's biggest weakness.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Guarantees products in use are **compatible** (same family) | Many classes/interfaces — heavyweight |
| Client decoupled from all concrete classes | Adding a new **product kind** requires changing every factory |
| Swap whole family via one constructor argument | Can be overkill when families are unlikely to grow |
| Easy to inject fakes/mocks for testing | |

---

## 7. Abstract Factory vs. similar patterns

| Compared with | Difference |
|---|---|
| **Factory Method** | Factory Method = **one** creation method for one product. Abstract Factory = an **object** bundling several factory methods that must produce a **matching family**. |
| **Builder** | Builder builds **one complex object** in steps; Abstract Factory immediately returns **many simple related objects**. |
| **Facade** | Facade simplifies *using* a subsystem; Abstract Factory standardizes *creating* object families. |

**Memory hook:** easy axis to remember — **new family: easy** (one new factory), **new product kind: painful** (edit all factories).

---

## 8. Quick recap

- One abstract factory interface, **one create-method per product kind**.
- One concrete factory **per family**; the family is chosen once, up front.
- Compatibility between products is **guaranteed by construction**.
- New family = easy. New product kind = modify every factory.

---

## 9. Interview Q&A

**Q1. What is the main guarantee Abstract Factory provides that Factory Method doesn't?**
**Family consistency** — all products created through one concrete factory are designed to work together; the client cannot mix incompatible variants.

**Q2. What's the biggest drawback of Abstract Factory?**
Adding a new **product kind** (a new abstract product, e.g., `Slider`) requires modifying the abstract factory interface and **every** concrete factory — it violates OCP along that axis.

**Q3. Give a real-world software example.**
Database access layers: a `PostgresFactory` vs `SQLiteFactory` each producing a matching `Connection`, `Cursor`, and `Transaction`; or cross-platform GUI toolkits; or test code injecting a `FakeServiceFactory`.

**Q4. How does Abstract Factory relate to Factory Method?**
Abstract Factory is usually **implemented using** Factory Methods — each `create_x()` on the factory is itself a factory method.

**Q5. How would you choose between Factory Method and Abstract Factory?**
Count the products: one varying product → Factory Method; multiple related products that must stay consistent → Abstract Factory.
