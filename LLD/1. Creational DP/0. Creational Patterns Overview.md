# Creational Design Patterns — Overview

> **TL;DR:** Creational patterns deal with **object creation**. They hide *how* objects are created so that the rest of the code depends only on *what* the objects can do. Use them when `__init__` + direct instantiation (`obj = MyClass()`) starts causing tight coupling, duplication, or complex setup logic.

---

## 1. Why a whole category for "creating objects"?

Directly writing `obj = ConcreteClass()` everywhere has problems:

- **Tight coupling** — the caller must know the exact concrete class.
- **Scattered logic** — if creation needs setup (config, validation, defaults), that logic gets duplicated.
- **Hard to change** — swapping one implementation for another means editing every call site.

Creational patterns centralize and abstract creation so the creating code and the using code are **decoupled**.

---

## 2. The 5 Creational Patterns at a Glance

| # | Pattern | One-line intent | Classic example |
|---|---------|-----------------|-----------------|
| 1 | **Factory Method** | Let subclasses decide **which one class** to instantiate | `NotificationFactory` returning Email/SMS/Push notifier |
| 2 | **Abstract Factory** | Create **families of related objects** without naming concrete classes | UI kit: `MacFactory` / `WinFactory` creating matching Button + Checkbox |
| 3 | **Builder** | Construct a **complex object step by step**, separating construction from representation | Building a `Pizza`/`HttpRequest` with many optional parts |
| 4 | **Singleton** | Ensure a class has **only one instance**, globally accessible | Logger, config manager, DB connection pool |
| 5 | **Prototype** | Create new objects by **cloning an existing one** instead of building from scratch | Copying a pre-configured game character / document template |

---

## 3. How to pick the right one (decision cheat-sheet)

- Need **one product**, but the exact type varies → **Factory Method**
- Need **several related products** that must match each other → **Abstract Factory**
- Object has **many optional parts / long constructor** → **Builder**
- Need exactly **one shared instance** → **Singleton**
- Creating from scratch is **expensive**; a copy of an existing object is enough → **Prototype**

---

## 4. Quick memory hooks

- **Factory Method** = "one factory, one product type"
- **Abstract Factory** = "factory of factories — whole product family"
- **Builder** = "step-by-step assembly line"
- **Singleton** = "there can be only one"
- **Prototype** = "photocopy machine"
