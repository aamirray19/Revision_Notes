# Pattern 3: Builder

> **TL;DR:** **Builder** constructs a **complex object step by step** instead of through one giant constructor call. The same construction process can produce different representations. Use it when a class has **many optional parameters** or needs **multi-step assembly**. In Python, method chaining (`.add_x().add_y().build()`) is the common form.

---

## 1. Problem it solves

**Without the pattern:** the "telescoping constructor" — a constructor with a long tail of optional parameters.

```python
class Pizza:
    def __init__(self, size, cheese=False, pepperoni=False, mushrooms=False,
                 onions=False, olives=False, extra_sauce=False, stuffed_crust=False):
        ...

# Which bool is which? Easy to get wrong, impossible to read:
pizza = Pizza("large", True, False, True, False, True, False, True)
```

Problems:

- **Unreadable call sites** — a wall of positional booleans.
- All combinations crammed into **one constructor**; validation logic becomes a mess.
- Object can exist in a **half-initialized** state if construction is split across setters.

**With the pattern:** each step is a **named, readable** method; `build()` returns the finished, validated object.

---

## 2. Real-world analogy

Ordering at **Subway**: the sandwich is built step by step — bread → size → fillings → toppings → sauces. Same *process* every time, but the *result* differs per order. The staff member (builder) assembles it; you receive the finished sandwich only at the end.

---

## 3. Structure

| Role | Responsibility | In our example |
|---|---|---|
| **Product** | The complex object being built | `Pizza` |
| **Builder** | Declares the construction steps | `PizzaBuilder` |
| **Concrete Builder** | Implements steps, tracks the work-in-progress, returns result via `build()` | `PizzaBuilder` (Python usually skips the abstract layer) |
| **Director** *(optional)* | Knows step **recipes** for common configurations | `PizzaDirector` |

```text
Client ──> Director ──uses──> Builder ──builds──> Product
   (or client drives the builder directly)
```

---

## 4. Python implementation

### 4a. Fluent builder (method chaining)

```python
class Pizza:
    def __init__(self, size: str, toppings: list[str], stuffed_crust: bool):
        self.size = size
        self.toppings = toppings
        self.stuffed_crust = stuffed_crust

    def __str__(self) -> str:
        crust = "stuffed crust" if self.stuffed_crust else "regular crust"
        return f"{self.size} pizza, {crust}, toppings: {', '.join(self.toppings) or 'none'}"


class PizzaBuilder:
    def __init__(self) -> None:
        self._size = "medium"
        self._toppings: list[str] = []
        self._stuffed_crust = False

    def size(self, size: str) -> "PizzaBuilder":
        self._size = size
        return self                      # return self => enables chaining

    def add_topping(self, topping: str) -> "PizzaBuilder":
        self._toppings.append(topping)
        return self

    def stuffed_crust(self) -> "PizzaBuilder":
        self._stuffed_crust = True
        return self

    def build(self) -> Pizza:
        if self._stuffed_crust and self._size == "small":
            raise ValueError("Stuffed crust needs medium or large")   # central validation
        return Pizza(self._size, self._toppings, self._stuffed_crust)


pizza = (
    PizzaBuilder()
    .size("large")
    .add_topping("cheese")
    .add_topping("mushrooms")
    .stuffed_crust()
    .build()
)
print(pizza)
```

```text
large pizza, stuffed crust, toppings: cheese, mushrooms
```

- Every step is **named** — no mystery booleans.
- Validation happens **once**, in `build()`, so an invalid `Pizza` can never exist.

### 4b. Optional Director — reusable recipes

```python
class PizzaDirector:
    """Knows standard recipes so clients don't repeat step sequences."""

    @staticmethod
    def margherita() -> Pizza:
        return PizzaBuilder().size("medium").add_topping("cheese").add_topping("basil").build()

    @staticmethod
    def meat_lovers() -> Pizza:
        return (PizzaBuilder().size("large")
                .add_topping("pepperoni").add_topping("sausage").add_topping("bacon")
                .stuffed_crust().build())


print(PizzaDirector.margherita())
print(PizzaDirector.meat_lovers())
```

```text
medium pizza, regular crust, toppings: cheese, basil
large pizza, stuffed crust, toppings: pepperoni, sausage, bacon
```

### 4c. Pythonic alternatives to know

```python
# Keyword arguments + defaults already solve mild cases:
pizza = Pizza(size="large", toppings=["cheese"], stuffed_crust=True)

# dataclasses reduce boilerplate for data-heavy products:
from dataclasses import dataclass, field

@dataclass
class PizzaDC:
    size: str = "medium"
    toppings: list[str] = field(default_factory=list)
    stuffed_crust: bool = False
```

Reach for a real Builder only when there is **multi-step logic, validation across fields, or incremental assembly** — not just many parameters.

---

## 5. When to use / when NOT to use

**Use when:**

- Constructor would need **many optional parameters** with inter-dependent validation.
- The object must be assembled **incrementally** (e.g., building an SQL query, an HTTP request, a report/document).
- The same build **process** should produce **different representations** (e.g., same report steps → HTML vs PDF builder).

**Avoid when:**

- Keyword arguments with defaults (or a `dataclass`) are enough — in Python this covers most simple cases.
- The object is simple and immutable — a plain constructor is clearer.

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Readable, self-documenting construction | Extra builder class per product |
| Object is complete & validated before use | More code than kwargs for simple cases |
| Same process → different representations | Mutable builder state can be misused if shared |
| Isolates complex assembly code | |

---

## 7. Builder vs. similar patterns

| Compared with | Difference |
|---|---|
| **Factory Method** | Factory returns the product in **one shot**; Builder assembles it in **multiple steps** and returns it at the end. |
| **Abstract Factory** | Abstract Factory creates **families of objects**; Builder focuses on **one complex object**. |
| **Prototype** | Prototype copies an existing configured object; Builder constructs a new one from scratch, step by step. |

**Real library examples:** `requests.Session` configuration, SQLAlchemy's query chaining (`query.filter(...).order_by(...)`), `pandas` method chains — all builder-flavored fluent APIs.

---

## 8. Quick recap

- Step-by-step construction; product delivered by **`build()`**.
- Methods **return `self`** → fluent chaining.
- Central **validation in `build()`** prevents half-made objects.
- Director = optional keeper of **standard recipes**.
- In Python, try **kwargs/dataclass first**; use Builder for genuinely multi-step construction.

---

## 9. Interview Q&A

**Q1. What problem does Builder solve?**
The telescoping-constructor problem: complex objects with many optional/interdependent parts become unreadable and error-prone to construct in one call. Builder gives named steps and a single validated completion point.

**Q2. What is the Director, and is it mandatory?**
The Director encapsulates **standard build sequences** (recipes) so clients don't repeat them. It's optional — clients can drive the builder directly.

**Q3. Builder vs Factory — one line?**
Factory is about **which** object to create; Builder is about **how** to assemble one complex object step by step.

**Q4. Why do builder methods return `self`?**
To enable **method chaining** (fluent interface): `builder.a().b().build()`. Each call mutates the work-in-progress and hands back the same builder.

**Q5. When would you NOT use Builder in Python?**
When keyword arguments with defaults or a `dataclass` suffice — Python's kwargs already eliminate the positional-boolean problem that forces Builder in Java/C++.
