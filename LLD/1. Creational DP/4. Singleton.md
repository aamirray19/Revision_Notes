# Pattern 4: Singleton

> **TL;DR:** **Singleton** ensures a class has **exactly one instance** and provides a global access point to it. In Python, implement it via `__new__`, a decorator, or a metaclass — or idiomatically, just use a **module-level instance**. Classic uses: logger, config, connection pool. Also the most **criticized** pattern (global state, hard to test).

---

## 1. Problem it solves

Some objects must be **shared and unique**: an app-wide config, a logger, a DB connection pool. Creating many of them wastes resources or causes inconsistent state.

**Without the pattern:**

```python
config_a = AppConfig()   # loads config file
config_b = AppConfig()   # loads it AGAIN — wasteful
config_a.debug = True    # config_b doesn't see this — two sources of truth!
```

Problems:

- **Multiple "sources of truth"** drift out of sync.
- Expensive setup (file/DB/network) repeated needlessly.
- No controlled global access point.

**With the pattern:** every `AppConfig()` call returns the **same object**.

---

## 2. Real-world analogy

A country's **government**: whatever office you walk into, there is only **one** central government. You can't instantiate a second one; every reference to "the government" points to the same entity.

---

## 3. Structure

| Role | Responsibility |
|---|---|
| **Singleton class** | Hides/overrides normal construction; stores the sole instance; returns it on every access |
| **Client** | Calls the usual constructor or `get_instance()` — always receives the same object |

```text
Client1 ──┐
Client2 ──┼──> AppConfig() ──> ┌───────────────┐
Client3 ──┘    (every call)    │ SAME instance │
                               └───────────────┘
```

## 4. Python implementations

### 4a. Via `__new__` (most common interview answer)

```python
class AppConfig:
    _instance = None

    def __new__(cls):
        if cls._instance is None:                      # first call → create
            cls._instance = super().__new__(cls)
            cls._instance.debug = False                # init ONCE here
            print("Loading configuration...")
        return cls._instance                           # later calls → same object


a = AppConfig()
b = AppConfig()
a.debug = True

print(a is b)        # identity check — the real test of a singleton
print(b.debug)       # change via `a` is visible via `b`
```

```text
Loading configuration...
True
True
```

> ⚠️ Gotcha: if you also define `__init__`, Python runs it on **every** `AppConfig()` call (even when `__new__` returns the cached instance) — it would re-reset your state. That's why initialization is done inside `__new__` above, or guarded with a flag.

### 4b. Via decorator (reusable)

```python
def singleton(cls):
    instances = {}
    def get_instance(*args, **kwargs):
        if cls not in instances:
            instances[cls] = cls(*args, **kwargs)
        return instances[cls]
    return get_instance


@singleton
class Logger:
    def __init__(self):
        print("Creating logger")


log1 = Logger()
log2 = Logger()
print(log1 is log2)
```

```text
Creating logger
True
```

### 4c. Via metaclass (cleanest for inheritance)

```python
class SingletonMeta(type):
    _instances = {}

    def __call__(cls, *args, **kwargs):               # intercepts Class() calls
        if cls not in cls._instances:
            cls._instances[cls] = super().__call__(*args, **kwargs)
        return cls._instances[cls]


class Database(metaclass=SingletonMeta):
    def __init__(self):
        print("Connecting to DB")


d1 = Database()
d2 = Database()
print(d1 is d2)
```

```text
Connecting to DB
True
```

### 4d. The *Pythonic* way — a module

Python modules are imported **once** and cached in `sys.modules` — a module **is** a natural singleton:

```python
# config.py
debug = False
db_url = "localhost:5432"

# anywhere else:
# import config
# config.debug = True      # every importer sees the same module object
```

For most Python code, this (or a module-level instance like `logging.getLogger()`) is preferred over a Singleton class.

### Thread-safety note

In multithreaded code, two threads may pass the `is None` check simultaneously. Guard creation with a lock:

```python
import threading

class ThreadSafeSingleton:
    _instance = None
    _lock = threading.Lock()

    def __new__(cls):
        if cls._instance is None:              # fast path, no lock
            with cls._lock:
                if cls._instance is None:      # double-checked locking
                    cls._instance = super().__new__(cls)
        return cls._instance
```

## 5. When to use / when NOT to use

**Use when:**

- Exactly **one shared instance** must coordinate state (config, logger, connection/thread pool, cache).
- The instance is **expensive** to create and safe to share.

**Avoid when:**

- You just need shared *data* → a module works.
- The object holds mutable state used by many components → it becomes **hidden global state**, making tests order-dependent and dependencies invisible. Prefer **dependency injection** (create once at startup, pass it in).

---

## 6. Pros & Cons

| Pros | Cons |
|---|---|
| Guaranteed single instance | **Global mutable state** — hidden coupling |
| Lazy initialization (created on first use) | Hard to unit test (state leaks between tests) |
| Single access point, controlled lifecycle | Hides dependencies (not visible in signatures) |
| Saves resources for expensive objects | Needs care for thread safety |
| | Often called an **anti-pattern** when overused |

---

## 7. Singleton vs. similar concepts

| Compared with | Difference |
|---|---|
| **Module-level instance** | Same effect, far simpler — idiomatic Python; but a class gives lazy init and inheritance control. |
| **Borg / Monostate** | Borg allows many instances that **share one `__dict__`** (shared state, different identities). Singleton shares **identity** (`is` returns True). |
| **Dependency Injection** | DI creates one instance at the composition root and **passes it explicitly** — same "one instance" goal without global access. Usually the better design. |
| **Static/class methods only** | No instance at all; but no lazy init, no interface to swap/mock. |

---

## 8. Quick recap

- Enforce one instance: `__new__` + cached `_instance`, a decorator, or a metaclass.
- Verify with **`a is b`** (identity, not equality).
- `__init__` re-runs on every call — guard it.
- Thread safety → **double-checked locking**.
- Pythonic alternative: **just use a module**; design-wise, prefer **DI** for testability.

---

## 9. Interview Q&A

**Q1. How do you implement a Singleton in Python?**
Override `__new__` to cache and return a single instance; or use a decorator holding an `instances` dict; or a metaclass overriding `__call__`; or — most Pythonic — a module-level instance, since modules are imported once.

**Q2. Why is Singleton often called an anti-pattern?**
It introduces **global mutable state**: dependencies become invisible, components get tightly coupled to it, and unit tests interfere with each other through leftover state. Dependency injection usually achieves the same goal more cleanly.

**Q3. What's the `__init__` gotcha in the `__new__`-based Singleton?**
`Class()` always calls `__init__` on the object returned by `__new__` — so a second `AppConfig()` call would **re-initialize** the shared instance. Fix: initialize inside `__new__` or use an `_initialized` flag.

**Q4. How do you make a Singleton thread-safe?**
Protect instance creation with a `threading.Lock`, typically with **double-checked locking** (check → lock → check again → create).

**Q5. Singleton vs Borg pattern?**
Singleton: one object, shared identity (`a is b` → True). Borg: many objects sharing one `__dict__` — same state, different identities. Borg plays nicer with inheritance.

**Q6. How would you unit-test code that uses a Singleton?**
With difficulty — you must reset `_instance` between tests or monkeypatch it. Better: have code accept the dependency as a parameter (DI) so tests pass a fresh fake.
