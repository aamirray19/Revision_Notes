# Topic 5: Inheritance

> **TL;DR:** **Inheritance** lets a **child class** reuse, extend and override the attributes and methods of a **parent class**. Python finds inherited members by walking the **MRO** at lookup time (nothing is copied), and `super()` delegates to the *next* class in that MRO. Use it for genuine **IS-A** relationships; prefer **composition** for HAS-A.

---

## 1. What Is Inheritance?

**Inheritance** lets one class acquire the attributes and methods of another, so you can reuse existing code and extend or modify it without rewriting it.

- **Parent class** = base class = superclass (the one inherited from).
- **Child class** = derived class = subclass (the one that inherits).

### Syntax

```python
class Parent:
    pass

class Child(Parent):
    pass
```

- `Child` inherits the accessible attributes and methods of `Parent`.
- `Child` can **add** new attributes and methods.
- `Child` can **override** inherited methods.

### Basic example

```python
class Animal:
    def eat(self):
        print("Animal is eating")

class Dog(Animal):
    def bark(self):
        print("Dog is barking")

dog = Dog()
dog.eat()    # Animal is eating
dog.bark()   # Dog is barking
```

- `Dog` defines only `bark()`, yet `dog.eat()` works.
- On `dog.eat()`, Python looks in `Dog`, doesn't find `eat`, continues to the parent `Animal`, finds it and runs it.

> **Key point:** inheritance does **not** copy parent methods into the child. Python finds them at lookup time through the class hierarchy and the **Method Resolution Order (MRO)**. See Section 5.

---

## 2. Why Do We Need Inheritance?

**Problem:** without inheritance, shared behavior is duplicated.

```python
class Dog:
    def eat(self):
        print("Eating")
    def sleep(self):
        print("Sleeping")
    def bark(self):
        print("Barking")

class Cat:
    def eat(self):
        print("Eating")
    def sleep(self):
        print("Sleeping")
    def meow(self):
        print("Meowing")
```

- Same `eat()` / `sleep()` written twice → **duplication**, more maintenance, risk of inconsistent behavior, hard to extend shared behavior.

**Fix:** move the shared behavior into a base class.

```python
class Animal:
    def eat(self):
        print("Eating")
    def sleep(self):
        print("Sleeping")

class Dog(Animal):
    def bark(self):
        print("Barking")

class Cat(Animal):
    def meow(self):
        print("Meowing")
```

- `eat()` and `sleep()` are now defined **once** and reused by both `Dog` and `Cat`.

### Advantages

| Advantage | Explanation |
|---|---|
| Code reusability | Reuse existing functionality without rewriting it |
| Reduced duplication | Common functionality lives in one base class |
| Extensibility | Child classes can add new functionality |
| Method overriding | Child classes can customize inherited behavior |
| Polymorphism | Different subclasses can be used through a common interface |
| Maintainability | Shared behavior is maintained centrally |
| Logical organization | Related classes form meaningful hierarchies |

> **Key point:** don't inherit *only* to reduce duplication. The child must be a meaningful **specialization** of the parent.

---

## 3. IS-A vs HAS-A (Inheritance vs Composition)

Inheritance models an **IS-A** relationship: a Dog *is an* Animal, a Car *is a* Vehicle, a Manager *is an* Employee.

```python
class Vehicle:
    def start(self):
        print("Vehicle started")

class Car(Vehicle):     # Car IS-A Vehicle
    pass

class Bike(Vehicle):    # Bike IS-A Vehicle
    pass
```

**HAS-A** relationships (a Car *has an* Engine, a Library *has* Books, a Computer *has a* Processor) are usually better modeled with **composition**: one object holds a reference to another.

```python
class Engine:
    def start(self):
        print("Engine started")

class Car:
    def __init__(self):
        self.engine = Engine()   # Car HAS-A Engine

    def start(self):
        self.engine.start()      # delegate to the contained object

car = Car()
car.start()   # Engine started
```

| Inheritance | Composition |
|---|---|
| Represents **IS-A** | Represents **HAS-A** |
| Uses subclassing | Uses object references |
| Reuses behavior through a class hierarchy | Reuses behavior through contained objects |
| Tighter coupling | Often more flexible |
| Can override inherited methods | Can replace or delegate to contained components |

> **Rule of thumb:** use inheritance when the child can legitimately be treated as an instance of the parent. Use composition when one object uses or contains another.

## 4. Types of Inheritance in Python

| Type | Shape | Example |
|---|---|---|
| **Single** | One child, one parent | `Dog(Animal)` |
| **Multilevel** | Chain of parents | `Dog(Mammal)`, `Mammal(Animal)` |
| **Hierarchical** | Many children, one parent | `Dog(Animal)`, `Cat(Animal)` |
| **Multiple** | One child, many parents | `Child(Father, Mother)` |
| **Hybrid** | Mix of the above (e.g. diamond) | `D(B, C)`, `B(A)`, `C(A)` |

### 4.1 Single Inheritance

A child inherits from **one** parent.

```text
Animal
  ^
  |
 Dog
```

```python
class Animal:
    def eat(self):
        print("Eating")

class Dog(Animal):
    def bark(self):
        print("Barking")

dog = Dog()
dog.eat()    # Eating
dog.bark()   # Barking
```

### 4.2 Multilevel Inheritance

A class inherits from a class that itself inherits from another class.

```python
class Animal:
    def eat(self):
        print("Eating")

class Mammal(Animal):
    def walk(self):
        print("Walking")

class Dog(Mammal):
    def bark(self):
        print("Barking")

dog = Dog()
dog.eat()    # Eating
dog.walk()   # Walking
dog.bark()   # Barking
```

- `Dog` gets methods from both `Mammal` and `Animal`.
- Chain: `Dog -> Mammal -> Animal -> object`.

### 4.3 Hierarchical Inheritance

Multiple children inherit from the **same** parent.

```python
class Animal:
    def eat(self):
        print("Eating")

class Dog(Animal):
    def bark(self):
        print("Barking")

class Cat(Animal):
    def meow(self):
        print("Meowing")

class Cow(Animal):
    def moo(self):
        print("Mooing")
```

- All three inherit `eat()`.
- Siblings share nothing with each other: `Dog` does **not** get `meow()` or `moo()`.

### 4.4 Multiple Inheritance

A child inherits from **more than one** parent.

```python
class Father:
    def skills(self):
        print("Gardening")

class Mother:
    def hobbies(self):
        print("Painting")

class Child(Father, Mother):
    pass

child = Child()
child.skills()    # Gardening
child.hobbies()   # Painting
```

- If several parents define the **same** name, the **MRO** decides which one wins (Section 9).

### 4.5 Hybrid Inheritance

A combination of two or more types. Common case: hierarchical + multiple = **diamond**.

```python
class A:
    def method_a(self):
        print("Method A")

class B(A):
    def method_b(self):
        print("Method B")

class C(A):
    def method_c(self):
        print("Method C")

class D(B, C):
    def method_d(self):
        print("Method D")

obj = D()
obj.method_a()   # Method A
obj.method_b()   # Method B
obj.method_c()   # Method C
obj.method_d()   # Method D
```

- `B` and `C` both inherit from `A` → diamond shape.
- Python resolves lookups here with **C3 linearization** (Section 10).

## 5. Internals: How Inheritance Lookup Works

```python
class Parent:
    def show(self):
        print("Parent method")

class Child(Parent):
    pass

obj = Child()
obj.show()   # Parent method
```

### What happens on `obj.show()`

1. Python looks up `show` on the object (instance `__dict__`, then the class, respecting descriptor precedence).
2. `Child` doesn't define `show`, so Python continues along the MRO.
3. It finds `show` in `Parent`.
4. It **binds** that function to `obj`, making a bound method.
5. The method runs with `self` = `obj`.

> **Key point:** inherited methods are **located** through the class hierarchy, not **copied** into each child.

### Proof: class dictionaries

```python
print("show" in Parent.__dict__)   # True
print("show" in Child.__dict__)    # False

child = Child()
print(hasattr(child, "show"))      # True (inherited)
```

- `show` physically lives only in `Parent`'s namespace.

### `__bases__` vs `__mro__`

```python
print(Child.__bases__)
print(Child.__mro__)
```

```text
(<class '__main__.Parent'>,)
(<class '__main__.Child'>, <class '__main__.Parent'>, <class 'object'>)
```

| Attribute | Contains |
|---|---|
| `Cls.__bases__` | Only the **direct** parent classes |
| `Cls.__mro__` / `Cls.mro()` | The **full** lookup order, ending in `object` |

- The `__main__.` prefix depends on the module where classes are defined.

## 6. Constructors and Inheritance

`__init__()` is technically an **initializer**: `__new__()` creates the object, `__init__()` sets it up. For inheritance, `__init__()` is what matters. Full details: [Topic 2: Constructors](2.%20constructors.md); chaining across classes: [Topic 3: Constructor Chaining](3.%20additional%20topics.md).

### 6.1 Child without its own `__init__()` → parent's is used

```python
class Parent:
    def __init__(self):
        print("Parent initializer")

class Child(Parent):
    pass

obj = Child()   # Parent initializer
```

- `Child` has no `__init__`, so lookup finds `Parent.__init__()` and calls it.

### 6.2 Child defines `__init__()` → parent's is **not** called

```python
class Parent:
    def __init__(self):
        print("Parent initializer")

class Child(Parent):
    def __init__(self):
        print("Child initializer")

obj = Child()   # Child initializer
```

- The child's `__init__` **overrides** the parent's.
- Python does **not** automatically run the parent initializer afterward (unlike Java/C++ constructors).
- Matters when the parent's `__init__` creates attributes that inherited methods rely on.

### 6.3 Calling the parent initializer with `super()`

```python
class Parent:
    def __init__(self):
        print("Parent initializer")

class Child(Parent):
    def __init__(self):
        super().__init__()
        print("Child initializer")

obj = Child()
```

```text
Parent initializer
Child initializer
```

- `super().__init__()` delegates to the **next class in the MRO** (here, `Parent`).

### Real-world example

```python
class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary

    def display(self):
        print(f"Name: {self.name}")
        print(f"Salary: {self.salary}")

class Manager(Employee):
    def __init__(self, name, salary, department):
        super().__init__(name, salary)
        self.department = department

    def show_department(self):
        print(f"Department: {self.department}")

manager = Manager("Aamir", 80000, "Engineering")
manager.display()
manager.show_department()
```

```text
Name: Aamir
Salary: 80000
Department: Engineering
```

**Flow of `Manager("Aamir", 80000, "Engineering")`:**

1. Python creates the `Manager` instance (`__new__`).
2. `Manager.__init__()` runs.
3. It calls `super().__init__(name, salary)` → `Employee.__init__()` sets `name` and `salary`.
4. Control returns to `Manager.__init__()`, which sets `department`.
5. Result: **one** `Manager` object holding all three instance attributes.

### Gotcha: forgetting `super().__init__()`

```python
class Parent:
    def __init__(self):
        self.name = "Python"

class Child(Parent):
    def __init__(self):
        self.age = 25

obj = Child()
print(obj.name)
```

```text
AttributeError: 'Child' object has no attribute 'name'
```

**Fix:**

```python
class Child(Parent):
    def __init__(self):
        super().__init__()
        self.age = 25
```

- Calling `super().__init__()` isn't strictly mandatory, but it's the norm when **extending** a parent initializer, and essential in cooperative multiple inheritance (Section 11).

## 7. Method Overriding

**Method overriding**: a child defines a method with the **same name** as an inherited one, providing a specialized implementation. See also [Topic 4: Polymorphism](4.%20Polymorphism.md).

```python
class Animal:
    def sound(self):
        print("Animals make sounds")

class Dog(Animal):
    def sound(self):
        print("Dog barks")

dog = Dog()
dog.sound()   # Dog barks
```

- `Dog.sound` is found first in the MRO, so it wins.
- Resolved at **runtime** based on the object's actual class.

### 7.1 Extending (not replacing) the parent method

```python
class Animal:
    def sound(self):
        print("Animal sound")

class Dog(Animal):
    def sound(self):
        super().sound()
        print("Dog barks")

dog = Dog()
dog.sound()
```

```text
Animal sound
Dog barks
```

- `super().sound()` runs the next implementation in the MRO, then the child adds its own behavior.

### 7.2 Calling the parent directly: `Parent.method(self)`

```python
class Parent:
    def show(self):
        print("Parent")

class Child(Parent):
    def show(self):
        Parent.show(self)
        print("Child")

Child().show()
```

```text
Parent
Child
```

| `Parent.show(self)` | `super().show()` |
|---|---|
| Hard-codes one specific class | Follows the MRO to the **next** class |
| Must pass `self` explicitly | `self` is bound automatically |
| In multiple inheritance, can **skip** classes or run a shared ancestor **twice** | Each class in the MRO runs once (if all cooperate) |

## 8. `super()` in Depth

"`super()` calls the parent class" is only true for simple single inheritance.

**Accurate definition:** `super()` returns a **proxy object** that delegates attribute lookup to the **next class in the MRO** of the object's actual type.

```python
class A:
    def show(self):
        print("A")

class B(A):
    def show(self):
        print("B")
        super().show()

class C(B):
    def show(self):
        print("C")
        super().show()

obj = C()
obj.show()
```

```text
C
B
A
```

- MRO: `C -> B -> A -> object`.
- `super()` inside `C` → `B.show()`; `super()` inside `B` → `A.show()`.

### Two forms

```python
class Parent:
    def show(self):
        print("Parent")

class Child(Parent):
    def show(self):
        super(Child, self).show()   # explicit form: super(CurrentClass, obj)
        # super().show()            # zero-argument form: identical here
```

- Prefer `super().method()` in Python 3. It works in instance methods and class methods.

### Key properties

- **Not** a fixed reference to the parent class.
- Follows the MRO of `type(self)`, which enables **cooperative multiple inheritance**.
- Works for regular methods and initializers.
- Does **not** call every parent's `__init__` unless every class in the chain also calls `super()`.
- Typically used to **extend** inherited methods while keeping their behavior.

## 9. Method Resolution Order (MRO)

The **MRO** is the ordered list of classes Python searches when resolving an attribute or method. Python computes it with the **C3 linearization** algorithm. Inspect it with `Cls.mro()` or `Cls.__mro__`.

### 9.1 Single inheritance

```python
class A:
    pass

class B(A):
    pass

class C(B):
    pass

print([cls.__name__ for cls in C.mro()])   # ['C', 'B', 'A', 'object']
```

### 9.2 Multiple inheritance: base order matters

```python
class A:
    def show(self):
        print("A")

class B:
    def show(self):
        print("B")

class C(A, B):
    pass

obj = C()
obj.show()                                  # A
print([cls.__name__ for cls in C.mro()])   # ['C', 'A', 'B', 'object']
```

- `A` comes before `B` in the MRO, so `A.show` wins.
- Swap the bases to `class C(B, A)` → MRO becomes `C -> B -> A -> object` and `C().show()` prints `B`.

> **Note:** MRO is **not** a plain left-to-right depth-first search. C3 also keeps the ordering constraints imposed by each parent's own hierarchy (see the diamond below).

## 10. The Diamond Problem

The **diamond problem**: a class inherits from two classes that share a common ancestor. Which path does lookup take, and does the shared ancestor run once or twice?

```text
    A
   / \
  B   C
   \ /
    D
```

- `B(A)`, `C(A)`, `D(B, C)`.

### Broken first attempt

```python
class A:
    def show(self):
        print("A")
        super().show()   # next in MRO is object, which has no show()

class B(A):
    def show(self):
        print("B")
        super().show()

class C(A):
    def show(self):
        print("C")
        super().show()

class D(B, C):
    def show(self):
        print("D")
        super().show()
```

- `D().show()` prints `D B C A` and then raises `AttributeError: 'super' object has no attribute 'show'`.
- **Fix:** the **root** class of the chain must stop delegating.

### Working version

```python
class A:
    def show(self):
        print("A")            # root: no super() call

class B(A):
    def show(self):
        print("B")
        super().show()

class C(A):
    def show(self):
        print("C")
        super().show()

class D(B, C):
    def show(self):
        print("D")
        super().show()

obj = D()
obj.show()
print([cls.__name__ for cls in D.mro()])
```

```text
D
B
C
A
['D', 'B', 'C', 'A', 'object']
```

### Why D → B → C → A (not D → B → A)?

- `super()` follows the MRO of the **actual object** (`D`), not the class where the code is written.
- Inside `B.show()`, the next class after `B` in **D's** MRO is `C`, not `A`.
- `A` runs only once, at the end.
- This is why "`super()` = call my parent" is wrong in multiple inheritance.

### What C3 linearization guarantees

- **Local precedence ordering:** the declared order of direct bases is respected.
- **Monotonicity:** a subclass keeps the relative ordering its parents established.
- **Consistency:** each class appears **exactly once** in the MRO.

### Python can reject an inconsistent hierarchy

```python
class A:
    pass

class B:
    pass

class X(A, B):
    pass

class Y(B, A):
    pass

class Z(X, Y):
    pass
```

```text
TypeError: Cannot create a consistent method resolution
order (MRO) for bases A, B
```

- `X` requires `A` before `B`; `Y` requires `B` before `A`.
- `Z` can't satisfy both, so class creation fails (exact wording may vary by version).

## 11. Cooperative Multiple Inheritance

Multiple inheritance works reliably only when **every** class in the chain cooperates: each calls `super()` and accepts/forwards arguments compatibly. Most important for `__init__`.

```python
class Base:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)

class LoggingMixin:
    def __init__(self, *, logging=False, **kwargs):
        self.logging = logging
        super().__init__(**kwargs)

class ValidationMixin:
    def __init__(self, *, validate=False, **kwargs):
        self.validate = validate
        super().__init__(**kwargs)

class Service(LoggingMixin, ValidationMixin, Base):
    def __init__(self, name, **kwargs):
        self.name = name
        super().__init__(**kwargs)

service = Service("PaymentService", logging=True, validate=True)
print(service.name)       # PaymentService
print(service.logging)    # True
print(service.validate)   # True
print([cls.__name__ for cls in Service.mro()])
# ['Service', 'LoggingMixin', 'ValidationMixin', 'Base', 'object']
```

**Initialization chain:**

```text
Service.__init__()
       |
       v
LoggingMixin.__init__()
       |
       v
ValidationMixin.__init__()
       |
       v
Base.__init__()
       |
       v
object.__init__()
```

- Each initializer **consumes** the keyword arguments it needs and **forwards** the rest via `**kwargs`.
- `object.__init__()` rejects extra arguments, so every custom kwarg must be consumed before the chain reaches `object`.

> **Key principle:** cooperative multiple inheritance needs **compatible method signatures** and **consistent `super()` calls** in every participating class.

## 12. Inheritance and Polymorphism

**Polymorphism**: different objects respond to the **same** call in different ways. Inheritance + overriding gives **runtime polymorphism**. Full topic: [Topic 4: Polymorphism](4.%20Polymorphism.md).

```python
class Animal:
    def speak(self):
        print("Animal sound")

class Dog(Animal):
    def speak(self):
        print("Bark")

class Cat(Animal):
    def speak(self):
        print("Meow")

animals = [Animal(), Dog(), Cat()]
for animal in animals:
    animal.speak()
```

```text
Animal sound
Bark
Meow
```

- Same call `animal.speak()`, behavior picked by the object's **actual class**.

### Dynamic dispatch

An inherited method can call a method that a subclass overrides.

```python
class Shape:
    def describe(self):
        print(f"Area: {self.area()}")

    def area(self):
        return 0

class Rectangle(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height

rectangle = Rectangle(10, 5)
rectangle.describe()   # Area: 50
```

- `describe()` lives in `Shape`, but `self` is a `Rectangle`, so `self.area()` resolves to `Rectangle.area()`.

### Polymorphism without inheritance

- Python also supports **duck typing**: unrelated classes with compatible methods can be used interchangeably.
- So inheritance is **one** way to get polymorphism, not the only one.

## 13. `isinstance()` and `issubclass()`

### 13.1 `isinstance(obj, Cls)`

True if `obj` is an instance of `Cls` **or any subclass** of it.

```python
class Animal:
    pass

class Dog(Animal):
    pass

dog = Dog()
print(isinstance(dog, Dog))      # True  (direct)
print(isinstance(dog, Animal))   # True  (Dog inherits Animal)
print(isinstance(dog, object))   # True  (every class inherits object)
```

### 13.2 `issubclass(Sub, Cls)`

True if `Sub` is `Cls` or inherits from it.

```python
print(issubclass(Dog, Animal))   # True
print(issubclass(Animal, Dog))   # False
print(issubclass(Dog, object))   # True
print(issubclass(Dog, Dog))      # True  (a class counts as its own subclass)
```

### `type()` vs `isinstance()`

```python
dog = Dog()
print(type(dog) is Animal)       # False
print(isinstance(dog, Animal))   # True
```

| `type(obj) is Cls` | `isinstance(obj, Cls)` |
|---|---|
| Exact class only (`Dog`) | Class **or** any subclass |
| Ignores inheritance | Respects inheritance |
| Rarely what you want | Preferred for inheritance-aware checks |

## 14. Inheritance of Class and Instance Attributes

Class attributes are inherited through the same lookup as methods. Basics of class vs instance attributes: [Topic 1](1.%20Classes%20and%20Objects.md).

### 14.1 Inheriting class attributes

```python
class Parent:
    language = "Python"

class Child(Parent):
    pass

obj = Child()
print(obj.language)     # Python
print(Child.language)   # Python
```

### 14.2 Overriding class attributes

```python
class Parent:
    language = "Python"

class Child(Parent):
    language = "Java"

print(Parent.language)  # Python
print(Child.language)   # Java
```

- The child's own class attribute **shadows** the inherited one; the parent is unchanged.

### 14.3 Instance attribute shadowing

```python
class Parent:
    value = 100

class Child(Parent):
    pass

obj = Child()
obj.value = 200
print(obj.value)      # 200
print(Child.value)    # 100
print(Parent.value)   # 100
```

- `obj.value = 200` creates a new **instance** attribute; the inherited class attribute is untouched.

### 14.4 Gotcha: mutable class attributes are shared

```python
class Parent:
    items = []

class Child(Parent):
    pass

a = Child()
b = Child()
a.items.append("Python")
print(b.items)        # ['Python']
print(Parent.items)   # ['Python']
```

- `append` **mutates** (doesn't assign), so every object finds and modifies the **same** inherited list.
- **Fix:** create per-object state in `__init__`:

```python
class Parent:
    def __init__(self):
        self.items = []   # new list for every instance

class Child(Parent):
    pass
```

## 15. Access Modifiers and Inheritance

Python has no enforced `public` / `protected` / `private`. It uses **naming conventions** and **name mangling**. Details: [Topic 6: Encapsulation](6.%20Encapsulation.md) and [Topic 8: Access Modifiers](8.%20access%20modifiers.md).

| Name | Meaning | Accessible in child? |
|---|---|---|
| `name` | **Public** | Yes |
| `_name` | **Protected** by convention ("internal use") | Yes, nothing enforced |
| `__name` | **Name-mangled** to `_ClassName__name` | Not under the same name |

### 15.1 Public

```python
class Parent:
    def __init__(self):
        self.name = "Python"

class Child(Parent):
    def display(self):
        print(self.name)

Child().display()   # Python
```

### 15.2 Protected convention: `_single`

```python
class Parent:
    def __init__(self):
        self._salary = 50000

class Child(Parent):
    def display(self):
        print(self._salary)

Child().display()   # 50000
```

- Python doesn't block access; the underscore only signals "internal".

### 15.3 Name mangling: `__double`

```python
class Parent:
    def __init__(self):
        self.__secret = "Hidden"

class Child(Parent):
    def display(self):
        print(self.__secret)

Child().display()
```

```text
AttributeError: 'Child' object has no attribute '_Child__secret'
```

**Why:** names starting with **two or more** underscores and ending with **fewer than two** are rewritten using the class they're written in.

- In `Parent`: `self.__secret` → `self._Parent__secret` (what actually gets stored).
- In `Child`: `self.__secret` → `self._Child__secret` (doesn't exist).

**Accessing the mangled name (works, but discouraged):**

```python
class Child(Parent):
    def display(self):
        print(self._Parent__secret)

Child().display()   # Hidden
```

**Better: expose a method or property:**

```python
class Parent:
    def __init__(self):
        self.__secret = "Hidden"

    @property
    def secret(self):
        return self.__secret

class Child(Parent):
    def display(self):
        print(self.secret)

Child().display()   # Hidden
```

> **Key point:** `__` is **not** security or true privacy. Name mangling mainly prevents **accidental name clashes** with subclasses.

## 16. Abstract Classes and Inheritance

An **abstract base class (ABC)** defines a contract that subclasses must fulfill, and can't be instantiated itself. Built with `abc.ABC` + `@abstractmethod`. Full topic: [Topic 7: Abstraction](7.%20abstraction.md).

```python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self):
        pass

class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

    def area(self):
        return 3.14 * self.radius ** 2

class Rectangle(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height

circle = Circle(5)
rectangle = Rectangle(10, 4)
print(circle.area())      # 78.5
print(rectangle.area())   # 40
```

**Instantiation rules:**

```python
shape = Shape()          # TypeError: has an unimplemented abstract method

class Triangle(Shape):
    pass

triangle = Triangle()    # TypeError: Triangle didn't implement area()
```

- ABCs **can** contain concrete (normal) methods.
- Abstract methods **can** have a body (callable via `super()`), but concrete subclasses must still override them.
- A subclass stays **abstract** until it implements every abstract method.
- ABCs tie together inheritance, abstraction and polymorphism.

## 17. Inheriting and Overriding Different Method Types

Instance methods, class methods, static methods and properties are **all** inherited and can all be overridden.

### 17.1 Instance methods

```python
class Parent:
    def show(self):
        print("Parent")

class Child(Parent):
    def show(self):
        print("Child")

Child().show()   # Child
```

### 17.2 Class methods: `cls` is the class it was called on

```python
class Animal:
    @classmethod
    def create(cls):
        return cls()

class Dog(Animal):
    pass

dog = Dog.create()
print(type(dog).__name__)   # Dog
```

- Called through `Dog`, so `cls` is `Dog` and `cls()` builds a `Dog`.
- This makes class methods ideal for **polymorphic factory methods**.

### 17.3 Static methods

```python
class Parent:
    @staticmethod
    def greet():
        print("Hello")

class Child(Parent):
    pass

Child.greet()   # Hello
```

- Inherited like any class attribute; receive neither `self` nor `cls`.

### 17.4 Properties

```python
class Person:
    def __init__(self, name):
        self._name = name

    @property
    def name(self):
        return self._name

class Employee(Person):
    pass

employee = Employee("Aamir")
print(employee.name)   # Aamir
```

- The property **descriptor** is inherited; a child can redefine the property to customize access.

## 18. Mixins

A **mixin** is a small class that adds one reusable **capability** (logging, serialization, validation, permission checks) to other classes via multiple inheritance. It represents a "can-do", not a full IS-A relationship.

```python
class LoggingMixin:
    def log(self, message):
        print(f"[LOG] {message}")

class SerializationMixin:
    def serialize(self):
        return self.__dict__.copy()

class User(LoggingMixin, SerializationMixin):
    def __init__(self, name, age):
        self.name = name
        self.age = age

user = User("Aamir", 25)
user.log("User created")   # [LOG] User created
print(user.serialize())    # {'name': 'Aamir', 'age': 25}
```

- Combine focused capabilities instead of building deep hierarchies:

```python
class AdminUser(LoggingMixin, SerializationMixin):
    pass
```

### Best practices

- One capability per mixin.
- Avoid depending on unrelated attributes; **document** what the host class must provide.
- Use cooperative `super()` when overriding methods shared across the hierarchy (Section 11).
- Avoid deep or confusing mixin combinations.

## 19. Every Class Inherits From `object`

In Python 3, a class with no declared parent inherits from `object`. These are equivalent:

```python
class A:
    pass

class A(object):
    pass
```

```python
class A:
    pass

print(A.__bases__)   # (<class 'object'>,)
print(A.__mro__)     # (<class '__main__.A'>, <class 'object'>)
```

- `object` provides default `__new__()`, `__init__()`, `__str__()`, `__repr__()`, `__eq__()`, `__hash__()`, etc. Subclasses can override them.

### Example: overriding `__str__()`

```python
class Employee:
    def __init__(self, name):
        self.name = name

    def __str__(self):
        return f"Employee: {self.name}"

employee = Employee("Aamir")
print(employee)   # Employee: Aamir
```

- Without it, `print` shows the default `<__main__.Employee object at 0x...>` (class + identity-based value).

## 20. Inheritance and Special (Dunder) Methods

Special methods (`__init__`, `__str__`, `__repr__`, `__len__`, `__eq__`, `__add__`, ...) are inherited like any other method.

```python
class Parent:
    def __len__(self):
        return 5

class Child(Parent):
    pass

obj = Child()
print(len(obj))   # 5 (inherited __len__)
```

### Internals: implicit calls look on the **type**, not the instance

```python
class MyClass:
    def __len__(self):
        return 5

obj = MyClass()
obj.__len__ = lambda: 100
print(obj.__len__())   # 100
print(len(obj))        # 5
```

- `obj.__len__()` is normal attribute access → finds the **instance** attribute first.
- `len(obj)` uses **special-method lookup** → goes straight to `type(obj)` and its MRO, ignoring the instance `__dict__`.

## 21. Liskov Substitution Principle (LSP)

**LSP:** objects of a subclass must be usable wherever the base class is expected, **without breaking the program's expectations**. Passing `isinstance(child, Parent)` isn't enough; the child must keep the parent's **behavioral contract**.

### Good design

```python
class Bird:
    def eat(self):
        print("Eating")

class Sparrow(Bird):
    def fly(self):
        print("Flying")

class Penguin(Bird):
    def swim(self):
        print("Swimming")
```

- The `Bird` contract doesn't promise flying, so both subclasses honor it.

### Violation

```python
class Bird:
    def fly(self):
        print("Flying")

class Penguin(Bird):
    def fly(self):
        raise NotImplementedError("Penguins cannot fly")
```

- Code that expects every `Bird` to fly will break on a `Penguin`.

### Fixed hierarchy

```python
class Bird:
    def eat(self):
        print("Eating")

class FlyingBird(Bird):
    def fly(self):
        print("Flying")

class Sparrow(FlyingBird):
    pass

class Penguin(Bird):
    def swim(self):
        print("Swimming")
```

> **Key point:** model **substitutable** relationships, not superficially similar objects. A badly designed parent forces children to inherit behavior that makes no sense for them.

## 22. Inheritance with Dataclasses

`@dataclass` generates `__init__`, `__repr__`, etc.; inherited dataclass fields are included.

```python
from dataclasses import dataclass

@dataclass
class Employee:
    name: str
    salary: int

@dataclass
class Manager(Employee):
    department: str

manager = Manager(name="Aamir", salary=80000, department="Engineering")
print(manager)
```

```text
Manager(name='Aamir', salary=80000, department='Engineering')
```

- Base-class fields come **first** in the generated `__init__`, followed by the subclass's fields.
- A field **without** a default can't follow one **with** a default (`TypeError`). Common trap when the base has defaults; `@dataclass(kw_only=True)` (Python 3.10+) avoids it.
- The generated `__init__` does **not** call a non-dataclass base's custom `__init__()`. Call it yourself in `__post_init__()` if needed.
- Treat dataclass inheritance as its own case when designing production code.

## 23. When Should You Use Inheritance?

| Use inheritance when | Avoid inheritance when |
|---|---|
| A genuine **IS-A** relationship exists | You only want a few unrelated helper methods |
| Subclasses share a meaningful behavioral contract | The relationship is **HAS-A** |
| Subclasses need to override or extend base behavior | Subclasses need many exceptions to parent behavior |
| Polymorphism through a shared parent is valuable | The hierarchy gets too deep to understand |
| The hierarchy is stable and understandable | Parent changes keep breaking unrelated subclasses |

### Design examples

| Situation | Recommended design |
|---|---|
| Dog and Animal | Inheritance |
| Car and Engine | Composition |
| Manager and Employee | Inheritance, if the employee contract applies |
| User and Logging | Mixin or composition |
| Order and PaymentProcessor | Composition |
| Circle and Shape | Inheritance |
| Two unrelated classes sharing a utility function | Function or composition |

> **Principle:** **favor composition over inheritance** unless the relationship clearly needs specialization.

## 24. Complete Example: Employee Management System

Combines inheritance, overriding, `super()`, polymorphism and abstract classes.

```python
from abc import ABC, abstractmethod

class Employee(ABC):
    def __init__(self, name, base_salary):
        self.name = name
        self.base_salary = base_salary

    @abstractmethod
    def calculate_salary(self):
        pass

    def display_details(self):
        print(f"Name: {self.name}")
        print(f"Salary: {self.calculate_salary()}")

class Developer(Employee):
    def __init__(self, name, base_salary, bonus):
        super().__init__(name, base_salary)
        self.bonus = bonus

    def calculate_salary(self):
        return self.base_salary + self.bonus

class Manager(Employee):
    def __init__(self, name, base_salary, allowance):
        super().__init__(name, base_salary)
        self.allowance = allowance

    def calculate_salary(self):
        return self.base_salary + self.allowance

employees = [
    Developer("Aamir", 70000, 10000),
    Manager("Rahul", 90000, 20000),
]
for employee in employees:
    employee.display_details()
    print("-" * 20)
```

```text
Name: Aamir
Salary: 80000
--------------------
Name: Rahul
Salary: 110000
--------------------
```

| Concept | Where |
|---|---|
| Inheritance | `Developer(Employee)`, `Manager(Employee)` |
| Abstraction | `Employee` is an ABC |
| Method overriding | Both subclasses implement `calculate_salary()` |
| `super()` | Reuses `Employee.__init__()` |
| Polymorphism | Same `display_details()` call works for each subclass |
| Dynamic dispatch | `display_details()` calls the subclass's `calculate_salary()` |

**Flow of `Developer("Aamir", 70000, 10000).display_details()`:**

1. A `Developer` object is created; `Developer.__init__()` runs.
2. `super().__init__()` sets `name` and `base_salary`; then `bonus` is set.
3. `display_details()` is found in `Employee` (inherited).
4. It calls `self.calculate_salary()`; `self` is a `Developer`, so `Developer.calculate_salary()` runs.
5. Salary `80000` is printed.

## 25. Common Mistakes / Gotchas

- **Child `__init__` without `super().__init__()`** → parent's attributes never get set (`AttributeError`). Call `super().__init__()` when extending (Section 6).
- **Assuming `super()` always calls the direct parent** → in multiple inheritance it calls the **next class in the MRO**, which may be a sibling (Section 10).
- **Calling parent initializers directly in a diamond** → shared ancestor runs twice (example below). Use cooperative `super()`.
- **Root class of a cooperative chain also calls `super().method()`** → `AttributeError` when it reaches `object`. The root must stop delegating.
- **Confusing overriding with overloading** → a second `def` with the same name **replaces** the first (example below).
- **Assuming `__name` means strict privacy** → it's only name-mangled; `obj._Class__name` still works.
- **Mutable class attribute in a base class** (`items = []`) → shared by every instance of every subclass. Create it in `__init__` (Section 14.4).
- **`type(obj) is Parent` checks** → fail for subclasses. Use `isinstance()`.
- **Inconsistent base order across a hierarchy** → `TypeError: Cannot create a consistent method resolution order`.
- **Inheriting only for code reuse** → fragile, artificial hierarchies. Use composition or a plain helper function.
- **Subclass that breaks the parent's contract** (e.g. `Penguin.fly()` raising) → violates LSP (Section 21).

### Example: calling parent initializers directly

```python
class A:
    def __init__(self):
        print("A")

class B(A):
    def __init__(self):
        A.__init__(self)

class C(A):
    def __init__(self):
        A.__init__(self)

class D(B, C):
    def __init__(self):
        B.__init__(self)
        C.__init__(self)

D()
```

```text
A
A
```

- `A.__init__` runs twice → duplicated initialization / inconsistent state in real systems.

### Example: overriding vs overloading

```python
# Overriding: child redefines an inherited method (supported)
class A:
    def show(self):
        print("A")

class B(A):
    def show(self):
        print("B")

# "Overloading": same name, different parameters (NOT supported this way)
class Calculator:
    def add(self, a, b):
        return a + b

    def add(self, a, b, c):   # replaces the first add() in the class namespace
        return a + b + c
```

| Overriding | Overloading |
|---|---|
| Same name in **child** class | Same name, **different parameters**, same class |
| Supported; resolved at runtime via MRO | No Java-style support; last definition wins |
| Used for specialization / polymorphism | Emulate with default args, `*args`, or `functools.singledispatchmethod` |

- More on overloading: [Topic 4: Polymorphism](4.%20Polymorphism.md).

## 26. Interview Questions

**Q1. What is inheritance in Python?**
An OOP mechanism where a class derives attributes and behavior from another class, enabling code reuse, specialization and polymorphism.

**Q2. What types of inheritance does Python support?**
Single, multilevel, hierarchical, multiple and hybrid.

**Q3. Does Python support multiple inheritance?**
Yes: `class C(A, B): pass`. Conflicts are resolved by the MRO.

**Q4. What is method overriding?**
A subclass defines a method with the same name as an inherited one, replacing or specializing it.

**Q5. What is `super()`?**
It returns a proxy that delegates attribute lookup to the **next class in the MRO** of the object's type, not necessarily the direct parent.

**Q6. What is MRO?**
Method Resolution Order: the order Python searches classes for attributes/methods. Computed with **C3 linearization**.

**Q7. How do you inspect the MRO?**
`ClassName.mro()` (returns a list) or `ClassName.__mro__` (a tuple).

**Q8. Does the parent `__init__()` run automatically when the child overrides `__init__()`?**
No. The child must call `super().__init__()` (or the parent explicitly) when needed.

**Q9. What is the diamond problem?**
Multiple inheritance paths lead to a shared ancestor. Python's MRO resolves lookups consistently and, with cooperative `super()`, runs the ancestor only once.

**Q10. Inheritance vs composition?**
Inheritance = specialization (**IS-A**). Composition = an object contains/uses another (**HAS-A**). Favor composition unless IS-A clearly holds.

**Q11. Can we inherit from built-in classes?**
Yes.

```python
class MyList(list):
    def first(self):
        return self[0] if self else None

obj = MyList([10, 20, 30])
print(obj.first())   # 10
```

**Q12. Can a child override a parent method?**
Yes: instance methods, class methods, static methods and properties can all be overridden.

**Q13. Can an abstract class be inherited?**
Yes. ABCs exist precisely to be inherited and define contracts for subclasses.

**Q14. Can we prevent inheritance in Python?**
No built-in runtime `final` keyword. `typing.final` marks a class as non-subclassable for **type checkers only**; for a runtime block, raise in `__init_subclass__()`.

```python
from typing import final

@final
class SecureClass:          # type checkers reject subclasses; runtime allows them
    pass

class Sealed:
    def __init_subclass__(cls, **kwargs):
        raise TypeError(f"{cls.__name__} cannot subclass Sealed")
```

**Q15. What happens when two parents define the same method?**
The one appearing first in the child's MRO is used (with `class C(A, B)`, `A`'s wins).

**Q16. Is inheritance necessary for polymorphism in Python?**
No. Duck typing and structural typing (protocols) give polymorphism without a shared parent. See [Topic 9](9.%20interface,%20wildcards%20and%20generics.md).

**Q17. Are parent instance attributes copied into the child class?**
No. Instance attributes are set on each object by initializers. Inheritance only makes methods and class-level definitions reachable via lookup.

## Quick Recap

- **Inheritance** → child class reuses, extends and overrides a parent class; models **IS-A**. Use **composition** for **HAS-A**.
- **Types** → single, multilevel, hierarchical, multiple, hybrid (diamond).
- **Lookup, not copying** → inherited members are found via the **MRO** (`Cls.mro()` / `__mro__`); `__bases__` = direct parents only. Every class ends in `object`.
- **`__init__`** → inherited if the child doesn't define one; if it does, the parent's runs **only** via `super().__init__()`.
- **Overriding** → same name in child wins; extend with `super().method()`. Python has no signature-based overloading.
- **`super()`** → proxy to the **next class in the MRO** of `type(self)`, not "the parent". `Parent.method(self)` hard-codes one class.
- **MRO / C3** → respects base order, keeps parents' ordering, lists each class once; inconsistent hierarchies raise `TypeError`.
- **Diamond + cooperative inheritance** → every class calls `super()` and forwards `**kwargs`; the root stops delegating; the shared ancestor runs once.
- **Polymorphism / dynamic dispatch** → `self.method()` in a parent calls the subclass override. Duck typing gives polymorphism without inheritance.
- **`isinstance()`** respects inheritance; `type(x) is C` doesn't. `issubclass(C, C)` is `True`.
- **Attributes** → class attributes are inherited and shadowable; mutable class attributes are **shared** by all subclasses' instances. `__name` is mangled to `_Class__name`.
- **Design** → ABCs define contracts, mixins add capabilities, LSP: subclasses must be substitutable. Favor composition when in doubt.

> **Core idea:** inheritance links classes; Python walks that link (the MRO) at lookup time to decide which attribute or method an object uses. Overriding customizes behavior, and `super()` lets implementations cooperate along the MRO.
