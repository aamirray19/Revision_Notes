# Topic 9: Interfaces, Generics, and Wildcards (Variance)

> **TL;DR:** An **interface** defines *what* an object must do; the class decides *how*. Python has no `interface` keyword: it uses **ABCs**, **Protocols** and **duck typing**. **Generics** (`TypeVar`, `class Box[T]`) give reusable code without losing type information, and **variance** (invariant / covariant / contravariant) is Python's answer to Java's `?` wildcards. Generics are checked **statically** (mypy/Pyright), not at runtime.

> **Prerequisites:** [Topic 1: Classes and Objects](1.%20Classes%20and%20Objects.md), [Topic 4: Polymorphism](4.%20Polymorphism.md), [Topic 5: Inheritance](5.%20inheritance.md), [Topic 7: Abstraction](7.%20abstraction.md) (abstract classes/methods), basic type annotations. Most examples need Python 3.10+; 3.12+ syntax is marked.

---

## Part 1: Interfaces

### 1. What Is an Interface?

An **interface** is a **contract**: it lists the operations an object must support, without fixing how they are implemented.

- Interface = **WHAT** an object must do. Implementing class = **HOW** it does it.
- **Analogy:** USB-C. Samsung, Pixel and OnePlus charge differently inside, but any compatible charger works through the same standard port.

**Software example:** a payment system with credit card, UPI and PayPal. Each processes payments differently, but the app only needs every provider to support `pay(amount)`.

```text
               Payment Interface
                      |
                 pay(amount)
                      |
         +------------+------------+
         |            |            |
         v            v            v
    CreditCard       UPI         PayPal
         |            |            |
         v            v            v
    Card Logic     UPI Logic    PayPal Logic
```

- The app calls `pay()` without knowing any provider's internals.

---

### 2. Why Do We Need Interfaces?

**Without a common interface**, every provider has its own method name:

```python
class CreditCard:
    def process_card(self, amount):
        print(f"Credit card payment: {amount}")


class UPI:
    def transfer_upi(self, amount):
        print(f"UPI payment: {amount}")


class PayPal:
    def send_money(self, amount):
        print(f"PayPal payment: {amount}")


# checkout must know every concrete class
def checkout(payment_method, amount):
    if isinstance(payment_method, CreditCard):
        payment_method.process_card(amount)
    elif isinstance(payment_method, UPI):
        payment_method.transfer_upi(amount)
    elif isinstance(payment_method, PayPal):
        payment_method.send_money(amount)
```

**Problems:**

1. Different method name per provider.
2. `checkout` depends on concrete classes.
3. Every new provider means editing `checkout`.
4. Testing needs the specific implementations.
5. Tight coupling.

**With a common interface** (every provider implements `pay(amount)`):

```python
def checkout(payment_method, amount):
    payment_method.pay(amount)
```

- `checkout` depends only on the expected behavior.

| Benefit | Explanation |
|---|---|
| **Loose coupling** | Code depends on a common contract |
| **Flexibility** | Implementations can be swapped |
| **Extensibility** | New implementations need no client changes |
| **Polymorphism** | Different objects respond to the same call |
| **Testability** | Fakes can replace real services |
| **Maintainability** | Implementations change independently |

---

### 3. Does Python Have an `interface` Keyword?

**No.** Unlike Java, Python has no `interface` keyword. It supports interface-style design through:

1. **Abstract Base Classes (ABCs)**: explicit, enforced at instantiation.
2. **Duck typing**: implicit, fails only at runtime.
3. **Protocols**: explicit, structural, checked statically.

They differ in how explicit and how enforced the contract is (compared in Section 9).

---

### 4. Interfaces Using Abstract Base Classes (ABCs)

An **ABC** (`from abc import ABC, abstractmethod`) defines an explicit contract that subclasses must fulfil. Full ABC coverage: [Topic 7: Abstraction](7.%20abstraction.md).

```python
from abc import ABC, abstractmethod


class PaymentProcessor(ABC):
    @abstractmethod
    def pay(self, amount):
        pass


class CreditCardPayment(PaymentProcessor):
    def pay(self, amount):
        print(f"Paid {amount} using Credit Card")


class UPIPayment(PaymentProcessor):
    def pay(self, amount):
        print(f"Paid {amount} using UPI")


def checkout(processor, amount):
    processor.pay(amount)


card = CreditCardPayment()
upi = UPIPayment()

checkout(card, 1000)  # Paid 1000 using Credit Card
checkout(upi, 2000)   # Paid 2000 using UPI
```

**How it works:**

1. **Define the contract:** `PaymentProcessor(ABC)` marks `pay()` with `@abstractmethod`.
2. **Inherit it:** `class CreditCardPayment(PaymentProcessor)`.
3. **Implement the required method:** defining `pay()` resolves the abstract requirement.
4. **Use it:** `checkout(card, 1000)` needs no provider-specific `if/elif` logic.

#### Missing implementation → cannot instantiate

```python
class CashPayment(PaymentProcessor):
    pass


cash = CashPayment()
```

```text
TypeError: Can't instantiate abstract class CashPayment without an implementation for abstract method 'pay'
```

- Exact wording varies by Python version (3.12+ shown).
- The check happens at **instantiation**, not when the class is defined.

#### Limitation

ABCs only check that abstract methods were **overridden**. They do **not** verify:

- method signatures
- return types
- business logic

→ Use static type checkers and tests for those.

---

### 5. Interface vs Abstract Class (interview favorite)

- **Interface:** describes the operations implementers must support (a pure contract).
- **Abstract class:** requires operations **and** can share implemented methods and state.
- Python has **no strict language-level split**: an ABC can be a pure interface, or also carry state and concrete methods.

```python
from abc import ABC, abstractmethod


class Vehicle(ABC):
    def __init__(self, brand):     # constructor
        self.brand = brand         # instance attribute (state)

    @abstractmethod
    def start(self):               # abstract method (contract)
        pass

    def display_brand(self):       # concrete method (shared behavior)
        print(self.brand)
```

- `Vehicle` is an abstract base class **with shared behavior**, not a pure interface.

| Conceptual Interface | Abstract Base Class |
|---|---|
| Primarily defines a contract | Contract plus possibly shared behavior/state |
| Focuses on capabilities | May represent a shared class hierarchy |
| In Python: often `Protocol` | In Python: `ABC` |
| Implementations may be unrelated | Implementations usually share ancestry |
| Structural typing possible | Nominal (inheritance-based) typing |

- Python's ABC system is flexible enough for interface-style design too.

### 6. Duck Typing as an Interface

**Duck typing:** if an object supports the operations the caller needs, it can be used, whatever its class. Possible because Python is dynamically typed. See [Topic 4: Polymorphism](4.%20Polymorphism.md).

```python
class EmailService:
    def send(self, message):
        print(f"Email: {message}")


class SMSService:
    def send(self, message):
        print(f"SMS: {message}")


class PushService:
    def send(self, message):
        print(f"Push: {message}")


def notify(service, message):
    service.send(message)


notify(EmailService(), "Hello")  # Email: Hello
notify(SMSService(), "Hello")    # SMS: Hello
notify(PushService(), "Hello")   # Push: Hello
```

- **No** common parent, **no** ABC, **no** explicit interface. Each class just has `send(message)`.
- `notify()` only cares about that one operation.

#### Limitation: errors appear only at runtime

```python
class BrokenService:
    pass


notify(BrokenService(), "Hello")
# AttributeError: 'BrokenService' object has no attribute 'send'
```

- A missing method is not detected before the call executes.

**Good for:** small apps, flexible APIs, simple interchangeable objects, libraries built on behavioral conventions (e.g. "file-like" objects).

---

### 7. Protocols: Modern Python Interfaces (Python 3.8+)

A **`Protocol`** (from `typing`) formally lists the methods/attributes an object must have. Any class with a matching structure satisfies it, **no inheritance needed**. This is **structural typing**.

- **Structural typing:** compatibility depends on what a type *has* (its methods/attributes).
- **Nominal typing:** compatibility depends on what a type *inherits from*. ABCs are nominal.

```python
from typing import Protocol


class NotificationService(Protocol):
    def send(self, message: str) -> None:
        ...


class Email:
    def send(self, message: str) -> None:
        print(f"Email: {message}")


class SMS:
    def send(self, message: str) -> None:
        print(f"SMS: {message}")


def notify(service: NotificationService, message: str) -> None:
    service.send(message)


notify(Email(), "Welcome")  # Email: Welcome
notify(SMS(), "Welcome")    # SMS: Welcome
```

- Neither `Email` nor `SMS` inherits from `NotificationService`, yet both satisfy it: each has a compatible `def send(self, message: str) -> None`.
- Static checkers (**mypy**, **Pyright**) verify this.
- Protocols are a **static** mechanism. Python does not enforce ordinary annotations at runtime.

---

### 8. `@runtime_checkable` Protocols

By default a Protocol is static-only (`isinstance()` against it raises `TypeError`). **`@runtime_checkable`** allows limited runtime structural checks with `isinstance()`.

```python
from typing import Protocol, runtime_checkable


@runtime_checkable
class Printable(Protocol):
    def print_data(self) -> None:
        ...


class Document:
    def print_data(self) -> None:
        print("Printing document")


class Image:
    def display(self) -> None:
        print("Displaying image")


doc = Document()
img = Image()

print(isinstance(doc, Printable))  # True
print(isinstance(img, Printable))  # False
```

#### Limitation: only checks that members exist

```python
class BadPrinter:
    def print_data(self, value):
        print(value)


print(isinstance(BadPrinter(), Printable))  # True
BadPrinter().print_data()
# TypeError: BadPrinter.print_data() missing 1 required positional argument: 'value'
```

- Runtime checks don't validate signatures, annotations or semantics.
- Use static type checkers for real compatibility checking. Don't treat `@runtime_checkable` as a validation system.

---

### 9. ABC vs Protocol vs Duck Typing

| Feature | ABC | Protocol | Duck Typing |
|---|---|---|---|
| Explicit contract | Yes | Yes | Implicit |
| Requires inheritance | Usually | No | No |
| Static type checking | Supported | Supported | Possible with annotations |
| Runtime abstract enforcement | Yes (at instantiation) | No | No |
| Structural compatibility | Not by default | Yes | Yes, through behavior |
| Shared implementation | Yes | Limited (default methods possible) | Not required |
| Best suited for | Formal class hierarchies | Flexible typed interfaces | Simple flexible APIs |

**Use an ABC when:**

- you control a related class hierarchy,
- you want abstract-method enforcement,
- you want to share implementation.

**Use a Protocol when:**

- the classes may be unrelated,
- you want static type safety,
- you want to depend on **capabilities**, not ancestry.

**Use duck typing when:**

- the expected behavior is simple,
- formal type declarations would add needless complexity.

### 10. Interfaces and the SOLID Principles

Interfaces underpin two SOLID principles: **DIP** and **ISP**.

#### Dependency Inversion Principle (DIP)

High-level components should depend on **abstractions**, not on concrete implementation details.

**Tightly coupled:**

```python
class EmailService:
    def send(self, message):
        print(f"Email: {message}")


class UserManager:
    def __init__(self):
        self.email_service = EmailService()   # hard-wired dependency

    def register(self):
        self.email_service.send("Welcome!")
```

- `UserManager` creates and depends on `EmailService` directly. Switching to SMS means editing `UserManager`.

**Better: depend on a Protocol and inject the implementation (dependency injection):**

```python
from typing import Protocol


class Notifier(Protocol):
    def send(self, message: str) -> None:
        ...


class EmailService:
    def send(self, message: str) -> None:
        print(f"Email: {message}")


class SMSService:
    def send(self, message: str) -> None:
        print(f"SMS: {message}")


class UserManager:
    def __init__(self, notifier: Notifier):
        self.notifier = notifier

    def register(self):
        self.notifier.send("Welcome!")


email_manager = UserManager(EmailService())
sms_manager = UserManager(SMSService())

email_manager.register()  # Email: Welcome!
sms_manager.register()    # SMS: Welcome!
```

- `UserManager` knows only the `Notifier` contract, not whether it's email or SMS.
- Testing is easy: inject a fake notifier.

#### Interface Segregation Principle (ISP)

Clients should not be forced to depend on operations they don't need.

**Poor design (one fat interface):**

```python
from typing import Protocol


class Machine(Protocol):
    def print_document(self) -> None:
        ...

    def scan_document(self) -> None:
        ...

    def fax_document(self) -> None:
        ...
```

- A basic printer only prints, but must now claim to scan and fax.

**Better design (small, focused interfaces):**

```python
from typing import Protocol


class Printer(Protocol):
    def print_document(self) -> None:
        ...


class Scanner(Protocol):
    def scan_document(self) -> None:
        ...


class SimplePrinter:
    def print_document(self) -> None:
        print("Printing")
```

- `SimplePrinter` only needs to satisfy `Printer`.
- **Takeaway:** prefer small interfaces that each describe one meaningful capability.

## Part 2: Generics

### 11. What Are Generics?

**Generics** let classes, functions and other type definitions work with **many types** while **preserving the relationships** between those types. In short: reusable code without losing type information.

```python
def get_first(items):
    return items[0]


print(get_first([10, 20, 30]))        # 10
print(get_first(["Python", "Java"]))  # Python
```

- This already works for any type, because Python is dynamically typed.
- **So why generics?** A **static type checker** needs to know:
  - what type goes into the function,
  - what type comes out,
  - which types must stay consistent,
  - which operations are safe.
- Generics express exactly these relationships.

---

### 12. Type Hints (Before Generics)

**Type annotations** tell developers and type checkers what types are expected.

```python
def add(a: int, b: int) -> int:
    return a + b
```

- `a` and `b` should be `int`; the result should be `int`.

**Collection type hints** (built-in generic collections, Python 3.9+):

```python
numbers: list[int] = [1, 2, 3]
names: list[str] = ["Ali", "Sara"]
scores: dict[str, int] = {"Ali": 90, "Sara": 95}
```

| Type | Meaning |
|---|---|
| `list[int]` | List of integers |
| `list[str]` | List of strings |
| `dict[str, int]` | Dict with `str` keys and `int` values |
| `set[str]` | Set of strings |
| `tuple[int, str]` | Fixed-length tuple: an `int` then a `str` |
| `tuple[int, ...]` | Variable-length tuple of integers |

#### Type hints are not enforced at runtime

```python
numbers: list[int] = [1, 2, 3]
numbers.append("Hello")   # runs fine; a static checker reports an error
```

> **Key point:** generics provide **static type safety**, not automatic runtime validation.

---

### 13. Generic Functions Using `TypeVar`

**`TypeVar`** declares a **type variable**: a placeholder type that the checker fills in from how the function is called.

```python
from typing import TypeVar
from collections.abc import Sequence


T = TypeVar("T")


def get_first(items: Sequence[T]) -> T:
    return items[0]


print(get_first([10, 20, 30]))        # 10
print(get_first(["Python", "Java"]))  # Python
```

- `T` **links** the element type of the input to the return type.
- `get_first([10, 20])` → checker infers the result is `int`.
- `get_first(["Python", "Java"])` → checker infers `str`.

#### Why not just use `object`?

```python
def get_first(items: list[object]) -> object:
    return items[0]
```

- The return type is always `object`; the original element type is **lost**. Generics preserve it.
- `TypeVar` is **not** a new runtime data type; it's a type parameter for static analysis only.

---

### 14. Modern Generic Function Syntax (Python 3.12+)

Python 3.12 (PEP 695) lets you declare the type parameter directly in the function signature.

```python
# Traditional (any version)
from typing import TypeVar

T = TypeVar("T")


def identity(value: T) -> T:
    return value
```

```python
# Python 3.12+
def identity[T](value: T) -> T:
    return value


print(identity(100))       # 100
print(identity("Python"))  # Python
```

- `def identity[T](...)` makes the generic relationship visible in one place. Both forms are valid.

| Syntax | Minimum Python version |
|---|---|
| `TypeVar("T")` | Older versions (3.5+) |
| Built-in `list[int]` annotations | 3.9 |
| `int \| str` union syntax | 3.10 |
| `def function[T](...)` | 3.12 |
| `class Box[T]:` | 3.12 |

- For older projects, the traditional `TypeVar` approach remains useful.

---

### 15. Generic Classes

A **generic class** is one reusable class whose contents' type is a parameter. E.g. one `Box` that can hold an `int`, `str`, `Employee`, `Product` or `User`, instead of a class per type.

```python
from typing import Generic, TypeVar


T = TypeVar("T")                 # 1. declare a type variable


class Box(Generic[T]):           # 2. make the class generic in T
    def __init__(self, value: T):  # 3. use T consistently
        self.value = value

    def get(self) -> T:
        return self.value

    def set(self, value: T) -> None:
        self.value = value


int_box = Box[int](100)          # 4. specialize: a box of ints
str_box = Box[str]("Python")

print(int_box.get())  # 100
print(str_box.get())  # Python
```

- `Box[int]` describes a box meant to hold integers; `Box[str]` one for strings.
- Writing `Box(100)` also works: the checker infers `Box[int]`.

#### Wrong type? Only the checker complains

```python
int_box = Box[int](100)
int_box.set("Hello")   # static checker: incompatible type; runtime: allowed
```

- Python generics do **not** reject wrong values at runtime.

---

### 16. Modern Generic Class Syntax (Python 3.12+)

```python
class Box[T]:
    def __init__(self, value: T):
        self.value = value

    def get(self) -> T:
        return self.value

    def set(self, value: T) -> None:
        self.value = value


box = Box[int](100)
print(box.get())  # 100
```

| Older syntax | Modern syntax (3.12+) |
|---|---|
| `T = TypeVar("T")` + `class Box(Generic[T]):` | `class Box[T]:` |

- The modern form creates the type parameter implicitly (no `TypeVar`, no `Generic` import).

---

### 17. Multiple Type Parameters

A generic class can take several type parameters, e.g. a key-value pair.

```python
from typing import Generic, TypeVar


K = TypeVar("K")
V = TypeVar("V")


class Pair(Generic[K, V]):
    def __init__(self, key: K, value: V):
        self.key = key
        self.value = value

    def display(self):
        print(f"{self.key}: {self.value}")


pair1 = Pair[str, int]("age", 25)   # K = str, V = int
pair2 = Pair[int, str](101, "Ali")  # K = int, V = str

pair1.display()  # age: 25
pair2.display()  # 101: Ali
```

**Modern syntax (3.12+):**

```python
class Pair[K, V]:
    def __init__(self, key: K, value: V):
        self.key = key
        self.value = value
```

### 18. Bounded Type Variables

A **bounded** TypeVar (`TypeVar("T", bound=SomeType)`) accepts only types compatible with an **upper bound**: the bound itself or its subclasses.

```python
from typing import TypeVar


class Animal:
    def speak(self):
        print("Animal sound")


class Dog(Animal):
    def bark(self):
        print("Bark")


class Cat(Animal):
    def meow(self):
        print("Meow")


T = TypeVar("T", bound=Animal)


def get_animal(animal: T) -> T:
    animal.speak()          # safe: guaranteed by the bound
    return animal


dog = get_animal(Dog())
cat = get_animal(Cat())

dog.bark()   # OK: checker knows dog is a Dog, not just an Animal
cat.meow()
```

```text
Animal sound
Animal sound
Bark
Meow
```

- Valid substitutions for `T`: `Dog`, `Cat`, `Animal`. An unrelated type like `str` → checker error.
- **Why useful:** the function can use operations the bound guarantees (`speak()`), **and** the return keeps the specific subtype (`Dog` in → `Dog` out).

**Modern syntax (3.12+):**

```python
def get_animal[T: Animal](animal: T) -> T:
    animal.speak()
    return animal
```

---

### 19. Constrained Type Variables

A **constrained** TypeVar (`TypeVar("T", str, bytes)`) limits `T` to a **fixed list** of allowed types. All uses of `T` in one call must resolve to the **same** choice.

```python
from typing import TypeVar


T = TypeVar("T", str, bytes)


def combine(a: T, b: T) -> T:
    return a + b


print(combine("Hello", " World"))    # Hello World
print(combine(b"Hello", b" World"))  # b'Hello World'
```

#### Invalid: mixing the constraints

```python
combine("Hello", b"World")
# static checker: rejected
# runtime: TypeError: can only concatenate str (not "bytes") to str
```

| Bound | Constraints |
|---|---|
| `TypeVar("T", bound=Animal)` | `TypeVar("T", str, bytes)` |
| Accepts any subtype of the bound | Picks one of the listed alternatives |
| Preserves the specific subtype | Resolves to exactly one listed constraint |
| An **upper limit** on a hierarchy | A **fixed set** of allowed types |

**Modern syntax (3.12+):**

```python
def combine[T: (str, bytes)](a: T, b: T) -> T:
    return a + b
```

- `[T: Animal]` = bound; `[T: (str, bytes)]` = constraints (note the tuple).

---

### 20. `Union` vs Generics

- **Union** (`int | str`): a value can be **one of several** types. Each position is independent.
- **TypeVar**: **links** several positions to one inferred type.

```python
def display(value: int | str) -> None:
    print(value)


def choose(a: int | str, b: int | str) -> int | str:
    return a


print(choose(10, "Hello"))  # 10
```

- `a` and `b` may have different allowed types; the return is just `int | str` (the checker doesn't know which).

```python
from typing import TypeVar


T = TypeVar("T")


def choose(a: T, b: T) -> T:
    return a
```

- The checker infers one `T` that fits both arguments. If they differ, it may infer a common supertype or a union (mypy and Pyright differ here).

#### Generics keep the specific type

```python
def identity[T](value: T) -> T:     # Dog in -> Dog out
    return value


def identity(value: Animal) -> Animal:   # Dog in -> Animal out (Dog-ness lost)
    return value
```

| Union | TypeVar / Generics |
|---|---|
| Lists **alternatives** | Expresses a **relationship** between positions |
| Positions are independent | Positions share one inferred type |
| Return type stays broad | Return type matches the input |

---

### 21. Generics With Inheritance

Generic classes can be inherited like any class. See [Topic 5: Inheritance](5.%20inheritance.md).

```python
from typing import Generic, TypeVar


T = TypeVar("T")


class Storage(Generic[T]):
    def __init__(self, value: T):
        self.value = value

    def get(self) -> T:
        return self.value


class IntegerStorage(Storage[int]):     # specializes T = int
    def double(self) -> int:
        return self.value * 2


storage = IntegerStorage(50)

print(storage.get())     # 50
print(storage.double())  # 100
```

- Parent is generic (`Storage[T]`); child specializes it (`Storage[int]`), so the inherited `get()` is typed as returning `int`.

A subclass can:

- **keep** the parent's type parameters (`class Child(Storage[T])`),
- **add** new type parameters (`class Child(Storage[T], Generic[T, U])`),
- **specialize** them with concrete types (`class Child(Storage[int])`).

## Part 3: Wildcards and Variance

### 22. What Are Wildcards?

In generic programming, a **wildcard** stands for an **unspecified type argument**. The term comes mostly from **Java**:

```java
List<?>                  // 1. unbounded wildcard
List<? extends Animal>   // 2. upper-bounded wildcard
List<? super Dog>        // 3. lower-bounded wildcard
```

**Python has no `?` wildcards.** These are invalid Python:

```text
list<?>
list<? extends Animal>
list<? super Dog>
```

Python covers similar use cases with:

- `Any` and `object`
- `TypeVar` (with upper bounds)
- `Union`
- **covariance** and **contravariance**
- generic protocols and collection ABCs (`Sequence`, `Iterable`, `Callable`, ...)

These are **not exact one-to-one** replacements for Java wildcards (mapping in Section 30).

---

### 23. Understanding `Any`

**`Any`** (from `typing`) marks a value as **dynamically typed**: the static checker stops checking it.

```python
from typing import Any


def display(value: Any) -> None:
    print(value)


display(10)          # 10
display("Python")    # Python
display([1, 2, 3])   # [1, 2, 3]
```

#### Any operation on `Any` is allowed, even unsafe ones

```python
from typing import Any


def process(value: Any):
    return value.some_method()   # checker: OK


process(5)   # runtime: AttributeError: 'int' object has no attribute 'some_method'
```

- `Any` is an **escape hatch** from static checking.
- It is **not** the same as Java's unbounded wildcard `<?>`.

---

### 24. `Any` vs `object` (interview favorite)

Both can describe a value of **any** runtime type, but the static checker treats them very differently.

```python
from typing import Any


def process_any(value: Any):
    value.some_method()      # checker: allowed, nothing verified


def process_obj(value: object):
    value.some_method()      # checker: ERROR, object has no some_method()
```

**Safe use of `object`: narrow first** with `isinstance()`:

```python
def process(value: object):
    if isinstance(value, str):
        print(value.upper())
    elif isinstance(value, int):
        print(value * 2)


process("hi")  # HI
process(21)    # 42
```

| `Any` | `object` |
|---|---|
| Dynamic-typing escape hatch | Top type: every Python object is an `object` |
| Allows unchecked operations | Requires **narrowing** before type-specific operations |
| Less static safety | More static safety |
| Use at genuinely dynamic boundaries | Use for arbitrary unknown values |

- They are **not interchangeable**. Prefer `object` to accept anything safely; use `Any` only when dynamic behavior is truly needed.

---

### 25. Understanding Variance

**Variance** describes how subtype relationships carry over when types are wrapped in a generic type (`list[...]`, `Sequence[...]`, `Callable[...]`). Three kinds:

1. **Invariance**
2. **Covariance**
3. **Contravariance**

They are the foundation for Java's bounded wildcards and their Python counterparts.

```python
class Animal:
    pass


class Dog(Animal):
    pass


class Cat(Animal):
    pass


dog = Dog()
animal: Animal = dog   # valid: Dog IS-A Animal
```

- Notation: `Dog <: Animal` means "`Dog` is a subtype of `Animal`".
- **Question:** can `list[Dog]` be used where `list[Animal]` is expected? That depends on variance.

---

### 26. Invariance

A generic type is **invariant** when `Dog <: Animal` does **not** make `G[Dog]` a subtype of `G[Animal]` (or the reverse).

- Even though a `Dog` is an `Animal`, **`list[Dog]` is not a `list[Animal]`**.

```python
class Animal:
    pass


class Dog(Animal):
    pass


dogs: list[Dog] = [Dog()]
animals: list[Animal] = dogs   # static checker: ERROR
```

#### Why? It would break the type guarantee

If the assignment were allowed:

```python
animals.append(Animal())   # same underlying list as `dogs`
# `dogs: list[Dog]` now contains a plain Animal -> guarantee violated
```

- **Why `list` is invariant:** lists support both **reading** and **writing** (append/replace). Covariance would be unsafe for mutable containers.
- At **runtime** Python doesn't enforce this; the code runs and mutates the list. The rule lives in the static type system.

```text
Dog <: Animal   does NOT imply   list[Dog] <: list[Animal]
```

---

### 27. Covariance

A generic type is **covariant** if it **preserves** the subtype direction:

```text
Dog <: Animal   implies   ReadOnly[Dog] <: ReadOnly[Animal]
```

**Python example: `Sequence`**

```python
from collections.abc import Sequence


class Animal:
    def speak(self):
        print("Animal")


class Dog(Animal):
    def speak(self):
        print("Woof")


def display_animals(animals: Sequence[Animal]) -> None:
    for animal in animals:
        animal.speak()


dogs: list[Dog] = [Dog(), Dog()]
display_animals(dogs)   # OK statically
```

```text
Woof
Woof
```

- `Sequence[Animal]` is a **read-only interface**: the function can read elements but has no `append()` through it.
- So a sequence of dogs can safely be treated as a sequence of animals **for reading**.
- `Sequence` doesn't mean the object is immutable: a `list` satisfies `Sequence`; the interface just doesn't expose mutation.

```text
Dog <: Animal   implies   Sequence[Dog] <: Sequence[Animal]
```

**Common covariant types:** `Sequence[T]`, `Iterable[T]`, `frozenset[T]`, `tuple[T, ...]`.

---

### 28. Contravariance

**Contravariance** **reverses** the subtype direction:

```text
Dog <: Animal   implies   Consumer[Animal] <: Consumer[Dog]
```

Easiest to see with **callbacks**:

```python
from collections.abc import Callable


class Animal:
    pass


class Dog(Animal):
    pass


def handle_animal(animal: Animal) -> None:
    print("Handling animal")


def process_dog(handler: Callable[[Dog], None]) -> None:
    dog = Dog()
    handler(dog)


process_dog(handle_animal)   # Handling animal
```

- `process_dog()` needs a function that can accept a `Dog`.
- `handle_animal()` accepts **any** `Animal`, and every `Dog` is an `Animal`, so it's safe.
- A handler for all animals can handle dogs; a dog-only handler **can't** handle every animal.

#### Invalid direction

```python
def handle_dog(dog: Dog) -> None:
    print("Handling dog")


def process_animal(handler: Callable[[Animal], None]) -> None:
    handler(Animal())


process_animal(handle_dog)   # static checker: ERROR
```

- `process_animal()` may pass a non-dog `Animal`, which `handle_dog` can't accept.

> **Rule:** function **parameter** types are **contravariant**; function **return** types are **covariant**.

---

### 29. Invariance vs Covariance vs Contravariance

Assume `Dog <: Animal`:

| Variance | Type relationship | Typical example | Typical use |
|---|---|---|---|
| **Invariant** | Neither direction allowed | `list[T]`, `dict[K, V]` | Read **and** write |
| **Covariant** | `G[Dog] <: G[Animal]` | `Sequence[T]`, `Iterable[T]`, return types | Read only (**producer**) |
| **Contravariant** | `G[Animal] <: G[Dog]` | `Callable` parameter types | Write only (**consumer**) |

**Easy way to remember:**

- **Covariance:** a **producer** of dogs works where a producer of animals is expected.
- **Contravariance:** a **consumer** of animals works where a consumer of dogs is expected.
- **Invariance:** a mutable container needs its exact element type preserved.

---

### 30. Java Wildcards vs Python Alternatives

Java has three wildcard forms. Python reaches similar goals through different type-system tools.

#### 30.1 Unbounded Wildcard: `<?>`

```java
List<?>   // a list of some unknown element type
```

Python, when you only need to **read** arbitrary items:

```python
from collections.abc import Sequence


def display(items: Sequence[object]) -> None:
    for item in items:
        print(item)


display([1, 2, 3])
display(["A", "B"])
```

- **Why `Sequence[object]`:** `Sequence` is covariant and read-only, so it accepts sequences of any more specific element type.
- **Alternative:** `list[Any]` works but weakens static checking (permits unsafe operations). Not identical to `<?>`.

```python
from typing import Any


def display(items: list[Any]) -> None:
    ...
```

- **Subtlety:** `list[object]` is **not** a safe replacement for `List<?>`. `list` is invariant, so a `list[int]` won't be accepted as `list[object]`.

#### 30.2 Upper-Bounded Wildcard: `<? extends Animal>`

```java
List<? extends Animal>   // elements are some subtype of Animal
```

Common Python equivalent for **read-only** use:

```python
from collections.abc import Sequence


class Animal:
    pass


class Dog(Animal):
    pass


def display(animals: Sequence[Animal]) -> None:
    for animal in animals:
        print(type(animal).__name__)


dogs: list[Dog] = [Dog(), Dog()]
display(dogs)
```

```text
Dog
Dog
```

- Works because `Sequence` is covariant.

**To preserve the specific subtype, use a bounded TypeVar:**

```python
from collections.abc import Sequence
from typing import TypeVar


TAnimal = TypeVar("TAnimal", bound=Animal)


def get_first_animal(animals: Sequence[TAnimal]) -> TAnimal:
    return animals[0]


dog = get_first_animal([Dog(), Dog()])   # checker infers: Dog
```

| Signature | Use when |
|---|---|
| `Sequence[Animal]` | The function only needs `Animal` behavior |
| `Sequence[TAnimal] -> TAnimal` | The result must keep the specific input subtype |

#### 30.3 Lower-Bounded Wildcard: `<? super Dog>`

```java
List<? super Dog>   // element type is Dog or a supertype of Dog
```

No identical Python syntax. **Contravariant consumers** model the important behavior:

```python
from collections.abc import Callable


class Animal:
    pass


class Dog(Animal):
    pass


def consume_animal(animal: Animal) -> None:
    print("Consumed animal")


def feed_dog(consumer: Callable[[Dog], None]) -> None:
    consumer(Dog())


feed_dog(consume_animal)   # Consumed animal
```

- The consumer accepts `Animal`, so it can safely accept a `Dog`.
- **Limitation:** no direct equivalent for **mutable lists**. Use a consumer abstraction, or design an API exposing only the operations needed.

#### Summary: Java wildcards vs Python

| Java | Meaning | Closest Python | Mechanism |
|---|---|---|---|
| `List<?>` | Unknown element type | `Sequence[object]` (or `list[Any]`, less safe) | Covariant read-only interface |
| `List<? extends Animal>` | Some subtype of `Animal` (producer) | `Sequence[Animal]`, or `Sequence[T]` with `T` bound to `Animal` | Covariance / upper bound |
| `List<? super Dog>` | `Dog` or a supertype (consumer) | `Callable[[Dog], None]`, contravariant `Consumer[Dog]` | Contravariance |
| `<T extends Animal>` (type parameter) | Bounded type parameter | `TypeVar("T", bound=Animal)` / `[T: Animal]` | Upper bound |

### 31. PECS Principle

Java guideline: **PECS = Producer Extends, Consumer Super.** Useful for reasoning about variance in general.

- **Producer** (supplies values; you read from it): a function that only reads animals can accept a producer of dogs.
  - Python: a `Sequence[Dog]` can be passed as `Sequence[Animal]` (covariant).
- **Consumer** (accepts values; you write to it): code that passes dogs to a consumer can safely use a consumer of any animal.
  - Python: a function taking `Animal` can be passed as `Callable[[Dog], None]` (contravariant).

```text
Producer     -> Covariance      (Java: ? extends)
Consumer     -> Contravariance  (Java: ? super)
Read + Write -> Often Invariance
```

- PECS is a **Java mnemonic**, not Python syntax. Use it to reason about type relationships, not as an exact translation.

### 32. Explicit Variance With `TypeVar`

In traditional generic classes, variance is declared on the `TypeVar`. Convention: suffix `_co` (covariant) / `_contra` (contravariant).

#### Covariant type variable

```python
from typing import Generic, TypeVar


T_co = TypeVar("T_co", covariant=True)


class ReadOnlyBox(Generic[T_co]):
    def __init__(self, value: T_co):
        self._value = value

    def get(self) -> T_co:
        return self._value


class Animal:
    pass


class Dog(Animal):
    pass


dog_box: ReadOnlyBox[Dog] = ReadOnlyBox(Dog())
animal_box: ReadOnlyBox[Animal] = dog_box   # valid statically
```

- Valid because the box only **exposes** its value; there's no method to put an arbitrary `Animal` into it.
- Checkers reject a covariant TypeVar as a method **parameter** type (`__init__` is exempt).

#### Contravariant type variable

```python
from typing import Generic, TypeVar


T_contra = TypeVar("T_contra", contravariant=True)


class Consumer(Generic[T_contra]):
    def consume(self, value: T_contra) -> None:
        print("Consumed", type(value).__name__)


class Animal:
    pass


class Dog(Animal):
    pass


animal_consumer: Consumer[Animal] = Consumer()
dog_consumer: Consumer[Dog] = animal_consumer   # valid statically

dog_consumer.consume(Dog())   # Consumed Dog
```

- A consumer of all animals works wherever a consumer of dogs is needed.
- Checkers reject a contravariant TypeVar as a **return** type.

#### Invariant type variable (the default)

```python
from typing import Generic, TypeVar


T = TypeVar("T")


class MutableBox(Generic[T]):
    def __init__(self, value: T):
        self.value = value

    def set(self, value: T) -> None:
        self.value = value

    def get(self) -> T:
        return self.value
```

- A plain `TypeVar("T")` is **invariant by default**. Correct here, because the box both reads and writes.

#### Modern syntax: variance is inferred (Python 3.12+)

```python
class ReadOnlyBox[T]:
    def __init__(self, value: T):
        self._value = value

    def get(self) -> T:
        return self._value
```

- With `class X[T]`, checkers **infer** variance from how `T` is used in the class's exposed API, not from the parameter's name.
- Only returned → covariant; only accepted → contravariant; both (e.g. a public mutable attribute `self.value: T`, or a setter) → invariant.
- Traditional syntax can opt into the same inference with `TypeVar("T", infer_variance=True)` (3.12+).

## Part 4: Interfaces + Generics Together

### 33. Generic Interfaces With Protocols

A **generic Protocol** is a contract parameterized by type: one interface for user storage, product storage, order storage, etc., all supporting the same operations.

```python
from typing import Protocol, TypeVar


T = TypeVar("T")


class Repository(Protocol[T]):
    def add(self, item: T) -> None:
        ...

    def get_all(self) -> list[T]:
        ...
```

- `Repository[User]` = a repository that accepts and returns `User` objects; `Repository[Product]` = one for products.
- `T` appears in an **input** position (`add(item: T)`) and an **output** position (`get_all() -> list[T]`), so this interface is naturally **invariant**.
- Modern syntax (3.12+): `class Repository[T](Protocol): ...`.

---

### 34. Complete Example: Generic Repository Pattern

Combines interfaces, Protocols, generics, encapsulation ([Topic 6](6.%20Encapsulation.md); `_items` is "protected" by convention, see [Topic 8](8.%20access%20modifiers.md)), dependency injection and polymorphism.

```python
from typing import Generic, Protocol, TypeVar


T = TypeVar("T")


# Interface
class Repository(Protocol[T]):
    def add(self, item: T) -> None:
        ...

    def get_all(self) -> list[T]:
        ...


# Generic implementation
class InMemoryRepository(Generic[T]):
    def __init__(self):
        self._items: list[T] = []

    def add(self, item: T) -> None:
        self._items.append(item)

    def get_all(self) -> list[T]:
        return self._items.copy()   # copy: callers can't mutate internal state


# Domain model
class User:
    def __init__(self, name: str):
        self.name = name


# Business logic
def register_user(repository: Repository[User], name: str) -> None:
    user = User(name)
    repository.add(user)


# Usage
user_repo: InMemoryRepository[User] = InMemoryRepository()

register_user(user_repo, "Ali")
register_user(user_repo, "Sara")

for user in user_repo.get_all():
    print(user.name)
```

```text
Ali
Sara
```

```text
                  Repository[T]
                  (Generic Protocol)
                         |
                  +------+------+
                  |             |
                  v             v
           add(item: T)    get_all() -> list[T]
                  |             |
                  +------+------+
                         |
                         v
               InMemoryRepository[T]
                         |
                         v
                    User Objects
                         |
                         v
                    register_user()
```

**How it fits together:**

1. `Repository(Protocol[T])` defines the contract.
2. `InMemoryRepository(Generic[T])` stores values of type `T`.
3. Internal storage uses the same type: `self._items: list[T] = []`.
4. Business logic asks for `repository: Repository[User]`.
5. `InMemoryRepository[User]` satisfies the Protocol **structurally**: no inheritance from `Repository` needed.
6. The implementation is **swappable** without touching business logic:

```python
class DatabaseUserRepository:
    def add(self, item: User) -> None:
        # Save the user to a database.
        ...

    def get_all(self) -> list[User]:
        # Read users from a database.
        ...
```

- A complete database implementation with these methods satisfies `Repository[User]`; `register_user` doesn't change.

> **Key takeaway:** interfaces define **capabilities**, generics preserve **type relationships**. Together: reusable, statically type-safe designs.

## Part 5: Advanced Generics

### 35. Generic Callables

**`Callable[[ArgTypes], ReturnType]`** describes a function's signature as a type.

```python
from collections.abc import Callable


def execute(operation: Callable[[int, int], int], a: int, b: int) -> int:
    return operation(a, b)


def add(a: int, b: int) -> int:
    return a + b


def multiply(a: int, b: int) -> int:
    return a * b


print(execute(add, 5, 3))       # 8
print(execute(multiply, 5, 3))  # 15
```

- `Callable[[int, int], int]` = takes two `int` arguments, returns an `int`.
- General form: `Callable[[ArgumentTypes], ReturnType]`.
- Used for callbacks, higher-order functions and dependency injection.

---

### 36. `ParamSpec`: Preserving Function Signatures (Python 3.10+)

**`ParamSpec`** captures a function's **entire parameter list** so a wrapper (typically a decorator) can keep the original signature.

```python
from collections.abc import Callable
from functools import wraps
from typing import ParamSpec, TypeVar


P = ParamSpec("P")   # the parameters
R = TypeVar("R")     # the return type


def log_call(func: Callable[P, R]) -> Callable[P, R]:
    @wraps(func)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        print("Function called")
        return func(*args, **kwargs)

    return wrapper


@log_call
def add(a: int, b: int) -> int:
    return a + b


print(add(10, 20))
```

```text
Function called
30
```

- `Callable[P, R]` = a callable with parameters `P` returning `R`.
- The decorated `add` keeps its `(a: int, b: int) -> int` signature, so `add("x")` is still a checker error.
- **Without `ParamSpec`**, decorator annotations typically lose argument info (e.g. `Callable[..., Any]`).

**Modern syntax (3.12+):** `**P` declares a ParamSpec.

```python
from collections.abc import Callable
from functools import wraps


def log_call[**P, R](func: Callable[P, R]) -> Callable[P, R]:
    @wraps(func)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        print("Called")
        return func(*args, **kwargs)

    return wrapper
```

### 37. Variadic Generics and `TypeVarTuple` (Python 3.11+)

**`TypeVarTuple`** stands for an **arbitrary number** of types (e.g. every element type of a tuple).

```python
# Python 3.12+ syntax (3.11: Ts = TypeVarTuple("Ts") + T = TypeVar("T"))
def rotate[T, *Ts](values: tuple[T, *Ts]) -> tuple[*Ts, T]:
    return (*values[1:], values[0])


result = rotate((1, "Python", True))
print(result)   # ('Python', True, 1)
```

- `T` = type of the first element; `*Ts` = types of all remaining elements.
- The return annotation says: first element moves to the end. A checker infers `tuple[str, bool, int]` here, preserving every position.
- The `*` in `*Ts` means **variadic type-parameter unpacking**. It is **not** a Java-style wildcard.

### 38. Runtime Behavior of Generics (Internals)

Type arguments exist **for the checker only**. At runtime there is one class, not one per type argument (similar in spirit to Java's **type erasure**).

```python
from typing import Generic, TypeVar


T = TypeVar("T")


class Box(Generic[T]):
    def __init__(self, value: T):
        self.value = value


box = Box[int](100)

print(type(box))             # <class '__main__.Box'>
print(isinstance(box, Box))  # True
```

- The object is just a `Box`. `Box[int]` doesn't create a separate runtime class.

#### Parameterized generics can't be used with `isinstance()`

```python
isinstance(box, Box[int])
# TypeError: Subscripted generics cannot be used with class and instance checks

isinstance([1, 2, 3], list[int])
# TypeError: isinstance() argument 2 cannot be a parameterized generic

isinstance([1, 2, 3], list)   # OK: True
```

- Use the **base** runtime type. To validate elements, check them explicitly or use a runtime validation library (e.g. Pydantic).

```python
def is_integer_list(value: object) -> bool:
    return isinstance(value, list) and all(type(item) is int for item in value)


print(is_integer_list([1, 2, 3]))      # True
print(is_integer_list([1, "two", 3]))  # False
```

- `type(item) is int` (not `isinstance`) rejects `True`/`False`, since `bool` is a subclass of `int`.
- Edge case: an empty list returns `True` (`all([])` is `True`).

### 39. Inspecting Generic Type Annotations

`typing.get_origin()` returns the **underlying generic type**; `typing.get_args()` returns its **type arguments**.

```python
from typing import get_args, get_origin


hint = list[int]
print(get_origin(hint))   # <class 'list'>
print(get_args(hint))     # (<class 'int'>,)

hint = dict[str, int]
print(get_origin(hint))   # <class 'dict'>
print(get_args(hint))     # (<class 'str'>, <class 'int'>)
```

**Used in:** framework development, serialization, validation systems, dependency-injection libraries, any runtime inspection of annotations.

## Common Mistakes / Gotchas

- **Assuming Python has an `interface` keyword** (`interface Payment: ...`) → `SyntaxError`. Use ABCs, Protocols or duck typing.
- **Assuming an ABC validates everything** → it only checks that abstract methods are overridden, not signatures or behavior.
- **Assuming Protocols require inheritance** → they are structural; any class with matching members satisfies them.
- **Calling `isinstance()` with a plain Protocol** → `TypeError`. Add `@runtime_checkable`, and remember it only checks that members exist.
- **Assuming generics enforce runtime types** → they don't:

```python
box = Box[int](100)
box.value = "Hello"   # runs fine; only a static checker complains
```

- **Confusing `Any` with `object`** → `Any` switches checking off; `object` keeps it on and forces narrowing before type-specific operations.
- **Assuming `list[Dog]` is a `list[Animal]`** → `list` is invariant. Accept `Sequence[Animal]` if you only read.
- **Assuming `Sequence` means immutable data** → it's a read-only *interface*; the underlying object may still be mutated through other references.
- **Using `list[object]` as Java's `List<?>`** → rejected for `list[int]` (invariance). Use `Sequence[object]`.
- **Writing Java wildcards in Python** (`?`, `? extends`, `? super`) → not valid. Use TypeVars, bounds, variance and `Sequence`/`Callable`.
- **Treating a TypeVar bound as a runtime validator** → `T = TypeVar("T", bound=Animal)` is a static constraint only; no automatic `isinstance()` check happens.
- **`isinstance(x, list[int])` or `isinstance(box, Box[int])`** → `TypeError`. Check the base type (`list`, `Box`) and validate elements yourself.
- **Confusing generic wildcards with file-pattern wildcards** → unrelated features:

```python
from glob import glob


files = glob("*.py")
# *     matches any sequence of characters
# ?     matches exactly one character
# [abc] matches one of the listed characters
```

- Likewise `from module import *` is a **wildcard import**, not generics.

## Interview Questions

### Interfaces

**Q1. What is an interface?**
A contract specifying the operations an object must support, without dictating how they're implemented.

**Q2. Does Python support interfaces?**
Conceptually, yes: through ABCs, Protocols and duck typing. There is no dedicated `interface` keyword.

**Q3. Difference between an interface and an abstract class?**
An interface describes required behavior. An abstract class can also provide shared implementation and state. Python ABCs can serve either role.

**Q4. Difference between ABC and Protocol?**
ABCs use explicit (nominal) inheritance and enforce abstract methods at instantiation. Protocols use structural static typing; no inheritance needed.

**Q5. What is duck typing?**
Using an object based on the operations it supports, not on the class it inherits from.

**Q6. Can a class implement multiple interfaces?**
Yes. It can satisfy several Protocols structurally, or inherit from multiple ABCs.

**Q7. What is structural typing?**
Compatibility decided by the attributes and methods a type provides, not by its inheritance.

**Q8. Can an interface contain implemented methods?**
In Python, yes: ABCs can have concrete methods, and Protocols can define default methods (though their main role is describing a structural contract).

**Q9. How do interfaces support polymorphism?**
Different implementations expose the same operations, so clients can use any of them through the common interface.

### Generics

**Q10. What are generics?**
Reusable classes, functions and interfaces that express type relationships through **type parameters**.

**Q11. What is `TypeVar`?**
A declaration of a type variable used to link types across annotations (e.g. input type = return type).

**Q12. What is `Generic[T]`?**
The base used to declare a user-defined generic class parameterized by `T` (pre-3.12 syntax; 3.12+ uses `class Box[T]`).

**Q13. Difference between `Any` and `TypeVar`?**
`Any` permits unchecked, dynamically typed operations. `TypeVar` preserves relationships between types and keeps checking on.

**Q14. What is a bounded TypeVar?**
A TypeVar restricted to types compatible with an upper bound, e.g. `T = TypeVar("T", bound=Animal)`.

**Q15. What are constrained TypeVars?**
TypeVars restricted to a fixed set of alternatives, e.g. `T = TypeVar("T", str, bytes)`.

**Q16. Are Python generics enforced at runtime?**
Generally no. They are used by static type checkers; `Box[int]` is still just a `Box` at runtime.

**Q17. Difference between `Union` and `TypeVar`?**
A union lists alternative types. A TypeVar is a reusable type parameter that ties multiple occurrences to the same type.

**Q18. What is `ParamSpec`?**
It captures a callable's parameter signature for generic typing, mainly so decorators preserve the wrapped function's signature.

**Q19. What is `TypeVarTuple`?**
A variable-length sequence of type parameters, used for **variadic generics** (e.g. typing every element of a tuple).

### Wildcards and Variance

**Q20. What is covariance?**
The generic type preserves subtyping: `Dog <: Animal` → `Sequence[Dog] <: Sequence[Animal]`.

**Q21. What is contravariance?**
The generic type reverses subtyping: `Dog <: Animal` → `Consumer[Animal] <: Consumer[Dog]`.

**Q22. What is invariance?**
Neither specialization is a subtype of the other: `list[Dog]` is not a subtype of `list[Animal]`.

**Q23. Why is `list` invariant?**
It supports reading **and** mutation. Covariance would allow inserting a broader type (e.g. a `Cat`) into a list of dogs.

**Q24. Why is `Sequence` covariant?**
Its interface only reads elements; it has no method to add arbitrary new ones.

**Q25. What does PECS stand for?**
Producer Extends, Consumer Super: a Java mnemonic for covariant producers and contravariant consumers.

**Q26. Does Python have Java's wildcard syntax?**
No. Python uses TypeVars, bounds, `Any`, `object`, Protocols and variance to express related ideas.

**Q27. Can we check `isinstance(value, list[int])`?**
No, it raises `TypeError`. Check the base type (`list`) and validate elements separately.

## Practice Questions

**1. Notification interface.** Create a `Notification` protocol with `send(message: str) -> None`. Implement `EmailNotification`, `SMSNotification` and `PushNotification`, and write one function that accepts any compatible implementation.

<details><summary>Answer</summary>

```python
from typing import Protocol


class Notification(Protocol):
    def send(self, message: str) -> None:
        ...


class EmailNotification:
    def send(self, message: str) -> None:
        print(f"Email: {message}")


class SMSNotification:
    def send(self, message: str) -> None:
        print(f"SMS: {message}")


class PushNotification:
    def send(self, message: str) -> None:
        print(f"Push: {message}")


def notify(service: Notification, message: str) -> None:
    service.send(message)


notify(EmailNotification(), "Hello")
notify(SMSNotification(), "Hello")
notify(PushNotification(), "Hello")
```

```text
Email: Hello
SMS: Hello
Push: Hello
```

- None of the classes inherits from `Notification`; they satisfy it structurally.

</details>

**2. Generic stack.** Implement a generic `Stack` with `push()`, `pop()`, `peek()` and `is_empty()`, reusable for any element type.

<details><summary>Answer</summary>

```python
from typing import Generic, TypeVar


T = TypeVar("T")


class Stack(Generic[T]):
    def __init__(self):
        self._items: list[T] = []

    def push(self, item: T) -> None:
        self._items.append(item)

    def pop(self) -> T:
        if not self._items:
            raise IndexError("Stack is empty")
        return self._items.pop()

    def peek(self) -> T:
        if not self._items:
            raise IndexError("Stack is empty")
        return self._items[-1]

    def is_empty(self) -> bool:
        return len(self._items) == 0


stack: Stack[int] = Stack()

stack.push(10)
stack.push(20)
stack.push(30)

print(stack.peek())      # 30
print(stack.pop())       # 30
print(stack.pop())       # 20
print(stack.is_empty())  # False
```

- **Why generics help:** the same class serves as `Stack[int]`, `Stack[str]`, `Stack[User]`, and the checker tracks each stack's element type.

</details>

**3. Covariance and invariance.** Which assignments are statically valid?

```python
from collections.abc import Sequence


class Animal:
    pass


class Dog(Animal):
    pass


dogs: list[Dog] = [Dog()]

a: list[Animal] = dogs
b: Sequence[Animal] = dogs
c: Sequence[Dog] = dogs
```

<details><summary>Answer</summary>

- `a: list[Animal] = dogs` → **invalid**: `list` is invariant.
- `b: Sequence[Animal] = dogs` → **valid**: `Sequence` is covariant.
- `c: Sequence[Dog] = dogs` → **valid**: a list of dogs satisfies the sequence-of-dogs interface.

</details>

## Quick Recap

### Interfaces

| Concept | Meaning |
|---|---|
| **Interface** | Contract defining required capabilities (WHAT, not HOW) |
| **ABC** + `@abstractmethod` | Explicit, nominal contract; enforced at instantiation |
| **Duck typing** | Compatibility based on usable behavior; fails only at runtime |
| **Protocol** | Structural typing contract; checked statically |
| `@runtime_checkable` | Limited runtime `isinstance()` check (member names only) |
| **Nominal typing** | Compatibility through inheritance |
| **Structural typing** | Compatibility through attributes/methods |
| **Dependency injection** | Supplying dependencies from outside |
| **DIP / ISP** | Depend on abstractions / keep interfaces small |

### Generics

| Concept | Python syntax |
|---|---|
| Generic list / dict | `list[T]`, `dict[K, V]` |
| Type variable (traditional) | `T = TypeVar("T")` |
| Generic class (traditional) | `class Box(Generic[T]):` |
| Generic class (3.12+) | `class Box[T]:` |
| Generic function (3.12+) | `def identity[T](x: T) -> T:` |
| Bounded TypeVar | `TypeVar("T", bound=Animal)` / `[T: Animal]` |
| Constrained TypeVar | `TypeVar("T", str, bytes)` / `[T: (str, bytes)]` |
| Union | `int \| str` |
| Arbitrary dynamic type (unchecked) | `Any` |
| General object type (checked) | `object` |
| Generic callable | `Callable[[int], str]` |
| Parameter specification | `ParamSpec` / `[**P]` |
| Variadic type parameters | `TypeVarTuple` / `[*Ts]` |
| Runtime introspection | `get_origin()`, `get_args()` |

### Wildcards and Variance

| Concept | Meaning | Python example |
|---|---|---|
| **Invariance** | Subtype relationship not preserved | `list[T]` |
| **Covariance** | Subtype relationship preserved | `Sequence[T]` |
| **Contravariance** | Subtype relationship reversed | `Callable` arguments |
| Upper bound | Restricts `T` to a type hierarchy | `TypeVar("T", bound=Animal)` |
| Unbounded values (read) | Arbitrary element types | `Sequence[object]` |
| Java `? extends` | Covariant producer | `Sequence[Animal]` |
| Java `? super` | Contravariant consumer | `Callable[[Dog], None]` |

```text
Invariance:      list[Dog]        is NOT a subtype of list[Animal]
Covariance:      Sequence[Dog]    is a subtype of     Sequence[Animal]
Contravariance:  Consumer[Animal] is a subtype of     Consumer[Dog]
```

### Key takeaways

1. **Interfaces define expected capabilities**, so code works with any implementation (ABC, Protocol or duck typing).
2. **Generics preserve type information**: reusable functions, classes and interfaces without losing static checking. Not enforced at runtime.
3. **Variance decides how generic types relate** under inheritance: mutable → invariant, read-only producer → covariant, consumer → contravariant.

### One-line interview definitions

- **Interface:** a behavioral contract that multiple implementations can satisfy.
- **Generics:** type-parameterized classes, functions and interfaces that preserve relationships between types.
- **Wildcards:** a Java-style feature for unknown or bounded type arguments; Python expresses the same relationships with TypeVars, variance and suitable generic interfaces.

> **Core idea:** interfaces say *what* an object can do, generics keep track of *which type* flows through, and variance says *when one generic type can stand in for another*.
