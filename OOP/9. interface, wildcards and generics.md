# PART 1: INTERFACES

## 1. What Is an Interface?

An **interface is a contract that specifies what operations an object must support without requiring a particular implementation of those operations.**

In simple words:

> An interface defines WHAT an object must do, while the implementing class decides HOW it does it.

### Real-World Example: Charging Port

Imagine different mobile phones:

- Samsung
- Google Pixel
- OnePlus

Different manufacturers implement their internal charging systems differently.

However, phones supporting a compatible USB-C charging interface can interact with compatible chargers through a standard connection.

The interface defines the expected interaction.

The internal implementation can differ.

### Software Example

Suppose we are developing a payment system.

We have:

- Credit card payments
- UPI payments
- PayPal payments

Each payment method processes transactions differently.

However, the application expects every payment provider to support:

```python
pay(amount)
```

This common operation acts as an interface.

### Conceptual Structure

```text
               Payment Interface
                      |
                 pay(amount)
                      |
         +------------+------------+
         |            |            |
         v            v            v
    CreditCard       UPI         PayPal
         |            |            |
         v            v            v
    Card Logic     UPI Logic    PayPal Logic
```

The application can use a common operation without knowing the provider's internal processing details.

---

## 2. Why Do We Need Interfaces?

Consider an application without a common interface.

```python
class CreditCard:
    def process_card(self, amount):
        print(f"Credit card payment: {amount}")


class UPI:
    def transfer_upi(self, amount):
        print(f"UPI payment: {amount}")


class PayPal:
    def send_money(self, amount):
        print(f"PayPal payment: {amount}")
```

Now our checkout logic needs to understand every implementation.

```python
def checkout(payment_method, amount):

    if isinstance(payment_method, CreditCard):
        payment_method.process_card(amount)

    elif isinstance(payment_method, UPI):
        payment_method.transfer_upi(amount)

    elif isinstance(payment_method, PayPal):
        payment_method.send_money(amount)
```

### Problems

1. Every payment provider has a different method name.
2. Checkout logic depends on concrete classes.
3. Adding new payment methods requires modifying checkout logic.
4. Testing requires dealing with specific implementations.
5. The application becomes tightly coupled.

### Better Design

Every implementation provides:

```python
pay(amount)
```

Now checkout becomes:

```python
def checkout(payment_method, amount):
    payment_method.pay(amount)
```

The checkout function only depends on the expected behavior.

### Main Benefits

| Benefit | Explanation |
|---|---|
| Loose coupling | Code depends on a common contract |
| Flexibility | Implementations can be replaced |
| Extensibility | New implementations can be introduced |
| Polymorphism | Different objects respond to the same operation |
| Testability | Fake implementations can replace real services |
| Maintainability | Implementations can change independently |

## 3. Does Python Have an `interface` Keyword?

**No. Python does not have a dedicated `interface` keyword like Java.**

Instead, Python supports interface-like design through:

1. Abstract Base Classes (ABCs)
2. Duck typing
3. Protocols

These approaches provide different levels of explicitness and enforcement.

---

# 4. Interfaces Using Abstract Base Classes

An Abstract Base Class can define an explicit contract for subclasses.

Python provides:

```python
from abc import ABC, abstractmethod
```

### Example

```python
from abc import ABC, abstractmethod


class PaymentProcessor(ABC):

    @abstractmethod
    def pay(self, amount):
        pass


class CreditCardPayment(PaymentProcessor):

    def pay(self, amount):
        print(f"Paid {amount} using Credit Card")


class UPIPayment(PaymentProcessor):

    def pay(self, amount):
        print(f"Paid {amount} using UPI")


def checkout(processor, amount):
    processor.pay(amount)


card = CreditCardPayment()
upi = UPIPayment()

checkout(card, 1000)
checkout(upi, 2000)
```

### Output

```text
Paid 1000 using Credit Card
Paid 2000 using UPI
```

### Step-by-Step Explanation

**Step 1: Define the contract.**

```python
class PaymentProcessor(ABC):

    @abstractmethod
    def pay(self, amount):
        pass
```

The base class declares that concrete implementations must provide `pay()`.

**Step 2: Implement the interface.**

```python
class CreditCardPayment(PaymentProcessor):
```

The concrete class inherits the abstract contract.

**Step 3: Implement the required method.**

```python
def pay(self, amount):
    print(...)
```

This resolves the abstract requirement.

**Step 4: Use the interface.**

```python
checkout(card, 1000)
```

The checkout function does not need provider-specific conditional logic.

### What If We Don't Implement `pay()`?

```python
class CashPayment(PaymentProcessor):
    pass


cash = CashPayment()
```

### Result

```text
TypeError: Can't instantiate abstract class CashPayment
```

Python prevents instantiation because an abstract method remains unresolved.

### Important Limitation

ABCs check whether abstract requirements have been resolved.

They do not fully verify:

- Correct method signatures
- Correct return types
- Correct business logic

Static type checkers and tests help verify these aspects.

# 5. Interface vs Abstract Class

This is a very common interview question.

## Interface

An interface describes the operations that implementing objects are expected to support.

## Abstract Class

An abstract class can establish required operations and share reusable functionality or state.

### Python-Specific Detail

Python doesn't enforce a strict language-level separation between interfaces and abstract classes.

An ABC can serve as an interface.

However, it can also contain implemented methods and state.

### Example

```python
from abc import ABC, abstractmethod


class Vehicle(ABC):

    def __init__(self, brand):
        self.brand = brand

    @abstractmethod
    def start(self):
        pass

    def display_brand(self):
        print(self.brand)
```

This class provides:

- An abstract method
- A constructor
- An instance attribute
- A concrete method

Therefore, it acts as an abstract base class with shared behavior.

### Comparison

| Conceptual Interface | Abstract Base Class |
|---|---|
| Primarily defines a contract | Defines a contract and possibly shared behavior |
| Focuses on capabilities | May represent a shared class hierarchy |
| Can use `Protocol` in Python | Typically uses `ABC` |
| Implementations may be unrelated | Implementations often share ancestry |
| Structural typing possible | Nominal inheritance commonly used |

**Important:** Python's ABC system is flexible enough to support interface-style design.

# 6. Duck Typing as an Interface

Python is dynamically typed.

This allows objects to be used based on their supported behavior rather than their inheritance relationships.

This is called **duck typing**.

### Definition

> If an object supports the operations required by the caller, it can be used regardless of its concrete class.

### Example

```python
class EmailService:

    def send(self, message):
        print(f"Email: {message}")


class SMSService:

    def send(self, message):
        print(f"SMS: {message}")


class PushService:

    def send(self, message):
        print(f"Push: {message}")


def notify(service, message):
    service.send(message)


notify(EmailService(), "Hello")
notify(SMSService(), "Hello")
notify(PushService(), "Hello")
```

### Output

```text
Email: Hello
SMS: Hello
Push: Hello
```

### What's Interesting?

There is:

- No common parent class
- No ABC
- No explicit interface declaration

But all objects provide:

```python
send(message)
```

The function only cares about the required operation.

### Limitation

Consider:

```python
class BrokenService:
    pass


notify(BrokenService(), "Hello")
```

This raises an `AttributeError` at runtime.

Duck typing provides flexibility, but the missing method is not necessarily detected before execution.

### When Is Duck Typing Useful?

- Small applications
- Flexible APIs
- Simple interchangeable objects
- Python libraries using behavioral conventions

# 7. Protocols: Modern Python Interfaces

Python provides `Protocol` through the `typing` module.

A Protocol formally describes the methods or attributes an object must provide.

It supports **structural typing**.

### What Is Structural Typing?

Structural typing checks whether a type has the required structure, rather than requiring inheritance from a particular class.

### Example

```python
from typing import Protocol


class NotificationService(Protocol):

    def send(self, message: str) -> None:
        ...


class Email:

    def send(self, message: str) -> None:
        print(f"Email: {message}")


class SMS:

    def send(self, message: str) -> None:
        print(f"SMS: {message}")


def notify(
    service: NotificationService,
    message: str
) -> None:

    service.send(message)


notify(Email(), "Welcome")
notify(SMS(), "Welcome")
```

### Output

```text
Email: Welcome
SMS: Welcome
```

### Key Observation

Neither `Email` nor `SMS` explicitly inherits from `NotificationService`.

Yet both satisfy the protocol structurally.

### Why?

The protocol requires:

```python
def send(self, message: str) -> None:
```

Both classes provide a compatible implementation.

Static type checkers such as mypy and Pyright can verify this.

### Important

Python does not automatically enforce ordinary type annotations during runtime.

Protocols are primarily a static typing mechanism.

---

# 8. `@runtime_checkable` Protocols

By default, protocols are intended for static type checking.

If we want limited runtime structural checks, Python provides:

```python
@runtime_checkable
```

### Example

```python
from typing import Protocol, runtime_checkable


@runtime_checkable
class Printable(Protocol):

    def print_data(self) -> None:
        ...


class Document:

    def print_data(self) -> None:
        print("Printing document")


class Image:

    def display(self) -> None:
        print("Displaying image")


doc = Document()
img = Image()

print(isinstance(doc, Printable))
print(isinstance(img, Printable))
```

### Output

```text
True
False
```

### Important Limitation

Runtime protocol checks primarily verify that required members exist.

They do not fully validate method signatures, annotations, or semantics.

For example:

```python
class BadPrinter:

    def print_data(self, value):
        print(value)
```

`isinstance(BadPrinter(), Printable)` can return `True` even though calling `print_data()` without an argument would fail.

### Key Point

Use static type checkers for more complete compatibility checking.

Don't treat runtime-checkable protocols as complete validation systems.

# 9. ABC vs Protocol vs Duck Typing

| Feature | ABC | Protocol | Duck Typing |
|---|---|---|---|
| Explicit contract | Yes | Yes | Implicit |
| Requires inheritance | Usually | No | No |
| Static type checking | Supported | Supported | Possible with annotations |
| Runtime abstract enforcement | Yes | No | No |
| Structural compatibility | Not by default | Yes | Yes, through behavior |
| Shared implementation | Yes | Limited/default methods possible | Not required |
| Best suited for | Formal class hierarchies | Flexible typed interfaces | Simple flexible APIs |

### Which Should You Use?

**Use ABC when:**

- You control a related class hierarchy.
- You want abstract-method enforcement.
- You want to share implementations.

**Use Protocol when:**

- Classes may be unrelated.
- You want static type safety.
- You want to depend on capabilities instead of ancestry.

**Use duck typing when:**

- The expected behavior is simple.
- Formal type declarations would add unnecessary complexity.

# 10. Interfaces and the SOLID Principles

Interfaces are closely associated with two important SOLID principles.

## Dependency Inversion Principle (DIP)

High-level application components should depend on abstractions instead of depending directly on implementation details.

### Tightly Coupled Example

```python
class EmailService:

    def send(self, message):
        print(f"Email: {message}")


class UserManager:

    def __init__(self):
        self.email_service = EmailService()

    def register(self):
        self.email_service.send("Welcome!")
```

`UserManager` directly creates and depends on `EmailService`.

Replacing email with another notification mechanism requires changing the manager.

### Better Design Using a Protocol

```python
from typing import Protocol


class Notifier(Protocol):

    def send(self, message: str) -> None:
        ...


class EmailService:

    def send(self, message: str) -> None:
        print(f"Email: {message}")


class SMSService:

    def send(self, message: str) -> None:
        print(f"SMS: {message}")


class UserManager:

    def __init__(self, notifier: Notifier):
        self.notifier = notifier

    def register(self):
        self.notifier.send("Welcome!")


email_manager = UserManager(EmailService())
sms_manager = UserManager(SMSService())

email_manager.register()
sms_manager.register()
```

### Output

```text
Email: Welcome!
SMS: Welcome!
```

### Why Is This Better?

`UserManager` depends on the `Notifier` contract.

It does not need to know whether notifications are sent by email or SMS.

This also makes testing easier because we can inject a fake notifier.

## Interface Segregation Principle (ISP)

Clients should not be forced to depend on operations they do not need.

### Poor Design

```python
class Machine(Protocol):

    def print_document(self) -> None:
        ...

    def scan_document(self) -> None:
        ...

    def fax_document(self) -> None:
        ...
```

A basic printer might only support printing.

Requiring it to support scanning and faxing creates an unnecessarily large contract.

### Better Design

```python
from typing import Protocol


class Printer(Protocol):

    def print_document(self) -> None:
        ...


class Scanner(Protocol):

    def scan_document(self) -> None:
        ...


class SimplePrinter:

    def print_document(self) -> None:
        print("Printing")
```

Now `SimplePrinter` only needs to satisfy the `Printer` interface.

### Key Takeaway

Prefer small, focused interfaces that describe meaningful capabilities.

# PART 2: GENERICS

## 11. What Are Generics?

**Generics allow classes, functions, and other type definitions to work with multiple types while preserving relationships between those types.**

In simple terms:

> Generics allow us to write reusable code without losing type information.

### Example Without Generics

```python
def get_first(items):
    return items[0]


print(get_first([10, 20, 30]))
print(get_first(["Python", "Java"]))
```

### Output

```text
10
Python
```

This function already works with different types because Python is dynamically typed.

So why do we need generics?

Because static type checking needs to understand:

- What type of data enters a function?
- What type of data comes out?
- Which types must remain consistent?
- Which operations are safe?

Generics allow us to express these relationships.

---

# 12. Type Hints Before Generics

Python provides type annotations.

### Example

```python
def add(a: int, b: int) -> int:
    return a + b
```

This tells developers and type checkers:

- `a` should be an integer.
- `b` should be an integer.
- The result should be an integer.

### Collection Type Hints

```python
numbers: list[int] = [1, 2, 3]

names: list[str] = ["Ali", "Sara"]

scores: dict[str, int] = {
    "Ali": 90,
    "Sara": 95
}
```

### Generic Collections

| Type | Meaning |
|---|---|
| `list[int]` | List of integers |
| `list[str]` | List of strings |
| `dict[str, int]` | Dictionary with string keys and integer values |
| `set[str]` | Set of strings |
| `tuple[int, str]` | Fixed-length tuple with int and str |
| `tuple[int, ...]` | Variable-length tuple of integers |

### Important

Type hints are generally not enforced at runtime.

```python
numbers: list[int] = [1, 2, 3]

numbers.append("Hello")
```

This can execute successfully.

However, a static type checker should report a type error.

**Generics provide static type safety, not automatic runtime validation.**

---

# 13. Generic Functions Using `TypeVar`

Python provides `TypeVar` for declaring type variables.

### Syntax

```python
from typing import TypeVar

T = TypeVar("T")
```

`T` represents a type that will be determined from usage.

### Example

```python
from typing import TypeVar
from collections.abc import Sequence


T = TypeVar("T")


def get_first(items: Sequence[T]) -> T:
    return items[0]


print(get_first([10, 20, 30]))

print(get_first(["Python", "Java"]))
```

### Output

```text
10
Python
```

### Explanation

The function is defined as:

```python
def get_first(items: Sequence[T]) -> T:
```

The type variable `T` connects the type of the input elements to the return type.

When given integers:

```python
get_first([10, 20])
```

A type checker infers the result as `int`.

When given strings:

```python
get_first(["Python", "Java"])
```

A type checker infers the result as `str`.

### Why Not Just Use `object`?

Consider:

```python
def get_first(items: list[object]) -> object:
    return items[0]
```

The return type is always described as `object`.

This loses information about the original element type.

Generics preserve that relationship.

### Important Concept

`TypeVar` does not mean that `T` is a new runtime data type.

It represents a type parameter for static analysis.

# 14. Modern Generic Function Syntax (Python 3.12+)

Python 3.12 introduced a cleaner syntax.

Instead of:

```python
from typing import TypeVar

T = TypeVar("T")


def identity(value: T) -> T:
    return value
```

We can write:

```python
def identity[T](value: T) -> T:
    return value


print(identity(100))
print(identity("Python"))
```

### Output

```text
100
Python
```

### Explanation

The type parameter is declared directly:

```python
def identity[T](...)
```

This makes the generic relationship more visible.

Both approaches are valid.

### Compatibility

| Syntax | Minimum Python Version |
|---|---|
| `TypeVar("T")` | Older Python versions |
| `def function[T](...)` | Python 3.12 |
| `class Box[T]:` | Python 3.12 |
| Built-in `list[int]` annotations | Python 3.9 |
| `int \| str` union syntax | Python 3.10 |

For compatibility with older projects, the traditional `TypeVar` approach remains useful.

# 15. Generic Classes

Generics are especially useful when creating reusable data structures.

Imagine a box that stores a value.

The value could be:

- Integer
- String
- Employee
- Product
- User object

Instead of creating separate classes, we can create one generic class.

### Example

```python
from typing import Generic, TypeVar


T = TypeVar("T")


class Box(Generic[T]):

    def __init__(self, value: T):
        self.value = value

    def get(self) -> T:
        return self.value

    def set(self, value: T) -> None:
        self.value = value


int_box = Box[int](100)

str_box = Box[str]("Python")

print(int_box.get())
print(str_box.get())
```

### Output

```text
100
Python
```

### Step-by-Step Explanation

**1. Declare a type variable.**

```python
T = TypeVar("T")
```

**2. Define a generic class.**

```python
class Box(Generic[T]):
```

**3. Use the type variable consistently.**

```python
def __init__(self, value: T):
```

```python
def get(self) -> T:
```

```python
def set(self, value: T) -> None:
```

**4. Specialize the class.**

```python
Box[int]
```

This describes a box intended to contain integers.

Similarly:

```python
Box[str]
```

describes a box intended to contain strings.

### What If We Store the Wrong Type?

```python
int_box = Box[int](100)

int_box.set("Hello")
```

A static type checker should flag the assignment as incompatible.

Python's runtime ordinarily permits it.

### Important

Generics in Python do not automatically reject incorrect values during runtime.

---

# 16. Modern Generic Class Syntax (Python 3.12+)

The previous example can be simplified.

```python
class Box[T]:

    def __init__(self, value: T):
        self.value = value

    def get(self) -> T:
        return self.value

    def set(self, value: T) -> None:
        self.value = value


box = Box[int](100)

print(box.get())
```

### Output

```text
100
```

### Difference

Older syntax:

```python
class Box(Generic[T]):
```

Modern syntax:

```python
class Box[T]:
```

The modern form implicitly creates the generic type parameter.

# 17. Generics With Multiple Type Parameters

A class can have multiple type parameters.

### Example: Key-Value Pair

```python
from typing import Generic, TypeVar


K = TypeVar("K")
V = TypeVar("V")


class Pair(Generic[K, V]):

    def __init__(self, key: K, value: V):
        self.key = key
        self.value = value

    def display(self):
        print(f"{self.key}: {self.value}")


pair1 = Pair[str, int]("age", 25)

pair2 = Pair[int, str](101, "Ali")

pair1.display()
pair2.display()
```

### Output

```text
age: 25
101: Ali
```

### Explanation

```python
Pair[str, int]
```

means:

- `K = str`
- `V = int`

Similarly:

```python
Pair[int, str]
```

means:

- `K = int`
- `V = str`

### Modern Syntax

Python 3.12+:

```python
class Pair[K, V]:

    def __init__(self, key: K, value: V):
        self.key = key
        self.value = value
```

# 18. Bounded Type Variables

Sometimes we want a generic type variable to accept only types satisfying a particular upper bound.

For this, Python provides:

```python
TypeVar("T", bound=SomeType)
```

### Example

```python
from typing import TypeVar


class Animal:

    def speak(self):
        print("Animal sound")


class Dog(Animal):

    def bark(self):
        print("Bark")


class Cat(Animal):

    def meow(self):
        print("Meow")


T = TypeVar("T", bound=Animal)


def get_animal(animal: T) -> T:
    animal.speak()
    return animal


dog = get_animal(Dog())
cat = get_animal(Cat())

dog.bark()
cat.meow()
```

### Output

```text
Animal sound
Animal sound
Bark
Meow
```

### Explanation

The bound:

```python
T = TypeVar("T", bound=Animal)
```

means a type substituted for `T` must be compatible with `Animal`.

Valid examples:

```python
Dog
Cat
Animal
```

For an unrelated type such as `str`, the type checker should report an error.

### Why Is This Useful?

The generic function can safely use operations guaranteed by the bound.

```python
animal.speak()
```

And it preserves the more specific return type.

If the input is a `Dog`, the return type is inferred as `Dog`.

### Modern Syntax

Python 3.12+:

```python
def get_animal[T: Animal](animal: T) -> T:
    animal.speak()
    return animal
```

# 19. Constrained Type Variables

A constrained TypeVar limits a type parameter to a particular set of allowed types.

### Example

```python
from typing import TypeVar


T = TypeVar("T", str, bytes)


def combine(a: T, b: T) -> T:
    return a + b


print(combine("Hello", " World"))

print(combine(b"Hello", b" World"))
```

### Output

```text
Hello World
b'Hello World'
```

### Why Does This Work?

The allowed types are:

```python
str
bytes
```

Both arguments must satisfy the same constrained type choice.

### Invalid Usage

```python
combine("Hello", b"World")
```

A static type checker should reject this combination.

Calling it at runtime raises a `TypeError` because Python does not allow adding `str` and `bytes`.

### Bound vs Constraints

| Bound | Constraints |
|---|---|
| `TypeVar("T", bound=Animal)` | `TypeVar("T", str, bytes)` |
| Accepts subtypes compatible with bound | Selects among specified alternatives |
| Preserves specific subtype relationships | Often resolves to one listed constraint |
| Represents an upper type limit | Represents a fixed set of allowed alternatives |

### Modern Constrained Syntax

Python 3.12+:

```python
def combine[T: (str, bytes)](a: T, b: T) -> T:
    return a + b
```

# 20. `Union` vs Generics

This is an important distinction.

## Union

A union means a value can belong to one of several types.

```python
def display(value: int | str) -> None:
    print(value)
```

This accepts integers and strings.

### Example

```python
def choose(
    a: int | str,
    b: int | str
) -> int | str:

    return a


print(choose(10, "Hello"))
```

The two arguments can have different allowed types.

## TypeVar

A TypeVar expresses a relationship between types.

```python
from typing import TypeVar


T = TypeVar("T")


def choose(a: T, b: T) -> T:
    return a
```

A checker infers a type for `T` that accommodates the arguments.

It may infer a common supertype or union when the two arguments differ.

### Key Difference

A union specifies alternatives.

A TypeVar links multiple positions in a function or class to an inferred type parameter.

### Example of Stronger Generic Relationship

```python
def identity[T](value: T) -> T:
    return value
```

If `value` is a `Dog`, the returned type remains `Dog`.

Using:

```python
def identity(value: Animal) -> Animal:
    return value
```

would lose the more specific `Dog` return type in static analysis.

# 21. Generics With Inheritance

Generic classes can participate in inheritance.

### Example

```python
from typing import Generic, TypeVar


T = TypeVar("T")


class Storage(Generic[T]):

    def __init__(self, value: T):
        self.value = value

    def get(self) -> T:
        return self.value


class IntegerStorage(Storage[int]):

    def double(self) -> int:
        return self.value * 2


storage = IntegerStorage(50)

print(storage.get())
print(storage.double())
```

### Output

```text
50
100
```

### Explanation

The parent is generic:

```python
Storage[T]
```

The child specializes it:

```python
Storage[int]
```

Therefore, the inherited `get()` method is typed as returning `int`.

### Key Point

A subclass can:

- Preserve its parent's type parameters.
- Introduce additional type parameters.
- Specialize the parent's type parameters with concrete types.

# PART 3: WILDCARDS AND VARIANCE

## 22. What Are Wildcards?

In generic programming, a wildcard generally represents an unspecified type argument.

The term is especially common in Java.

For example, Java uses:

```text
List<?>
List<? extends Animal>
List<? super Dog>
```

These are called:

1. Unbounded wildcard
2. Upper-bounded wildcard
3. Lower-bounded wildcard

### Important Python Difference

**Python does not support Java-style `?` wildcards in generic type annotations.**

These are not valid Python:

```text
list<?>
list<? extends Animal>
list<? super Dog>
```

Instead, Python uses concepts such as:

- `Any`
- `object`
- `TypeVar`
- Upper bounds
- `Union`
- Covariance
- Contravariance
- Generic protocols and collection interfaces

They cover many similar use cases, but are not exact one-to-one replacements for Java wildcards.

---

# 23. Understanding `Any`

Python provides:

```python
from typing import Any
```

`Any` represents a dynamically typed value for static type checking.

### Example

```python
from typing import Any


def display(value: Any) -> None:
    print(value)


display(10)
display("Python")
display([1, 2, 3])
```

### Output

```text
10
Python
[1, 2, 3]
```

### What Makes `Any` Special?

A static type checker generally permits operations on `Any` without verifying their safety.

For example:

```python
from typing import Any


def process(value: Any):
    return value.some_method()
```

A static type checker may allow this.

But calling it with an integer will fail at runtime.

### Important

`Any` is not simply the same thing as Java's unbounded wildcard.

`Any` is an escape hatch from normal static type checking.

---

# 24. `Any` vs `object`

This is a very important Python typing concept.

Both `Any` and `object` can describe values of arbitrary runtime types.

However, they behave differently during static checking.

## Using `Any`

```python
from typing import Any


def process(value: Any):
    value.some_method()
```

Static type checking generally permits the method call without knowing whether the method exists.

## Using `object`

```python
def process(value: object):
    value.some_method()
```

A static type checker reports an error because the base `object` type does not guarantee that `some_method()` exists.

### Safe Use of `object`

```python
def process(value: object):

    if isinstance(value, str):
        print(value.upper())

    elif isinstance(value, int):
        print(value * 2)
```

### Comparison

| `Any` | `object` |
|---|---|
| Dynamically typed escape hatch | General top type for Python objects |
| Allows unchecked operations | Requires narrowing before specific operations |
| Less static safety | Greater static safety |
| Useful at dynamic boundaries | Useful for arbitrary unknown values |

### Interview Point

`Any` and `object` are not interchangeable.

Use `object` when you want to preserve type safety while accepting arbitrary objects.

Use `Any` when dynamic behavior is genuinely required.

# 25. Understanding Variance

Variance describes how subtype relationships behave when types are placed inside generic containers or other generic type constructors.

There are three important types:

1. Invariance
2. Covariance
3. Contravariance

These concepts are the foundation for understanding Java-style bounded wildcards and their Python counterparts.

### Initial Class Hierarchy

```python
class Animal:
    pass


class Dog(Animal):
    pass


class Cat(Animal):
    pass
```

We know:

```text
Dog IS-A Animal
Cat IS-A Animal
```

Therefore:

```python
dog = Dog()

animal: Animal = dog
```

is valid.

But what happens with:

```python
list[Dog]
```

and:

```python
list[Animal]
```

Can they be used interchangeably?

That depends on variance.

---

# 26. Invariance

## Definition

A generic type is invariant when a subtype relationship between its type arguments does not automatically create a subtype relationship between the corresponding generic types.

In simple words:

> Even if Dog is an Animal, `list[Dog]` is not considered a subtype of `list[Animal]`.

### Example

```python
class Animal:
    pass


class Dog(Animal):
    pass


dogs: list[Dog] = [Dog()]

animals: list[Animal] = dogs
```

A static type checker should reject the last assignment.

### Why?

Imagine the assignment were allowed.

```python
animals.append(Animal())
```

Now the same underlying list contains a plain `Animal`.

But the original variable was declared as:

```python
dogs: list[Dog]
```

The type guarantee would be violated.

### Important

At runtime, Python does not enforce these list type annotations.

The code can execute and mutate the list.

The restriction exists in the static type system.

### Why Is `list` Invariant?

Because lists support both:

- Reading elements
- Writing/replacing/appending elements

Allowing covariance would be unsafe for arbitrary mutable lists.

### Rule

```text
Dog <: Animal
```

does NOT imply:

```text
list[Dog] <: list[Animal]
```

where `<:` means "is a subtype of".

---

# 27. Covariance

## Definition

A generic type is covariant if it preserves the subtype relationship of its type arguments.

If:

```text
Dog <: Animal
```

then for a covariant generic type `ReadOnly[T]`:

```text
ReadOnly[Dog] <: ReadOnly[Animal]
```

### Python Example: `Sequence`

```python
from collections.abc import Sequence


class Animal:

    def speak(self):
        print("Animal")


class Dog(Animal):

    def speak(self):
        print("Woof")


def display_animals(
    animals: Sequence[Animal]
) -> None:

    for animal in animals:
        animal.speak()


dogs: list[Dog] = [Dog(), Dog()]

display_animals(dogs)
```

### Output

```text
Woof
Woof
```

### Why Does This Work?

`Sequence[Animal]` describes a read-only sequence interface.

The function can read elements but cannot append new elements through that interface.

Therefore, a sequence of dogs can safely be treated as a sequence of animals for reading.

### Important

A `Sequence` annotation does not necessarily mean the underlying object is immutable.

A list can satisfy `Sequence`.

However, the `Sequence` interface does not expose list mutation operations such as `append()`.

### Covariance Rule

```text
Dog <: Animal
```

implies:

```text
Sequence[Dog] <: Sequence[Animal]
```

### Common Covariant Containers

Examples include:

- `Sequence[T]`
- `Iterable[T]`
- `frozenset[T]`

---

# 28. Contravariance

Contravariance reverses the subtype relationship.

If:

```text
Dog <: Animal
```

then for a contravariant consumer `Consumer[T]`:

```text
Consumer[Animal] <: Consumer[Dog]
```

This initially seems confusing.

Let's understand it using callbacks.

## Example

```python
from collections.abc import Callable


class Animal:
    pass


class Dog(Animal):
    pass


def handle_animal(animal: Animal) -> None:
    print("Handling animal")


def process_dog(
    handler: Callable[[Dog], None]
) -> None:

    dog = Dog()
    handler(dog)


process_dog(handle_animal)
```

### Output

```text
Handling animal
```

### Why Does This Work?

`process_dog()` needs a function capable of accepting a `Dog`.

But `handle_animal()` accepts any `Animal`.

Since every `Dog` is an `Animal`, `handle_animal()` can safely process the dog.

### Think About It

A function that handles all animals can also handle dogs.

However, a function that only handles dogs cannot necessarily handle every animal.

### Invalid Direction

```python
def handle_dog(dog: Dog) -> None:
    print("Handling dog")


def process_animal(
    handler: Callable[[Animal], None]
) -> None:

    handler(Animal())


process_animal(handle_dog)
```

A static type checker should reject the final call.

The handler accepts only dogs, but `process_animal()` may provide a non-dog animal.

### Key Takeaway

Function parameter types are contravariant.

Function return types are covariant.

---

# 29. Invariance vs Covariance vs Contravariance

Assume:

```text
Dog <: Animal
```

| Variance | Type Relationship | Typical Example |
|---|---|---|
| Invariant | Neither direction allowed | `list[T]` |
| Covariant | `Container[Dog] <: Container[Animal]` | `Sequence[T]` |
| Contravariant | `Consumer[Animal] <: Consumer[Dog]` | Callable parameter types |

### Easy Way to Remember

**Covariance:**

A producer of dogs can be used where a producer of animals is expected.

**Contravariance:**

A consumer of animals can be used where a consumer of dogs is expected.

**Invariance:**

A mutable container generally needs its precise element type preserved.

---

# 30. Java Wildcards vs Python Alternatives

Java provides three common wildcard forms.

Python achieves similar goals through different type-system mechanisms.

## 30.1 Unbounded Wildcard: `<?>`

Java:

```text
List<?>
```

This means a list whose element type is unknown.

A Python approach when only reading arbitrary items is needed:

```python
from collections.abc import Sequence


def display(items: Sequence[object]) -> None:

    for item in items:
        print(item)


display([1, 2, 3])
display(["A", "B"])
```

### Why `Sequence[object]`?

Because `Sequence` is covariant and only exposes a read-oriented interface.

It accepts sequences whose elements are more specific types.

### Alternative

```python
from typing import Any


def display(items: list[Any]) -> None:
    ...
```

But `Any` weakens static checking and permits potentially unsafe operations.

It is not identical to the Java unbounded wildcard.

### Important Subtlety

```python
list[object]
```

is not a safe general replacement for:

```text
List<?>
```

because Python's `list` is invariant.

---

## 30.2 Upper-Bounded Wildcard: `<? extends Animal>`

Java:

```text
List<? extends Animal>
```

This expresses a collection whose elements are some subtype of `Animal`.

A common Python equivalent for read-only operations is:

```python
from collections.abc import Sequence


class Animal:
    pass


class Dog(Animal):
    pass


def display(
    animals: Sequence[Animal]
) -> None:

    for animal in animals:
        print(type(animal).__name__)


dogs: list[Dog] = [Dog(), Dog()]

display(dogs)
```

### Output

```text
Dog
Dog
```

### Why Does This Work?

`Sequence` is covariant.

Therefore, a sequence of dogs can be passed where a sequence of animals is expected.

### If We Need to Preserve the Subtype

Use a bounded TypeVar.

```python
from collections.abc import Sequence
from typing import TypeVar


TAnimal = TypeVar("TAnimal", bound=Animal)


def get_first_animal(
    animals: Sequence[TAnimal]
) -> TAnimal:

    return animals[0]


dog = get_first_animal([Dog(), Dog()])
```

A static type checker can infer `dog` as `Dog`.

### Key Difference

`Sequence[Animal]` is enough when the function only needs animal behavior.

`Sequence[TAnimal] -> TAnimal` is useful when the function needs to preserve the specific input subtype in its result.

---

## 30.3 Lower-Bounded Wildcard: `<? super Dog>`

Java:

```text
List<? super Dog>
```

This permits a list whose element type is `Dog` or one of its supertypes.

Python does not provide an identical lower-bounded wildcard syntax.

However, contravariant consumer interfaces model the important behavior.

### Example

```python
from collections.abc import Callable


class Animal:
    pass


class Dog(Animal):
    pass


def consume_animal(animal: Animal) -> None:
    print("Consumed animal")


def feed_dog(
    consumer: Callable[[Dog], None]
) -> None:

    consumer(Dog())


feed_dog(consume_animal)
```

### Output

```text
Consumed animal
```

The consumer accepts `Animal`, so it can safely accept a `Dog`.

### Important Limitation

Python does not have a direct equivalent of Java's lower-bounded wildcard for mutable lists.

Use a suitable consumer abstraction or design an API that expresses the specific operations needed.

---

# 31. PECS Principle

In Java generics, a commonly used guideline is:

> PECS: Producer Extends, Consumer Super.

This is useful for understanding variance in general.

## Producer

A producer supplies values.

If a function only reads animals, it can safely accept a producer of dogs.

Python example:

```python
Sequence[Animal]
```

A `Sequence[Dog]` can be passed because `Sequence` is covariant.

## Consumer

A consumer accepts values.

If code must pass dogs to a consumer, a consumer that accepts all animals is also safe.

Python example:

```python
Callable[[Dog], None]
```

A function accepting `Animal` can be used in this position.

### Memory Trick

```text
Producer -> Covariance
Consumer -> Contravariance
Read + Write -> Often Invariance
```

### Important

PECS is a Java-oriented mnemonic, not a Python syntax rule.

Use it to understand type relationships rather than treating it as an exact translation of Java's wildcard system.

# 32. Explicit Variance With `TypeVar`

Older-style Python generic classes allow variance declarations through `TypeVar`.

## Covariant Type Variable

```python
from typing import Generic, TypeVar


T_co = TypeVar("T_co", covariant=True)


class ReadOnlyBox(Generic[T_co]):

    def __init__(self, value: T_co):
        self._value = value

    def get(self) -> T_co:
        return self._value
```

### Example

```python
class Animal:
    pass


class Dog(Animal):
    pass


dog_box: ReadOnlyBox[Dog] = ReadOnlyBox(Dog())

animal_box: ReadOnlyBox[Animal] = dog_box
```

This assignment is valid under static typing.

### Why?

The box exposes its value but does not provide a method to replace it with an arbitrary `Animal`.

Therefore, covariance is appropriate.

---

## Contravariant Type Variable

```python
from typing import Generic, TypeVar


T_contra = TypeVar(
    "T_contra",
    contravariant=True
)


class Consumer(Generic[T_contra]):

    def consume(self, value: T_contra) -> None:
        print("Consumed", type(value).__name__)
```

### Usage

```python
class Animal:
    pass


class Dog(Animal):
    pass


animal_consumer: Consumer[Animal] = Consumer()

dog_consumer: Consumer[Dog] = animal_consumer

dog_consumer.consume(Dog())
```

### Output

```text
Consumed Dog
```

### Explanation

A consumer that accepts all animals can be used wherever a consumer of dogs is needed.

---

## Invariant Type Variable

```python
from typing import Generic, TypeVar


T = TypeVar("T")


class MutableBox(Generic[T]):

    def __init__(self, value: T):
        self.value = value

    def set(self, value: T) -> None:
        self.value = value

    def get(self) -> T:
        return self.value
```

The type variable is invariant by default in this traditional declaration.

This makes sense because the box supports both reading and writing.

### Modern Python Note

With generic class syntax introduced in Python 3.12, type checkers infer variance from how type parameters are used.

```python
class ReadOnlyBox[T]:

    def __init__(self, value: T):
        self._value = value

    def get(self) -> T:
        return self._value
```

Variance inference is based on the class's exposed type behavior, not simply the spelling of the type parameter.

# PART 4: INTERFACES + GENERICS TOGETHER

## 33. Generic Interfaces With Protocols

Interfaces and generics become especially powerful when combined.

Imagine a system that stores different kinds of data.

We want:

- User storage
- Product storage
- Order storage

But all storage implementations should support the same operations.

### Generic Repository Contract

```python
from typing import Protocol, TypeVar


T = TypeVar("T")


class Repository(Protocol[T]):

    def add(self, item: T) -> None:
        ...

    def get_all(self) -> list[T]:
        ...
```

### Explanation

`Repository[T]` represents a generic repository contract.

For example:

```python
Repository[User]
```

means a repository that accepts and returns `User` objects.

Similarly:

```python
Repository[Product]
```

represents a repository for products.

### Important

The contract uses the type variable in both:

- Input positions: `add(item: T)`
- Output positions: `get_all() -> list[T]`

This is naturally an invariant interface.

---

# 34. Complete Real-World Example: Generic Repository Pattern

This example combines:

- Interfaces
- Protocols
- Generics
- Inheritance-related type relationships
- Encapsulation
- Dependency injection
- Polymorphism

```python
from typing import Generic, Protocol, TypeVar


T = TypeVar("T")


# Interface

class Repository(Protocol[T]):

    def add(self, item: T) -> None:
        ...

    def get_all(self) -> list[T]:
        ...


# Generic Implementation

class InMemoryRepository(Generic[T]):

    def __init__(self):
        self._items: list[T] = []

    def add(self, item: T) -> None:
        self._items.append(item)

    def get_all(self) -> list[T]:
        return self._items.copy()


# Domain Model

class User:

    def __init__(self, name: str):
        self.name = name


# Business Logic

def register_user(
    repository: Repository[User],
    name: str
) -> None:

    user = User(name)
    repository.add(user)


# Usage

user_repo: InMemoryRepository[User] = (
    InMemoryRepository()
)

register_user(user_repo, "Ali")
register_user(user_repo, "Sara")

users = user_repo.get_all()

for user in users:
    print(user.name)
```

### Output

```text
Ali
Sara
```

### Architecture

```text
                  Repository[T]
                  (Generic Protocol)
                         |
                  +------+------+
                  |             |
                  v             v
           add(item: T)    get_all() -> list[T]
                  |             |
                  +------+------+
                         |
                         v
               InMemoryRepository[T]
                         |
                         v
                    User Objects
                         |
                         v
                    register_user()
```

### Step-by-Step Explanation

**1. Interface defines the contract.**

```python
class Repository(Protocol[T]):
```

**2. Generic implementation stores values of type `T`.**

```python
class InMemoryRepository(Generic[T]):
```

**3. Internal storage is annotated with the same type.**

```python
self._items: list[T] = []
```

**4. Business logic expects a repository for users.**

```python
repository: Repository[User]
```

**5. The implementation satisfies the Protocol structurally.**

```python
InMemoryRepository[User]
```

No explicit inheritance from `Repository` is required.

**6. We can replace the repository implementation.**

For example, we could introduce:

```python
class DatabaseUserRepository:

    def add(self, item: User) -> None:
        # Save the user to a database.
        ...

    def get_all(self) -> list[User]:
        # Read users from a database.
        ...
```

A complete database implementation providing these methods could satisfy `Repository[User]`.

The business logic would not need to change.

### Key Takeaway

**Interfaces define capabilities. Generics preserve type relationships. Together, they allow reusable and statically type-safe designs.**

# 36. `ParamSpec` — Preserving Function Signatures

This is an advanced generic feature.

Suppose we write a decorator that wraps another function.

We want to preserve the original function's parameter types.

Python provides `ParamSpec`.

### Example

```python
from collections.abc import Callable
from functools import wraps
from typing import ParamSpec, TypeVar


P = ParamSpec("P")
R = TypeVar("R")


def log_call(
    func: Callable[P, R]
) -> Callable[P, R]:

    @wraps(func)
    def wrapper(
        *args: P.args,
        **kwargs: P.kwargs
    ) -> R:

        print("Function called")
        return func(*args, **kwargs)

    return wrapper


@log_call
def add(a: int, b: int) -> int:
    return a + b


print(add(10, 20))
```

### Output

```text
Function called
30
```

### Explanation

`P` captures the function's parameter signature.

`R` represents the return type.

```python
Callable[P, R]
```

describes a callable with those parameters and that return type.

The wrapper preserves the relationship between the original function and the decorated function.

### Why Is This Useful?

Without `ParamSpec`, type annotations for decorators can lose information about the arguments accepted by the wrapped function.

### Modern Syntax

Python 3.12+:

```python
from collections.abc import Callable
from functools import wraps


def log_call[**P, R](
    func: Callable[P, R]
) -> Callable[P, R]:

    @wraps(func)
    def wrapper(
        *args: P.args,
        **kwargs: P.kwargs
    ) -> R:

        print("Called")
        return func(*args, **kwargs)

    return wrapper
```

# 37. Variadic Generics and `TypeVarTuple`

Sometimes we want a generic definition to work with an arbitrary number of type parameters.

Python provides `TypeVarTuple`.

This is an advanced feature.

### Example

Python 3.12+:

```python
def rotate[T, *Ts](
    values: tuple[T, *Ts]

result = rotate((1, "Python", True))

```

### Output

```text
('Python', True, 1)
```

### Explanation

`T` represents the first element's type.

For this example, static type analysis can preserve the positional types.

### Important Distinction

The `*` in:

```python

```

means variadic type parameter unpacking.

# 38. Runtime Behavior of Generics

This is a frequently asked advanced interview topic.

### Example

```python
from typing import Generic, TypeVar


T = TypeVar("T")


class Box(Generic[T]):

    def __init__(self, value: T):
        self.value = value


box = Box[int](100)

print(type(box))
print(isinstance(box, Box))
```

### Output

```text
<class '__main__.Box'>
True
```

### Explanation

The runtime object is an instance of `Box`.

The type argument helps static type checkers reason about the intended contents.

It does not normally create a completely separate runtime class for each type argument.

### Can We Use This?

```python
isinstance(box, Box[int])
```

No.

Parameterized generics such as `Box[int]` are not generally valid as the second argument to `isinstance()`.

This raises a `TypeError`.

### Similarly

```python
isinstance([1, 2, 3], list[int])
```

raises a `TypeError`.

Use:

```python
isinstance([1, 2, 3], list)
```

for basic runtime checking.

To validate elements, check them explicitly or use a runtime validation library.

### Example

```python
def is_integer_list(value: object) -> bool:

    return (
        isinstance(value, list)
        and all(
            type(item) is int
            for item in value
        )
    )


print(is_integer_list([1, 2, 3]))
print(is_integer_list([1, "two", 3]))
```

### Output

```text
True
False
```

This example deliberately uses `type(item) is int` to require exact integers rather than also accepting booleans, which are subclasses of `int`.

# PART 6: COMMON MISTAKES

## 40. Common Mistakes and Edge Cases

### Mistake 1: Assuming Python Has an `interface` Keyword

Incorrect:

```text
interface Payment:
    ...
```

Python uses ABCs, protocols, and duck typing instead.

### Mistake 2: Assuming an ABC Validates Everything

An ABC does not fully validate method signatures or behavior at runtime.

### Mistake 3: Assuming Protocols Require Inheritance

Protocols use structural compatibility.

A class can satisfy a protocol without explicitly inheriting from it.

### Mistake 4: Assuming Generics Enforce Runtime Types

```python
box = Box[int](100)
box.value = "Hello"
```

This can execute despite violating the static type contract.

### Mistake 5: Confusing `Any` With `object`

`Any` relaxes static checks.

`object` preserves type safety by requiring narrowing before type-specific operations.

### Mistake 6: Assuming `list[Dog]` Is a Subtype of `list[Animal]`

Python's mutable list is invariant.

### Mistake 7: Assuming `Sequence` Means Immutable Data

A `Sequence` is a read-only interface.

Its underlying object may still be mutable through other references.

### Mistake 8: Assuming Python Supports Java Wildcards

Python does not use:

```text
?
? extends
? super
```

Use Python's generic typing tools instead.

### Mistake 9: Treating a TypeVar as a Runtime Validator

```python
T = TypeVar("T", bound=Animal)
```

is a static typing constraint.

It does not automatically perform runtime `isinstance()` validation.

### Mistake 10: Confusing Generic Wildcards With File-Pattern Wildcards

Python also supports wildcard patterns for filesystem matching.

For example:

```python
from glob import glob


files = glob("*.py")
```

Here:

- `*` matches any sequence of characters.
- `?` matches one character.
- Character patterns such as `[abc]` match character alternatives.

These are filesystem matching patterns, not OOP generic wildcards.

Likewise:

```python
from module import *
```

is wildcard import syntax, not generics.

# PART 7: INTERVIEW QUESTIONS

## 41. Interface Interview Questions

### Q1. What is an interface?

An interface is a contract specifying the operations an object must support without dictating its implementation.

### Q2. Does Python support interfaces?

Yes, conceptually.

Python supports interface-like design through ABCs, Protocols, and duck typing.

It does not have a dedicated `interface` keyword.

### Q3. What is the difference between an interface and an abstract class?

An interface primarily describes required behavior.

An abstract class can describe required behavior and provide shared implementations or state.

Python ABCs can be used for both purposes.

### Q4. What is the difference between ABC and Protocol?

ABCs typically use explicit nominal inheritance and can enforce abstract methods at instantiation.

Protocols primarily support structural static typing without requiring explicit inheritance.

### Q5. What is duck typing?

Duck typing means using an object based on the operations it supports rather than requiring a particular inherited class type.

### Q6. Can a class implement multiple interfaces?

Yes.

A Python class can satisfy multiple protocols structurally or inherit from multiple ABCs.

### Q7. What is structural typing?

Structural typing determines compatibility based on the attributes and methods provided by a type.

### Q8. Can an interface contain implemented methods?

In Python, interface-like ABCs may have implemented methods.

Protocols can also define default methods, although their primary role is describing a structural contract.

### Q9. How do interfaces support polymorphism?

Different implementations expose the same operations, allowing clients to use them through a common interface.

---

## 42. Generics Interview Questions

### Q10. What are generics?

Generics allow reusable classes, functions, and interfaces to express type relationships through type parameters.

### Q11. What is `TypeVar`?

`TypeVar` declares a type variable used to express relationships between type annotations.

### Q12. What is `Generic[T]`?

`Generic[T]` declares a user-defined generic class parameterized by a type variable.

### Q13. What is the difference between `Any` and `TypeVar`?

`Any` permits dynamically typed operations.

`TypeVar` preserves relationships between types.

### Q14. What is a bounded TypeVar?

A bounded TypeVar restricts possible substitutions to types compatible with an upper bound.

Example:

```python
T = TypeVar("T", bound=Animal)
```

### Q15. What are constrained TypeVars?

They restrict a type variable to a specified collection of type alternatives.

Example:

```python
T = TypeVar("T", str, bytes)
```

### Q16. Are Python generics enforced at runtime?

Generally, no.

They are primarily used by static type checkers.

### Q17. What is the difference between `Union` and `TypeVar`?

A union expresses alternative types.

A TypeVar expresses a reusable type parameter and relationships among occurrences of that parameter.

### Q18. What is `ParamSpec`?

`ParamSpec` captures callable parameter signatures for use in generic typing, especially decorators.

### Q19. What is `TypeVarTuple`?

`TypeVarTuple` represents a variable-length sequence of type parameters.

It is used in variadic generics.

---

## 43. Wildcards and Variance Interview Questions

### Q20. What is covariance?

Covariance preserves subtype relationships through a generic type.

Example:

```text
Dog <: Animal

Sequence[Dog] <: Sequence[Animal]
```

### Q21. What is contravariance?

Contravariance reverses subtype relationships through a generic type.

Example:

```text
Dog <: Animal

Consumer[Animal] <: Consumer[Dog]
```

### Q22. What is invariance?

Invariance means neither generic specialization is automatically a subtype of the other.

Example:

```text
list[Dog] is not a subtype of list[Animal]
```

### Q23. Why is `list` invariant?

Because it supports both reading and mutation.

Covariance would allow unsafe insertion of broader types into a list of more specific types.

### Q24. Why is `Sequence` covariant?

Because its exposed interface supports reading elements without providing methods to add arbitrary new elements.

### Q25. What does PECS stand for?

Producer Extends, Consumer Super.

It is a Java-oriented mnemonic for reasoning about covariant producers and contravariant consumers.

### Q26. Does Python have Java's wildcard syntax?

No.

Python uses TypeVars, bounded types, `Any`, `object`, protocols, and variance relationships to express related ideas.

### Q27. Can we check `isinstance(value, list[int])`?

No.

Parameterized generic aliases like `list[int]` cannot generally be used with `isinstance()`.

Use the base runtime type and validate elements separately if needed.

## Problem 2: Generic Stack

Implement a generic stack with:

- `push()`
- `pop()`
- `peek()`
- `is_empty()`

The stack should be reusable for different data types.

### Solution

```python
from typing import Generic, TypeVar


T = TypeVar("T")


class Stack(Generic[T]):

    def __init__(self):
        self._items: list[T] = []

    def push(self, item: T) -> None:
        self._items.append(item)

    def pop(self) -> T:

        if not self._items:
            raise IndexError("Stack is empty")

        return self._items.pop()

    def peek(self) -> T:

        if not self._items:
            raise IndexError("Stack is empty")

        return self._items[-1]

    def is_empty(self) -> bool:
        return len(self._items) == 0


stack: Stack[int] = Stack()

stack.push(10)
stack.push(20)
stack.push(30)

print(stack.peek())
print(stack.pop())
print(stack.pop())
print(stack.is_empty())
```

### Output

```text
30
30
20
False
```

### Why Are Generics Useful Here?

The same `Stack` implementation can be used as:

```python
Stack[int]
Stack[str]
Stack[User]
```

The type checker can track which element type each stack is intended to contain.

## Problem 3: Covariance and Invariance

Predict which examples are statically valid.

```python
from collections.abc import Sequence


class Animal:
    pass


class Dog(Animal):
    pass


dogs: list[Dog] = [Dog()]

a: list[Animal] = dogs

b: Sequence[Animal] = dogs

c: Sequence[Dog] = dogs
```

### Answer

```python
a: list[Animal] = dogs
```

Statically invalid because `list` is invariant.

```python
b: Sequence[Animal] = dogs
```

Valid because `Sequence` is covariant.

```python
c: Sequence[Dog] = dogs
```

Valid because a list of dogs satisfies the sequence-of-dogs interface.

# 47. Final Summary

## Interfaces

An interface describes what behavior an object must provide.

Python supports interface-like design through:

```python
ABC
Protocol
Duck Typing
```

## Generics

Generics allow reusable, statically type-safe APIs.

Traditional syntax:

```python
from typing import Generic, TypeVar

T = TypeVar("T")


class Box(Generic[T]):
    pass
```

Modern Python 3.12+ syntax:

```python
class Box[T]:
    pass
```

## Wildcards and Variance

Python does not use Java-style generic wildcards.

Instead, it relies on the type system's subtype relationships.

```text
Invariance:
    list[Dog] is not a subtype of list[Animal]

Covariance:
    Sequence[Dog] is a subtype of Sequence[Animal]

Contravariance:
    Consumer[Animal] is a subtype of Consumer[Dog]
```

## The Three Most Important Takeaways

**1. Interfaces define expected capabilities.**

They make it possible to write code that works with different implementations.

**2. Generics preserve type information.**

They allow functions, classes, and interfaces to remain reusable without sacrificing static type checking.

**3. Variance determines how generic types relate to one another.**

Understanding invariance, covariance, and contravariance is essential when working with inheritance and generic collections.

### One-Line Interview Definitions

**Interface:**

> An interface defines a behavioral contract that multiple implementations can satisfy.

**Generics:**

> Generics enable reusable type-parameterized classes, functions, and interfaces while preserving relationships between types.

**Wildcards:**

> Wildcards are a feature of generic type systems such as Java's for expressing unknown or bounded type arguments; Python expresses many related relationships using TypeVars, variance, and suitable generic interfaces.
