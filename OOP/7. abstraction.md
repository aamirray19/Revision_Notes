
# Abstraction in Python — Complete OOP Notes

## 1. What Is Abstraction?

**Abstraction is an Object-Oriented Programming (OOP) principle that hides unnecessary implementation details and exposes only the essential functionality to the user.**

In simple terms:

> Abstraction focuses on **what an object does**, rather than **how it does it**.

### Real-World Example: ATM

When you withdraw money from an ATM:

1. Insert your card.
2. Enter your PIN.
3. Enter the withdrawal amount.
4. Collect your money.

You don't need to know:

- How the ATM communicates with the bank server.
- How your PIN is verified internally.
- How the bank updates your account balance.
- How the ATM controls its cash dispenser.

You only interact with the required functionality.

This is abstraction.

### Key Idea

```text
User
  |
  v
Public Interface (What to do)
  |
  v
Hidden Implementation (How it works)
```

Abstraction reduces complexity by separating the functionality exposed to users from the implementation behind it.

---

## 2. Why Do We Need Abstraction?

Imagine developing a payment system that supports:

- Credit cards
- UPI
- PayPal
- Net banking

Each payment method uses a different internal process.

Without a common abstraction, application code may need to understand every payment provider's implementation.

This creates problems:

1. **Tight coupling:** Application logic depends on specific implementations.
2. **Poor maintainability:** Changes to payment processing can require changes throughout the application.
3. **Difficult extensibility:** Adding new payment methods becomes complicated.
4. **Code duplication:** Similar workflows may be implemented repeatedly.
5. **Inconsistent interfaces:** Different implementations may expose different method names.

Abstraction helps solve these problems by establishing a common interface.

For example:

```python
payment.process_payment(500)
```

The application calls the same method regardless of the payment method.

The individual payment class determines how payment processing happens.

### Main Benefits

| Benefit | Explanation |
|---|---|
| Reduced complexity | Users interact with essential functionality |
| Loose coupling | Code depends less on implementation details |
| Maintainability | Internal implementations can change independently |
| Extensibility | New implementations can follow the same interface |
| Polymorphism | Different objects can be used through a common contract |
| Testability | Implementations can be replaced with test doubles |

---

## 3. How Is Abstraction Achieved in Python?

Python supports abstraction through several mechanisms:

1. Regular classes and public methods
2. Abstract Base Classes (ABCs)
3. Abstract methods
4. Duck typing
5. Protocols (structural typing)

For formal abstraction with abstract classes, Python provides the built-in `abc` module.

```python
from abc import ABC, abstractmethod
```

Here:

- `ABC` stands for **Abstract Base Class**.
- `abstractmethod` is a decorator used to declare abstract methods.

Before studying abstract classes, let's understand abstraction without them.

---

## 4. Abstraction Without Abstract Classes

Abstraction is a design principle, not a feature that requires the `abc` module.

### Example: Coffee Machine

```python
class CoffeeMachine:

    def make_coffee(self):
        self._boil_water()
        self._grind_beans()
        self._brew_coffee()
        print("Coffee is ready!")

    def _boil_water(self):
        print("Boiling water")

    def _grind_beans(self):
        print("Grinding beans")

    def _brew_coffee(self):
        print("Brewing coffee")


machine = CoffeeMachine()
machine.make_coffee()
```

### Output

```text
Boiling water
Grinding beans
Brewing coffee
Coffee is ready!
```

### Explanation

The user interacts with:

```python
machine.make_coffee()
```

They do not need to call the individual operations.

The `make_coffee()` method provides a simple interface that coordinates the internal steps.

**Important:** The `_` prefix in Python indicates that a method is intended for internal use. It does not make the method inaccessible.

This example demonstrates abstraction through API design without using an abstract base class.

# 5. Abstract Classes in Python

An **abstract class** is a class designed to provide a common interface or foundation for other classes.

It can contain:

- Abstract methods
- Concrete (regular) methods
- Instance variables
- Constructors
- Properties
- Class methods
- Static methods

An abstract class containing unresolved abstract methods cannot be instantiated directly.

### Basic Syntax

```python
from abc import ABC, abstractmethod


class Parent(ABC):

    @abstractmethod
    def display(self):
        pass


class Child(Parent):

    def display(self):
        print("Implemented in Child")


obj = Child()
obj.display()
```

### Output

```text
Implemented in Child
```

### Understanding Each Component

#### 1. `ABC`

```python
class Parent(ABC):
```

This creates an abstract base class using the support provided by `ABC`.

Internally, `ABC` uses the metaclass `ABCMeta`.

#### 2. `@abstractmethod`

```python
@abstractmethod
def display(self):
    pass
```

This marks `display()` as an abstract method.

The intention is that concrete subclasses must provide an implementation.

#### 3. Concrete Subclass

```python
class Child(Parent):
```

`Child` inherits from `Parent`.

To become instantiable, it must implement all inherited abstract methods that remain unresolved.

#### 4. Method Implementation

```python
def display(self):
    print("Implemented in Child")
```

This satisfies the abstract-method requirement.

#### 5. Object Creation

```python
obj = Child()
```

This works because `Child` has implemented the required method.

---

## 6. What Happens If We Instantiate an Abstract Class?

Consider:

```python
from abc import ABC, abstractmethod


class Animal(ABC):

    @abstractmethod
    def sound(self):
        pass


animal = Animal()
```

### Result

```text
TypeError: Can't instantiate abstract class Animal
without an implementation for abstract method 'sound'
```

(The exact wording depends on the Python version.)

### Why Does This Happen?

The `Animal` class defines an abstract method that has not been implemented by a concrete subclass.

Python prevents the creation of an instance while abstract methods remain unresolved.

### Important Rule

An abstract class with unresolved abstract methods cannot be instantiated directly.

However, inheriting from `ABC` alone does not prevent instantiation.

For example:

```python
from abc import ABC


class Demo(ABC):
    pass


obj = Demo()
print("Object created")
```

### Output

```text
Object created
```

This works because `Demo` has no abstract methods.

**Interview Point:** An abstract base class is not automatically non-instantiable merely because it inherits from `ABC`.

# 7. Abstract Methods

An **abstract method** defines an operation that a concrete subclass is expected to implement.

### Example

```python
from abc import ABC, abstractmethod


class Vehicle(ABC):

    @abstractmethod
    def start_engine(self):
        pass


class Car(Vehicle):

    def start_engine(self):
        print("Car engine started")


class Bike(Vehicle):

    def start_engine(self):
        print("Bike engine started")


car = Car()
bike = Bike()

car.start_engine()
bike.start_engine()
```

### Output

```text
Car engine started
Bike engine started
```

### Explanation

The parent class establishes a common contract:

```python
start_engine()
```

Different subclasses provide their own implementations.

This combines two OOP principles:

- **Abstraction:** Establishes the common operation.
- **Polymorphism:** Allows different objects to respond differently to the same operation.

### What If a Child Class Does Not Implement an Abstract Method?

```python
from abc import ABC, abstractmethod


class Vehicle(ABC):

    @abstractmethod
    def start_engine(self):
        pass


class Car(Vehicle):
    pass


car = Car()
```

This raises a `TypeError`.

Why?

Because `Car` inherits the unresolved abstract method.

### Important Detail

A subclass does not necessarily need to implement every abstract method immediately.

It can remain abstract itself.

```python
from abc import ABC, abstractmethod


class A(ABC):

    @abstractmethod
    def show(self):
        pass


class B(A):
    pass


class C(B):

    def show(self):
        print("Implemented")


obj = C()
obj.show()
```

### Output

```text
Implemented
```

`A` and `B` cannot be instantiated, but `C` can.

# 8. Real-World Example: Payment Processing System

This is one of the most useful ways to understand abstraction.

### Problem

We want to support different payment methods without changing the main checkout logic.

### Implementation

```python
from abc import ABC, abstractmethod


class PaymentProcessor(ABC):

    @abstractmethod
    def pay(self, amount):
        pass


class CreditCardPayment(PaymentProcessor):

    def pay(self, amount):
        print(f"Paid ${amount} using Credit Card")


class UPIPayment(PaymentProcessor):

    def pay(self, amount):
        print(f"Paid ${amount} using UPI")


class PayPalPayment(PaymentProcessor):

    def pay(self, amount):
        print(f"Paid ${amount} using PayPal")


def checkout(payment_processor, amount):
    payment_processor.pay(amount)


card = CreditCardPayment()
upi = UPIPayment()
paypal = PayPalPayment()

checkout(card, 100)
checkout(upi, 200)
checkout(paypal, 300)
```

### Output

```text
Paid $100 using Credit Card
Paid $200 using UPI
Paid $300 using PayPal
```

### Architecture

```text
                PaymentProcessor
                 (Abstract Class)
                        |
           +------------+------------+
           |            |            |
           v            v            v
      CreditCard       UPI         PayPal
       Payment       Payment       Payment
           |            |            |
           +------------+------------+
                        |
                        v
                 checkout()
```

### Why Is This Good Design?

The checkout function:

```python
def checkout(payment_processor, amount):
    payment_processor.pay(amount)
```

does not need to know which payment system is being used.

To add another payment provider:

```python
class NetBankingPayment(PaymentProcessor):

    def pay(self, amount):
        print(f"Paid ${amount} using Net Banking")
```

We don't need to modify the checkout function.

The new implementation follows the same abstraction.

### Connection to SOLID Principles

This design relates to:

**Open/Closed Principle (OCP)**

The system can be extended with additional payment implementations without modifying the existing checkout function.

**Dependency Inversion Principle (DIP)**

High-level checkout logic can be designed to depend on a common abstraction instead of a specific payment provider.

Note that the example demonstrates the structure. A production system would also need payment validation, error handling, security, and actual provider integrations.

# 9. Abstract Class With Abstract and Concrete Methods

An abstract class can provide both required operations and reusable behavior.

### Example

```python
from abc import ABC, abstractmethod


class Employee(ABC):

    def __init__(self, name):
        self.name = name

    @abstractmethod
    def calculate_salary(self):
        pass

    def display_name(self):
        print(f"Employee: {self.name}")


class FullTimeEmployee(Employee):

    def calculate_salary(self):
        return 50000


class PartTimeEmployee(Employee):

    def calculate_salary(self):
        return 20000


emp1 = FullTimeEmployee("Ali")
emp2 = PartTimeEmployee("Sara")

emp1.display_name()
print(emp1.calculate_salary())

emp2.display_name()
print(emp2.calculate_salary())
```

### Output

```text
Employee: Ali
50000
Employee: Sara
20000
```

### Explanation

The abstract class contains:

**Abstract method**

```python
calculate_salary()
```

Each concrete subclass must implement this method.

**Concrete method**

```python
display_name()
```

All subclasses inherit and can reuse this implementation.

**Constructor**

```python
__init__()
```

Initializes the common employee information.

### Key Takeaway

An abstract class is not limited to declarations of abstract methods.

It can also act as a reusable base class.

# 10. Can an Abstract Method Have an Implementation?

**Yes. This is an important Python-specific concept.**

Unlike a common misconception, an abstract method in Python does not have to contain only `pass`.

It can provide a real implementation.

### Example

```python
from abc import ABC, abstractmethod


class Logger(ABC):

    @abstractmethod
    def log(self, message):
        print(f"Base log: {message}")


class FileLogger(Logger):

    def log(self, message):
        super().log(message)
        print(f"File log: {message}")


logger = FileLogger()
logger.log("Application started")
```

### Output

```text
Base log: Application started
File log: Application started
```

### Explanation

The parent method:

```python
@abstractmethod
def log(self, message):
    print(f"Base log: {message}")
```

is still abstract, even though it contains working code.

The subclass must override it to become concrete.

It can use:

```python
super().log(message)
```

to reuse the parent implementation.

### Interview Point

**Question:** Can an abstract method contain a body in Python?

**Answer:** Yes. An abstract method may contain an implementation, and subclasses can access it using `super()`. The abstract declaration still prevents instantiation until the abstract requirement is satisfied.

# 11. Abstract Properties

Python allows abstract properties using `@property` and `@abstractmethod`.

This is useful when all concrete subclasses must expose a particular attribute-like interface.

### Example

```python
from abc import ABC, abstractmethod


class Shape(ABC):

    @property
    @abstractmethod
    def area(self):
        pass


class Square(Shape):

    def __init__(self, side):
        self.side = side

    @property
    def area(self):
        return self.side ** 2


square = Square(5)

print(square.area)
```

### Output

```text
25
```

### Explanation

In the abstract class:

```python
@property
@abstractmethod
def area(self):
    pass
```

`area` is defined as an abstract property.

The concrete subclass implements it as a property.

Now we access:

```python
square.area
```

instead of:

```python
square.area()
```

### Decorator Order Matters

Correct:

```python
@property
@abstractmethod
def area(self):
    pass
```

The `@abstractmethod` decorator is applied first.

Then `@property` wraps the resulting method.

### Abstract Property With a Setter

It is also possible to require a property setter.

```python
from abc import ABC, abstractmethod


class Person(ABC):

    @property
    @abstractmethod
    def name(self):
        pass

    @name.setter
    @abstractmethod
    def name(self, value):
        pass


class Student(Person):

    def __init__(self, name):
        self.name = name

    @property
    def name(self):
        return self._name

    @name.setter
    def name(self, value):
        self._name = value


student = Student("Ali")

print(student.name)

student.name = "Sara"

print(student.name)
```

### Output

```text
Ali
Sara
```

This is useful when the contract requires readable and writable properties.

# 12. Abstract Class Methods and Static Methods

Python also supports abstract class methods and abstract static methods.

### Abstract Class Method

```python
from abc import ABC, abstractmethod


class Factory(ABC):

    @classmethod
    @abstractmethod
    def create(cls):
        pass


class UserFactory(Factory):

    @classmethod
    def create(cls):
        return cls()


obj = UserFactory.create()
print(type(obj).__name__)
```

### Output

```text
UserFactory
```

### Abstract Static Method

```python
from abc import ABC, abstractmethod


class Validator(ABC):

    @staticmethod
    @abstractmethod
    def validate(value):
        pass


class AgeValidator(Validator):

    @staticmethod
    def validate(value):
        return value >= 18


print(AgeValidator.validate(20))
```

### Output

```text
True
```

### Important Rule

The decorator order should be:

```python
@classmethod
@abstractmethod
```

or:

```python
@staticmethod
@abstractmethod
```

`@abstractmethod` should be the innermost decorator.

# 13. Abstraction vs Encapsulation

This is a very common interview question.

Although abstraction and encapsulation are related, they are different concepts.

## Abstraction

Abstraction focuses on:

> What functionality should be exposed?

Example:

```python
car.start()
```

The user doesn't need to understand the internal engine-starting process.

## Encapsulation

Encapsulation focuses on:

> How should data and related behavior be organized and access controlled?

Example:

```python
class BankAccount:

    def __init__(self, balance):
        self.__balance = balance

    def deposit(self, amount):
        if amount > 0:
            self.__balance += amount

    def get_balance(self):
        return self.__balance
```

The balance is accessed and modified through controlled methods.

Note that Python uses conventions and name mangling rather than strict private-access enforcement.

### Comparison

| Abstraction | Encapsulation |
|---|---|
| Hides unnecessary implementation details | Bundles data and behavior and manages access |
| Focuses on what an object does | Focuses on how an object's state is managed |
| Simplifies interaction | Protects object invariants |
| Can use ABCs, protocols, and APIs | Can use classes, properties, and naming conventions |
| Example: `payment.pay()` | Example: controlled balance updates |

### Remember

**Abstraction = Hiding complexity**

**Encapsulation = Organizing and controlling access to state and behavior**

Both principles can work together.

# 14. Abstraction vs Inheritance vs Polymorphism

These three concepts are closely connected.

### Example

```python
from abc import ABC, abstractmethod


class Animal(ABC):

    @abstractmethod
    def speak(self):
        pass


class Dog(Animal):

    def speak(self):
        return "Bark"


class Cat(Animal):

    def speak(self):
        return "Meow"


def make_animal_speak(animal):
    print(animal.speak())


make_animal_speak(Dog())
make_animal_speak(Cat())
```

### Output

```text
Bark
Meow
```

### How the Concepts Work Together

**Abstraction**

```python
class Animal(ABC):
```

Defines a common interface requiring `speak()`.

**Inheritance**

```python
class Dog(Animal):
```

Connects the concrete subclass to the parent abstraction.

**Polymorphism**

```python
animal.speak()
```

The same method call produces different behavior depending on the object.

### Important Distinction

Abstraction does not require inheritance in every case.

Python can also provide abstraction through duck typing and protocols.

# 15. Duck Typing: Abstraction Without ABC

Python is dynamically typed and supports duck typing.

The idea is:

> If an object provides the operations your code needs, you can use it without requiring inheritance from a particular class.

### Example

```python
class EmailNotification:

    def send(self, message):
        print(f"Email: {message}")


class SMSNotification:

    def send(self, message):
        print(f"SMS: {message}")


def notify(service, message):
    service.send(message)


notify(EmailNotification(), "Hello")
notify(SMSNotification(), "Hello")
```

### Output

```text
Email: Hello
SMS: Hello
```

### Explanation

Neither class inherits from a shared abstract base class.

However, both classes provide:

```python
send()
```

The `notify()` function simply expects a compatible operation.

This is another form of abstraction.

### ABC vs Duck Typing

| ABC | Duck Typing |
|---|---|
| Explicit interface contract | Implicit interface expectation |
| Usually relies on inheritance | Does not require inheritance |
| Abstract requirements checked at instantiation | Missing operations often fail when called |
| Useful for formal class hierarchies | Useful for flexible Python APIs |

Neither approach is universally better.

Choose based on the needs of the application.

# 16. Protocols: Structural Abstraction

Modern Python also provides `Protocol` through the `typing` module.

A protocol describes which methods or attributes an object is expected to provide.

It supports **structural typing**.

This means a class can satisfy a protocol without explicitly inheriting from it.

### Example

```python
from typing import Protocol


class Notification(Protocol):

    def send(self, message: str) -> None:
        ...


class EmailService:

    def send(self, message: str) -> None:
        print(f"Email: {message}")


class SMSService:

    def send(self, message: str) -> None:
        print(f"SMS: {message}")


def notify(service: Notification, message: str) -> None:
    service.send(message)


notify(EmailService(), "Welcome")
notify(SMSService(), "Welcome")
```

### Output

```text
Email: Welcome
SMS: Welcome
```

### Why Is This Useful?

`EmailService` and `SMSService` do not inherit from `Notification`.

However, they provide the required method with a compatible signature.

Static type checkers such as mypy and Pyright can verify this compatibility.

### ABC vs Protocol

| ABC | Protocol |
|---|---|
| Nominal typing through inheritance | Structural typing through method/attribute compatibility |
| Usually requires explicit subclassing | No explicit inheritance required |
| Can enforce abstract methods at instantiation | Primarily checked by static type checkers |
| Can provide reusable concrete methods | Primarily describes an expected interface |
| Suitable for related class hierarchies | Suitable for loosely coupled APIs |

### Important

Python does not enforce ordinary type annotations at runtime.

A protocol is primarily a static typing mechanism.

`@runtime_checkable` can enable limited runtime compatibility checks, but those checks do not validate complete method signatures or behavior.

# 17. Abstract Base Class vs `NotImplementedError`

These approaches are often confused.

## Approach 1: `NotImplementedError`

```python
class Animal:

    def speak(self):
        raise NotImplementedError(
            "Subclass must implement speak()"
        )


class Dog(Animal):
    pass


dog = Dog()
dog.speak()
```

### Result

```text
NotImplementedError: Subclass must implement speak()
```

The problem is that:

```python
dog = Dog()
```

succeeds.

The error happens only when the unimplemented method is called.

## Approach 2: `@abstractmethod`

```python
from abc import ABC, abstractmethod


class Animal(ABC):

    @abstractmethod
    def speak(self):
        pass


class Dog(Animal):
    pass


dog = Dog()
```

Now a `TypeError` occurs during object creation.

### Difference

| `NotImplementedError` | `@abstractmethod` |
|---|---|
| Raises an error when executed | Prevents instantiation while abstract requirements remain |
| Does not require an ABC | Uses ABC machinery |
| Can be used in ordinary methods | Explicitly marks a method abstract |
| Provides manual runtime signaling | Provides abstract-method enforcement |

### Interview Point

`NotImplementedError` and `@abstractmethod` are not interchangeable.

You can use both together, but they serve different purposes.

# 18. How Abstraction Works Internally in Python

Now let's look at the internal mechanism.

## Step 1: ABC Uses `ABCMeta`

Consider:

```python
from abc import ABC, abstractmethod


class Shape(ABC):

    @abstractmethod
    def area(self):
        pass
```

`ABC` uses a special metaclass called `ABCMeta`.

You can verify this:

```python
print(type(Shape))
```

### Output

```text
<class 'abc.ABCMeta'>
```

A metaclass controls aspects of class creation and behavior.

## Step 2: Python Tracks Abstract Methods

During class creation, `ABCMeta` determines the unresolved abstract requirements.

These are exposed through:

```python
Shape.__abstractmethods__
```

Example:

```python
print(Shape.__abstractmethods__)
```

### Output

```text
frozenset({'area'})
```

`__abstractmethods__` contains the names of abstract methods that remain unresolved.

## Step 3: The Subclass Implements the Method

```python
class Circle(Shape):

    def area(self):
        return 100
```

Now:

```python
print(Circle.__abstractmethods__)
```

### Output

```text
frozenset()
```

The empty set indicates that there are no unresolved abstract methods.

## Step 4: Python Allows Instantiation

```python
circle = Circle()
print(circle.area())
```

### Output

```text
100
```

### Internal Flow

```text
Class Definition
       |
       v
ABCMeta processes class
       |
       v
Collect unresolved abstract methods
       |
       v
Are abstract methods unresolved?
       |
   +---+---+
   |       |
  Yes      No
   |       |
   v       v
Cannot   Can be
instantiate instantiated
```

### Very Important Limitation

At runtime, ABC machinery primarily checks whether required abstract attributes have been implemented.

It does **not** fully validate:

- Parameter types
- Return types
- Logical correctness
- Method behavior
- Every aspect of a method's signature

For example:

```python
from abc import ABC, abstractmethod


class Parent(ABC):

    @abstractmethod
    def show(self, value):
        pass


class Child(Parent):

    def show(self):
        print("Hello")


obj = Child()
```

Object creation succeeds because the method has been overridden.

But:

```python
obj.show(10)
```

raises a `TypeError` because the replacement method doesn't accept the argument.

Static type checkers can detect many such signature mismatches.

**Conclusion:** An ABC enforces the presence of implementations, not complete behavioral correctness.

# 19. Complete Practical Example: Shape System

This example combines abstraction, inheritance, polymorphism, constructors, and reusable methods.

```python
from abc import ABC, abstractmethod
import math


class Shape(ABC):

    def __init__(self, color):
        self.color = color

    @abstractmethod
    def area(self):
        pass

    @abstractmethod
    def perimeter(self):
        pass

    def describe(self):
        print(f"Shape color: {self.color}")


class Circle(Shape):

    def __init__(self, color, radius):
        super().__init__(color)
        self.radius = radius

    def area(self):
        return math.pi * self.radius ** 2

    def perimeter(self):
        return 2 * math.pi * self.radius


class Rectangle(Shape):

    def __init__(self, color, length, width):
        super().__init__(color)
        self.length = length
        self.width = width

    def area(self):
        return self.length * self.width

    def perimeter(self):
        return 2 * (self.length + self.width)


shapes = [
    Circle("Red", 5),
    Rectangle("Blue", 4, 6)
]


for shape in shapes:
    shape.describe()
    print(f"Area: {shape.area():.2f}")
    print(f"Perimeter: {shape.perimeter():.2f}")
    print("---")
```

### Output

```text
Shape color: Red
Area: 78.54
Perimeter: 31.42
---
Shape color: Blue
Area: 24.00
Perimeter: 20.00
---
```

### Step-by-Step Explanation

**1. `Shape` provides the abstraction.**

```python
class Shape(ABC):
```

Every concrete shape must implement `area()` and `perimeter()`.

**2. The parent constructor stores common data.**

```python
def __init__(self, color):
    self.color = color
```

**3. Subclasses reuse parent initialization.**

```python
super().__init__(color)
```

**4. Subclasses define their own calculations.**

Circle:

```python
math.pi * self.radius ** 2
```

Rectangle:

```python
self.length * self.width
```

**5. The loop uses polymorphism.**

```python
for shape in shapes:
    shape.area()
```

The appropriate method is selected based on the actual object.

### Why This Design Is Powerful

We could introduce a `Triangle` class later without changing the iteration logic, as long as it implements the required operations.

# 20. When Should You Use Abstraction?

Use formal abstractions when:

1. Multiple classes share an important behavioral contract.
2. The application should depend on interfaces rather than specific implementations.
3. You want to enforce required methods in subclasses.
4. You expect to introduce new implementations.
5. You want to separate high-level application logic from implementation details.
6. You need interchangeable implementations for testing.

### Common Real-World Uses

| Application | Abstraction |
|---|---|
| Payment systems | `PaymentProcessor` |
| Database systems | `DatabaseConnection` |
| File storage | `StorageProvider` |
| Notifications | `NotificationService` |
| Cloud infrastructure | `CloudProvider` |
| Logging | `Logger` |
| Authentication | `AuthenticationProvider` |
| Machine learning | Model or estimator interface |

### When Should You Avoid Excessive Abstraction?

Do not introduce an ABC for every class.

For example, if there is only one simple implementation and no meaningful shared contract, a regular class may be sufficient.

Unnecessary abstractions can increase code complexity.

**Rule of thumb:** Abstract stable behavior and meaningful contracts, not every implementation detail.

# 21. Common Mistakes and Edge Cases

## Mistake 1: Forgetting to Implement an Abstract Method

```python
class Child(Parent):
    pass
```

If `Parent` has unresolved abstract methods, `Child` cannot be instantiated.

## Mistake 2: Forgetting `ABC`

```python
from abc import abstractmethod


class Demo:

    @abstractmethod
    def show(self):
        pass


obj = Demo()
```

This can succeed because simply decorating a method does not activate ABC enforcement when the class uses the ordinary `type` metaclass.

Use:

```python
class Demo(ABC):
```

or explicitly use:

```python
class Demo(metaclass=ABCMeta):
```

## Mistake 3: Assuming Abstract Methods Cannot Have Bodies

They can contain actual implementation code.

## Mistake 4: Assuming ABC Validates Method Signatures

It doesn't fully check parameter or return-type compatibility at runtime.

## Mistake 5: Confusing `_method` With an Abstract Method

A leading underscore signals intended internal use.

It does not declare an abstract method.

## Mistake 6: Assuming Every Abstraction Needs Inheritance

Duck typing and protocols are alternatives.

## Mistake 7: Using ABCs Unnecessarily

A simple public API or normal class may be all you need.

# 22. Frequently Asked Interview Questions

### Q1. What is abstraction in Python?

Abstraction is an OOP principle that hides unnecessary implementation details while exposing essential functionality.

Python supports formal abstraction using the `abc` module, abstract base classes, and abstract methods. It also supports abstraction through ordinary APIs, duck typing, and protocols.

### Q2. What is an abstract class?

An abstract class is a class intended to define common behavior or required operations for subclasses.

An abstract class with unresolved abstract methods cannot be instantiated directly.

### Q3. What is an abstract method?

An abstract method is a method declared using `@abstractmethod`.

Concrete subclasses must resolve inherited abstract methods before they can be instantiated.

### Q4. Can we create an object of an abstract class?

Not if the class has unresolved abstract methods.

A class inheriting from `ABC` without abstract methods can still be instantiated.

### Q5. Can an abstract class have a constructor?

Yes.

```python
class Parent(ABC):

    def __init__(self, value):
        self.value = value
```

Concrete subclasses can reuse it using `super()`.

### Q6. Can an abstract class have normal methods?

Yes.

Abstract classes may contain abstract methods and concrete methods.

### Q7. Can an abstract class contain instance variables?

Yes.

They can be initialized inside `__init__()` or other instance methods.

### Q8. Can an abstract method have implementation code?

Yes.

The method remains abstract, but its body can be called through `super()` from a subclass.

### Q9. What happens if a subclass does not implement an abstract method?

The subclass remains abstract and cannot be instantiated while the requirement is unresolved.

### Q10. What is the difference between abstraction and encapsulation?

Abstraction focuses on simplifying an interface by hiding unnecessary details.

Encapsulation focuses on organizing data and behavior and controlling how state is accessed or modified.

### Q11. Does Python support interfaces?

Yes, in several forms.

Python does not require a separate Java-style `interface` keyword.

Common approaches include:

- Abstract Base Classes
- Protocols
- Duck typing

### Q12. Can we achieve abstraction without ABC?

Yes.

Ordinary APIs, duck typing, and protocols can all provide abstraction.

### Q13. What is `ABCMeta`?

`ABCMeta` is the metaclass that implements Python's Abstract Base Class machinery.

It tracks abstract methods and prevents instantiation when abstract requirements remain unresolved.

### Q14. What is the difference between `@abstractmethod` and `NotImplementedError`?

`@abstractmethod` marks a method abstract and participates in class-instantiation enforcement.

`NotImplementedError` is an exception that is raised only when execution reaches the `raise` statement.

### Q15. Does an ABC enforce correct business logic?

No.

ABCs enforce declared abstract requirements at the class level.

They do not verify whether an implementation produces the correct result.

Testing, validation, and static analysis remain important.

# 23. Practice Problems

## Problem 1: Banking System

Create an abstract class `BankAccount` with:

- An abstract method `calculate_interest()`.
- A concrete method `show_balance()`.
- A constructor accepting `balance`.

Create:

- `SavingsAccount`
- `CurrentAccount`

Implement different interest calculations.

### Solution

```python
from abc import ABC, abstractmethod


class BankAccount(ABC):

    def __init__(self, balance):
        self.balance = balance

    @abstractmethod
    def calculate_interest(self):
        pass

    def show_balance(self):
        print(f"Balance: {self.balance}")


class SavingsAccount(BankAccount):

    def calculate_interest(self):
        return self.balance * 0.04


class CurrentAccount(BankAccount):

    def calculate_interest(self):
        return 0


accounts = [
    SavingsAccount(10000),
    CurrentAccount(20000)
]

for account in accounts:
    account.show_balance()
    print("Interest:", account.calculate_interest())
```

### Output

```text
Balance: 10000
Interest: 400.0
Balance: 20000
Interest: 0
```

# 25. Final Summary

Abstraction is one of the four fundamental principles of Object-Oriented Programming.

The four pillars are:

1. Encapsulation
2. Abstraction
3. Inheritance
4. Polymorphism

### Five Things You Must Remember

**1. Abstraction means exposing what is needed while hiding unnecessary implementation complexity.**

**2. Python provides the `abc` module to create formal abstract base classes.**

**3. Concrete subclasses must resolve abstract-method requirements before object creation.**

**4. Abstract classes can contain constructors, instance variables, concrete methods, and abstract methods with implementations.**

**5. Abstraction is broader than ABCs: ordinary APIs, duck typing, and protocols are also valid approaches.**

### The Core Syntax

```python
from abc import ABC, abstractmethod


class Parent(ABC):

    @abstractmethod
    def execute(self):
        pass


class Child(Parent):

    def execute(self):
        print("Execution completed")


obj = Child()
obj.execute()
```

### Output

```text
Execution completed
```

> Abstraction is the OOP principle of exposing essential functionality while hiding unnecessary implementation details, commonly implemented in Python using abstract base classes, abstract methods, protocols, and well-designed APIs.
