# Topic 7: Abstraction

> **TL;DR:** **Abstraction** exposes **what** an object does and hides **how** it does it. Python provides it through plain public APIs, **Abstract Base Classes** (`abc.ABC` + `@abstractmethod`), **duck typing** and **Protocols**. A class with unresolved abstract methods cannot be instantiated.

---

## 1. What Is Abstraction?

**Abstraction** is the OOP principle of hiding unnecessary implementation details and exposing only the essential functionality. Focus on **what** an object does, not **how**.

**Example: ATM.** You insert the card, enter the PIN, enter the amount, collect the cash. You don't need to know:

- how the ATM talks to the bank server
- how the PIN is verified
- how the bank updates your balance
- how the cash dispenser is controlled

```text
User
  |
  v
Public Interface (what to do)
  |
  v
Hidden Implementation (how it works)
```

- Reduces complexity by separating the exposed interface from the implementation behind it.
- One of the four OOP pillars: **encapsulation, abstraction, inheritance, polymorphism**.

---

## 2. Why Do We Need Abstraction?

**Problem:** a payment system supports credit cards, UPI, PayPal and net banking, each with a different internal process. Without a common abstraction, application code must know every provider's implementation:

- **Tight coupling:** app logic depends on specific implementations.
- **Poor maintainability:** a change in payment processing ripples through the app.
- **Hard to extend:** adding a payment method is complicated.
- **Code duplication:** similar workflows written repeatedly.
- **Inconsistent interfaces:** each provider exposes different method names.

**Fix:** one common interface. The app always makes the same call; each payment class decides how it works.

```python
payment.process_payment(500)
```

| Benefit | Explanation |
|---|---|
| Reduced complexity | Users interact only with essential functionality |
| Loose coupling | Code depends less on implementation details |
| Maintainability | Internals can change independently |
| Extensibility | New implementations follow the same interface |
| Polymorphism | Different objects used through one common contract |
| Testability | Implementations can be swapped for test doubles |

---

## 3. How Is Abstraction Achieved in Python?

1. Regular classes with public methods (good API design)
2. **Abstract Base Classes (ABCs)**
3. **Abstract methods**
4. **Duck typing**
5. **Protocols** (structural typing)

Formal abstract classes come from the built-in `abc` module:

```python
from abc import ABC, abstractmethod
```

- `ABC` → **Abstract Base Class** helper; subclass it to make a class abstract.
- `abstractmethod` → decorator that declares an abstract method.

---

## 4. Abstraction Without Abstract Classes

Abstraction is a **design principle**; it doesn't require the `abc` module.

```python
class CoffeeMachine:

    def make_coffee(self):
        self._boil_water()
        self._grind_beans()
        self._brew_coffee()
        print("Coffee is ready!")

    def _boil_water(self):
        print("Boiling water")

    def _grind_beans(self):
        print("Grinding beans")

    def _brew_coffee(self):
        print("Brewing coffee")


machine = CoffeeMachine()
machine.make_coffee()
```

```text
Boiling water
Grinding beans
Brewing coffee
Coffee is ready!
```

- The user calls only `machine.make_coffee()`; it coordinates the internal steps.
- The `_` prefix means "internal use" **by convention**. It does **not** make the method inaccessible. See [Topic 8: Access Modifiers](8.%20access%20modifiers.md).
- This is abstraction through **API design**, no ABC needed.

## 5. Abstract Classes

An **abstract class** provides a common interface/foundation for subclasses. It can contain **abstract methods**, **concrete (regular) methods**, instance variables, constructors, properties, class methods and static methods.

- An abstract class with **unresolved abstract methods cannot be instantiated** directly.

### Basic syntax (the core template)

```python
from abc import ABC, abstractmethod


class Parent(ABC):

    @abstractmethod
    def display(self):
        pass


class Child(Parent):

    def display(self):
        print("Implemented in Child")


obj = Child()
obj.display()   # Implemented in Child
```

| Piece | Role |
|---|---|
| `class Parent(ABC)` | Makes `Parent` an ABC. `ABC` uses the metaclass `ABCMeta` internally. |
| `@abstractmethod def display(self)` | Marks `display()` abstract: concrete subclasses must implement it. |
| `class Child(Parent)` | Inherits the requirement; must implement every unresolved abstract method to be instantiable. |
| `def display(self)` in `Child` | Satisfies the abstract-method requirement. |
| `obj = Child()` | Works because nothing abstract remains. |

---

## 6. Instantiating an Abstract Class

```python
from abc import ABC, abstractmethod


class Animal(ABC):

    @abstractmethod
    def sound(self):
        pass


animal = Animal()
```

```text
TypeError: Can't instantiate abstract class Animal without an implementation for abstract method 'sound'
```

- Exact wording varies by Python version (older: `...with abstract method sound`).
- `Animal` has an unresolved abstract method, so Python blocks instance creation.

### Gotcha: inheriting from `ABC` alone does not block instantiation

```python
from abc import ABC


class Demo(ABC):
    pass


obj = Demo()
print("Object created")   # Object created
```

- Works because `Demo` has **no** abstract methods.
- **Interview point:** a class is not non-instantiable just because it inherits from `ABC`. It needs at least one unresolved `@abstractmethod`.

## 7. Abstract Methods

An **abstract method** declares an operation that every concrete subclass must implement.

```python
from abc import ABC, abstractmethod


class Vehicle(ABC):

    @abstractmethod
    def start_engine(self):
        pass


class Car(Vehicle):

    def start_engine(self):
        print("Car engine started")


class Bike(Vehicle):

    def start_engine(self):
        print("Bike engine started")


car = Car()
bike = Bike()

car.start_engine()    # Car engine started
bike.start_engine()   # Bike engine started
```

- The parent defines the contract `start_engine()`; each subclass provides its own implementation.
- **Abstraction** establishes the common operation; **polymorphism** lets each object respond differently to it. See [Topic 4: Polymorphism](4.%20Polymorphism.md).

### Subclass that doesn't implement the abstract method

```python
from abc import ABC, abstractmethod


class Vehicle(ABC):

    @abstractmethod
    def start_engine(self):
        pass


class Car(Vehicle):
    pass


car = Car()   # TypeError
```

- `Car` inherits the unresolved abstract method, so it is still abstract.

### Intermediate subclasses can stay abstract

A subclass doesn't have to implement every abstract method immediately; it just remains abstract itself.

```python
from abc import ABC, abstractmethod


class A(ABC):

    @abstractmethod
    def show(self):
        pass


class B(A):
    pass


class C(B):

    def show(self):
        print("Implemented")


obj = C()
obj.show()   # Implemented
```

- `A` and `B` cannot be instantiated; `C` can.

## 8. Real-World Example: Payment Processing

**Goal:** support many payment methods without changing the checkout logic.

```python
from abc import ABC, abstractmethod


class PaymentProcessor(ABC):

    @abstractmethod
    def pay(self, amount):
        pass


class CreditCardPayment(PaymentProcessor):

    def pay(self, amount):
        print(f"Paid ${amount} using Credit Card")


class UPIPayment(PaymentProcessor):

    def pay(self, amount):
        print(f"Paid ${amount} using UPI")


class PayPalPayment(PaymentProcessor):

    def pay(self, amount):
        print(f"Paid ${amount} using PayPal")


def checkout(payment_processor, amount):
    payment_processor.pay(amount)


card = CreditCardPayment()
upi = UPIPayment()
paypal = PayPalPayment()

checkout(card, 100)
checkout(upi, 200)
checkout(paypal, 300)
```

```text
Paid $100 using Credit Card
Paid $200 using UPI
Paid $300 using PayPal
```

```text
                PaymentProcessor
                 (Abstract Class)
                        |
           +------------+------------+
           |            |            |
           v            v            v
      CreditCard       UPI         PayPal
       Payment       Payment       Payment
           |            |            |
           +------------+------------+
                        |
                        v
                 checkout()
```

### Why this is good design

- `checkout()` doesn't know or care which payment system it receives.
- Adding a provider = adding a subclass. `checkout()` is untouched:

```python
class NetBankingPayment(PaymentProcessor):

    def pay(self, amount):
        print(f"Paid ${amount} using Net Banking")
```

### Connection to SOLID

- **Open/Closed Principle (OCP):** extend with new payment classes without modifying `checkout()`.
- **Dependency Inversion Principle (DIP):** high-level checkout logic depends on the abstraction, not a specific provider.
- This shows structure only. Production code also needs validation, error handling, security and real provider integrations.

## 9. Abstract Class With Abstract and Concrete Methods

An abstract class can define **required** operations and provide **reusable** behavior at the same time.

```python
from abc import ABC, abstractmethod


class Employee(ABC):

    def __init__(self, name):
        self.name = name

    @abstractmethod
    def calculate_salary(self):
        pass

    def display_name(self):
        print(f"Employee: {self.name}")


class FullTimeEmployee(Employee):

    def calculate_salary(self):
        return 50000


class PartTimeEmployee(Employee):

    def calculate_salary(self):
        return 20000


emp1 = FullTimeEmployee("Ali")
emp2 = PartTimeEmployee("Sara")

emp1.display_name()
print(emp1.calculate_salary())

emp2.display_name()
print(emp2.calculate_salary())
```

```text
Employee: Ali
50000
Employee: Sara
20000
```

- **Abstract method** `calculate_salary()` → each concrete subclass must implement it.
- **Concrete method** `display_name()` → inherited and reused by all subclasses.
- **Constructor** `__init__()` → initializes the common employee data.
- An abstract class is a contract **and** a reusable base class. See [Topic 5: Inheritance](5.%20inheritance.md).

## 10. Can an Abstract Method Have an Implementation?

**Yes** (Python-specific). An abstract method doesn't have to contain only `pass`; it can hold real code.

```python
from abc import ABC, abstractmethod


class Logger(ABC):

    @abstractmethod
    def log(self, message):
        print(f"Base log: {message}")


class FileLogger(Logger):

    def log(self, message):
        super().log(message)
        print(f"File log: {message}")


logger = FileLogger()
logger.log("Application started")
```

```text
Base log: Application started
File log: Application started
```

- `Logger.log` is **still abstract** even though it has working code.
- `FileLogger` must override it to become concrete.
- The override can reuse the base code with `super().log(message)`.

## 11. Abstract Properties

Stack `@property` on top of `@abstractmethod` to require every concrete subclass to expose an attribute-like interface.

```python
from abc import ABC, abstractmethod


class Shape(ABC):

    @property
    @abstractmethod
    def area(self):
        pass


class Square(Shape):

    def __init__(self, side):
        self.side = side

    @property
    def area(self):
        return self.side ** 2


square = Square(5)

print(square.area)   # 25
```

- The subclass implements `area` as a property, so it's accessed as `square.area`, not `square.area()`.
- **Decorator order matters:** `@abstractmethod` goes **innermost** (applied first); `@property` wraps the result.

### Abstract property with a setter

Use when the contract requires a readable **and** writable property.

```python
from abc import ABC, abstractmethod


class Person(ABC):

    @property
    @abstractmethod
    def name(self):
        pass

    @name.setter
    @abstractmethod
    def name(self, value):
        pass


class Student(Person):

    def __init__(self, name):
        self.name = name

    @property
    def name(self):
        return self._name

    @name.setter
    def name(self, value):
        self._name = value


student = Student("Ali")
print(student.name)   # Ali

student.name = "Sara"
print(student.name)   # Sara
```

- `self.name = name` in `__init__` already goes through the setter.
- Properties themselves are covered in [Topic 6: Encapsulation](6.%20Encapsulation.md).

## 12. Abstract Class Methods and Static Methods

### Abstract class method

```python
from abc import ABC, abstractmethod


class Factory(ABC):

    @classmethod
    @abstractmethod
    def create(cls):
        pass


class UserFactory(Factory):

    @classmethod
    def create(cls):
        return cls()


obj = UserFactory.create()
print(type(obj).__name__)   # UserFactory
```

### Abstract static method

```python
from abc import ABC, abstractmethod


class Validator(ABC):

    @staticmethod
    @abstractmethod
    def validate(value):
        pass


class AgeValidator(Validator):

    @staticmethod
    def validate(value):
        return value >= 18


print(AgeValidator.validate(20))   # True
```

- Order: `@classmethod` / `@staticmethod` on top, `@abstractmethod` **innermost**.
- The old `abc.abstractclassmethod`, `abc.abstractstaticmethod` and `abc.abstractproperty` are deprecated (since 3.3); stack decorators instead.

## 13. Abstraction vs Encapsulation (interview favorite)

Related but different.

- **Abstraction** asks: *what functionality should be exposed?* e.g. `car.start()`; the user doesn't need the engine-starting details.
- **Encapsulation** asks: *how is data bundled with behavior, and how is access controlled?*

```python
class BankAccount:

    def __init__(self, balance):
        self.__balance = balance

    def deposit(self, amount):
        if amount > 0:
            self.__balance += amount

    def get_balance(self):
        return self.__balance
```

- The balance is read and changed only through controlled methods.
- Python uses conventions and **name mangling** (`__balance` → `_BankAccount__balance`), not strict private access. See [Topic 6: Encapsulation](6.%20Encapsulation.md).

| Abstraction | Encapsulation |
|---|---|
| Hides unnecessary implementation details | Bundles data + behavior and manages access |
| Focuses on **what** an object does | Focuses on **how** an object's state is managed |
| Simplifies interaction | Protects object invariants |
| Uses ABCs, protocols, clean APIs | Uses classes, properties, naming conventions |
| e.g. `payment.pay()` | e.g. controlled balance updates |

> **Remember:** Abstraction = hiding complexity. Encapsulation = organizing and controlling access to state and behavior. They work together.

## 14. Abstraction vs Inheritance vs Polymorphism

Three closely connected concepts in one example:

```python
from abc import ABC, abstractmethod


class Animal(ABC):

    @abstractmethod
    def speak(self):
        pass


class Dog(Animal):

    def speak(self):
        return "Bark"


class Cat(Animal):

    def speak(self):
        return "Meow"


def make_animal_speak(animal):
    print(animal.speak())


make_animal_speak(Dog())   # Bark
make_animal_speak(Cat())   # Meow
```

| Concept | Where in the code | Role |
|---|---|---|
| **Abstraction** | `class Animal(ABC)` + abstract `speak()` | Defines the common interface |
| **Inheritance** | `class Dog(Animal)` | Connects the concrete class to the abstraction |
| **Polymorphism** | `animal.speak()` | Same call, different behavior per object |

- Abstraction does **not** always need inheritance: duck typing and protocols also provide it (next sections).

## 15. Duck Typing: Abstraction Without ABC

**Duck typing:** if an object provides the operations your code needs, you can use it, no shared base class required.

```python
class EmailNotification:

    def send(self, message):
        print(f"Email: {message}")


class SMSNotification:

    def send(self, message):
        print(f"SMS: {message}")


def notify(service, message):
    service.send(message)


notify(EmailNotification(), "Hello")   # Email: Hello
notify(SMSNotification(), "Hello")     # SMS: Hello
```

- Neither class inherits from a shared ABC; both simply provide `send()`.
- `notify()` only expects a compatible operation. That is still abstraction.

| ABC | Duck Typing |
|---|---|
| Explicit interface contract | Implicit interface expectation |
| Usually relies on inheritance | No inheritance required |
| Missing abstract methods caught at **instantiation** | Missing operations usually fail only when **called** |
| Good for formal class hierarchies | Good for flexible Python APIs |

- Neither is universally better; choose per application.

## 16. Protocols: Structural Abstraction

A **`Protocol`** (from `typing`) describes the methods/attributes an object must provide. It uses **structural typing**: a class satisfies it by having the right shape, without inheriting from it.

```python
from typing import Protocol


class Notification(Protocol):

    def send(self, message: str) -> None:
        ...


class EmailService:

    def send(self, message: str) -> None:
        print(f"Email: {message}")


class SMSService:

    def send(self, message: str) -> None:
        print(f"SMS: {message}")


def notify(service: Notification, message: str) -> None:
    service.send(message)


notify(EmailService(), "Welcome")   # Email: Welcome
notify(SMSService(), "Welcome")     # SMS: Welcome
```

- `EmailService` and `SMSService` don't inherit from `Notification`, but have a compatible `send()`.
- Static type checkers (**mypy**, **Pyright**) verify this compatibility.

| ABC | Protocol |
|---|---|
| **Nominal** typing (via inheritance) | **Structural** typing (via matching methods/attributes) |
| Usually requires explicit subclassing | No inheritance required |
| Enforces abstract methods at instantiation | Mainly checked by static type checkers |
| Can provide reusable concrete methods | Mainly describes an expected interface |
| Suits related class hierarchies | Suits loosely coupled APIs |

- Python does **not** enforce type annotations at runtime; a Protocol is mainly a static-typing tool.
- `@runtime_checkable` enables limited `isinstance()` checks, which only check that the members exist, not their signatures or behavior.
- More on ABC vs Protocol in [Topic 9: Interfaces, Wildcards and Generics](9.%20interface,%20wildcards%20and%20generics.md).

## 17. Abstract Base Class vs `NotImplementedError`

Often confused; they fail at different times.

### Approach 1: `NotImplementedError`

```python
class Animal:

    def speak(self):
        raise NotImplementedError(
            "Subclass must implement speak()"
        )


class Dog(Animal):
    pass


dog = Dog()     # succeeds
dog.speak()     # NotImplementedError: Subclass must implement speak()
```

- Object creation succeeds; the error appears only when the method is **called**.

### Approach 2: `@abstractmethod`

```python
from abc import ABC, abstractmethod


class Animal(ABC):

    @abstractmethod
    def speak(self):
        pass


class Dog(Animal):
    pass


dog = Dog()     # TypeError at object creation
```

| `NotImplementedError` | `@abstractmethod` |
|---|---|
| Raised only when the method executes | Blocks **instantiation** while requirements remain |
| No ABC needed | Uses ABC machinery |
| Usable in ordinary methods | Explicitly marks a method abstract |
| Manual runtime signal | Built-in enforcement |

- **Interview point:** not interchangeable. You can use both together, but they serve different purposes.

## 18. Internals: How Abstraction Works in Python

### Step 1: `ABC` uses the `ABCMeta` metaclass

```python
from abc import ABC, abstractmethod


class Shape(ABC):

    @abstractmethod
    def area(self):
        pass


print(type(Shape))   # <class 'abc.ABCMeta'>
```

- A **metaclass** controls how classes are created and behave. `ABC` is just a helper class whose metaclass is `ABCMeta`.

### Step 2: `ABCMeta` records unresolved abstract methods

```python
print(Shape.__abstractmethods__)   # frozenset({'area'})
```

- When the class is created, `ABCMeta` collects every name whose attribute has `__isabstractmethod__ = True` (set by `@abstractmethod`) and is not overridden. The result is stored in `__abstractmethods__`.

### Step 3: a subclass implements the method

```python
class Circle(Shape):

    def area(self):
        return 100


print(Circle.__abstractmethods__)   # frozenset()
```

- Empty set = nothing unresolved.

### Step 4: instantiation is allowed

```python
circle = Circle()
print(circle.area())   # 100
```

- The actual check happens in `object.__new__`: if the class still has abstract methods, it raises `TypeError`.

```text
Class definition
       |
       v
ABCMeta processes class
       |
       v
Collect unresolved abstract methods
       |
       v
Any unresolved?
   +---+---+
   |       |
  Yes      No
   |       |
   v       v
Cannot    Can be
instantiate  instantiated
```

### Limitation: ABCs check presence, not correctness

At runtime ABCs do **not** validate parameter types, return types, signatures, logic or behavior.

```python
from abc import ABC, abstractmethod


class Parent(ABC):

    @abstractmethod
    def show(self, value):
        pass


class Child(Parent):

    def show(self):
        print("Hello")


obj = Child()     # succeeds: show() is overridden
obj.show(10)      # TypeError: Child.show() takes 1 positional argument but 2 were given
```

- Static type checkers catch many such signature mismatches.
- **Conclusion:** an ABC enforces that implementations **exist**, not that they are correct.

## 19. Complete Example: Shape System

Combines abstraction, inheritance, polymorphism, constructors and reusable methods.

```python
from abc import ABC, abstractmethod
import math


class Shape(ABC):

    def __init__(self, color):
        self.color = color

    @abstractmethod
    def area(self):
        pass

    @abstractmethod
    def perimeter(self):
        pass

    def describe(self):
        print(f"Shape color: {self.color}")


class Circle(Shape):

    def __init__(self, color, radius):
        super().__init__(color)
        self.radius = radius

    def area(self):
        return math.pi * self.radius ** 2

    def perimeter(self):
        return 2 * math.pi * self.radius


class Rectangle(Shape):

    def __init__(self, color, length, width):
        super().__init__(color)
        self.length = length
        self.width = width

    def area(self):
        return self.length * self.width

    def perimeter(self):
        return 2 * (self.length + self.width)


shapes = [
    Circle("Red", 5),
    Rectangle("Blue", 4, 6)
]


for shape in shapes:
    shape.describe()
    print(f"Area: {shape.area():.2f}")
    print(f"Perimeter: {shape.perimeter():.2f}")
    print("---")
```

```text
Shape color: Red
Area: 78.54
Perimeter: 31.42
---
Shape color: Blue
Area: 24.00
Perimeter: 20.00
---
```

1. **`Shape` is the abstraction:** every concrete shape must implement `area()` and `perimeter()`.
2. **Parent constructor** stores common data (`self.color = color`).
3. **Subclasses reuse it** with `super().__init__(color)`. See [Topic 2: Constructors](2.%20constructors.md).
4. **Subclasses define their own calculations:** `math.pi * self.radius ** 2` vs `self.length * self.width`.
5. **The loop is polymorphic:** `shape.area()` runs the method of the actual object.

- A `Triangle` can be added later without touching the loop, as long as it implements the required methods.

## 20. When Should You Use Abstraction?

Use formal abstractions when:

1. Multiple classes share an important behavioral contract.
2. The app should depend on interfaces, not specific implementations.
3. You want to **enforce** required methods in subclasses.
4. You expect new implementations later.
5. You want high-level logic separated from implementation details.
6. You need interchangeable implementations for testing.

| Application | Abstraction |
|---|---|
| Payment systems | `PaymentProcessor` |
| Database systems | `DatabaseConnection` |
| File storage | `StorageProvider` |
| Notifications | `NotificationService` |
| Cloud infrastructure | `CloudProvider` |
| Logging | `Logger` |
| Authentication | `AuthenticationProvider` |
| Machine learning | Model / estimator interface |

### When to avoid it

- Don't create an ABC for every class. One simple implementation with no meaningful shared contract → a regular class is enough.
- Unnecessary abstractions add complexity.
- **Rule of thumb:** abstract stable behavior and meaningful contracts, not every implementation detail.

## 21. Common Mistakes / Gotchas

- **Not implementing an inherited abstract method** (`class Child(Parent): pass`) → the subclass stays abstract; `Child()` raises `TypeError`.
- **Using `@abstractmethod` without `ABC`** → no enforcement; the object is created normally:

```python
from abc import abstractmethod


class Demo:

    @abstractmethod
    def show(self):
        pass


obj = Demo()   # succeeds: plain `type` metaclass ignores @abstractmethod
```

- **Fix for the above:** `class Demo(ABC):` or `class Demo(metaclass=ABCMeta):` (import `ABCMeta` from `abc`).
- **Assuming inheriting `ABC` makes a class non-instantiable** → only unresolved abstract methods do.
- **Assuming abstract methods can't have bodies** → they can; subclasses reuse them via `super()`.
- **Assuming ABCs validate signatures** → only presence is checked at runtime; parameter/return mismatches surface on call (or via type checkers).
- **Wrong decorator order** (`@abstractmethod` above `@property`/`@classmethod`/`@staticmethod`) → `@abstractmethod` must be innermost; above `@property` it raises `AttributeError`.
- **Confusing `_method` with an abstract method** → a leading underscore only signals internal use; it declares nothing abstract.
- **Treating `NotImplementedError` like `@abstractmethod`** → it only fails when the method is called, not at object creation.
- **Assuming every abstraction needs inheritance** → duck typing and protocols are valid alternatives.
- **Using ABCs unnecessarily** → a simple public API or normal class may be all you need.

## 22. Interview Questions

**Q1. What is abstraction in Python?**
An OOP principle that hides unnecessary implementation details and exposes essential functionality. Formally via the `abc` module (ABCs, abstract methods); informally via plain APIs, duck typing and protocols.

**Q2. What is an abstract class?**
A class that defines common behavior or required operations for subclasses. With unresolved abstract methods, it cannot be instantiated directly.

**Q3. What is an abstract method?**
A method decorated with `@abstractmethod`. Concrete subclasses must resolve all inherited abstract methods before they can be instantiated.

**Q4. Can we create an object of an abstract class?**
Not while it has unresolved abstract methods. A class inheriting from `ABC` with no abstract methods can still be instantiated.

**Q5. Can an abstract class have a constructor?**
Yes. Concrete subclasses reuse it with `super().__init__(...)`.

```python
class Parent(ABC):

    def __init__(self, value):
        self.value = value
```

**Q6. Can an abstract class have normal methods?**
Yes. It can mix abstract and concrete methods.

**Q7. Can an abstract class contain instance variables?**
Yes. Set them in `__init__()` or other instance methods.

**Q8. Can an abstract method have implementation code?**
Yes. It stays abstract, but subclasses can call its body via `super()`.

**Q9. What happens if a subclass does not implement an abstract method?**
The subclass remains abstract and cannot be instantiated until the requirement is resolved.

**Q10. Abstraction vs encapsulation?**
Abstraction simplifies the interface by hiding unnecessary details. Encapsulation bundles data with behavior and controls how state is accessed or modified.

**Q11. Does Python support interfaces?**
Yes, without a Java-style `interface` keyword: via ABCs, Protocols and duck typing. See [Topic 9](9.%20interface,%20wildcards%20and%20generics.md).

**Q12. Can we achieve abstraction without ABC?**
Yes. Ordinary APIs, duck typing and protocols all provide abstraction.

**Q13. What is `ABCMeta`?**
The metaclass implementing Python's ABC machinery. It tracks abstract methods (`__abstractmethods__`) so instantiation is blocked while any remain unresolved.

**Q14. `@abstractmethod` vs `NotImplementedError`?**
`@abstractmethod` marks a method abstract and blocks instantiation. `NotImplementedError` is an exception raised only when execution reaches the `raise`.

**Q15. Does an ABC enforce correct business logic?**
No. It enforces declared abstract requirements at class level, not correct results. Testing, validation and static analysis are still needed.

**1. Banking system.** Create an abstract class `BankAccount` with a constructor taking `balance`, an abstract method `calculate_interest()` and a concrete method `show_balance()`. Implement `SavingsAccount` and `CurrentAccount` with different interest calculations.

class SavingsAccount(BankAccount):

class CurrentAccount(BankAccount):

        return 0


accounts = [

    CurrentAccount(20000)
]

for account in accounts:

    print("Interest:", account.calculate_interest())

## Quick Recap

- **Abstraction** → expose **what**, hide **how**. One of the four OOP pillars.
- **`abc` module** → `ABC` (metaclass `ABCMeta`) + `@abstractmethod`.
- **Unresolved abstract methods** → `TypeError` on instantiation; a subclass missing one stays abstract.
- Inheriting `ABC` **alone** doesn't block instantiation; `@abstractmethod` **without** `ABC` isn't enforced.
- Abstract classes can have **constructors, instance variables and concrete methods**.
- Abstract methods **can have bodies**; reuse them via `super()`.
- Abstract **properties / classmethods / staticmethods** → `@abstractmethod` innermost.
- **`__abstractmethods__`** lists unresolved names; ABCs check presence, not signatures or behavior.
- **`NotImplementedError`** fails at call time; **`@abstractmethod`** fails at object creation.
- **Duck typing** and **`Protocol`** → abstraction without inheritance (Protocols checked statically).
- **Polymorphism** → different implementations behind one common call.
- Don't over-abstract: abstract meaningful, stable contracts only.

> **Core idea:** abstraction exposes essential functionality while hiding implementation details; in Python it's done with ABCs, abstract methods, protocols and well-designed APIs.
