# Topic 4: Polymorphism

> **TL;DR:** **Polymorphism** ("many forms") means the same operation behaves differently depending on the object it acts on. In Python it comes from **method overriding**, **operator overloading** (dunder methods) and **duck typing**; traditional **method overloading** is not supported. Write code against **behavior**, not concrete types.

---

## 1. What is Polymorphism?

**Poly** = many, **morph** = forms. **Polymorphism** means the **same interface or operation** produces **different behavior** depending on the object involved. It is one of the four OOP pillars (with encapsulation, inheritance and abstraction) and a frequent interview topic because it ties together overriding, overloading, operator overloading, inheritance and duck typing.

**Analogy:** a customer can pay by credit card, UPI or wallet. The action is the same (`pay(amount)`); the implementation differs.

| `pay(amount)` on | Implementation |
|---|---|
| Credit Card | Card processing |
| UPI | UPI transfer |
| Wallet | Wallet balance |

```python
class CreditCard:
    def pay(self, amount):
        print(f"Paid {amount} using Credit Card")


class UPI:
    def pay(self, amount):
        print(f"Paid {amount} using UPI")


class Wallet:
    def pay(self, amount):
        print(f"Paid {amount} using Wallet")


payments = [CreditCard(), UPI(), Wallet()]

for payment in payments:
    payment.pay(1000)
```

```text
Paid 1000 using Credit Card
Paid 1000 using UPI
Paid 1000 using Wallet
```

- `payment.pay(1000)` is **one line** that works with **three different types**.
- At runtime Python looks up `pay()` on each object and runs **that object's** implementation. That is polymorphism.

## 2. Why Polymorphism?

**Without polymorphism:** the caller checks the type itself.

```python
def process_payment(payment_type, amount):
    if payment_type == "credit":
        print("Credit card payment")
    elif payment_type == "upi":
        print("UPI payment")
    elif payment_type == "wallet":
        print("Wallet payment")
```

- Works, but every new payment type means **editing this function**.

**With polymorphism:** the caller just calls the common method.

```python
def process_payment(payment, amount):
    payment.pay(amount)

process_payment(CreditCard(), 1000)   # Paid 1000 using Credit Card
process_payment(UPI(), 2000)          # Paid 2000 using UPI
process_payment(Wallet(), 500)        # Paid 500 using Wallet
```

- The function doesn't need to know the concrete type. Each class handles its own implementation.

**Benefits:**
- **Extensibility:** new types work with existing functions.
- **Code reuse:** one function operates on many types.
- **Less conditional logic:** no repeated `if-elif` type checks.
- **Loose coupling:** code depends on a common behavior, not a specific implementation.
- **Maintainability:** behavior changes stay inside individual classes.

> **Key principle:** program against **behavior**, not unnecessarily against concrete types.

---

## 3. Types of Polymorphism

Classical OOP splits polymorphism into two types:

| Type | Also called | Forms |
|---|---|---|
| **Compile-time** | Static polymorphism | Method overloading, operator overloading\* |
| **Runtime** | Dynamic polymorphism | Method overriding, duck typing |

\*A common textbook classification, not a precise description of Python's execution model.

- Python is **dynamically typed**. It has **no Java-style compile-time method overloading**.
- Operator behavior is resolved **at runtime** through special methods.
- So in Python, practically all polymorphism is **runtime** polymorphism.

## 4. Method Overloading

**Method overloading** = several methods with the **same name** but **different parameter signatures**; the language picks one based on the arguments. Java example:

```java
add(int a, int b)
add(int a, int b, int c)
add(double a, double b)
```

### Python does not support it

```python
class Calculator:
    def add(self, a, b):
        return a + b

    def add(self, a, b, c):
        return a + b + c


calc = Calculator()

print(calc.add(10, 20, 30))   # 60
print(calc.add(10, 20))       # TypeError
```

```text
60
TypeError: Calculator.add() missing 1 required positional argument: 'c'
```

**Why:** Python executes the class body top to bottom. The second `def add` **rebinds** the name `add` in the class namespace, replacing the first. Only the **last definition** survives.

### Approach 1: Default arguments

```python
class Calculator:
    def add(self, a, b, c=0):
        return a + b + c


calc = Calculator()

print(calc.add(10, 20))       # 30
print(calc.add(10, 20, 30))   # 60
```

- `c` defaults to `0`, so both 2 and 3 arguments work.

### Approach 2: Variable-length arguments (`*args`)

```python
class Calculator:
    def add(self, *args):
        return sum(args)


calc = Calculator()

print(calc.add(10, 20))           # 30
print(calc.add(10, 20, 30))       # 60
print(calc.add(10, 20, 30, 40))   # 100
```

- `*args` collects positional arguments into a **tuple**: `calc.add(10, 20, 30)` gives `args = (10, 20, 30)`.
- This is flexible argument handling, not true signature-based overloading.

### Approach 3: `functools.singledispatch` (type-based dispatch)

```python
from functools import singledispatch

@singledispatch
def display(value):
    print("General:", value)


@display.register
def _(value: int):
    print("Integer:", value)


@display.register
def _(value: str):
    print("String:", value)


display(10)          # Integer: 10
display("Python")    # String: Python
display([1, 2, 3])   # General: [1, 2, 3]
```

- Picks an implementation based on the **type of the first argument**, at **runtime**.
- Unregistered types fall back to the base function.
- For methods inside a class, use `functools.singledispatchmethod`.

> **Interview takeaway:** Python has no traditional signature-based method overloading. Get similar behavior with **default arguments**, **`*args`**, **manual dispatch** (`isinstance` checks), or **`functools.singledispatch`**.

## 5. Method Overriding

**Method overriding** = a subclass defines a method with the **same name** as an inherited one, giving it a **different implementation**. The most important form of polymorphism in Python. See also [Topic 5: Inheritance](5.%20inheritance.md).

```python
class Animal:
    def sound(self):
        print("Animal makes a sound")


class Dog(Animal):
    def sound(self):
        print("Dog barks")


class Cat(Animal):
    def sound(self):
        print("Cat meows")


a = Animal()
d = Dog()
c = Cat()

a.sound()
d.sound()
c.sound()
```

```text
Animal makes a sound
Dog barks
Cat meows
```

- `Animal.sound()` defines the parent behavior; `Dog.sound()` and `Cat.sound()` **override** it.
- All three support `sound()` but behave differently.

### Runtime polymorphism with inheritance

```python
animals = [Animal(), Dog(), Cat()]

for animal in animals:
    animal.sound()
```

```text
Animal makes a sound
Dog barks
Cat meows
```

- Python picks the method from each object's **runtime class**, following its **MRO** (method resolution order).

### Extending the parent with `super()`

Use `super()` when the child should **extend** the parent behavior instead of replacing it.

```python
class Employee:
    def work(self):
        print("Employee is working")


class Developer(Employee):
    def work(self):
        super().work()
        print("Developer is writing Python code")


dev = Developer()
dev.work()
```

```text
Employee is working
Developer is writing Python code
```

- `super().work()` calls the **next implementation in the MRO** (here `Employee.work`), then the child adds its own behavior.

### Rules and key points

- Overriding requires **inheritance**.
- The subclass defines an attribute/method under the **inherited name**.
- No `@Override` annotation is required. Python 3.12+ has `@typing.override`, used only by static type checkers.
- A subclass **may change the signature**, but incompatible signatures break callers expecting the parent interface (see Gotchas).

### Overloading vs Overriding

| Feature | Overloading | Overriding |
|---|---|---|
| Meaning | Same method name, different accepted arguments | Subclass redefines inherited behavior |
| Inheritance required | No | Yes |
| Python support | No traditional declaration-based overloading | Yes |
| Typical purpose | Flexible ways to call an operation | Specialized behavior in subclasses |
| Example | `add(a, b)` and `add(a, b, c)` | `Dog.sound()` overriding `Animal.sound()` |

## 6. Operator Overloading

The same operator behaves differently for different types.

```python
print(10 + 20)              # 30
print("Hello" + " World")   # Hello World
print([1, 2] + [3, 4])      # [1, 2, 3, 4]
```

- `+` means **addition** for numbers and **concatenation** for strings and lists. This is **operator polymorphism**.

### How Python implements it: dunder methods

Each operator maps to a **special (dunder) method**. `+` maps to `__add__()`.

```python
a + b   # roughly: a.__add__(b)
```

Full resolution of `a + b`:
1. Try `a.__add__(b)`.
2. If it is missing or returns `NotImplemented`, try the **reflected** method `b.__radd__(a)`.
3. If both fail, raise `TypeError: unsupported operand type(s)`.

### Custom example: `Vector`

```python
class Vector:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __add__(self, other):
        if not isinstance(other, Vector):
            return NotImplemented

        return Vector(
            self.x + other.x,
            self.y + other.y
        )

    def __repr__(self):
        return f"Vector({self.x}, {self.y})"


v1 = Vector(2, 3)
v2 = Vector(4, 5)

v3 = v1 + v2

print(v3)   # Vector(6, 8)
```

**Behind the scenes:**

```text
v1 + v2
-> v1.__add__(v2)
-> Vector(2 + 4, 3 + 5)
-> Vector(6, 8)
```

- **Why return `NotImplemented`** instead of raising an error? It lets Python try the other operand's method (`__radd__`) before deciding the operation is unsupported.

```python
print(v1 + 5)
```

```text
TypeError: unsupported operand type(s) for +: 'Vector' and 'int'
```

### Common operator / built-in special methods

| Operator / call | Special method |
|---|---|
| `+` | `__add__()` |
| `-` | `__sub__()` |
| `*` | `__mul__()` |
| `/` | `__truediv__()` |
| `//` | `__floordiv__()` |
| `==` | `__eq__()` |
| `<` | `__lt__()` |
| `>` | `__gt__()` |
| `len(obj)` | `__len__()` |
| `str(obj)` | `__str__()` |

### Built-ins are polymorphic too: `len()`

```python
print(len("Python"))            # 6
print(len([10, 20, 30]))        # 3
print(len({"a": 1, "b": 2}))    # 2
```

Define `__len__` to make your own class work with `len()`:

```python
class Team:
    def __init__(self, members):
        self.members = members

    def __len__(self):
        return len(self.members)


team = Team(["Aamir", "Rahul", "Ali"])

print(len(team))   # 3
```

- `len()` works with any type that implements the common `__len__` **protocol**.

## 7. Duck Typing

> "If it walks like a duck and quacks like a duck, treat it as a duck."

**Duck typing** = Python cares about **what an object can do** (which methods it supports), not **which class hierarchy** it belongs to. It is polymorphism **without inheritance**.

```python
class Duck:
    def speak(self):
        print("Quack")


class Human:
    def speak(self):
        print("Hello")


class Robot:
    def speak(self):
        print("Beep")


def make_speak(obj):
    obj.speak()


make_speak(Duck())    # Quack
make_speak(Human())   # Hello
make_speak(Robot())   # Beep
```

- `Duck`, `Human` and `Robot` share **no parent class**.
- `make_speak()` works with all three because each provides `speak()`.

### Duck typing vs inheritance-based polymorphism

| Inheritance-based | Duck typing |
|---|---|
| Objects share a class hierarchy | Common parent not required |
| Subclasses override methods | Unrelated classes expose matching methods |
| Relationships are explicitly declared | Compatibility follows supported behavior |
| Example: `Dog(Animal)` | Example: `Robot.speak()` and `Human.speak()` |

### Missing behavior fails at runtime

```python
class Car:
    def drive(self):
        print("Driving")


make_speak(Car())
```

```text
AttributeError: 'Car' object has no attribute 'speak'
```

- Python does **not** check in advance that `Car` has `speak()`. The call fails only when the missing attribute is accessed.

### EAFP: Easier to Ask Forgiveness than Permission

Pythonic style: don't check every type beforehand; **try the operation** and handle the exception.

```python
def make_speak(obj):
    try:
        obj.speak()
    except AttributeError:
        print("Object does not support speaking")
```

- **Caveat:** this also swallows unrelated `AttributeError`s raised *inside* `speak()`. Safer: guard only the attribute lookup.

```python
def make_speak(obj):
    try:
        speak = obj.speak
    except AttributeError:
        print("Object does not support speaking")
    else:
        speak()
```

| EAFP | LBYL (Look Before You Leap) |
|---|---|
| `try: obj.speak()` / `except AttributeError` | `if hasattr(obj, "speak"): obj.speak()` |
| Pythonic default | Common in other languages |
| Attempt first, handle failure | Check first, then act |

## 8. Polymorphism with Abstract Classes

Duck typing is flexible but enforces nothing. An **abstract base class** (`ABC` + `@abstractmethod` from the `abc` module) **forces** concrete subclasses to implement required methods.

```python
from abc import ABC, abstractmethod


class Shape(ABC):
    @abstractmethod
    def area(self):
        pass


class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

    def area(self):
        return 3.14 * self.radius ** 2


class Rectangle(Shape):
    def __init__(self, length, width):
        self.length = length
        self.width = width

    def area(self):
        return self.length * self.width


shapes = [
    Circle(5),
    Rectangle(4, 6)
]

for shape in shapes:
    print(shape.area())
```

```text
78.5
24
```

- Both classes implement the same interface, `area()`, with different implementations.

### Missing implementation → `TypeError`

```python
class Triangle(Shape):
    pass


t = Triangle()
```

```text
TypeError: Can't instantiate abstract class Triangle without an implementation for abstract method 'area'
```

- `Triangle` is still abstract, so it can't be instantiated (exact message varies by Python version).
- Use ABCs when you need a **formally declared contract**.
- Alternative: **`typing.Protocol`** lets static type checkers verify that classes support an interface **without a shared base class** ("static duck typing").
- Details: [Topic 7: Abstraction](7.%20abstraction.md) and [Topic 9: Interfaces](9.%20interface,%20wildcards%20and%20generics.md).

## 9. Internals: How Python Resolves Polymorphic Calls

```python
class Animal:
    def sound(self):
        print("Animal sound")


class Dog(Animal):
    def sound(self):
        print("Bark")


dog = Dog()
dog.sound()   # Bark
```

Python doesn't pick `Animal.sound()` just because `Dog` inherits from `Animal`. Lookup starts from the **runtime class**:

```text
dog.sound()
-> search Dog: does Dog define sound()?  Yes -> use Dog.sound()
-> (if not found) continue along Dog's MRO: Animal -> object
-> output: Bark
```

- Full attribute lookup also involves the instance `__dict__` and **descriptors**, but for methods the class MRO search is what decides.
- Inspect the order with `__mro__`:

```python
print(Dog.__mro__)
```

```text
(<class '__main__.Dog'>, <class '__main__.Animal'>, <class 'object'>)
```

- This lookup is what makes overriding and inheritance-based polymorphism work.
- Operators and built-ins look up dunder methods on the **type**, not the instance: `len(obj)` → `type(obj).__len__(obj)`.

### Liskov Substitution Principle (LSP)

A subclass should be usable **anywhere its parent is expected**, without breaking the expected behavior.

```python
class Bird:
    def move(self):
        print("Moving")


class Penguin(Bird):
    def move(self):
        print("Walking or swimming")
```

- Both support the general `move()` operation, so substitution is safe.
- **Violation:** if every `Bird` had `fly()` and `Penguin.fly()` raised an exception, code that assumes all birds can fly would break.
- Good polymorphism needs **compatible behavior**, not just matching method names.

## 10. Real-World Example: Notification System

```python
class EmailNotification:
    def send(self, message):
        print(f"Email sent: {message}")


class SMSNotification:
    def send(self, message):
        print(f"SMS sent: {message}")


class PushNotification:
    def send(self, message):
        print(f"Push notification: {message}")


class NotificationService:
    def notify(self, notification, message):
        notification.send(message)


service = NotificationService()

service.notify(EmailNotification(), "Order confirmed")
service.notify(SMSNotification(), "OTP generated")
service.notify(PushNotification(), "New message received")
```

```text
Email sent: Order confirmed
SMS sent: OTP generated
Push notification: New message received
```

- `NotificationService` doesn't care whether it gets an email, SMS or push object; it just calls `notification.send(message)`.
- A new `WhatsAppNotification` with a compatible `send()` works **without modifying** the service.
- The example only prints; a real system would deliver through the relevant provider.

## 11. Must-Know Distinctions

### Overloading-like vs overriding vs duck typing

**Method overloading-like flexibility** (default arguments):

```python
def add(a, b, c=0):
    return a + b + c
```

**Method overriding** (subclass replaces inherited behavior):

```python
class Parent:
    def show(self):
        print("Parent")

class Child(Parent):
    def show(self):
        print("Child")
```

**Duck typing** (any object with a compatible `run()` works, shared parent or not):

```python
def execute(obj):
    obj.run()
```

### Polymorphism vs Abstraction

| Polymorphism | Abstraction |
|---|---|
| The same operation has **different implementations** | Expose **essential behavior**, hide implementation details |
| Answers "which implementation runs?" | Answers "what does the caller need to know?" |
| e.g. `shape.area()` differs per shape | e.g. `Shape` declares `area()` without implementing it |

- They often work together (Section 8), but neither is the other. See [Topic 7: Abstraction](7.%20abstraction.md).

## 12. Common Mistakes / Gotchas

- **Defining the same method twice to "overload" it** → the second definition replaces the first; Python doesn't select by argument count. Use default args, `*args` or `singledispatch`.

```python
class A:
    def show(self):
        print("First")

    def show(self, x):
        print("Second")

A().show()   # TypeError: A.show() missing 1 required positional argument: 'x'
```

- **Thinking inheritance is required for polymorphism** → it isn't; duck typing lets unrelated classes support a common operation.
- **Thinking `super()` always calls the direct parent** → it calls the next class in the **MRO**, which matters with multiple inheritance. See [Topic 5: Inheritance](5.%20inheritance.md).
- **Assuming overriding methods are automatically compatible** → Python allows a changed signature, but callers using the parent interface break:

```python
class Parent:
    def calculate(self, x):
        return x * 2


class Child(Parent):
    def calculate(self, x, y):
        return x + y


obj = Child()
obj.calculate(10)   # TypeError: Child.calculate() missing 1 required positional argument: 'y'
```

- **Confusing polymorphism with abstraction** → different concepts that often work together (Section 11).
- **Mixing up `NotImplemented` and `NotImplementedError`** → **return** `NotImplemented` from operator dunders (lets Python try `__radd__`); **raise** `NotImplementedError` for "subclass must implement this".
- **Wrapping a whole method call in `except AttributeError`** → hides real bugs inside the method. Guard only the attribute lookup (Section 7).

## 13. Interview Questions

**Q1. Is polymorphism possible without inheritance in Python?**
Yes. **Duck typing**: unrelated classes that provide the same method work with the same code.

**Q2. Does Python support compile-time polymorphism?**
Not in the Java sense. There's no signature-based overloading; dispatch happens at runtime. Overloading-like behavior comes from default args, `*args` or `functools.singledispatch`.

**Q3. Difference between method overriding and duck typing?**
Overriding needs **inheritance**: a subclass redefines a parent method. Duck typing needs **no relationship**: any object with a matching method works.

**Q4. Can a child class call an overridden parent method?**
Yes, with `super().method()` (follows the MRO) or explicitly `Parent.method(self)`.

**Q5. Is operator overloading an example of polymorphism?**
Yes. The same operator (`+`) behaves differently per type, via dunder methods like `__add__()`.

**Q6. Relationship between polymorphism and the Liskov Substitution Principle?**
Polymorphism lets a subclass stand in for its parent. LSP says that substitution must not break the parent's expected behavior, so overrides need compatible signatures and semantics.

**Q7. What happens if a class defines two methods with the same name?**
The later definition rebinds the name and replaces the earlier one. Only the last one exists.

**Q8. Why should `__add__` return `NotImplemented` for unsupported types?**
So Python can try the other operand's reflected method (`__radd__`) before raising `TypeError`.

## 14. Practice Questions

**1. What is the output?**

```python
class A:
    def show(self):
        print('A')

class B(A):
    def show(self):
        print('B')

obj = B()
obj.show()
```

(a) `A`  (b) `B`  (c) `A` followed by `B`  (d) Error

<details><summary>Answer</summary>

**(b) `B`**: `B.show()` overrides `A.show()`. Lookup starts at the runtime class `B`, and `super()` is never called, so `A.show()` doesn't run.

</details>

**2. What happens here?**

```python
class Test:
    def add(self, a):
        return a

    def add(self, a, b):
        return a + b

print(Test().add(5))
```

(a) `5`  (b) `10`  (c) `None`  (d) `TypeError`

<details><summary>Answer</summary>

**(d) `TypeError`**: the second `add` replaces the first, so only `add(self, a, b)` exists and `add(5)` is missing `b`.

</details>

**3. Which concept is illustrated?**

```python
class Car:
    def start(self):
        print('Car')

class Robot:
    def start(self):
        print('Robot')

def run(obj):
    obj.start()
```

(a) Constructor chaining  (b) Duck typing  (c) Method overloading  (d) Encapsulation

<details><summary>Answer</summary>

**(b) Duck typing**: `Car` and `Robot` are unrelated, but `run()` works with both because each provides `start()`.

</details>

**4. Which method customizes the `+` operator?**

(a) `__plus__`  (b) `__sum__`  (c) `__add__`  (d) `__operator__`

<details><summary>Answer</summary>

**(c) `__add__`**: `a + b` calls `a.__add__(b)` (falling back to `b.__radd__(a)`). The other names are not special methods.

</details>

## Quick Recap

- **Polymorphism** → same interface or operation, different behavior per object.
- **Method overloading** → not supported traditionally; the last same-name definition wins. Use default args, `*args` or `singledispatch`.
- **Method overriding** → a subclass replaces or extends inherited behavior; the runtime class decides which method runs.
- **`super()`** → delegates to the next class in the **MRO**, not necessarily the direct parent.
- **Operator overloading** → dunder methods (`__add__`, `__eq__`, `__len__`, ...) customize operators and built-ins; return `NotImplemented` for unsupported types.
- **Duck typing** → compatible behavior matters more than shared inheritance; missing methods fail at runtime with `AttributeError`.
- **EAFP** → try the operation, handle the exception; don't pre-check types.
- **Runtime polymorphism** → behavior is selected for the actual objects during execution.
- **Abstract classes** → enforce required methods on concrete subclasses; `typing.Protocol` does it statically without a base class.
- **Liskov Substitution Principle** → subtypes must preserve the expectations of their parent's contract.

> **Core idea:** polymorphism is not just "many methods with the same name"; it lets code work with different implementations through a common operation, without knowing every concrete type.
