# OOP in Python — Topic 4: Polymorphism

Polymorphism is one of the four main pillars of Object-Oriented Programming, alongside encapsulation, inheritance, and abstraction.

It is also a frequently asked OOP interview topic because it connects several concepts: method overriding, method overloading, operator overloading, inheritance, and duck typing.

We'll study it in this order:

## 1. What is polymorphism?

The word polymorphism comes from two Greek words:

- Poly = Many
    
- Morph = Forms
    

In programming, polymorphism means that the same interface or operation can exhibit different behavior depending on the object involved.

### Real-world analogy

Consider a payment system.

A customer can pay using a credit card, UPI, or a digital wallet.

The action is the same: `pay()`.

But the implementation depends on the payment method.

`pay(amount)`

Common operation

Credit Card

Card processing

UPI

UPI transfer

Wallet

Wallet balance

Same operation, different implementations.

### Python implementation

```
class CreditCard:
    def pay(self, amount):
        print(f"Paid {amount} using Credit Card")


class UPI:
    def pay(self, amount):
        print(f"Paid {amount} using UPI")


class Wallet:
    def pay(self, amount):
        print(f"Paid {amount} using Wallet")


payments = [CreditCard(), UPI(), Wallet()]

for payment in payments:
    payment.pay(1000)
```

Output:

```
Paid 1000 using Credit Card
Paid 1000 using UPI
Paid 1000 using Wallet
```

Notice:

```
payment.pay(1000)
```

The same line works with three different object types.

Python looks up the `pay()` method on the appropriate object and executes its implementation.

This is polymorphism.

## 2. Why do we need polymorphism?

Imagine writing a payment processing function without polymorphism:

```
def process_payment(payment_type, amount):
    if payment_type == "credit":
        print("Credit card payment")

    elif payment_type == "upi":
        print("UPI payment")

    elif payment_type == "wallet":
        print("Wallet payment")
```

This works, but adding another payment type requires modifying this function.

With polymorphism:

```
def process_payment(payment, amount):
    payment.pay(amount)
```

Usage:

```
process_payment(CreditCard(), 1000)
process_payment(UPI(), 2000)
process_payment(Wallet(), 500)
```

Now the processing function doesn't need to know which particular payment type it receives.

Each payment class handles its own implementation.

### Benefits

- Extensibility: New object types can work with existing functions.
    
- Code reuse: One function can operate on many types.
    
- Reduced conditional logic: Avoid repeated `if-elif` type checking.
    
- Loose coupling: Code depends on a common behavior rather than a particular implementation.
    
- Maintainability: Behavior can be changed within individual classes.
    

A key principle is to program against behavior, not unnecessarily against concrete types.

## 3. Types of polymorphism

In classical OOP discussions, polymorphism is often classified into two broad types.

Polymorphism

Compile-time

Static polymorphism

Method overloading

Operator overloading*

Runtime

Dynamic polymorphism

Method overriding

Duck typing

*This is a common textbook classification, not a precise description of Python's execution model.

Important Python-specific distinction: Python is dynamically typed. It doesn't provide Java-style compile-time method overloading, and operator behavior is generally resolved at runtime through special methods.

Let's understand each concept separately.

## 4. Method overloading

### What is method overloading?

Method overloading means having multiple methods with the same name but different parameter signatures.

For example, in Java, you might have:

```
add(int a, int b)
add(int a, int b, int c)
add(double a, double b)
```

The language chooses an appropriate implementation based on the arguments.

### Does Python support method overloading?

Python does not support traditional method overloading by defining several methods with the same name in a class.

Consider:

```
class Calculator:
    def add(self, a, b):
        return a + b

    def add(self, a, b, c):
        return a + b + c


calc = Calculator()

print(calc.add(10, 20, 30))
```

Output:

```
60
```

But:

```
print(calc.add(10, 20))
```

Raises:

```
TypeError: Calculator.add() missing 1 required positional argument: 'c'
```

### Why?

Python executes class definitions in order.

The second `add()` definition replaces the first binding for `add` in the class namespace.

Therefore, only the latest definition remains accessible under that name.

### How can we achieve similar behavior in Python?

#### Approach 1: Default arguments

```
class Calculator:
    def add(self, a, b, c=0):
        return a + b + c


calc = Calculator()

print(calc.add(10, 20))
print(calc.add(10, 20, 30))
```

Output:

```
30
60
```

The method accepts both two and three arguments because `c` has a default value.

#### Approach 2: Variable-length arguments (`*args`)

```
class Calculator:
    def add(self, *args):
        return sum(args)


calc = Calculator()

print(calc.add(10, 20))
print(calc.add(10, 20, 30))
print(calc.add(10, 20, 30, 40))
```

Output:

```
30
60
100
```

Here:

```
*args
```

collects the positional arguments into a tuple.

For example:

```
calc.add(10, 20, 30)
```

Inside the function:

```
args = (10, 20, 30)
```

This is flexible argument handling, not traditional signature-based overloading.

#### Approach 3: `functools.singledispatch`

Python also supports type-based dispatch through its standard library.

```
from functools import singledispatch

@singledispatch
def display(value):
    print("General:", value)


@display.register
def _(value: int):
    print("Integer:", value)


@display.register
def _(value: str):
    print("String:", value)


display(10)
display("Python")
display([1, 2, 3])
```

Output:

```
Integer: 10
String: Python
General: [1, 2, 3]
```

`singledispatch` selects an implementation based on the type of the first argument. This selection happens at runtime.

For methods, Python also provides `functools.singledispatchmethod`.

### Interview takeaway

Python doesn't natively perform traditional signature-based method overloading. Similar behavior can be implemented using default arguments, `*args`, manual dispatch, or `functools.singledispatch`.

## 5. Method overriding

This is one of the most important forms of polymorphism in Python.

### What is method overriding?

Method overriding occurs when a subclass defines a method with the same name as a method inherited from its parent class, providing a different implementation.

### Example

```
class Animal:
    def sound(self):
        print("Animal makes a sound")


class Dog(Animal):
    def sound(self):
        print("Dog barks")


class Cat(Animal):
    def sound(self):
        print("Cat meows")


a = Animal()
d = Dog()
c = Cat()

a.sound()
d.sound()
c.sound()
```

Output:

```
Animal makes a sound
Dog barks
Cat meows
```

Here:

- `Animal.sound()` defines the parent behavior.
    
- `Dog.sound()` overrides the parent behavior.
    
- `Cat.sound()` also overrides the parent behavior.
    

All three objects support `sound()`, but behave differently.

### Runtime polymorphism with inheritance

```
animals = [Animal(), Dog(), Cat()]

for animal in animals:
    animal.sound()
```

Output:

```
Animal makes a sound
Dog barks
Cat meows
```

Python chooses the method according to the runtime class and method resolution order of each object.

### Method overriding with `super()`

Sometimes the child class needs to extend the parent behavior instead of replacing it entirely.

```
class Employee:
    def work(self):
        print("Employee is working")


class Developer(Employee):
    def work(self):
        super().work()
        print("Developer is writing Python code")


dev = Developer()
dev.work()
```

Output:

```
Employee is working
Developer is writing Python code
```

Here, `super().work()` invokes the next applicable implementation in the MRO.

The child method adds specialized functionality after that call.

### Rules and important points

- Overriding is associated with inheritance.
    
- The subclass supplies an attribute or method under the inherited name.
    
- Python does not require an `@Override` annotation.
    
- Python 3.12+ has `typing.override`, useful for static type checking.
    
- A subclass may change a method's signature, but incompatible signatures can break callers expecting the parent interface.
    

### Method overloading vs method overriding

|Feature|Overloading|Overriding|
|---|---|---|
|Meaning|Same method name, different accepted arguments|Subclass redefines inherited behavior|
|Inheritance required|No|Yes|
|Python support|No traditional declaration-based overloading|Yes|
|Typical purpose|Flexible ways to call an operation|Specialized behavior in subclasses|
|Example|`add(a,b)` and `add(a,b,c)`|`Dog.sound()` overriding `Animal.sound()`|

## 6. Operator overloading

Python allows operators to behave differently for objects of different types.

Consider the `+` operator:

```
print(10 + 20)
print("Hello" + " World")
print([1, 2] + [3, 4])
```

Output:

```
30
Hello World
[1, 2, 3, 4]
```

The same operator performs different operations:

- Addition for numbers
    
- Concatenation for strings
    
- Concatenation for lists
    

This is operator polymorphism.

### How does Python implement operator overloading?

Through special methods, often called dunder methods.

For example, the `+` operator is associated with `__add__()`.

For supported operand types:

```
a + b
```

can invoke:

```
a.__add__(b)
```

Python's actual binary operator resolution also accounts for reflected methods such as `__radd__()` and `NotImplemented`.

### Custom operator overloading

Suppose we want to add two vector objects.

```
class Vector:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __add__(self, other):
        if not isinstance(other, Vector):
            return NotImplemented

        return Vector(
            self.x + other.x,
            self.y + other.y
        )

    def __repr__(self):
        return f"Vector({self.x}, {self.y})"


v1 = Vector(2, 3)
v2 = Vector(4, 5)

v3 = v1 + v2

print(v3)
```

Output:

```
Vector(6, 8)
```

### Behind the scenes

When Python evaluates:

```
v1 + v2
```

the usual operation for these objects is equivalent to:

```
v1.__add__(v2)
```

This creates:

```
Vector(2 + 4, 3 + 5)
```

Therefore, the result is:

```
Vector(6, 8)
```

Why return `NotImplemented` instead of raising an error immediately? It lets Python try another supported operand implementation before deciding that the operation is unsupported.

### Common operator overloading methods

|Operator|Special method|
|---|---|
|`+`|`__add__()`|
|`-`|`__sub__()`|
|`*`|`__mul__()`|
|`/`|`__truediv__()`|
|`//`|`__floordiv__()`|
|`==`|`__eq__()`|
|`<`|`__lt__()`|
|`>`|`__gt__()`|
|`len(obj)`|`__len__()`|
|`str(obj)`|`__str__()`|

### Another example: Polymorphism with `len()`

```
print(len("Python"))
print(len([10, 20, 30]))
print(len({"a": 1, "b": 2}))
```

Output:

```
6
3
2
```

We can also define length behavior for our own class:

```
class Team:
    def __init__(self, members):
        self.members = members

    def __len__(self):
        return len(self.members)


team = Team(["Aamir", "Rahul", "Ali"])

print(len(team))
```

Output:

```
3
```

The built-in function `len()` works with many different types through a common protocol.

## 7. Duck typing in Python

This is particularly important because Python's approach to polymorphism is not limited to inheritance.

### What is duck typing?

The idea is commonly summarized as:

> If an object behaves like a duck in the ways we need, we can treat it as one.

In programming terms, Python often cares more about which operations an object supports than whether it belongs to a particular class hierarchy.

### Example

```
class Duck:
    def speak(self):
        print("Quack")


class Human:
    def speak(self):
        print("Hello")


class Robot:
    def speak(self):
        print("Beep")


def make_speak(obj):
    obj.speak()


make_speak(Duck())
make_speak(Human())
make_speak(Robot())
```

Output:

```
Quack
Hello
Beep
```

Notice something interesting.

There is no inheritance relationship among `Duck`, `Human`, and `Robot`.

Yet the function:

```
def make_speak(obj):
    obj.speak()
```

works with all three.

Why?

Because each object provides the `speak()` method.

This is duck typing, a form of polymorphism.

### Duck typing vs inheritance-based polymorphism

|Inheritance-based|Duck typing|
|---|---|
|Objects share a class hierarchy|Common parent not required|
|Subclasses can override methods|Unrelated classes can expose matching methods|
|Relationships are explicitly declared|Compatibility follows supported behavior|
|Example: `Dog(Animal)`|Example: `Robot.speak()` and `Human.speak()`|

### What happens when the required behavior is missing?

```
class Car:
    def drive(self):
        print("Driving")


make_speak(Car())
```

Output:

```
AttributeError: 'Car' object has no attribute 'speak'
```

Python doesn't automatically check that `Car` has `speak()` before calling the function.

The operation fails when the missing attribute is accessed.

### An important Python principle: EAFP

Python often follows the principle:

EAFP — Easier to Ask Forgiveness than Permission

Instead of checking every possible object type beforehand, code can attempt the operation and handle an appropriate exception.

```
def make_speak(obj):
    try:
        obj.speak()
    except AttributeError:
        print("Object does not support speaking")
```

This demonstrates the general idea, though real applications should avoid catching unrelated `AttributeError` exceptions that may originate inside `speak()` itself.

## 8. Polymorphism with abstract classes

Duck typing is flexible, but sometimes we want to explicitly require subclasses to implement particular behavior.

That's where abstract classes become useful.

Python provides `ABC` and `abstractmethod` from the `abc` module.

```
from abc import ABC, abstractmethod


class Shape(ABC):
    @abstractmethod
    def area(self):
        pass


class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

    def area(self):
        return 3.14 * self.radius ** 2


class Rectangle(Shape):
    def __init__(self, length, width):
        self.length = length
        self.width = width

    def area(self):
        return self.length * self.width


shapes = [
    Circle(5),
    Rectangle(4, 6)
]

for shape in shapes:
    print(shape.area())
```

Output:

```
78.5
24
```

Both classes implement the same interface:

```
area()
```

But their implementations are different.

### What if a subclass doesn't implement the abstract method?

```
class Triangle(Shape):
    pass


t = Triangle()
```

Python raises a `TypeError` because `Triangle` is still abstract.

This makes abstract classes useful when you need a formally declared contract.

Another Python mechanism is `typing.Protocol`, which allows static type checkers to verify that different classes support a required interface even without a shared base class. We'll cover both mechanisms more thoroughly under abstraction.

## 9. How Python resolves polymorphic method calls

Consider:

```
class Animal:
    def sound(self):
        print("Animal sound")


class Dog(Animal):
    def sound(self):
        print("Bark")


dog = Dog()
dog.sound()
```

Python doesn't simply choose `Animal.sound()` because `Dog` inherits from `Animal`.

Instead, method lookup starts from the runtime class.

`dog.sound()`

Search `Dog`

Does `Dog` define `sound()`?

Yes — use `Dog.sound()`

Output: Bark

If the method wasn't found in Dog, normal lookup would continue according to its MRO. Descriptor and instance-attribute rules also participate in Python's full attribute lookup process.

You can inspect the method resolution order:

```
print(Dog.__mro__)
```

Output resembles:

```
(<class '__main__.Dog'>,
 <class '__main__.Animal'>,
 <class 'object'>)
```

This method lookup system enables overriding and inheritance-based polymorphism.

### Connection with the Liskov Substitution Principle

A related OOP design principle is that a subclass should be usable wherever its parent type is expected, without breaking the expected behavior.

Consider:

```
class Bird:
    def move(self):
        print("Moving")


class Penguin(Bird):
    def move(self):
        print("Walking or swimming")
```

Both support the general `move()` operation.

But suppose we define every bird as having `fly()` and then force a penguin to implement it by raising an exception. Code that assumes all birds can fly will break.

This illustrates why good polymorphism requires compatible behavior, not just matching method names.

## 10. Real-world example: Notification system

Imagine you're building an application that sends different kinds of notifications.

```
class EmailNotification:
    def send(self, message):
        print(f"Email sent: {message}")


class SMSNotification:
    def send(self, message):
        print(f"SMS sent: {message}")


class PushNotification:
    def send(self, message):
        print(f"Push notification: {message}")


class NotificationService:
    def notify(self, notification, message):
        notification.send(message)


service = NotificationService()

service.notify(
    EmailNotification(),
    "Order confirmed"
)

service.notify(
    SMSNotification(),
    "OTP generated"
)

service.notify(
    PushNotification(),
    "New message received"
)
```

Output:

```
Email sent: Order confirmed
SMS sent: OTP generated
Push notification: New message received
```

Notice how `NotificationService` doesn't care whether it receives an email, SMS, or push notification object.

It just invokes:

```
notification.send(message)
```

If you later create a `WhatsAppNotification` class with a compatible `send()` method, the service can use it without modification.

This is an example of polymorphism being useful in real application architecture. The example prints messages; an actual system would implement delivery through the relevant provider.

## 11. Common mistakes and interview traps

### Trap 1: Method overloading using multiple definitions

```
class A:
    def show(self):
        print("First")

    def show(self, x):
        print("Second")
```

The second definition replaces the first. Python does not select them by argument count.

### Trap 2: Thinking inheritance is compulsory for polymorphism

It isn't.

Duck typing allows unrelated classes to support a common operation.

### Trap 3: Thinking `super()` always invokes the direct parent

It follows the MRO, which becomes particularly important in multiple inheritance.

### Trap 4: Assuming all overriding methods are automatically compatible

```
class Parent:
    def calculate(self, x):
        return x * 2


class Child(Parent):
    def calculate(self, x, y):
        return x + y
```

This is allowed in Python, but:

```
obj = Child()
obj.calculate(10)
```

raises a `TypeError`.

The child has overridden the method with an incompatible required parameter.

### Trap 5: Confusing polymorphism and abstraction

They are different concepts.

- Polymorphism: The same operation can have different implementations.
    
- Abstraction: Exposing essential behavior while hiding unnecessary implementation details.
    

They frequently work together, but neither is identical to the other.

## 14. Final revision notes

|Concept|Key takeaway|
|---|---|
|Polymorphism|Same interface or operation, different behavior|
|Method overloading|Python doesn't support traditional same-name, different-signature definitions|
|Method overriding|Subclass replaces or extends inherited method behavior|
|Operator overloading|Special methods such as `__add__()` customize operators|
|Duck typing|Compatible behavior matters more than shared inheritance|
|Runtime polymorphism|Behavior is selected for the actual objects during execution|
|`super()`|Delegates according to the MRO|
|Abstract classes|Can enforce required methods for concrete subclasses|
|Liskov Substitution Principle|Subtypes should preserve the expectations of their parent contracts|

### The most important interview distinction

Remember these three examples:

Method overloading-like flexibility:

```
def add(a, b, c=0):
    return a + b + c
```

Method overriding:

```
class Parent:
    def show(self):
        print("Parent")

class Child(Parent):
    def show(self):
        print("Child")
```

Duck typing:

```
def execute(obj):
    obj.run()
```

The final example works for any object that provides a compatible `run()` method, regardless of whether that object shares a parent class with others.

Core takeaway: Polymorphism is not simply having multiple methods with the same name. Its real purpose is to let code work with different implementations through a common operation, without needing to know every concrete object type.

The next natural concepts to study are inheritance, abstraction, and encapsulation, because they help explain how polymorphic interfaces are designed and maintained.
