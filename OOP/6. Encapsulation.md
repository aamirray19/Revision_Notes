# Topic 6: Encapsulation

> **TL;DR:** **Encapsulation** = bundle data + the methods that manage it in one class, and **control** how that state is read/changed so it stays valid. Python has no enforced `private`: it uses conventions (`_name`), **name mangling** (`__name`) and **`@property`**. It's an API-design discipline, not a security boundary.

---

## 1. What Is Encapsulation?

**Encapsulation** (one of the four OOP pillars) means keeping an object's **data** and the **operations** that manage it together in a class, while providing **controlled access** to that data. Goal: protect internal state from unintended or invalid changes.

```python
class Student:
    def __init__(self, name, marks):
        self.name = name
        self.marks = marks

    def display(self):
        print(f"Name: {self.name}")
        print(f"Marks: {self.marks}")

student = Student("Aamir", 85)
student.display()
```

```text
Name: Aamir
Marks: 85
```

- `name`, `marks` → attributes; `display()` → method. The class **bundles** data and behavior.
- But nothing **controls** modification:

```python
student.marks = -100
print(student.marks)   # -100  (invalid, but allowed)
```

- Bundling alone is not enough; controlled access is the other half.

---

## 2. Why Encapsulation?

### Preventing invalid data

**Without encapsulation:** anyone can set any value.

```python
class BankAccount:
    def __init__(self, balance):
        self.balance = balance

account = BankAccount(1000)
account.balance = -5000
print(account.balance)   # -5000
```

**With encapsulation:** state changes go through validating methods.

```python
class BankAccount:
    def __init__(self, balance):
        if balance < 0:
            raise ValueError("Balance cannot be negative")
        self._balance = balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Deposit amount must be positive")
        self._balance += amount

    def get_balance(self):
        return self._balance

account = BankAccount(1000)
account.deposit(500)
print(account.get_balance())   # 1500
```

- Callers use `account.deposit(500)`; the method **validates before updating**.
- The `_` in `_balance` does **not** block access. It signals "internal, don't touch".

### Benefits

| Benefit | Explanation |
|---|---|
| Data protection | Reduces unintended modification of internal state |
| Data validation | Ensures values satisfy required conditions |
| Controlled access | Defines how attributes can be read or modified |
| Maintainability | Internals can change without changing the public interface |
| Reduced coupling | Other classes depend on public behavior, not internal details |
| Debugging | State changes are centralized in methods |
| Flexibility | Implementation can be replaced while preserving the API |
| Consistency | Helps maintain object **invariants** |

### Invariants

An **invariant** is a condition that must stay true for the object's whole valid lifetime.

```python
balance >= 0            # bank account without overdraft
0 <= marks <= 100       # student
price >= 0              # product
```

- Encapsulation **centralizes** the logic that keeps invariants true.

## 3. Encapsulation in Python vs Other Languages

- **Java/C++:** `public` / `protected` / `private` are **enforced** by the language.
- **Python:** no strict access modifiers for ordinary attributes. It relies on **naming conventions**, **name mangling** and **controlled interfaces**.

| Naming style | Meaning | Enforced privacy? |
|---|---|---|
| `name` | Public | No |
| `_name` | Non-public / internal (by convention) | No |
| `__name` | Name-mangled (`_Class__name`) | No, but accidental access is discouraged |
| `__name__` | Special / dunder name (not mangled) | No |

```python
class Example:
    def __init__(self):
        self.name = "Public"
        self._salary = 50000
        self.__password = "secret"
```

> **Key point:** Python achieves encapsulation through well-designed interfaces and conventions, not access restrictions. Full detail on access levels: [Topic 8: Access Modifiers](8.%20access%20modifiers.md).

## 4. Public Members

**Public** members have no leading underscore and are meant to be used from outside the class.

```python
class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary

    def display(self):
        print(self.name)
        print(self.salary)

employee = Employee("Aamir", 50000)
print(employee.name)     # Aamir
print(employee.salary)   # 50000
employee.display()       # Aamir / 50000

employee.salary = 80000  # direct modification is allowed
print(employee.salary)   # 80000
```

**Use public attributes when:**

- Direct access is safe and needs no validation.
- The attribute is part of the intended API.
- Getters/setters would just add noise.

> **Key point:** encapsulation does **not** mean every attribute must be private. Python favors plain public attributes when they suffice.

---

## 5. Protected Members: Single Underscore `_name`

A single leading underscore marks a member as **internal use** (by convention only).

```python
class Employee:
    def __init__(self, name, salary):
        self.name = name
        self._salary = salary

    def display_salary(self):
        print(self._salary)

employee = Employee("Aamir", 50000)
employee.display_salary()    # 50000

print(employee._salary)      # 50000   (still accessible)
employee._salary = 100000    # still modifiable
print(employee._salary)      # 100000
```

- Not protected by any language rule. The `_` says: *"implementation detail, don't depend on it."*

### Access through inheritance

```python
class Employee:
    def __init__(self, salary):
        self._salary = salary

class Manager(Employee):
    def display_salary(self):
        print(self._salary)

manager = Manager(90000)
manager.display_salary()     # 90000
```

- Subclasses use inherited `_` attributes normally.
- Unlike Java's `protected`, Python's `_` does **not** restrict access to the class and its subclasses.
- **Wildcard imports:** module-level names starting with `_` are excluded by `from module import *` unless listed in `__all__`.

## 6. Private Members: Double Underscore `__name` (Name Mangling)

Names starting with `__` (and not ending with `__`) inside a class are **name-mangled**: Python renames them to `_ClassName__name`.

```python
class Employee:
    def __init__(self, salary):
        self.__salary = salary

    def display_salary(self):
        print(self.__salary)

employee = Employee(50000)
employee.display_salary()    # 50000
print(employee.__salary)
```

```text
AttributeError: 'Employee' object has no attribute '__salary'
```

- Inside the class, `__salary` is rewritten to `_Employee__salary`, so the outside name `__salary` doesn't exist.
- The rename uses the class **where the identifier is written**.
- Purpose: avoid **accidental name clashes**, especially in inheritance (Section 8).

### Not truly private

```python
class Employee:
    def __init__(self):
        self.__salary = 50000

employee = Employee()
print(employee._Employee__salary)   # 50000
print(employee.__dict__)            # {'_Employee__salary': 50000}
```

- The value is stored under its **mangled name**; anyone who knows it can access it.
- Name mangling is **not encryption or security**. Never rely on `__` to hide sensitive data.

---

## 7. Internals: How Name Mangling Works

```python
class Example:
    def __init__(self):
        self.name = 10
        self._name = 20
        self.__name = 30
        self.__name__ = 40

obj = Example()
print(obj.__dict__)
```

```text
{'name': 10, '_name': 20, '_Example__name': 30, '__name__': 40}
```

| Attribute | Mangled? | Stored as |
|---|---|---|
| `name` | No | `name` |
| `_name` | No | `_name` |
| `__name` | **Yes** | `_Example__name` |
| `__name__` | No | `__name__` |

### Rules

- Applies to identifiers written **inside a class body**.
- Must **start** with at least two underscores.
- Must **not end** with two or more underscores (so dunders are untouched).
- Python prefixes `_` + class name: `__marks` in `Student` → `_Student__marks`.
- Leading underscores of the class name are stripped (`class _Foo` → `_Foo__x`).
- Done at **compile time**, not dynamically on each access.

### Methods are mangled too

```python
class Example:
    def __secret_method(self):
        print("Private method")

    def call_method(self):
        self.__secret_method()

obj = Example()
obj.call_method()                # Private method
obj._Example__secret_method()    # Private method  (possible, but discouraged)
obj.__secret_method()            # AttributeError
```

## 8. Name Mangling and Inheritance (interview favorite)

### A child can't reach the parent's `__attr` by its short name

```python
class Parent:
    def __init__(self):
        self.__value = 100          # stored as _Parent__value

class Child(Parent):
    def display(self):
        print(self.__value)         # compiled as self._Child__value

obj = Child()
obj.display()
```

```text
AttributeError: 'Child' object has no attribute '_Child__value'
```

- Same source name `__value`, but two **different mangled names**.
- The attribute **is** inherited (it's on the instance); only the name used in `Child` differs:

```python
class Child(Parent):
    def display(self):
        print(self._Parent__value)  # 100, works but couples Child to Parent's internals
```

**Preferred:** expose a method or property.

```python
class Parent:
    def __init__(self):
        self.__value = 100

    def get_value(self):
        return self.__value

class Child(Parent):
    def display(self):
        print(self.get_value())

obj = Child()
obj.display()    # 100
```

- The child doesn't need to know how the parent stores data.

### Why it's useful: preventing accidental clashes

**Without mangling**, the child silently overwrites the parent's attribute:

```python
class Parent:
    def __init__(self):
        self.value = 100

class Child(Parent):
    def __init__(self):
        super().__init__()
        self.value = 200

obj = Child()
print(obj.value)   # 200  (parent's 100 is gone)
```

**With mangling**, both coexist:

```python
class Parent:
    def __init__(self):
        self.__value = 100

    def parent_value(self):
        return self.__value

class Child(Parent):
    def __init__(self):
        super().__init__()
        self.__value = 200

    def child_value(self):
        return self.__value

obj = Child()
print(obj.parent_value())   # 100
print(obj.child_value())    # 200
print(obj.__dict__)         # {'_Parent__value': 100, '_Child__value': 200}
```

- `_Parent__value` and `_Child__value` are separate, so neither class breaks the other. This is the **main reason** name mangling exists.
- Same applies to `__methods`: a child's `__show` does **not** override the parent's `__show` (see Practice Q9). More on inheritance: [Topic 5: Inheritance](5.%20inheritance.md).

## 9. Getters and Setters

Methods that control access to internal state:

- **Getter** → reads a value.
- **Setter** → updates a value, usually with validation.
- **Deleter** → controls removal of an attribute.

```python
class Student:
    def __init__(self, marks):
        self.__marks = marks

    def get_marks(self):
        return self.__marks

    def set_marks(self, marks):
        if 0 <= marks <= 100:
            self.__marks = marks
        else:
            raise ValueError("Marks must be between 0 and 100")

student = Student(80)
print(student.get_marks())   # 80
student.set_marks(95)
print(student.get_marks())   # 95
student.set_marks(150)       # ValueError: Marks must be between 0 and 100
```

- Instead of unrestricted `student.marks = 150`, the setter enforces the business rule.
- **Problem 1:** verbose call syntax (`get_marks()`, `set_marks(90)`). Python's idiomatic fix: **properties**.
- **Problem 2:** `__init__` assigns `self.__marks` directly, so `Student(150)` skips validation. Validate the initial value through the same path (Section 10).

## 10. The `@property` Decorator

`@property` makes a method **behave like an attribute**. It's Python's main tool for encapsulated interfaces.

### 10.1 Getter only (read-only property)

```python
class Employee:
    def __init__(self, salary):
        self._salary = salary

    @property
    def salary(self):
        return self._salary

employee = Employee(50000)
print(employee.salary)       # 50000  (no parentheses; the getter runs)
employee.salary = 70000
```

```text
AttributeError: property 'salary' of 'Employee' object has no setter
```

- Accessed as `employee.salary`, not `employee.salary()`.
- No setter → **read-only** public property. (Python < 3.11 message: `AttributeError: can't set attribute`.)
- The underlying `_salary` can still be changed directly.

### 10.2 Adding a setter: `@<name>.setter`

```python
class Employee:
    def __init__(self, salary):
        self.salary = salary            # goes through the setter

    @property
    def salary(self):
        return self._salary

    @salary.setter
    def salary(self, value):
        if value < 0:
            raise ValueError("Salary cannot be negative")
        self._salary = value

employee = Employee(50000)
print(employee.salary)       # 50000
employee.salary = 75000      # setter runs
print(employee.salary)       # 75000
Employee(-5000)              # ValueError: Salary cannot be negative
```

- Callers use plain attribute syntax; Python runs the getter/setter behind it.
- **Validate during init:** `__init__` uses `self.salary = salary` (not `self._salary = salary`) so the setter validates the initial value too. One validation path, no duplication.
- More on `@property` vs access levels: [Topic 8: Access Modifiers](8.%20access%20modifiers.md).

## 11. Internals: How `@property` Works

A property is a **descriptor**: an object that customizes attribute access by defining `__get__()`, `__set__()` and/or `__delete__()`.

### Decorator form = `property()` call

```python
class Employee:
    def __init__(self, salary):
        self._salary = salary

    @property
    def salary(self):
        return self._salary

    @salary.setter
    def salary(self, value):
        self._salary = value
```

is conceptually the same as:

```python
class Employee:
    def __init__(self, salary):
        self._salary = salary

    def get_salary(self):
        return self._salary

    def set_salary(self, value):
        self._salary = value

    salary = property(get_salary, set_salary)
```

- The built-in `property()` creates a **property descriptor** stored in the **class** namespace.

### Execution flow

```python
employee.salary          # → Employee.__dict__["salary"].__get__(employee, Employee)
employee.salary = 80000  # → Employee.__dict__["salary"].__set__(employee, 80000)
```

- A property is a **data descriptor** (defines `__set__`/`__delete__`), so it **takes precedence** over an instance `__dict__` entry with the same name.
- It is not "a method called because its name matches"; it's a special class-level object that intercepts attribute access.

## 12. Getter, Setter and Deleter Together

```python
class Person:
    def __init__(self, name):
        self.name = name

    @property
    def name(self):
        return self._name

    @name.setter
    def name(self, value):
        if not isinstance(value, str) or not value.strip():
            raise ValueError("Name must be a non-empty string")
        self._name = value

    @name.deleter
    def name(self):
        print("Deleting name")
        del self._name

person = Person("Aamir")
print(person.name)       # Aamir
person.name = "Rahul"
print(person.name)       # Rahul
del person.name          # Deleting name
print(person.name)       # AttributeError: 'Person' object has no attribute '_name'
```

| Operation | Runs |
|---|---|
| `person.name` | Getter (`@property`) |
| `person.name = "Rahul"` | Setter (`@name.setter`) |
| `del person.name` | Deleter (`@name.deleter`) |

- **Should every property have a deleter?** No. Deleting an essential attribute leaves the object invalid. Add one only when deletion is a meaningful operation.

## 13. Read-Only (Computed) vs Writable Properties

### Read-only computed property

```python
class Circle:
    def __init__(self, radius):
        if radius < 0:
            raise ValueError("Radius cannot be negative")
        self._radius = radius

    @property
    def area(self):
        return 3.14159 * self._radius ** 2

circle = Circle(5)
print(circle.area)   # 78.53975
```

- `area` is **computed** from `radius`, not stored.
- Storing both (`self.radius = 5; self.area = 78.53975`) risks a **stale** `area` when `radius` changes. A computed property can't go stale.

### Writable property + computed property

```python
class Circle:
    def __init__(self, radius):
        self.radius = radius

    @property
    def radius(self):
        return self._radius

    @radius.setter
    def radius(self, value):
        if value < 0:
            raise ValueError("Radius cannot be negative")
        self._radius = value

    @property
    def area(self):
        return 3.14159 * self._radius ** 2

circle = Circle(5)
print(circle.area)   # 78.53975
circle.radius = 10
print(circle.area)   # 314.159
```

- `radius` is validated and writable; `area` updates automatically.

## 14. Gotcha: Infinite Recursion in Properties

**Wrong:** property and storage use the **same name**.

```python
class Student:
    def __init__(self, marks):
        self.marks = marks

    @property
    def marks(self):
        return self.marks       # calls the getter again

    @marks.setter
    def marks(self, value):
        self.marks = value      # calls the setter again
```

```text
RecursionError: maximum recursion depth exceeded
```

- `self.marks = value` inside the setter triggers the setter, which triggers it again, forever. Same for `return self.marks` in the getter.

**Right:** store the value under a different (internal) name.

```python
class Student:
    def __init__(self, marks):
        self.marks = marks

    @property
    def marks(self):
        return self._marks

    @marks.setter
    def marks(self, value):
        if not 0 <= value <= 100:
            raise ValueError("Invalid marks")
        self._marks = value
```

- **Rule:** public property `marks` → storage `_marks`; `salary` → `_salary`.

## 15. Methods vs Properties

Both give controlled access; pick by **meaning**.

- **Methods** → **actions** with business behavior:

```python
account.deposit(1000)
account.withdraw(500)
order.cancel()
user.change_password("new-password")
```

- **Properties** → things that feel like **reading/assigning an attribute**:

```python
employee.salary
circle.area
student.marks
product.price
```

| Feature | Methods | Properties |
|---|---|---|
| Syntax | `obj.method()` | `obj.attribute` |
| Best for | Actions / commands | Attribute-like access |
| Validation | Yes | Yes |
| Computed values | Yes | Yes |
| Side effects | Expected in commands | Should be minimal for getters |
| Clarity | Explicit operation | Natural attribute syntax |

- **Guideline:** getters should be **cheap and side-effect free**. If `user.balance` secretly makes a network request and writes to a database, prefer an explicit `user.fetch_balance()`.

## 16. Real-World Example: Bank Account

Combines a read-only property, validating methods and controlled state changes. Uses `Decimal` because binary floats introduce rounding errors with money.

```python
from decimal import Decimal

class BankAccount:
    def __init__(self, owner, initial_balance=0):
        self.owner = owner
        balance = Decimal(str(initial_balance))
        if not balance.is_finite() or balance < 0:
            raise ValueError("Invalid initial balance")
        self._balance = balance

    @property
    def balance(self):
        return self._balance

    def deposit(self, amount):
        amount = Decimal(str(amount))
        if not amount.is_finite() or amount <= 0:
            raise ValueError("Deposit must be positive")
        self._balance += amount

    def withdraw(self, amount):
        amount = Decimal(str(amount))
        if not amount.is_finite() or amount <= 0:
            raise ValueError("Withdrawal must be positive")
        if amount > self._balance:
            raise ValueError("Insufficient balance")
        self._balance -= amount

    def display_balance(self):
        print(f"Available balance: {self._balance:.2f}")

account = BankAccount("Aamir", "1000.00")
account.deposit("500.00")
account.withdraw("300.00")
account.display_balance()     # Available balance: 1200.00

account.balance = 100000
```

```text
AttributeError: property 'balance' of 'BankAccount' object has no setter
```

**What the class guarantees:**

- Deposits and withdrawals must be positive.
- Withdrawals can't exceed the balance.
- Balance changes only through intended operations.
- Callers can **read** `balance` but not assign it.

**Limitations:**

- `account._balance = Decimal("-1000")` still works. Protection relies on callers respecting the interface.
- Educational in-memory example only; real banking needs transactions, concurrency control, persistence, authorization.

## 17. Encapsulation and Mutable Objects (often overlooked)

A read-only property returning a **mutable** object leaks a reference to internal state.

```python
class Student:
    def __init__(self):
        self._marks = [80, 90, 85]

    @property
    def marks(self):
        return self._marks

student = Student()
student.marks.append(-100)
print(student.marks)   # [80, 90, 85, -100]
```

- `student.marks = [...]` is blocked (no setter), but **mutating** the returned list is not.
- Read-only property ≠ immutable data.

### Fix 1: return a copy

```python
class Student:
    def __init__(self):
        self._marks = [80, 90, 85]

    @property
    def marks(self):
        return self._marks.copy()

student = Student()
student.marks.append(-100)   # modifies a throwaway copy
print(student.marks)         # [80, 90, 85]
```

- A **shallow** copy doesn't protect nested mutable objects. See [Topic 3: Shallow vs Deep Copy](3.%20additional%20topics.md).

### Fix 2: return an immutable view + a validating method to change it

```python
class Student:
    def __init__(self):
        self._marks = [80, 90, 85]

    @property
    def marks(self):
        return tuple(self._marks)

    def add_marks(self, value):
        if not 0 <= value <= 100:
            raise ValueError("Invalid marks")
        self._marks.append(value)

student = Student()
print(student.marks)    # (80, 90, 85)
student.add_marks(95)
print(student.marks)    # (80, 90, 85, 95)
```

- A tuple has no `append()`; changes must go through `add_marks()`.

> **Key lesson:** consider not only whether callers can **assign** attributes, but whether they can **mutate** internal objects through exposed references.

## 18. Encapsulating Class Attributes

Class-level attributes can be kept internal and exposed through **class methods**.

```python
class Employee:
    _employee_count = 0

    def __init__(self, name):
        self.name = name
        Employee._employee_count += 1

    @classmethod
    def get_employee_count(cls):
        return cls._employee_count

emp1 = Employee("Aamir")
emp2 = Employee("Rahul")
print(Employee.get_employee_count())   # 2
```

- `_employee_count` is internal; `get_employee_count()` is the read interface.
- It updates `Employee._employee_count` explicitly, so the counter belongs to `Employee` (subclass instances also increment it; subclasses don't get their own counter).
- `Employee._employee_count = 100` still works; the `_` enforces nothing.
- **Uses:** object counters, shared configuration, class-wide metadata, resource tracking, shared policies.
- Be careful with **shared mutable state** and inheritance: one change affects many objects. Class vs instance attributes: [Topic 1](1.%20Classes%20and%20Objects.md).

## 19. Encapsulation and Inheritance Together

Subclasses should go through the parent's **public interface**, not its internals.

```python
class Employee:
    def __init__(self, salary):
        self._salary = salary

    @property
    def salary(self):
        return self._salary

    @salary.setter
    def salary(self, value):
        if value < 0:
            raise ValueError("Salary cannot be negative")
        self._salary = value

class Manager(Employee):
    def increase_salary(self, amount):
        if amount <= 0:
            raise ValueError("Increase must be positive")
        self.salary += amount       # uses the property, not self._salary

manager = Manager(50000)
manager.increase_salary(10000)
print(manager.salary)   # 60000
```

- `self.salary += amount` runs the parent's getter and **setter**, so the parent's validation is kept.
- If the parent later changes storage (database, deductions, etc.), the child keeps working.

> **Design principle:** subclasses should use the parent's supported interface instead of depending on its implementation details.

## 20. Encapsulation vs Abstraction (and the Other Pillars)

- **Encapsulation** → *How do we protect and manage the object's internal state?*
- **Abstraction** → *What should the object expose, without callers needing to know how it works?*

```python
class Car:
    def __init__(self):
        self._engine_running = False

    def start(self):
        self._engine_running = True
        print("Car started")

car = Car()
car.start()   # Car started
```

- **Encapsulation aspect:** `_engine_running` is internal; `start()` is the intended way to change it.
- **Abstraction aspect:** the caller just calls `car.start()` without knowing what starting a real engine involves.

| Encapsulation | Abstraction |
|---|---|
| Organizes data and behavior | Exposes essential behavior |
| Controls access to state | Hides unnecessary implementation details |
| Helps maintain invariants | Reduces conceptual complexity |
| Methods and properties | Interfaces, APIs, abstract classes |
| Focus: state management | Focus: what functionality is provided |

- **Remember:** encapsulation = control **how** data is accessed/changed; abstraction = expose **what** an object can do. Good classes use both. See [Topic 7: Abstraction](7.%20abstraction.md).

### All four pillars

| Principle | Purpose | Python example |
|---|---|---|
| **Encapsulation** | Organize and control state | Properties, validating methods |
| **Inheritance** | Reuse and specialize behavior | `class Dog(Animal)` |
| **Polymorphism** | Same operation, different implementations | Overridden `speak()` |
| **Abstraction** | Expose essentials, hide complexity | Abstract classes, public interfaces |

```python
from abc import ABC, abstractmethod

class Employee(ABC):
    def __init__(self, salary):
        self.salary = salary

    @property                       # Encapsulation: validated salary
    def salary(self):
        return self._salary

    @salary.setter
    def salary(self, value):
        if value < 0:
            raise ValueError("Invalid salary")
        self._salary = value

    @abstractmethod                 # Abstraction: required interface
    def calculate_bonus(self):
        pass

class Developer(Employee):          # Inheritance
    def calculate_bonus(self):
        return self.salary * 0.10

class Manager(Employee):
    def calculate_bonus(self):
        return self.salary * 0.20

employees = [Developer(50000), Manager(80000)]
for employee in employees:
    print(employee.calculate_bonus())   # Polymorphism: same call, type-specific result
```

```text
5000.0
16000.0
```

- Related: [Topic 4: Polymorphism](4.%20Polymorphism.md), [Topic 5: Inheritance](5.%20inheritance.md).

## 21. `__slots__` Is Not Privacy

`__slots__` declares a fixed set of instance attribute names. It's about **storage**, not privacy.

```python
class Student:
    __slots__ = ("name", "_marks")

    def __init__(self, name, marks):
        self.name = name
        self._marks = marks

student = Student("Aamir", 90)
print(student.name)     # Aamir
print(student._marks)   # 90
student.age = 25
```

```text
AttributeError: 'Student' object has no attribute 'age'
```

- No instance `__dict__` (when the whole hierarchy uses slots), so new arbitrary attributes are rejected.
- `student._marks = -100` still works: **no privacy, no validation**.

**Uses:** lower per-instance memory, block arbitrary attribute creation, explicit attribute layout.

**Limitations:**

- A subclass without its own `__slots__` gets a `__dict__` again.
- Slots don't validate assigned values.
- Not a security boundary.
- Each slot is implemented as a **descriptor** on the class.

> `__slots__` can support a controlled design, but don't confuse it with encapsulation.

## 22. Dataclasses and `frozen=True`

`dataclasses` cut boilerplate but add **no** encapsulation or validation by default.

```python
from dataclasses import dataclass

@dataclass
class Student:
    name: str
    marks: int

student = Student("Aamir", 90)
student.marks = -100
print(student.marks)    # -100  (invalid value allowed)
```

### `frozen=True` blocks reassignment

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Student:
    name: str
    marks: int

student = Student("Aamir", 90)
print(student.marks)    # 90
student.marks = 100
```

```text
dataclasses.FrozenInstanceError: cannot assign to field 'marks'
```

### ...but not deep immutability

```python
from dataclasses import dataclass, field

@dataclass(frozen=True)
class Student:
    marks: list[int] = field(default_factory=list)

student = Student([80, 90])
student.marks.append(100)
print(student.marks)    # [80, 90, 100]
```

- Fields can't be **rebound**, but mutable field contents can still be **mutated**. Frozen = restricted assignment, not deep immutability.

## 23. Best Practices

1. **Prefer plain public attributes** when no validation is needed. Don't auto-generate getters/setters.

```python
class User:
    def __init__(self, name):
        self.name = name        # perfectly valid Python design
```

2. **Use properties** when validation or computation is needed.

```python
class Product:
    def __init__(self, price):
        self.price = price

    @property
    def price(self):
        return self._price

    @price.setter
    def price(self, value):
        if value < 0:
            raise ValueError("Price cannot be negative")
        self._price = value
```

3. **Use methods for meaningful state transitions**: prefer `account.withdraw(500)` over `account.balance -= 500` when withdrawal has business rules.
4. **Use `_name`** for internal implementation details (`self._balance`). Common, readable convention.
5. **Use `__name` only to prevent subclass name collisions** (`self.__internal_state`), not because data is "important".
6. **Don't return mutable internals directly**: instead of `return self._items`, return `tuple(self._items)` or a copy.
7. **Centralize validation**: one property setter used by both `__init__` and updates.
8. **Don't force others to reach into internals** like `obj._SomeClass__secret`; provide a method or property.
9. **Keep invariants in mind**: every state-changing operation must preserve valid state. Make invalid transitions hard through the public interface.

### Mental model: let the object manage its own rules

```python
# Good: the object enforces its rules
account.deposit(1000)
account.withdraw(500)
print(account.balance)

# Bad: rules are spread across every caller
account._balance += 1000
account._balance -= 500
```

## 24. Common Mistakes / Gotchas

- **Assuming `_name` is protected** → `obj._name = "Changed"` works. It's only a convention.
- **Assuming `__name` is secure** → `obj._ClassName__name` reaches it. Mangling is not encryption or access control.
- **Bypassing validation in `__init__`** (`self._marks = marks` while a setter exists) → invalid initial state. Assign via the property: `self.marks = marks`.
- **Recursive property** (`return self.age` inside the `age` getter) → `RecursionError`. Use `return self._age`.
- **Exposing mutable internals** (`return self._items`) → callers can mutate the list. Return a copy or tuple.
- **Treating a read-only property as full immutability** → it only blocks assignment to the property; internal storage and returned mutable objects can still change.
- **Child accessing parent's `__attr` as `self.__attr`** → `AttributeError` (`_Child__attr`). Use a parent method/property.
- **Expecting a child's `__method` to override the parent's** → it doesn't; the parent still calls `_Parent__method`.
- **Believing `__slots__` or `frozen=True` gives privacy/deep immutability** → neither does.
- **Writing needless getters/setters** → boilerplate with no benefit. With no validation or special behavior, use a public attribute instead of:

```python
class Person:
    def get_name(self):
        return self._name

    def set_name(self, name):
        self._name = name
```

## 25. Interview Questions

**Q1. What is encapsulation in Python?**
Bundling attributes and methods into a class while providing controlled interfaces for reading and modifying the object's internal state.

**Q2. Does Python support private variables?**
Not strictly. Double underscores trigger name mangling, but there are no enforced private instance variables like Java's `private`.

**Q3. `_variable` vs `__variable`?**
`_variable` is a convention meaning "internal use". `__variable` (inside a class) is **name-mangled** to `_ClassName__variable`, preventing accidental naming conflicts.

**Q4. What is name mangling?**
Python's compile-time renaming of `__name` identifiers in a class body to `_ClassName__name`.

**Q5. What is the purpose of `@property`?**
Lets a method be accessed with attribute syntax, enabling validation, computed values and controlled access without exposing the implementation.

**Q6. What happens if a property has no setter?**
Assigning to it raises `AttributeError`.

**Q7. Can child classes override properties?**
Yes. A subclass can define a property with the same name to override the inherited one.

**Q8. Is encapsulation the same as data hiding?**
No. Data hiding is one aspect. Encapsulation is broader: organizing data with behavior and exposing controlled operations.

**Q9. Is encapsulation possible without private attributes?**
Yes. Public attributes plus well-defined methods still encapsulate related data and behavior; how much access control you need depends on requirements.

**Q10. Should every attribute have a getter and setter?**
No. Plain public attributes are preferable when no validation or special behavior is needed.

**Q11. Method vs property?**
Methods are explicit operations with call syntax; properties give attribute-like access that can run custom logic.

**Q12. Are name-mangled attributes inherited?**
The attribute exists on subclass instances (via the parent's `__init__`), but `__name` is mangled by the class where it's **written**, so the child must use a different name to reach it.

**Q13. What is a data descriptor?**
A descriptor defining `__set__()` or `__delete__()`. It takes priority over instance `__dict__` entries in attribute lookup. Properties are data descriptors.

**Q14. Is a frozen dataclass completely immutable?**
No. It blocks field reassignment, but mutable objects stored in fields can still be modified.

**Q15. Does `__slots__` make attributes private?**
No. It controls instance storage and can block new arbitrary attributes, but existing attributes stay fully accessible.

**Q16. Main advantages of encapsulation?**
Control over state changes, validation, reduced coupling, preserved invariants, and internals that can evolve without breaking callers.

**Q17. Can encapsulation be bypassed in Python?**
Yes: direct attribute access, mangled names, introspection, low-level mechanisms. Python encapsulation is an **API-design discipline**, not a security boundary.

```python
        return self._items
```

**5. What does this print?**

```python
class Parent:
    def __init__(self):
        self.__x = 10

    def get_x(self):
        return self.__x

class Child(Parent):
    def __init__(self):
        super().__init__()
        self.__x = 20

obj = Child()
print(obj.get_x())
print(obj._Child__x)
```

(a) `20` `20`  (b) `10` `20`  (c) `10` `10`  (d) `AttributeError`

<details><summary>Answer</summary>

**(b) `10` then `20`**: the parent's attribute is `_Parent__x`, the child's is `_Child__x`. Both exist independently; `get_x()` (written in `Parent`) reads `_Parent__x`.

</details>

**6. What does this print?**

```python
class A:
    def __init__(self, x):
        self.x = x

    @property
    def x(self):
        return self._x

    @x.setter
    def x(self, value):
        print("Setter called")
        self._x = value

obj = A(10)
print(obj.x)
```

(a) `10`  (b) `Setter called` then `10`  (c) `AttributeError`  (d) `RecursionError`

<details><summary>Answer</summary>

**(b)**: `self.x = x` in `__init__` invokes the property setter.

</details>

**9. What does this print?**

```python
class Parent:
    def __show(self):
        print("Parent")

    def call_show(self):
```

(a) `Child`  (b) `Parent`  (c) `AttributeError`  (d) `Parent` then `Child`

## Quick Recap

| Concept | Key point |
|---|---|
| Encapsulation | Bundle data + behavior, control access |
| Public | `self.name` |
| Non-public (convention) | `self._name` |
| Name-mangled | `self.__name` → `_ClassName__name` |
| Getter / Setter / Deleter | Read / validated update / controlled deletion |
| `@property` | Method exposed with attribute syntax |
| `@name.setter` / `@name.deleter` | Assignment / deletion behavior |
| Read-only property | Property without a setter |
| Descriptor | Object customizing attribute access (`__get__`/`__set__`/`__delete__`) |
| `__dict__` | Per-instance dict of attributes (absent with `__slots__`) |
| `__slots__` | Fixed slot-based storage; not privacy |
| Invariant | Condition valid object state must always satisfy |
| Defensive copy | Stops callers mutating internals via shared references |
| Frozen dataclass | Blocks field reassignment, not deep immutability |
| Abstraction | Expose essential behavior, hide complexity |

- **Encapsulation** = bundling + **controlling how state changes** (invariants, validation, low coupling).
- Python **doesn't enforce** public/protected/private; `_name` is a convention.
- **`__name`** triggers **name mangling**: prevents accidental clashes in inheritance, **not** security.
- **`@property`** is the idiomatic tool: setter validates (use it in `__init__` too), getter can compute values without storing redundant state.
- Property storage must use a **different name** (`_x`) or you get `RecursionError`.
- A **read-only property** doesn't make referenced **mutable** data immutable; return copies/tuples.
- **`__slots__`** controls storage; **frozen dataclasses** restrict assignment. Neither is privacy or deep immutability.
- **Subclasses** should use the parent's public interface, not its internals.
- **Methods** for actions/state changes, **properties** for attribute-like access, **plain public attributes** when nothing needs controlling.
- **Encapsulation vs abstraction:** *how* state is managed vs *what* functionality is exposed.

> **Core idea:** encapsulation in Python is about letting an object enforce its own rules through a clear public interface, not about making data impossible to access.
