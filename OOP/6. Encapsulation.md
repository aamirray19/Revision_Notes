# Python OOP — Encapsulation (Complete Revision Notes)

## 1. What Is Encapsulation?

Encapsulation is one of the four fundamental principles of Object-Oriented Programming (OOP).

It is the concept of bundling data (attributes) and the methods that operate on that data inside a single unit (class), while controlling how the object’s internal state is accessed and modified.

**In simple terms:**

Encapsulation means keeping an object’s data and the operations that manage it together, while providing controlled access to that data.

The main objective is to protect an object’s internal state from unintended or invalid modifications.

### Basic Example

```python
class Student:
    def __init__(self, name, marks):
        self.name = name
        self.marks = marks
    def display(self):
        print(f"Name: {self.name}")
        print(f"Marks: {self.marks}")
student = Student("Aamir", 85)
student.display()
```

**Output:**

```text
Name: Aamir
Marks: 85
```

**Here:**

- name and marks are attributes.
- display() is a method.
- The Student class bundles data and behavior together.

This demonstrates the basic idea of encapsulation.

However, it does not provide controlled modification of the attributes.

**For example:**

```python
student.marks = -100
print(student.marks)
```

**Output:**

```text
-100
```

A student cannot logically have negative marks, but our class allows it.

This is where controlled access becomes important.

## 2. Why Do We Need Encapsulation?

Encapsulation solves several important problems in software design.

### 2.1 Preventing Invalid Data

Consider a bank account.

#### Without Proper Encapsulation

```python
class BankAccount:
    def __init__(self, balance):
        self.balance = balance
account = BankAccount(1000)
account.balance = -5000
print(account.balance)
```

**Output:**

```text
-5000
```

The user can directly modify the balance to an invalid value.

The class has no control over how its internal state changes.

#### With Encapsulation

```python
class BankAccount:
    def __init__(self, balance):
        if balance < 0:
            raise ValueError("Balance cannot be negative")
        self._balance = balance
    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Deposit amount must be positive")
        self._balance += amount
    def get_balance(self):
        return self._balance
account = BankAccount(1000)
account.deposit(500)
print(account.get_balance())
```

**Output:**

```text
1500
```

Now the class provides an intended way to modify the balance.

Instead of directly manipulating state, callers use methods such as:

```python
account.deposit(500)
```

The method validates the operation before updating the internal data.

**Important:** The single underscore in `_balance` does not prevent direct access in Python. It signals that the attribute is internal and should not be modified directly by callers.

### 2.2 Main Benefits of Encapsulation

| Benefit | Explanation |
| --- | --- |
| Data protection | Reduces unintended modification of internal state |
| Data validation | Ensures values satisfy required conditions |
| Controlled access | Defines how attributes can be read or modified |
| Maintainability | Internal implementation can change without changing the public interface |
| Reduced coupling | Other classes depend on public behavior rather than internal details |
| Debugging | State changes can be centralized in methods |
| Flexibility | Implementation details can be replaced while preserving the API |
| Consistency | Helps maintain object invariants |

#### What Is an Invariant?

An invariant is a condition that should remain true throughout an object’s valid lifetime.

For a bank account that does not allow overdrafts:

```python
balance >= 0
```

For a student:

```python
0 <= marks <= 100
```

For a product:

```python
price >= 0
```

Encapsulation helps centralize the logic that maintains these conditions.

## 3. Encapsulation in Python vs Other Languages

Python handles encapsulation differently from languages such as Java and C++.

In Java, access modifiers include:

- `public`
- `protected`
- `private`

These modifiers have language-enforced access rules.

Python does not provide equivalent strict access modifiers for ordinary instance attributes.

Instead, Python primarily uses naming conventions, name mangling, and controlled interfaces.

### Access Levels in Python

| Naming style | Common interpretation | Enforced privacy? |
| --- | --- | --- |
| name | Public | No |
| `_name` | Non-public / internal | No |
| `__name` | Name-mangled | No, but accidental access is discouraged |
| `__name__` | Special or dunder name | No |

**For example:**

```python
class Example:
    def __init__(self):
        self.name = "Public"
        self._salary = 50000
        self.__password = "secret"
```

The three attributes follow different naming conventions.

**Key point:** Python encourages encapsulation through well-designed interfaces and developer conventions rather than strict access restrictions.

## 4. Public Members

Public attributes and methods are intended to be accessed from outside the class.

They do not have a leading underscore.

### Example

```python
class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary
    def display(self):
        print(self.name)
        print(self.salary)
employee = Employee("Aamir", 50000)
print(employee.name)
print(employee.salary)
employee.display()
```

**Output:**

```text
Aamir
50000
Aamir
50000
```

We can also directly modify public attributes:

```python
employee.salary = 80000
print(employee.salary)
```

**Output:**

```text
80000
```

### When Should You Use Public Attributes?

Public attributes are appropriate when:

- Direct access is safe.
- No special validation is required.
- Exposing the attribute is part of the intended API.
- Additional getter/setter methods would add unnecessary complexity.

Python generally favors simple public attributes when they are sufficient.

**Important:** Encapsulation does not mean every attribute must be private.

## 5. Protected Members: Single Underscore `_`

Python uses a single leading underscore to indicate that a member is intended for internal use.

### Syntax

```python
self._attribute
```

Example:

```python
class Employee:
    def __init__(self, name, salary):
        self.name = name
        self._salary = salary
    def display_salary(self):
        print(self._salary)
employee = Employee("Aamir", 50000)
employee.display_salary()
```

**Output:**

```text
50000
```

### Can We Access a Protected Attribute Outside the Class?

Yes.

```python
print(employee._salary)
```

**Output:**

```text
50000
```

We can also modify it:

```python
employee._salary = 100000
print(employee._salary)
```

**Output:**

```text
100000
```

**Why?**

Because `_salary` is not truly protected by a language-level access modifier.

The underscore is a convention that communicates:

This attribute is an internal implementation detail. External code should avoid depending on it.

### Accessing Protected Members Through Inheritance

```python
class Employee:
    def __init__(self, salary):
        self._salary = salary
class Manager(Employee):
    def display_salary(self):
        print(self._salary)
manager = Manager(90000)
manager.display_salary()
```

**Output:**

```text
90000
```

The child class can access the inherited internal attribute.

### Important Note

Unlike Java’s protected, Python’s single underscore does not restrict access to a class or its subclasses.

A leading underscore also affects wildcard imports: module-level names beginning with _ are normally excluded by from module import * unless explicitly exported through `__all__`.

## 6. Private Members: Double Underscore `__`

Python supports name mangling for certain names beginning with double underscores.

### Syntax

```python
self.__attribute
```

Example:

```python
class Employee:
    def __init__(self, salary):
        self.__salary = salary
    def display_salary(self):
        print(self.__salary)
employee = Employee(50000)
employee.display_salary()
```

**Output:**

```text
50000
```

**Now try:**

```python
print(employee.__salary)
```

**Error:**

```text
AttributeError: 'Employee' object has no attribute '__salary'
```

### Why Does This Happen?

Python internally transforms the name:

```python
__salary
```

into:

```python
_Employee__salary
```

This process is called name mangling.

The transformation is based on the class in which the identifier appears.

It helps prevent accidental naming conflicts, especially in inheritance hierarchies.

### 6.1 Accessing Name-Mangled Attributes

```python
class Employee:
    def __init__(self):
        self.__salary = 50000
employee = Employee()
print(employee._Employee__salary)
```

**Output:**

```text
50000
```

This proves that double-underscore attributes are not truly private.

Python does not encrypt or securely hide them.

#### Inspecting the Instance Dictionary

```python
print(employee.__dict__)
```

**Output:**

```text
{'_Employee__salary': 50000}
```

The attribute is stored under its mangled name.

#### Important Conclusion

Name mangling is not a security mechanism.

It is primarily intended to avoid accidental attribute-name collisions.

Do not store sensitive information in Python objects on the assumption that double underscores will make it inaccessible.

## 7. How Name Mangling Works Internally

Let’s examine the rules.

**Consider:**

```python
class Example:
    def __init__(self):
        self.name = 10
        self._name = 20
        self.__name = 30
        self.__name__ = 40
obj = Example()
print(obj.__dict__)
```

**Output:**

```text
{
    'name': 10,
    '_name': 20,
    '_Example__name': 30,
    '__name__': 40
}
```

### Explanation

| Attribute | Mangled? | Stored name |
| --- | --- | --- |
| name | No | name |
| `_name` | No | `_name` |
| `__name` | Yes | `_Example__name` |
| `__name__` | No | `__name__` |

### Name Mangling Rules

For identifiers written within a class definition:

- The identifier must begin with at least two underscores.
- The identifier must not end with two or more underscores.
- Python prefixes the identifier with an underscore and the class name.
- Leading underscores in the class name are removed for mangling purposes.
- The transformation happens during compilation, not dynamically whenever attributes are accessed.

**For example:**

```python
class Student:
    def __init__(self):
        self.__marks = 90
```

Python uses the attribute name:

```python
_Student__marks
```

### Is Name Mangling Applied to Methods?

Yes.

```python
class Example:
    def __secret_method(self):
        print("Private method")
    def call_method(self):
        self.__secret_method()
obj = Example()
obj.call_method()
```

**Output:**

```text
Private method
```

This will fail:

```python
obj.__secret_method()
```

But the mangled method can technically be accessed:

```python
obj._Example__secret_method()
```

**Output:**

```text
Private method
```

Again, this is possible but generally discouraged.

## 8. Private Members and Inheritance

This is an important Python interview topic.

**Consider:**

```python
class Parent:
    def __init__(self):
        self.__value = 100
class Child(Parent):
    def display(self):
        print(self.__value)
obj = Child()
obj.display()
```

**Error:**

```text
AttributeError: 'Child' object has no attribute '_Child__value'
```

Why Does This Happen?

The parent class creates:

```python
self._Parent__value
```

But inside the child class:

```python
self.__value
```

is transformed into:

```python
self._Child__value
```

These are different names.

Therefore, Python cannot find the child-mangled attribute.

### Does This Mean Private Attributes Are Not Inherited?

Not exactly.

The Child instance still contains the attribute initialized by Parent.

However, code using `__value` inside Child refers to a different mangled name.

**For example:**

```python
class Parent:
    def __init__(self):
        self.__value = 100
class Child(Parent):
    def display(self):
        print(self._Parent__value)
obj = Child()
obj.display()
```

**Output:**

```text
100
```

The parent-mangled attribute is present.

But accessing it directly from the child creates unnecessary coupling to the parent’s implementation.

### Preferred Approach

Expose a method or property.

```python
class Parent:
    def __init__(self):
        self.__value = 100
    def get_value(self):
        return self.__value
class Child(Parent):
    def display(self):
        print(self.get_value())
obj = Child()
obj.display()
```

**Output:**

```text
100
```

This is more maintainable because the child does not need to know how the parent stores its data.

## 9. Why Name Mangling Is Useful in Inheritance

Name mangling helps prevent accidental clashes between parent and child attributes.

### Without Name Mangling

```python
class Parent:
    def __init__(self):
        self.value = 100
class Child(Parent):
    def __init__(self):
        super().__init__()
        self.value = 200
obj = Child()
print(obj.value)
```

**Output:**

```text
200
```

Both classes use the same attribute name.

The child assignment overwrites the value initialized by the parent.

### With Name Mangling

```python
class Parent:
    def __init__(self):
        self.__value = 100
    def parent_value(self):
        return self.__value
class Child(Parent):
    def __init__(self):
        super().__init__()
        self.__value = 200
    def child_value(self):
        return self.__value
obj = Child()
print(obj.parent_value())
print(obj.child_value())
print(obj.__dict__)
```

**Output:**

```text
100
200
{'_Parent__value': 100, '_Child__value': 200}
```

**Explanation**

Python stores two separate attributes:

- `_Parent__value`
- `_Child__value`

Therefore, the child does not accidentally overwrite the parent’s attribute.

This is one of the main reasons Python provides name mangling.

## 10. Getters and Setters

Getters and setters are methods used to access and modify an object’s internal state.

- Getter: Retrieves an attribute’s value.
- Setter: Updates an attribute, potentially performing validation.
- Deleter: Controls removal of an attribute.

### 10.1 Traditional Getters and Setters

```python
class Student:
    def __init__(self, marks):
        self.__marks = marks
    def get_marks(self):
        return self.__marks
    def set_marks(self, marks):
        if 0 <= marks <= 100:
            self.__marks = marks
        else:
            raise ValueError("Marks must be between 0 and 100")
student = Student(80)
print(student.get_marks())
student.set_marks(95)
print(student.get_marks())
```

**Output:**

```text
80
95
```

#### Attempting an Invalid Value

```python
student.set_marks(150)
```

**Error:**

```text
ValueError: Marks must be between 0 and 100
```

#### What Does This Achieve?

Instead of allowing unrestricted modification:

```python
student.marks = 150
```

the setter ensures that updates satisfy the business rule.

#### Problem With Traditional Getters and Setters

The syntax becomes verbose:

```python
student.get_marks()
student.set_marks(90)
```

Python provides a more idiomatic solution: properties.

**Note:** The example above validates updates but not the initial value passed to `__init__()`. A robust implementation should validate both, ideally through one shared validation path.

## 11. The `@property` Decorator

The `@property` decorator allows us to define methods that behave like attributes.

This is one of the most important Python tools for building encapsulated interfaces.

### Example

```python
class Employee:
    def __init__(self, salary):
        self._salary = salary
    @property
    def salary(self):
        return self._salary
employee = Employee(50000)
print(employee.salary)
```

**Output:**

```text
50000
```

### What Is Happening?

The method:

```python
@property
def salary(self):
    return self._salary
```

is accessed as:

```python
employee.salary
```

instead of:

```python
employee.salary()
```

Although it looks like attribute access, Python executes the getter method.

### Can We Modify This Property?

**Try:**

```python
employee.salary = 70000
```

**Error:**

```text
AttributeError: property 'salary' of 'Employee' object has no setter
```

Because we defined a getter but no setter.

This creates a read-only public property.

However, the underlying `_salary` attribute can still be modified directly in ordinary Python code.

## 12. `@property` With a Setter

To allow controlled modification, use:

```python
@attribute_name.setter
```

### Example

```python
class Employee:
    def __init__(self, salary):
        self.salary = salary
    @property
    def salary(self):
        return self._salary
    @salary.setter
    def salary(self, value):
        if value < 0:
            raise ValueError("Salary cannot be negative")
        self._salary = value
employee = Employee(50000)
print(employee.salary)
employee.salary = 75000
print(employee.salary)
```

**Output:**

```text
50000
75000
```

### Why Is This Better?

External code uses normal attribute syntax:

```python
employee.salary
```

and:

```python
employee.salary = 75000
```

But internally Python executes the getter or setter.

The class can validate values while exposing a clean public interface.

### Important: Validation During Initialization

**Notice:**

```python
def __init__(self, salary):
    self.salary = salary
```

We deliberately used:

```python
self.salary = salary
```

instead of:

```python
self._salary = salary
```

**Why?**

Because `self.salary` = salary invokes the property setter.

Therefore, validation happens during object initialization as well.

**For example:**

employee = Employee(-5000)

**raises:**

```text
ValueError: Salary cannot be negative
```

This avoids duplicating validation logic.

## 13. How `@property` Works Internally

A property is implemented using Python’s descriptor protocol.

Understanding this is useful for advanced Python interviews.

### What Is a Descriptor?

A descriptor is an object that participates in attribute access by defining special methods such as:

`__get__()`
`__set__()`
`__delete__()`

A property uses these mechanisms to customize reading, assignment, and deletion.

### Equivalent Property Implementation

**Consider:**

```python
class Employee:
    def __init__(self, salary):
        self._salary = salary
    @property
    def salary(self):
        return self._salary
    @salary.setter
    def salary(self, value):
        self._salary = value
```

Conceptually, this is equivalent to:

```python
class Employee:
    def __init__(self, salary):
        self._salary = salary
    def get_salary(self):
        return self._salary
    def set_salary(self, value):
        self._salary = value
    salary = property(get_salary, set_salary)
```

The built-in property() function creates a property descriptor.

### Execution Flow

When we execute:

```python
employee.salary
```

Python finds the property on the class and calls its getter.

Conceptually:

```python
Employee.__dict__["salary"].__get__(employee, Employee)
```

When we execute:

```python
employee.salary = 80000
```

Python calls the property’s setter.

Conceptually:

```python
Employee.__dict__["salary"].__set__(employee, 80000)
```

Properties are data descriptors. Their descriptor behavior takes precedence over ordinary instance dictionary entries with the same name.

### Important Distinction

A property is not simply a method that gets called automatically because its name matches an attribute.

It is a special object placed in the class namespace that controls attribute access through Python’s descriptor protocol.

## 14. Getter, Setter, and Deleter Together

Python also supports:

```python
@property
@name.setter
@name.deleter
```

### Complete Example

```python
class Person:
    def __init__(self, name):
        self.name = name
    @property
    def name(self):
        return self._name
    @name.setter
    def name(self, value):
        if not isinstance(value, str) or not value.strip():
            raise ValueError("Name must be a non-empty string")
        self._name = value
    @name.deleter
    def name(self):
        print("Deleting name")
        del self._name
person = Person("Aamir")
print(person.name)
person.name = "Rahul"
print(person.name)
del person.name
```

**Output:**

```text
Aamir
Rahul
Deleting name
```

**Explanation**

| Operation | Method executed |
| --- | --- |
| `person.name` | Getter |
| `person.name` = “Rahul” | Setter |
| del `person.name` | Deleter |

After deletion, trying:

```python
print(person.name)
```

will raise an `AttributeError`, because `_name` no longer exists.

### Should Every Property Have a Deleter?

No.

In many real-world applications, deleting an essential attribute would leave the object in an invalid state.

Only define a deleter when deletion is a meaningful supported operation.

## 15. Read-Only vs Writable Properties

Properties are useful for exposing calculated or protected values.

### 15.1 Read-Only Property

```python
class Circle:
    def __init__(self, radius):
        if radius < 0:
            raise ValueError("Radius cannot be negative")
        self._radius = radius
    @property
    def area(self):
        return 3.14159 * self._radius ** 2
circle = Circle(5)
print(circle.area)
```

**Output:**

```text
78.53975
```

Here, area is calculated using the radius.

It is not stored separately.

#### Why Is This Useful?

Imagine storing both:

```python
self.radius = 5
self.area = 78.53975
```

If the radius changes, the stored area might become outdated.

A computed property avoids this inconsistency.

### 15.2 Writable Property

```python
class Circle:
    def __init__(self, radius):
        self.radius = radius
    @property
    def radius(self):
        return self._radius
    @radius.setter
    def radius(self, value):
        if value < 0:
            raise ValueError("Radius cannot be negative")
        self._radius = value
    @property
    def area(self):
        return 3.14159 * self._radius ** 2
circle = Circle(5)
print(circle.area)
circle.radius = 10
print(circle.area)
```

**Output:**

```text
78.53975
314.159
```

The public radius property can be updated, while area is computed automatically.

## 16. Common Mistake: Infinite Recursion in Setters

This is a very common mistake when learning `@property`.

### Incorrect Implementation

```python
class Student:
    def __init__(self, marks):
        self.marks = marks
    @property
    def marks(self):
        return self.marks
    @marks.setter
    def marks(self, value):
        self.marks = value
```

This implementation causes infinite recursion.

**Why?**

Inside the setter:

```python
self.marks = value
```

calls the same setter again.

That setter executes:

```python
self.marks = value
```

which calls the setter again.

This continues until Python raises:

```text
RecursionError: maximum recursion depth exceeded
```

The getter has the same problem:

```python
return self.marks
```

It invokes itself repeatedly.

### Correct Implementation

```python
class Student:
    def __init__(self, marks):
        self.marks = marks
    @property
    def marks(self):
        return self._marks
    @marks.setter
    def marks(self, value):
        if not 0 <= value <= 100:
            raise ValueError("Invalid marks")
        self._marks = value
```

### Important Rule

The public property and its internal storage attribute should normally use different names.

- Public property: marks
- Internal storage: `_marks`

**Or:**

- Public property: salary
- Internal storage: `_salary`

This prevents recursive property access.

## 17. Encapsulation With Methods vs Properties

Both methods and properties can provide controlled access.

However, they serve slightly different purposes.

### Methods

Use methods when the operation represents an action.

**Examples:**

```python
account.deposit(1000)
account.withdraw(500)
order.cancel()
user.change_password("new-password")
```

These operations have meaningful business behavior.

### Properties

Use properties when the operation behaves conceptually like reading or assigning an attribute.

**Examples:**

```python
employee.salary
circle.area
student.marks
product.price
```

### Comparison

| Feature | Methods | Properties |
| --- | --- | --- |
| Syntax | `obj.method()` | `obj.attribute` |
| Best suited for | Actions and commands | Attribute-like access |
| Validation | Supported | Supported |
| Computed values | Supported | Supported |
| Side effects | Expected in commands | Usually should be minimal for getters |
| Interface clarity | Explicit operation | Natural attribute syntax |

### Design Guideline

A getter should ideally be inexpensive and free of surprising side effects.

For example, this is less intuitive:

```python
user.balance
```

if accessing it unexpectedly performs an expensive network request and modifies database records.

An explicit method may be clearer:

```python
user.fetch_balance()
```

The choice should reflect what the operation means.

## 18. Complete Real-World Example: Bank Account

Let’s combine encapsulation, properties, validation, and controlled state modification.

For financial values, Python’s Decimal type is useful because binary floating-point arithmetic can introduce rounding errors.

```python
from decimal import Decimal
class BankAccount:
    def __init__(self, owner, initial_balance=0):
        self.owner = owner
        balance = Decimal(str(initial_balance))
        if not balance.is_finite() or balance < 0:
            raise ValueError("Invalid initial balance")
        self._balance = balance
    @property
    def balance(self):
        return self._balance
    def deposit(self, amount):
        amount = Decimal(str(amount))
        if not amount.is_finite() or amount <= 0:
            raise ValueError("Deposit must be positive")
        self._balance += amount
    def withdraw(self, amount):
        amount = Decimal(str(amount))
        if not amount.is_finite() or amount <= 0:
            raise ValueError("Withdrawal must be positive")
        if amount > self._balance:
            raise ValueError("Insufficient balance")
        self._balance -= amount
    def display_balance(self):
        print(f"Available balance: {self._balance:.2f}")
account = BankAccount("Aamir", "1000.00")
account.deposit("500.00")
account.withdraw("300.00")
account.display_balance()
```

**Output:**

```text
Available balance: 1200.00
```

### What Happens If We Try Direct Assignment?

```python
account.balance = 100000
```

**Error:**

```text
AttributeError: property 'balance' of 'BankAccount' object has no setter
```

The public balance property has no setter.

This prevents normal assignment through that public interface.

### How Does Encapsulation Help?

The class ensures that:

- Deposits must be positive.
- Withdrawals must be positive.
- Withdrawals cannot exceed the balance.
- Balance changes happen through intended operations.
- External code can read the balance without using a setter.

### Important Limitation

An external caller could still write:

```python
account._balance = Decimal("-1000")
```

Python allows this.

Therefore, the protection is based on respecting the documented class interface.

Also, this example is an in-memory educational implementation. A production banking system requires transaction management, concurrency control, persistence, authorization, and additional validation.

## 19. Encapsulation and Mutable Objects

This is an advanced concept that is frequently overlooked.

Suppose a class stores a list internally.

```python
class Student:
    def __init__(self):
        self._marks = [80, 90, 85]
    @property
    def marks(self):
        return self._marks
```

**Now:**

student = Student()
`student.marks.append(-100)`
print(`student.marks`)

**Output:**

```text
[80, 90, 85, -100]
```

### What Went Wrong?

Even though marks is a read-only property, it returns a reference to the internal mutable list.

The caller cannot assign a new list using:

```python
student.marks = [...]
```

But the caller can mutate the returned list.

This means that a read-only property does not automatically make the underlying data immutable.

### Solution 1: Return a Copy

```python
class Student:
    def __init__(self):
        self._marks = [80, 90, 85]
    @property
    def marks(self):
        return self._marks.copy()
student = Student()
student.marks.append(-100)
print(student.marks)
```

**Output:**

```text
[80, 90, 85]
```

The caller modifies a copy rather than the original list.

However, a shallow copy does not protect nested mutable objects.

### Solution 2: Return an Immutable Representation

```python
class Student:
    def __init__(self):
        self._marks = [80, 90, 85]
    @property
    def marks(self):
        return tuple(self._marks)
    def add_marks(self, value):
        if not 0 <= value <= 100:
            raise ValueError("Invalid marks")
        self._marks.append(value)
student = Student()
print(student.marks)
student.add_marks(95)
print(student.marks)
```

**Output:**

```text
(80, 90, 85)
(80, 90, 85, 95)
```

The returned tuple cannot be modified using append().

### Key Lesson

Encapsulation must consider not only whether callers can assign attributes, but also whether they can mutate internal objects through exposed references.

## 20. Encapsulation of Class Attributes

Encapsulation is not limited to instance attributes.

Class-level attributes can also be exposed or managed through class methods.

### Example

```python
class Employee:
    _employee_count = 0
    def __init__(self, name):
        self.name = name
        Employee._employee_count += 1
    @classmethod
    def get_employee_count(cls):
        return cls._employee_count
emp1 = Employee("Aamir")
emp2 = Employee("Rahul")
print(Employee.get_employee_count())
```

**Output:**

```text
2
```

### Explanation

`_employee_count` is an internal class attribute.

The class exposes a method to read it.

However, the implementation explicitly updates `Employee._employee_count`, meaning the counter belongs to Employee rather than being independently maintained for every subclass.

### Can We Modify the Counter Directly?

Yes.

```python
Employee._employee_count = 100
```

The underscore does not enforce privacy.

### When Is This Useful?

Class-level encapsulation can be used for:

- Object counters.
- Shared configuration.
- Class-wide metadata.
- Resource tracking.
- Shared policies.

Be careful with shared mutable state and inheritance because changes to class attributes can affect many objects.

## 21. Encapsulation and Inheritance Together

Encapsulation becomes especially valuable when a class is inherited.

**Consider:**

```python
class Employee:
    def __init__(self, salary):
        self._salary = salary
    @property
    def salary(self):
        return self._salary
    @salary.setter
    def salary(self, value):
        if value < 0:
            raise ValueError("Salary cannot be negative")
        self._salary = value
class Manager(Employee):
    def increase_salary(self, amount):
        if amount <= 0:
            raise ValueError("Increase must be positive")
        self.salary += amount
manager = Manager(50000)
manager.increase_salary(10000)
print(manager.salary)
```

**Output:**

```text
60000
```

### What Is Important Here?

The child class uses the parent’s public property:

```python
self.salary
```

rather than directly updating:

```python
self._salary
```

This preserves the validation provided by the parent class.

### Why Is This Better?

Suppose the parent changes its internal implementation later.

For example, it might store salary in a database or calculate deductions.

If the child uses the public interface, it is less likely to break.

**Design principle:** Subclasses should generally use a parent’s supported interface instead of unnecessarily depending on its implementation details.

## 22. Encapsulation vs Abstraction

Encapsulation and abstraction are related but different OOP concepts.

### Encapsulation

Encapsulation focuses on organizing state and behavior and controlling access to internal state.

Question it answers:

How do we protect and manage an object’s internal state?

### Abstraction

Abstraction focuses on exposing essential capabilities while hiding unnecessary implementation complexity.

Question it answers:

What functionality should an object expose without requiring callers to understand how it is implemented?

### Example

```python
class Car:
    def __init__(self):
        self._engine_running = False
    def start(self):
        self._engine_running = True
        print("Car started")
```

**Usage:**

car = Car()
`car.start()`

**Output:**

```text
Car started
```

### Encapsulation Aspect

The engine state is stored internally:

```python
self._engine_running
```

The start() method is the intended way to change it.

### Abstraction Aspect

The caller simply uses:

```python
car.start()
```

without needing to understand all the internal operations required to start a real engine.

### Comparison

| Encapsulation | Abstraction |
| --- | --- |
| Organizes data and behavior | Exposes essential behavior |
| Controls access to state | Hides unnecessary implementation details |
| Helps maintain invariants | Helps reduce conceptual complexity |
| Often implemented with methods and properties | Often implemented through interfaces, APIs, and abstract classes |
| Focuses on state management | Focuses on what functionality is provided |

### Easy Way to Remember

- Encapsulation: Control how internal data is accessed or changed.
- Abstraction: Expose what an object can do without exposing all implementation details.

A well-designed class frequently uses both.

## 23. Encapsulation vs Inheritance vs Polymorphism

These OOP principles solve different problems.

| OOP Principle | Primary Purpose | Python Example |
| --- | --- | --- |
| Encapsulation | Organize and control state | Properties and validation methods |
| Inheritance | Reuse and specialize behavior | class Dog(Animal) |
| Polymorphism | Support different implementations through a common operation | Overridden speak() methods |
| Abstraction | Expose essential functionality while hiding complexity | Abstract classes and public interfaces |

### Combined Example

```python
from abc import ABC, abstractmethod
class Employee(ABC):
    def __init__(self, salary):
        self.salary = salary
    @property
    def salary(self):
        return self._salary
    @salary.setter
    def salary(self, value):
        if value < 0:
            raise ValueError("Invalid salary")
        self._salary = value
    @abstractmethod
    def calculate_bonus(self):
        pass
class Developer(Employee):
    def calculate_bonus(self):
        return self.salary * 0.10
class Manager(Employee):
    def calculate_bonus(self):
        return self.salary * 0.20
employees = [
    Developer(50000),
    Manager(80000)
]
for employee in employees:
    print(employee.calculate_bonus())
```

**Output:**

```text
5000.0
16000.0
```

### OOP Principles Used

### Encapsulation

```python
@property
def salary(self):
    return self._salary
```

Salary modification is controlled through a validated property.

### Abstraction

```python
@abstractmethod
def calculate_bonus(self):
    pass
```

The base class defines the required interface.

### Inheritance

```python
class Developer(Employee):
```

The child inherits common employee functionality.

### Polymorphism

```python
employee.calculate_bonus()
```

The same method call produces behavior specific to each employee type.

## 24. Encapsulation With `__slots__`

Python allows classes to declare `__slots__`.

This is related to instance attribute storage, but it is not a privacy feature.

### Example

```python
class Student:
    __slots__ = ("name", "_marks")
    def __init__(self, name, marks):
        self.name = name
        self._marks = marks
student = Student("Aamir", 90)
print(student.name)
print(student._marks)
```

**Output:**

```text
Aamir
90
```

**Now try:**

```python
student.age = 25
```

**Error:**

```text
AttributeError: 'Student' object has no attribute 'age'
```

**Why?**

For this class, `__slots__` declares the supported instance attribute storage names.

Normally, this prevents arbitrary new instance attributes when the class and its hierarchy do not provide an instance `__dict__`.

### Does `__slots__` Provide Privacy?

No.

```python
student._marks = -100
```

still works.

### Main Uses of `__slots__`

- Potentially reduce per-instance memory usage.
- Restrict arbitrary attribute creation.
- Define a more explicit instance attribute layout.

### Important Limitations

- Subclasses can introduce `__dict__` unless their design prevents it.
- Slots do not automatically validate assigned values.
- Slots are not a security boundary.
- Slot descriptors are part of Python’s descriptor mechanism.

```python
__slots__ can support a controlled object design, but should not be confused with encapsulation itself.
```

## 25. Encapsulation With Dataclasses

Python’s dataclasses module can reduce boilerplate for data-oriented classes.

However, dataclasses do not automatically provide encapsulation or validation.

### Basic Dataclass

```python
from dataclasses import dataclass
@dataclass
class Student:
    name: str
    marks: int
student = Student("Aamir", 90)
student.marks = -100
print(student.marks)
```

**Output:**

```text
-100
```

The dataclass still allows invalid modification.

### Using `frozen=True`

```python
from dataclasses import dataclass
@dataclass(frozen=True)
class Student:
    name: str
    marks: int
student = Student("Aamir", 90)
print(student.marks)
```

**Output:**

```text
90
```

**Now:**

```python
student.marks = 100
```

**raises:**

```text
dataclasses.FrozenInstanceError: cannot assign to field 'marks'
```

### Does `frozen=True` Make an Object Completely Immutable?

No.

**Consider:**

```python
from dataclasses import dataclass, field
@dataclass(frozen=True)
class Student:
    marks: list[int] = field(default_factory=list)
student = Student([80, 90])
student.marks.append(100)
print(student.marks)
```

**Output:**

```text
[80, 90, 100]
```

The attribute cannot normally be rebound, but the contained list can still be modified.

**Therefore:**

Frozen dataclasses provide restricted assignment, not deep immutability.

## 26. Best Practices for Encapsulation in Python

### 26.1 Prefer Simple Public Attributes When Appropriate

Do not create getters and setters for every attribute automatically.

For simple data:

```python
class User:
    def __init__(self, name):
        self.name = name
```

This is perfectly valid Python design.

### 26.2 Use Properties When Validation or Computation Is Needed

```python
class Product:
    def __init__(self, price):
        self.price = price
    @property
    def price(self):
        return self._price
    @price.setter
    def price(self, value):
        if value < 0:
            raise ValueError("Price cannot be negative")
        self._price = value
```

### 26.3 Use Methods for Meaningful State Transitions

Prefer:

```python
account.withdraw(500)
```

over:

```python
account.balance -= 500
```

when withdrawal requires business rules.

### 26.4 Use Single Underscores for Internal Implementation Details

```python
self._balance
```

This is a common and readable Python convention.

### 26.5 Use Double Underscores When Preventing Subclass Name Collisions

Use:

```python
self.__internal_state
```

when name mangling is genuinely useful.

Do not use double underscores merely because an attribute contains important information.

### 26.6 Avoid Returning Mutable Internal Objects Directly

Instead of:

```python
return self._items
```

consider:

```python
return tuple(self._items)
```

or returning a suitable copy.

### 26.7 Centralize Validation

Avoid duplicating the same checks across initialization and update methods.

A property setter can provide one validation path.

### 26.8 Do Not Expose Implementation Details Unnecessarily

Avoid forcing other classes to access:

```python
obj._SomeClass__secret
```

Provide an appropriate method or property instead.

### 26.9 Keep Object Invariants in Mind

Every state-changing operation should preserve the object’s valid conditions.

Encapsulation is strongest when the public interface makes invalid state transitions difficult.

## 27. Common Mistakes in Encapsulation

### Mistake 1: Assuming `_name` Is Actually Protected

```python
obj._name = "Changed"
```

Python permits this.

The underscore is a convention.

### Mistake 2: Assuming `__name` Provides Security

```python
obj._ClassName__name
```

can often access the attribute.

Name mangling is not encryption or an access-control boundary.

### Mistake 3: Forgetting Validation During Initialization

```python
class Student:
    def __init__(self, marks):
        self._marks = marks
```

Even if a setter exists elsewhere, assigning directly to `_marks` can bypass validation.

Prefer a shared validation path.

### Mistake 4: Writing Recursive Properties

**Incorrect:**

```python
@property
def age(self):
    return self.age
```

**Correct:**

```python
@property
def age(self):
    return self._age
```

### Mistake 5: Exposing Mutable Internal References

```python
@property
def items(self):
    return self._items
```

Callers may mutate the returned list.

### Mistake 6: Treating Read-Only Properties as Complete Immutability

A read-only property prevents ordinary assignment to that property.

It does not automatically prevent modification of internal storage or mutable returned objects.

### Mistake 7: Writing Unnecessary Getters and Setters

This is often unnecessary:

```python
class Person:
    def get_name(self):
        return self._name
    def set_name(self, name):
        self._name = name
```

If no validation or special behavior is needed, a public attribute may be simpler.

## 28. Tricky Interview Questions With Outputs

### Question 1: What Happens When We Access a Double-Underscore Attribute?

```python
class A:
    def __init__(self):
        self.__x = 100
obj = A()
print(obj.__x)
```

**Answer:**

```text
AttributeError
```

Because `__x` is name-mangled to `_A__x`.

```python
    def __init__(self):
        self.__x = 100
obj = A()

```

**Output:**

```text
100
```

Name mangling does not provide strict privacy.

### Question 3: What Happens With a Read-Only Property?

```python
class A:
    def __init__(self):
        self._x = 10
    @property
    def x(self):
        return self._x
obj = A()
obj.x = 20
```

**Answer:**

```text
AttributeError
```

The x property has no setter.

### Question 4: Does a Read-Only Property Prevent All Mutation?

```python

    def __init__(self):
        self._items = [1, 2, 3]
    @property
    def items(self):
        return self._items

```

**Output:**

```text
[1, 2, 3, 4]
```

The property returns a reference to a mutable list.

### Question 5: What Is the Output?

```python
class Parent:
    def __init__(self):
        self.__x = 10
    def get_x(self):
        return self.__x
class Child(Parent):
    def __init__(self):
        super().__init__()
        self.__x = 20
obj = Child()
print(obj.get_x())
print(obj._Child__x)
```

**Output:**

```text
10
20
```

**Because:**

- Parent's attribute: `_Parent__x`
- Child's attribute:  `_Child__x`

Both exist independently.

### Question 6: Does a Property Setter Execute During Initialization?

```python
class A:
    def __init__(self, x):
        self.x = x
    @property
    def x(self):
        return self._x
    @x.setter
    def x(self, value):
        print("Setter called")
        self._x = value
obj = A(10)
print(obj.x)
```

**Output:**

```text
Setter called
10
```

**Because:**

```python
self.x = x
```

invokes the property setter.

### Question 7: What Happens When Property Storage Uses the Same Name?

```python
class A:
    @property
    def x(self):
        return self.x
obj = A()
print(obj.x)
```

**Answer:**

```text
RecursionError
```

The getter repeatedly calls itself.

### Question 8: Can a Child Override a Property?

```python
class Parent:
    @property
    def value(self):
        return 10
class Child(Parent):
    @property
    def value(self):
        return 20
obj = Child()
print(obj.value)
```

**Output:**

```text
20
```

Properties participate in inheritance and overriding.

### Question 9: Does Double Underscore Prevent Method Overriding?

```python
class Parent:
    def __show(self):
        print("Parent")
    def call_show(self):
        self.__show()
class Child(Parent):
    def __show(self):
        print("Child")
obj = Child()
obj.call_show()
```

**Output:**

```text
Parent
```

**Explanation**

Inside Parent:

```python
self.__show()
```

uses the mangled name:

```python
self._Parent__show()
```

Inside Child, `__show` becomes:

```python
_Child__show
```

Therefore, the child method does not override the parent’s mangled method.

This is an important reason name mangling exists.

### Question 10: What Is the Difference Between Public and Private Attributes in Python?

```python
class Example:
    def __init__(self):
        self.x = 10
        self.__y = 20
obj = Example()
print(obj.__dict__)
```

**Output:**

```text
{'x': 10, '_Example__y': 20}
```

The important difference is how Python stores and resolves the names, not whether the data is securely hidden.

## 29. Interview Questions and Answers

### Q1. What is encapsulation in Python?

Encapsulation is the practice of bundling attributes and methods into a class while providing controlled interfaces for accessing and modifying the object’s internal state.

### Q2. Does Python support private variables?

Python supports name mangling using double underscores, but does not provide strict private instance variables like Java.

### Q3. What is the difference between `_variable` and `__variable`?

`_variable` is a convention indicating internal use.

```python
__variable triggers name mangling when used within a class definition, helping prevent accidental naming conflicts.
```

### Q4. What is name mangling?

Name mangling is Python’s automatic transformation of certain double-underscore identifiers into class-qualified names such as `_ClassName__attribute`.

### Q5. What is the purpose of `@property`?

It allows a method to be accessed using attribute syntax, enabling validation, computation, and controlled access without exposing the implementation.

### Q6. What happens if a property does not have a setter?

Normal assignment to the property raises an `AttributeError`.

### Q7. Can we override properties in child classes?

Yes. A subclass can override an inherited property.

### Q8. Is encapsulation the same as data hiding?

No.

Data hiding is one possible aspect of encapsulation. Encapsulation is broader and includes organizing data and behavior and exposing controlled operations.

### Q9. Is encapsulation possible without private attributes?

Yes.

A class with public attributes and well-defined methods can still encapsulate related data and behavior. The amount of access control needed depends on the requirements.

### Q10. Should every Python attribute have a getter and setter?

No. Simple public attributes are often preferable when validation or special behavior is unnecessary.

### Q11. What is the difference between a method and a property?

Methods represent explicit operations using call syntax, while properties expose attribute-like access that can execute custom logic.

### Q12. Are name-mangled attributes inherited?

The attributes can exist on subclass instances through inherited initialization, but identifiers using double underscores are mangled according to the class where they are written.

### Q13. What is a data descriptor?

A descriptor defining `__set__()` or `__delete__()` is a data descriptor. Data descriptors participate in attribute lookup with priority over ordinary instance dictionary attributes.

Python properties are data descriptors.

### Q14. Is a frozen dataclass completely immutable?

No. Frozen dataclasses restrict ordinary field reassignment, but mutable objects stored in fields may still be modified.

### Q15. Does `__slots__` make attributes private?

No. It controls certain aspects of instance attribute storage and can restrict arbitrary new attributes, but does not make existing attributes private.

### Q16. What are the main advantages of encapsulation?

It improves control over state changes, supports validation, reduces coupling, preserves invariants, and allows internal implementation details to evolve.

### Q17. Can encapsulation be bypassed in Python?

Many conventional encapsulation mechanisms can be bypassed through direct attribute access, mangled names, introspection, or low-level mechanisms.

Encapsulation in Python is primarily an API-design discipline, not a general security boundary.

## 31. Final Key Takeaways

- Encapsulation combines related data and behavior inside a class.
- Its practical value comes from controlling how object state changes.
- Python does not enforce traditional public, protected, and private access modifiers.
- A single underscore indicates an internal member by convention.
- A double underscore triggers name mangling for suitable identifiers.
- Name mangling prevents many accidental naming conflicts but does not provide security.
- `@property` is Python’s preferred tool for attribute-like access with custom behavior.
- A property setter can validate changes and preserve object invariants.
- A property getter can compute values dynamically without storing redundant state.
- A read-only property does not automatically make referenced mutable data immutable.
- Exposing mutable internal objects can allow callers to bypass intended restrictions.
- `__slots__` controls aspects of attribute storage but is not a privacy mechanism.
- Frozen dataclasses restrict assignment but do not guarantee deep immutability.
- Subclasses should generally interact with parent state through supported interfaces.
- Prefer meaningful methods for state-changing operations and simple public attributes where appropriate.
- Encapsulation and abstraction are related, but encapsulation focuses on state management while abstraction focuses on exposed functionality.
- Good encapsulation protects invariants, reduces coupling, and makes classes easier to evolve.

### Core Mental Model

Encapsulation in Python is about controlling behavior and preserving valid state, not about making data impossible to access.

A well-encapsulated object provides a clear public interface:

```python
account.deposit(1000)
account.withdraw(500)
print(account.balance)
```

Rather than requiring callers to manipulate internal state:

```python
account._balance += 1000
account._balance -= 500
```

The first approach allows the object to manage its own rules.

The second approach spreads responsibility for those rules across the rest of the program.

The most important principle to remember: Design classes so that users can perform valid operations through a clear interface without needing to understand or manipulate the internal implementation.
