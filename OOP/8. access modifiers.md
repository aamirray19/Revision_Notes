
# Access Modifiers in Python — Complete OOP Notes

## 1. What Are Access Modifiers?

**Access modifiers define the intended visibility and accessibility of attributes and methods in a class.**

They help communicate which parts of a class are meant to be used from outside and which parts are intended for internal implementation.

In Object-Oriented Programming, access modifiers are closely associated with **encapsulation**.

### Types of Access Modifiers

In languages like Java and C++, access modifiers are enforced through keywords.

Python takes a different approach.

Python primarily uses **naming conventions** instead of strict access-control keywords.

| Access Level | Python Syntax | Meaning |
|---|---|---|
| Public | `name` | Intended for unrestricted access |
| Protected | `_name` | Intended for internal use and subclasses |
| Private | `__name` | Uses name mangling to avoid accidental conflicts |

### Important

Python does not have traditional `public`, `protected`, and `private` keywords.

These are conventions or mechanisms used to communicate the intended usage of class members.

**Python does not provide strict private or protected access enforcement like Java or C++.**

---

# 2. Why Do We Need Access Modifiers?

Consider a bank account.

A bank account contains:

- Account holder's name
- Account number
- Account balance
- Deposit functionality
- Withdrawal functionality

We may want users to access their account information.

However, we do not want external code to arbitrarily modify the account balance without validation.

### Example: Without Controlled Access

```python
class BankAccount:

    def __init__(self, balance):
        self.balance = balance


account = BankAccount(1000)

account.balance = -50000

print(account.balance)
```

### Output

```text
-50000
```

### Problem

External code can directly assign an invalid balance.

This can violate the business rules of the application.

We want to provide controlled operations such as:

```python
account.deposit(500)
account.withdraw(200)
```

Instead of encouraging unrestricted modification:

```python
account.balance = -50000
```

This is where encapsulation, access conventions, and properties become useful.

### Benefits

1. Communicate which attributes are part of the public API.
2. Reduce accidental modifications to internal state.
3. Protect business rules through controlled methods.
4. Improve maintainability.
5. Reduce dependencies on implementation details.
6. Prevent accidental naming conflicts in inheritance.

Remember that naming conventions alone do not enforce data security or validate business rules.

# 3. Public Access Modifier

## Definition

A public attribute or method is intended to be accessible from anywhere.

By default, ordinary Python attributes and methods are public.

### Syntax

```python
class ClassName:

    def __init__(self):
        self.name = "Python"

    def display(self):
        print(self.name)
```

Here:

- `name` is a public attribute.
- `display()` is a public method.

### Example

```python
class Student:

    def __init__(self, name, age):
        self.name = name
        self.age = age

    def display(self):
        print(f"Name: {self.name}")
        print(f"Age: {self.age}")


student = Student("Ali", 22)

print(student.name)
print(student.age)

student.display()
```

### Output

```text
Ali
22
Name: Ali
Age: 22
```

### Modifying Public Attributes

```python
student.name = "Ahmed"

print(student.name)
```

### Output

```text
Ahmed
```

Public attributes can ordinarily be read, updated, and deleted from outside the class.

### Key Point

Python does not need an explicit `public` keyword.

```python
self.name
```

is public by convention.

# 4. Protected Access Modifier

## Definition

A protected attribute or method is intended for use within the class and its subclasses.

In Python, a single leading underscore indicates this convention.

### Syntax

```python
self._attribute
```

```python
def _method(self):
    pass
```

### Example

```python
class Employee:

    def __init__(self, name, salary):
        self.name = name
        self._salary = salary

    def _show_salary(self):
        print(f"Salary: {self._salary}")


employee = Employee("Ali", 50000)

print(employee.name)
print(employee._salary)

employee._show_salary()
```

### Output

```text
Ali
50000
Salary: 50000
```

### Important Observation

Even though `_salary` and `_show_salary()` are protected by convention, external code can access them.

```python
print(employee._salary)
```

works.

Why?

Because **Python does not enforce protected access restrictions**.

The underscore acts as a signal to other developers:

> This member is an implementation detail. Avoid depending on it from external code.

---

## 4.1 Protected Attributes With Inheritance

Protected members are commonly used when subclasses need to access internal functionality of a parent class.

### Example

```python
class Employee:

    def __init__(self, name, salary):
        self.name = name
        self._salary = salary

    def _calculate_bonus(self):
        return self._salary * 0.10


class Manager(Employee):

    def display_compensation(self):
        bonus = self._calculate_bonus()

        print("Salary:", self._salary)
        print("Bonus:", bonus)


manager = Manager("Sara", 80000)

manager.display_compensation()
```

### Output

```text
Salary: 80000
Bonus: 8000.0
```

### Explanation

The parent class defines:

```python
self._salary
```

and:

```python
_calculate_bonus()
```

The child class accesses both.

This is an intended use of protected members.

### Can External Code Still Access Them?

Yes.

```python
print(manager._salary)
```

### Output

```text
80000
```

### Key Takeaway

**Protected in Python means "intended for internal and subclass use", not "accessible only by the class and subclasses".**

# 5. Private Access Modifier

## Definition

A private attribute is intended to avoid accidental access or name collisions, especially in subclasses.

In Python, an identifier beginning with two underscores and not ending with two underscores triggers **name mangling** in a class definition.

### Syntax

```python
self.__attribute
```

```python
def __method(self):
    pass
```

### Example

```python
class BankAccount:

    def __init__(self, balance):
        self.__balance = balance

    def show_balance(self):
        print(self.__balance)


account = BankAccount(1000)

account.show_balance()
```

### Output

```text
1000
```

Inside the class:

```python
self.__balance
```

works.

But what happens when we try:

```python
print(account.__balance)
```

### Result

```text
AttributeError: 'BankAccount' object has no attribute '__balance'
```

### Why?

Python changes the name of the attribute internally.

This mechanism is called **name mangling**.

# 6. Name Mangling in Python

This is the most important concept to understand about Python's private members.

## What Is Name Mangling?

**Name mangling is a mechanism that transforms certain double-underscore-prefixed identifiers inside a class definition.**

For example:

```python
class BankAccount:

    def __init__(self, balance):
        self.__balance = balance
```

Python internally transforms:

```text
__balance
```

into:

```text
_BankAccount__balance
```

### General Pattern

```text
_ClassName__attribute
```

### Accessing the Mangled Attribute

```python
class BankAccount:

    def __init__(self, balance):
        self.__balance = balance


account = BankAccount(1000)

print(account._BankAccount__balance)
```

### Output

```text
1000
```

This demonstrates that Python's double underscore is not a strict security boundary.

### Modifying a Mangled Attribute

```python
account._BankAccount__balance = 5000

print(account._BankAccount__balance)
```

### Output

```text
5000
```

### Important

The main purpose of name mangling is to prevent accidental naming conflicts between classes and subclasses.

It is **not a security feature**.

---

## 6.1 Understanding Name Mangling Internally

Consider:

```python
class Demo:

    def __init__(self):
        self.public = 10
        self._protected = 20
        self.__private = 30


obj = Demo()

print(obj.__dict__)
```

### Output

```python
{
    'public': 10,
    '_protected': 20,
    '_Demo__private': 30
}
```

### Explanation

Python stores these instance attributes under different names.

| Defined Name | Stored Name |
|---|---|
| `public` | `public` |
| `_protected` | `_protected` |
| `__private` | `_Demo__private` |

Notice that:

```python
__private
```

has been transformed into:

```python
_Demo__private
```

### Why Does Python Do This?

Primarily to prevent a subclass from accidentally overwriting a parent's internal attributes.

We will examine this through inheritance.

# 7. Private Members and Inheritance

This is a very important interview topic.

## Example

```python
class Parent:

    def __init__(self):
        self.__value = 100

    def show_parent_value(self):
        print(self.__value)


class Child(Parent):

    def __init__(self):
        super().__init__()
        self.__value = 200

    def show_child_value(self):
        print(self.__value)


obj = Child()

obj.show_parent_value()
obj.show_child_value()

print(obj.__dict__)
```

### Output

```text
100
200
{'_Parent__value': 100, '_Child__value': 200}
```

### What's Happening?

The parent defines:

```python
self.__value
```

Inside `Parent`, Python mangles it to:

```text
_Parent__value
```

The child also defines:

```python
self.__value
```

Inside `Child`, Python mangles it to:

```text
_Child__value
```

Therefore, the same object contains two distinct attributes.

### Internal Representation

```text
Child Object
    |
    |-- _Parent__value = 100
    |
    |-- _Child__value  = 200
```

### Key Takeaway

Private names with double underscores help prevent accidental collisions between attributes defined in different classes.

# 8. Are Private Members Inherited?

This question requires careful explanation.

Consider:

```python
class Parent:

    def __init__(self):
        self.__secret = 100

    def show_secret(self):
        print(self.__secret)


class Child(Parent):
    pass


obj = Child()

obj.show_secret()
```

### Output

```text
100
```

The inherited parent method can access the private attribute.

But:

```python
print(obj.__secret)
```

raises an `AttributeError`.

### Why?

The attribute is stored as:

```python
obj._Parent__secret
```

The parent method was compiled to reference the mangled name.

### Important Distinction

It is inaccurate to say that private members are never inherited.

A subclass instance can contain attributes initialized by its parent and inherit methods that access them.

However, writing `self.__secret` directly inside the subclass refers to a different mangled name.

### Interview Answer

Private members participate in normal Python object behavior, but name mangling prevents subclasses from accidentally referencing or overriding them using the same double-underscore spelling.

# 9. Private Methods in Python

Double underscores also work with method names.

### Example

```python
class Authentication:

    def __init__(self, password):
        self.__password = password

    def __verify_password(self, password):
        return self.__password == password

    def login(self, password):
        if self.__verify_password(password):
            print("Login successful")
        else:
            print("Invalid password")


auth = Authentication("python123")

auth.login("python123")
auth.login("wrong")
```

### Output

```text
Login successful
Invalid password
```

The internal method:

```python
__verify_password()
```

is called from:

```python
login()
```

But calling:

```python
auth.__verify_password("python123")
```

raises an `AttributeError`.

### Can We Still Access It?

Yes.

```python
print(
    auth._Authentication__verify_password("python123")
)
```

### Output

```text
True
```

Again, name mangling is intended to avoid accidental access and naming conflicts, not to guarantee secrecy.

# 10. Double Underscore vs Dunder Methods

Do not confuse:

```python
__name
```

with:

```python
__name__
```

They have different meanings.

## Double Leading Underscore

```python
self.__balance
```

Triggers name mangling inside a class definition.

## Double Leading and Trailing Underscores

```python
__init__
__str__
__repr__
__len__
```

These are commonly called **dunder methods**, short for double underscore methods.

They are special names used by Python's object model.

### Example

```python
class Student:

    def __init__(self, name):
        self.name = name

    def __str__(self):
        return f"Student({self.name})"


student = Student("Ali")

print(student)
```

### Output

```text
Student(Ali)
```

### Are Dunder Methods Name-Mangled?

No.

Names such as:

```python
__init__
```

are not name-mangled.

### Comparison

| Name | Meaning | Name Mangling |
|---|---|---|
| `name` | Public | No |
| `_name` | Non-public convention | No |
| `__name` | Private-style identifier | Yes, in class scope |
| `__name__` | Dunder name | No |
| `name_` | Often avoids naming conflicts with keywords | No |

### Important

Avoid inventing custom double-leading-and-trailing-underscore names.

These naming patterns are reserved for Python-defined special use.

# 11. Access Modifiers With Class Variables

Access conventions apply to class attributes as well as instance attributes.

### Example

```python
class Configuration:

    app_name = "MyApp"

    _version = "1.0"

    __api_key = "demo-key"


print(Configuration.app_name)

print(Configuration._version)

print(Configuration._Configuration__api_key)
```

### Output

```text
MyApp
1.0
demo-key
```

### Explanation

- `app_name` is public.
- `_version` is non-public by convention.
- `__api_key` is name-mangled.

### Important Security Warning

Double underscores do not protect credentials.

Never rely on name mangling to hide passwords, API keys, or secrets stored directly in source code.

Use appropriate credential management mechanisms.

# 12. Getters and Setters

Access modifiers alone do not validate state.

To control how attributes are accessed or modified, we can use getter and setter methods.

## Getter

A getter retrieves an attribute's value.

## Setter

A setter updates an attribute, potentially performing validation.

### Example

```python
class BankAccount:

    def __init__(self, balance):
        self.__balance = balance

    def get_balance(self):
        return self.__balance

    def set_balance(self, balance):
        if balance >= 0:
            self.__balance = balance
        else:
            print("Balance cannot be negative")


account = BankAccount(1000)

print(account.get_balance())

account.set_balance(2000)

print(account.get_balance())

account.set_balance(-500)

print(account.get_balance())
```

### Output

```text
1000
2000
Balance cannot be negative
2000
```

### What Is Happening?

The getter:

```python
get_balance()
```

exposes the value.

The setter:

```python
set_balance()
```

checks whether the new balance is valid.

### Problem With Traditional Getters and Setters

Python often favors property syntax rather than writing explicit getters and setters for every attribute.

For example:

```python
account.get_balance()
```

is less natural than:

```python
account.balance
```

while maintaining controlled access.

Python provides the `@property` decorator for this.

---

# 13. The `@property` Decorator

`@property` allows us to control attribute access while exposing a natural attribute-like interface.

It is commonly used for encapsulation.

## Example

```python
class Employee:

    def __init__(self, salary):
        self._salary = salary

    @property
    def salary(self):
        return self._salary

    @salary.setter
    def salary(self, value):
        if value < 0:
            raise ValueError("Salary cannot be negative")

        self._salary = value


employee = Employee(50000)

print(employee.salary)

employee.salary = 60000

print(employee.salary)
```

### Output

```text
50000
60000
```

### Explanation

The getter:

```python
@property
def salary(self):
    return self._salary
```

is executed when:

```python
employee.salary
```

is accessed.

The setter:

```python
@salary.setter
def salary(self, value):
```

is executed when:

```python
employee.salary = 60000
```

is performed.

### Invalid Assignment

```python
employee.salary = -1000
```

### Result

```text
ValueError: Salary cannot be negative
```

### Important Detail

This example validates assignments through the property, but the constructor initializes `_salary` directly.

A stronger implementation should also validate the initial value.

---

# 14. A Better Property-Based Implementation

```python
class Employee:

    def __init__(self, salary):
        self.salary = salary

    @property
    def salary(self):
        return self._salary

    @salary.setter
    def salary(self, value):
        if value < 0:
            raise ValueError("Salary cannot be negative")

        self._salary = value


employee = Employee(50000)

print(employee.salary)
```

### Output

```text
50000
```

### Why Is This Better?

During construction:

```python
self.salary = salary
```

calls the property setter.

Therefore, invalid initial values are rejected too.

### Important Concept: Encapsulation

The public interface is:

```python
employee.salary
```

The implementation uses:

```python
employee._salary
```

The class controls normal assignment through the public property.

However, external code can still directly modify `_salary`.

Python's encapsulation is based on cooperative conventions, not absolute restrictions.

# 15. Read-Only Properties

Sometimes we want users to read an attribute but not assign a new value through its public interface.

### Example

```python
class Circle:

    def __init__(self, radius):
        self._radius = radius

    @property
    def area(self):
        return 3.14 * self._radius ** 2


circle = Circle(5)

print(circle.area)
```

### Output

```text
78.5
```

Now:

```python
circle.area = 100
```

raises:

```text
AttributeError
```

### Why?

The property defines a getter but no setter.

Therefore, the property cannot be assigned through its public name.

### Important

A read-only property does not make the entire object immutable.

For instance:

```python
circle._radius = 10
```

can still modify the underlying state.

Also, if the property returns a mutable object, callers may be able to mutate that object.

---

# 16. Property Deleters

Properties can also control deletion.

### Example

```python
class Student:

    def __init__(self, name):
        self._name = name

    @property
    def name(self):
        return self._name

    @name.setter
    def name(self, value):
        self._name = value

    @name.deleter
    def name(self):
        print("Deleting name")
        del self._name


student = Student("Ali")

print(student.name)

student.name = "Sara"

print(student.name)

del student.name
```

### Output

```text
Ali
Sara
Deleting name
```

### Property Decorators

| Decorator | Purpose |
|---|---|
| `@property` | Getter |
| `@attribute.setter` | Setter |
| `@attribute.deleter` | Deleter |

All three are optional in the sense that a property may be defined with only the accessor operations it needs.

# 17. Real-World Example: Encapsulated Bank Account

Let's combine access conventions, private attributes, properties, and validation.

```python
class BankAccount:

    def __init__(self, owner, initial_balance=0):

        if initial_balance < 0:
            raise ValueError(
                "Initial balance cannot be negative"
            )

        self.owner = owner
        self.__balance = initial_balance

    @property
    def balance(self):
        return self.__balance

    def deposit(self, amount):

        if amount <= 0:
            raise ValueError(
                "Deposit amount must be positive"
            )

        self.__balance += amount

    def withdraw(self, amount):

        if amount <= 0:
            raise ValueError(
                "Withdrawal amount must be positive"
            )

        if amount > self.__balance:
            raise ValueError(
                "Insufficient funds"
            )

        self.__balance -= amount


account = BankAccount("Ali", 1000)

print(account.balance)

account.deposit(500)

print(account.balance)

account.withdraw(300)

print(account.balance)
```

### Output

```text
1000
1500
1200
```

### Why This Is Good Design

**1. Public attribute**

```python
self.owner
```

The account holder's name is exposed directly.

**2. Private-style internal attribute**

```python
self.__balance
```

The internal balance uses name mangling.

**3. Read-only public property**

```python
@property
def balance(self):
```

Allows reading the balance without providing a public assignment setter.

**4. Controlled operations**

```python
deposit()
withdraw()
```

Perform validation before changing the balance.

### Important Limitation

A determined caller can still access the mangled balance name.

This implementation protects application invariants during normal use, but it is not a security boundary or production-ready financial ledger.

# 18. Name Mangling and Method Overriding

This is an advanced and important Python-specific behavior.

Consider:

```python
class Parent:

    def __display(self):
        print("Parent display")

    def call_display(self):
        self.__display()


class Child(Parent):

    def __display(self):
        print("Child display")


obj = Child()

obj.call_display()
```

### Output

```text
Parent display
```

### Why Doesn't the Child Method Override It?

Inside `Parent`:

```python
__display
```

becomes:

```python
_Parent__display
```

Inside `Child`:

```python
__display
```

becomes:

```python
_Child__display
```

They are different method names.

Therefore, the child's method does not override the parent's method.

### Compare With Protected Methods

```python
class Parent:

    def _display(self):
        print("Parent display")

    def call_display(self):
        self._display()


class Child(Parent):

    def _display(self):
        print("Child display")


obj = Child()

obj.call_display()
```

### Output

```text
Child display
```

### Explanation

Both classes use the same method name:

```python
_display
```

Python resolves the method using normal method lookup and dispatch.

The child implementation overrides the parent method.

### Major Difference

| Protected Method | Private-Style Method |
|---|---|
| `_display()` | `__display()` |
| No name mangling | Name mangling |
| Naturally overridden by subclasses | Same spelling in subclass becomes a different name |
| Suitable for subclass extension points | Suitable for avoiding accidental collisions |

### Design Recommendation

Use single-underscore methods when subclasses are intended to override or extend behavior.

Use double-underscore methods when avoiding accidental subclass name collisions is important.

# 19. How Name Mangling Works at Class Definition Time

Name mangling occurs as Python compiles identifiers within the class definition.

It is not a runtime access-control check.

### Example

```python
class Example:

    def __init__(self):
        self.__value = 10


obj = Example()

print(obj.__dict__)
```

### Output

```text
{'_Example__value': 10}
```

When Python compiles:

```python
self.__value
```

inside `Example`, the identifier becomes effectively:

```python
self._Example__value
```

### Is the Class Name Always Included?

For ordinary class names, yes.

Python's mangling rules remove leading underscores from the class name when constructing the mangled identifier.

For example:

```python
class _Example:

    def __init__(self):
        self.__value = 10


obj = _Example()

print(obj.__dict__)
```

### Output

```text
{'_Example__value': 10}
```

The stored name reflects the class name after removing its leading underscores.

### Does Name Mangling Apply Everywhere?

No.

It applies to qualifying identifiers in class definition scope, including names used in methods defined there.

It does not automatically mangle arbitrary strings passed to functions.

Consider:

```python
class Demo:

    def __init__(self):
        self.__value = 10


obj = Demo()

print(getattr(obj, "_Demo__value"))
```

### Output

```text
10
```

But:

```python
getattr(obj, "__value")
```

raises an `AttributeError`, because the string is not rewritten.

### Key Point

Name mangling happens to identifiers in class scope, not to arbitrary string values.

# 20. Single Underscore in Modules

A single leading underscore is also used outside classes.

### Example

File: `utilities.py`

```python
PUBLIC_VALUE = 10

_INTERNAL_VALUE = 20


def display():
    print("Public function")


def _helper():
    print("Internal helper")
```

The underscore indicates that `_INTERNAL_VALUE` and `_helper()` are intended for internal module use.

### Special Behavior of Wildcard Imports

```python
from utilities import *
```

By default, wildcard imports exclude names beginning with `_`.

Therefore:

```python
print(PUBLIC_VALUE)
```

works.

But:

```python
print(_INTERNAL_VALUE)
```

normally produces a `NameError`.

### Important Exception

A module can define `__all__` to explicitly control the exported names for wildcard imports.

Names listed in `__all__` can include underscore-prefixed identifiers.

### Can We Import Internal Names Explicitly?

Yes.

```python
from utilities import _INTERNAL_VALUE

print(_INTERNAL_VALUE)
```

### Output

```text
20
```

Again, the underscore is primarily a convention.

# 21. Access Modifiers vs Encapsulation vs Abstraction

These concepts are closely related but not identical.

## Access Modifiers

Communicate the intended accessibility of attributes and methods.

Example:

```python
self._balance
self.__balance
```

## Encapsulation

Bundles related data and behavior inside objects and controls how state is manipulated.

Example:

```python
account.deposit(500)
```

instead of allowing arbitrary balance changes.

## Abstraction

Exposes essential functionality while hiding unnecessary implementation details.

Example:

```python
payment.process_payment(500)
```

without requiring the caller to know how the provider processes the payment.

### Comparison

| Concept | Main Focus |
|---|---|
| Access conventions | Which members are intended for external use |
| Encapsulation | Organizing and controlling object state |
| Abstraction | Exposing functionality while hiding complexity |

### Important Connection

Naming conventions help communicate encapsulation boundaries.

Properties and methods can enforce validation rules during normal access.

Abstraction determines which operations callers should depend on.

# 22. Common Mistakes

## Mistake 1: Believing `_name` Is Enforced Protected Access

```python
obj._name
```

is accessible.

Python does not restrict it to subclasses.

## Mistake 2: Believing `__name` Provides Absolute Privacy

```python
obj._ClassName__name
```

can access a name-mangled attribute in ordinary cases.

## Mistake 3: Confusing `__name` and `__name__`

These have different purposes.

Only qualifying double-leading-underscore identifiers are name-mangled.

## Mistake 4: Using Double Underscores for Every Internal Attribute

Double underscores are not required for encapsulation.

Often:

```python
self._balance
```

is sufficient.

Use double underscores when preventing accidental subclass collisions is valuable.

## Mistake 5: Assuming Read-Only Properties Make Objects Immutable

A property without a setter prevents assignment through that property name.

It does not necessarily prevent changes through other attributes or references.

## Mistake 6: Using Properties Without Validation Where Validation Is Needed

```python
self._age = -10
```

is still possible unless application logic validates the value.

## Mistake 7: Assuming a Private-Style Method Can Be Overridden Normally

A subclass method with the same `__method` spelling receives a different mangled name.

## Mistake 8: Treating Access Conventions as Security

Private-style attributes do not provide credential protection, authorization, or isolation from untrusted code.

# 23. Interview Questions and Answers

## Q1. What are access modifiers in Python?

Access modifiers describe the intended visibility of class members.

Python uses naming conventions for public and protected-style members and name mangling for private-style members.

It does not enforce traditional access-control modifiers like Java or C++.

## Q2. How many types of access modifiers are commonly discussed in Python?

Three:

1. Public
2. Protected
3. Private

These correspond to `name`, `_name`, and `__name`.

## Q3. Is there a `private` keyword in Python?

No.

Python uses double-leading-underscore names for name mangling.

## Q4. What is name mangling?

Name mangling is the transformation of qualifying double-underscore-prefixed identifiers inside a class definition into names incorporating the class name.

Example:

```python
__balance
```

becomes:

```python
_BankAccount__balance
```

when defined inside `BankAccount`.

## Q5. Can protected attributes be accessed outside the class?

Yes.

A single underscore is only a naming convention.

## Q6. Can private attributes be accessed outside the class?

Yes, through their mangled names in ordinary Python code.

They are not strictly inaccessible.

## Q7. What is the difference between `_name` and `__name`?

`_name` communicates that a member is intended for internal use.

`__name` triggers name mangling in class scope and helps avoid accidental subclass collisions.

## Q8. Are private attributes inherited?

Private-style attributes can exist on subclass instances, and inherited parent methods can access them.

However, the same `__name` spelling in a child class is mangled using the child class name.

## Q9. Can private methods be overridden?

A method with the same double-underscore spelling in a subclass usually has a different mangled name, so it does not override the parent's method under that spelling.

## Q10. What is the difference between `__init__` and `__value`?

`__init__` is a Python special method and is not name-mangled.

`__value` is a private-style identifier that triggers name mangling in class scope.

## Q11. What is the use of `@property`?

`@property` allows methods to provide controlled attribute-like access.

It can support validation, computed values, and read-only interfaces.

## Q12. What happens if we define a property without a setter?

Assignments through that property name raise an `AttributeError` in normal usage.

## Q13. Does Python support strict private variables?

No, not through standard naming conventions or name mangling.

Python code can generally inspect or modify object internals using ordinary mechanisms.

## Q14. Why would we use `__name` instead of `_name`?

To reduce accidental attribute or method name collisions when designing classes that may be subclassed.

## Q15. Which naming style is more Pythonic for internal attributes?

A single leading underscore is often preferred for ordinary non-public implementation details.

Use double underscores selectively when name mangling provides a concrete benefit.

| Feature | Syntax | Enforced Access Restriction? |
|---|---|---|
| Public attribute | `self.name` | No |

| Protected-style method | `def _show(self)` | No |

### Most Important Rules

1. Python doesn't have strict access-modifier keywords.
2. Public names have no leading underscore.
3. A single leading underscore indicates a non-public member.
4. A double leading underscore triggers name mangling in class scope.
5. Name mangling is designed primarily to avoid accidental subclass collisions.
6. Dunder methods are not private methods.
7. Private-style attributes can be accessed through mangled names.
8. `@property` supports controlled attribute-like access.
9. Use validation to protect object invariants.
10. Never rely on underscores for security.

# 27. Final Summary

Access modifiers in Python are best understood as naming conventions and name-mangling behavior rather than strict visibility rules.

### Public

```python
self.name
```

Intended to be accessed freely.

### Protected

```python
self._name
```

Intended for internal and subclass use, but still accessible externally.

### Private

```python
self.__name
```

Uses name mangling to reduce accidental naming conflicts.

### Core Example

```python
class Example:

    def __init__(self):
        self.public = 10
        self._protected = 20
        self.__private = 30

    @property
    def private_value(self):
        return self.__private


obj = Example()

print(obj.public)
print(obj._protected)
print(obj.private_value)

print(obj.__dict__)
```

### Output

```text
10
20
30
{'public': 10, '_protected': 20, '_Example__private': 30}
```

### One-Line Interview Definition

> Access modifiers in Python are implemented primarily through naming conventions and name mangling, with public, protected-style, and private-style members communicating intended accessibility rather than enforcing strict access restrictions.

### Final Concept to Remember

**Public:** Meant for everyone.

**Protected:** Meant for internal use and subclasses.

**Private:** Name-mangled to avoid accidental conflicts.

**`@property`:** Controls ordinary attribute access and modification.

**Encapsulation:** Uses well-designed methods and properties to maintain valid object state.
