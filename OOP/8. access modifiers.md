# Topic 8: Access Modifiers

> **TL;DR:** Access modifiers signal **who should use** a class member. Python has no `public` / `protected` / `private` keywords: it uses **naming conventions** (`name`, `_name`) and **name mangling** (`__name` → `_ClassName__name`). Nothing is truly private; use **methods and `@property`** to keep object state valid.

---

## 1. What Are Access Modifiers?

**Access modifiers** define the intended **visibility** of a class's attributes and methods: which parts are the public API and which are internal implementation. They are closely tied to **encapsulation** (see [Topic 6: Encapsulation](6.%20Encapsulation.md)).

| Access level | Python syntax | Meaning |
|---|---|---|
| **Public** | `name` | Intended for unrestricted access |
| **Protected** | `_name` | Intended for internal use and subclasses (convention only) |
| **Private** | `__name` | Name-mangled to avoid accidental conflicts |

```python
class Example:
    def __init__(self):
        self.public = 10
        self._protected = 20
        self.__private = 30

    @property
    def private_value(self):
        return self.__private

obj = Example()
print(obj.public)          # 10
print(obj._protected)      # 20
print(obj.private_value)   # 30
print(obj.__dict__)        # {'public': 10, '_protected': 20, '_Example__private': 30}
```

### Python vs Java / C++

| | Java / C++ | Python |
|---|---|---|
| Mechanism | Keywords: `public`, `protected`, `private` | Naming conventions + name mangling |
| Enforced by | Compiler | Nobody: cooperative convention |
| Private really hidden? | Yes (barring reflection) | No: reachable as `_ClassName__name` |

- Python does **not** enforce private or protected access. Underscores communicate **intent**.

---

## 2. Why Do We Need Access Modifiers?

A bank account has an owner name, account number, balance, and deposit/withdraw operations. Users may read their info, but external code should **not** change the balance arbitrarily without validation.

```python
class BankAccount:
    def __init__(self, balance):
        self.balance = balance

account = BankAccount(1000)
account.balance = -50000
print(account.balance)   # -50000
```

- **Problem:** any code can assign an invalid balance and break business rules.
- **Goal:** expose controlled operations (`account.deposit(500)`, `account.withdraw(200)`) instead of raw assignment (`account.balance = -50000`). Encapsulation, access conventions and properties make this possible.

**Benefits:**

1. Communicate which members are the **public API**.
2. Reduce **accidental modification** of internal state.
3. Protect **business rules** through controlled methods.
4. Improve **maintainability**.
5. Reduce dependence on **implementation details**.
6. Prevent accidental **naming conflicts** in inheritance.

> Naming conventions alone do **not** enforce security or validate data. Validation needs methods or properties.

## 3. Public Members

A **public** member is meant to be accessed from anywhere. Ordinary attributes and methods are public **by default**; there is no `public` keyword.

```python
class Student:
    def __init__(self, name, age):
        self.name = name          # public attribute
        self.age = age

    def display(self):            # public method
        print(f"Name: {self.name}")
        print(f"Age: {self.age}")

student = Student("Ali", 22)
print(student.name)
print(student.age)
student.display()

student.name = "Ahmed"            # modify freely from outside
print(student.name)
```

```text
Ali
22
Name: Ali
Age: 22
Ahmed
```

- Public attributes can be **read, updated and deleted** from outside the class.
- `self.name` (no underscore) is public by convention.

---

## 4. Protected Members (`_name`)

A **protected** member is intended for use **inside the class and its subclasses**. Python marks it with a **single leading underscore**: `self._attribute`, `def _method(self)`.

```python
class Employee:
    def __init__(self, name, salary):
        self.name = name
        self._salary = salary            # protected attribute

    def _show_salary(self):              # protected method
        print(f"Salary: {self._salary}")

employee = Employee("Ali", 50000)
print(employee.name)       # Ali
print(employee._salary)    # 50000  (still works from outside)
employee._show_salary()    # Salary: 50000
```

- Python does **not enforce** protected access; external code can still read `_salary`.
- The underscore is a signal to other developers: *"implementation detail, don't depend on it from outside."*

### 4.1 Protected Members With Inheritance

Typical use: a subclass needs the parent's internal data or helpers.

```python
class Employee:
    def __init__(self, name, salary):
        self.name = name
        self._salary = salary

    def _calculate_bonus(self):
        return self._salary * 0.10


class Manager(Employee):
    def display_compensation(self):
        bonus = self._calculate_bonus()
        print("Salary:", self._salary)
        print("Bonus:", bonus)


manager = Manager("Sara", 80000)
manager.display_compensation()
print(manager._salary)     # external access still works
```

```text
Salary: 80000
Bonus: 8000.0
80000
```

- The child uses the parent's `_salary` and `_calculate_bonus()`: the **intended** use of protected members.
- **Key point:** protected in Python means *"intended for internal and subclass use"*, **not** *"accessible only by the class and subclasses"*.
- More on subclassing: [Topic 5: Inheritance](5.%20inheritance.md).

## 5. Private Members (`__name`)

A **private** member is meant to avoid accidental access and **name collisions**, especially in subclasses. An identifier that **starts with two underscores and doesn't end with two underscores** triggers **name mangling** inside a class: `self.__attribute`, `def __method(self)`.

```python
class BankAccount:
    def __init__(self, balance):
        self.__balance = balance       # private attribute

    def show_balance(self):
        print(self.__balance)          # works inside the class

account = BankAccount(1000)
account.show_balance()
print(account.__balance)               # fails outside
```

```text
1000
AttributeError: 'BankAccount' object has no attribute '__balance'
```

- It fails because Python **renamed** the attribute internally. This is **name mangling**.

---

## 6. Name Mangling

**Name mangling** rewrites qualifying `__name` identifiers inside a class definition to `_ClassName__name`. It is the key to understanding Python's "private" members.

```text
__balance (inside class BankAccount)  ->  _BankAccount__balance
General pattern:                          _ClassName__attribute
```

### Accessing and modifying the mangled name

```python
class BankAccount:
    def __init__(self, balance):
        self.__balance = balance

account = BankAccount(1000)
print(account._BankAccount__balance)   # 1000

account._BankAccount__balance = 5000
print(account._BankAccount__balance)   # 5000
```

- The double underscore is **not a security boundary**.
- Main purpose: prevent **accidental naming conflicts** between a class and its subclasses.

### 6.1 Internals: What `__dict__` Shows

```python
class Demo:
    def __init__(self):
        self.public = 10
        self._protected = 20
        self.__private = 30

obj = Demo()
print(obj.__dict__)
```

```text
{'public': 10, '_protected': 20, '_Demo__private': 30}
```

| Defined name | Stored name |
|---|---|
| `public` | `public` |
| `_protected` | `_protected` |
| `__private` | `_Demo__private` |

- Only `__private` is renamed. `__dict__` itself is covered in [Topic 1: Classes and Objects](1.%20Classes%20and%20Objects.md).
- **Why?** So a subclass can't **accidentally overwrite** a parent's internal attribute (next section).

## 7. Private Members and Inheritance (interview favorite)

```python
class Parent:
    def __init__(self):
        self.__value = 100

    def show_parent_value(self):
        print(self.__value)


class Child(Parent):
    def __init__(self):
        super().__init__()
        self.__value = 200

    def show_child_value(self):
        print(self.__value)


obj = Child()
obj.show_parent_value()
obj.show_child_value()
print(obj.__dict__)
```

```text
100
200
{'_Parent__value': 100, '_Child__value': 200}
```

- Inside `Parent`, `self.__value` → `_Parent__value`.
- Inside `Child`, `self.__value` → `_Child__value`.
- The same object holds **two distinct attributes**:

```text
Child object
 |-- _Parent__value = 100
 |-- _Child__value  = 200
```

- **Key point:** `__name` keeps attributes defined in different classes from colliding.

### 7.1 Are Private Members Inherited?

```python
class Parent:
    def __init__(self):
        self.__secret = 100

    def show_secret(self):
        print(self.__secret)


class Child(Parent):
    pass


obj = Child()
obj.show_secret()      # 100
print(obj.__secret)    # AttributeError
```

- The attribute is stored as `obj._Parent__secret`. The inherited parent method was compiled to use that mangled name, so it works.
- Saying "private members are never inherited" is **inaccurate**: the subclass instance holds the attribute and inherits methods that use it.
- But writing `self.__secret` **inside the subclass** refers to `_Child__secret`, a different name.
- **Interview answer:** private members behave like normal attributes, but name mangling stops subclasses from accidentally referencing or overriding them with the same `__name` spelling.

## 8. Private Methods

Double underscores work on method names too.

```python
class Authentication:
    def __init__(self, password):
        self.__password = password

    def __verify_password(self, password):     # private helper
        return self.__password == password

    def login(self, password):
        if self.__verify_password(password):
            print("Login successful")
        else:
            print("Invalid password")


auth = Authentication("python123")
auth.login("python123")     # Login successful
auth.login("wrong")         # Invalid password

# auth.__verify_password("python123")                       -> AttributeError
print(auth._Authentication__verify_password("python123"))   # True
```

- `__verify_password()` is called internally from `login()`.
- Calling it by its plain name from outside fails; its mangled name still works.
- Name mangling avoids **accidental** access and naming conflicts; it does not guarantee secrecy.

## 9. Name Mangling and Method Overriding

A **private-style method cannot be overridden** by redefining the same `__name` in a subclass.

```python
class Parent:
    def __display(self):
        print("Parent display")

    def call_display(self):
        self.__display()          # compiled as self._Parent__display()


class Child(Parent):
    def __display(self):          # becomes _Child__display
        print("Child display")


obj = Child()
obj.call_display()                # Parent display
```

- `__display` in `Parent` → `_Parent__display`; in `Child` → `_Child__display`. Different names, so **no override**.

Same code with a **protected** method:

```python
class Parent:
    def _display(self):
        print("Parent display")

    def call_display(self):
        self._display()


class Child(Parent):
    def _display(self):
        print("Child display")


obj = Child()
obj.call_display()                # Child display
```

- Both classes use the same name `_display`, so normal method lookup finds the child's version: it **overrides** (see [Topic 4: Polymorphism](4.%20Polymorphism.md)).

| Protected method | Private-style method |
|---|---|
| `_display()` | `__display()` |
| No name mangling | Name mangling |
| Naturally overridden by subclasses | Same spelling in subclass becomes a different name |
| Suitable for subclass **extension points** | Suitable for avoiding **accidental collisions** |

**Design rule:**

- Use `_method` when subclasses are **meant** to override or extend it.
- Use `__method` when avoiding accidental subclass name collisions matters.

## 10. Internals: How Name Mangling Works

Name mangling happens when Python **compiles the class body**. It is a text rewrite of identifiers, **not a runtime access check**.

```python
class Example:
    def __init__(self):
        self.__value = 10       # compiled as self._Example__value

obj = Example()
print(obj.__dict__)             # {'_Example__value': 10}
```

### Leading underscores in the class name are stripped

```python
class _Example:
    def __init__(self):
        self.__value = 10

obj = _Example()
print(obj.__dict__)             # {'_Example__value': 10}
```

- The mangled name is `_` + class name **without its leading underscores** + `__value`.

### Only identifiers are mangled, not strings

Mangling applies to qualifying identifiers in class scope (including inside its methods). Strings passed to `getattr()`, `setattr()`, `hasattr()` are **not** rewritten.

```python
class Demo:
    def __init__(self):
        self.__value = 10

obj = Demo()
print(getattr(obj, "_Demo__value"))   # 10
getattr(obj, "__value")                # AttributeError: string is not rewritten
```

### Rules summary

- Mangled: names with **2+ leading underscores** and **at most 1 trailing underscore**, written inside a class body.
- Not mangled: dunders like `__init__` (2 trailing underscores), names outside a class (e.g. `obj.__value = 1` at module level creates a plain `__value` attribute; see Practice Question 4), and string values.

## 11. `__name` vs `__name__` (Dunder Methods)

Don't confuse them:

- `__name` (double **leading** underscore only) → **name-mangled** inside a class. e.g. `self.__balance`.
- `__name__` (double leading **and trailing**) → **dunder** ("double underscore") names: special names of Python's object model, e.g. `__init__`, `__str__`, `__repr__`, `__len__`. **Not** name-mangled and **not** private.

```python
class Student:
    def __init__(self, name):
        self.name = name

    def __str__(self):
        return f"Student({self.name})"

student = Student("Ali")
print(student)    # Student(Ali)
```

| Name | Meaning | Name mangling |
|---|---|---|
| `name` | Public | No |
| `_name` | Non-public by convention | No |
| `__name` | Private-style identifier | Yes, in class scope |
| `__name__` | Dunder (special) name | No |
| `name_` | Avoids clashing with a keyword, e.g. `class_` | No |

- Don't invent your own `__name__` style names: that pattern is **reserved** for Python's special use.

## 12. Access Conventions on Class Variables

The same conventions apply to **class attributes**, not just instance attributes.

```python
class Configuration:
    app_name = "MyApp"        # public
    _version = "1.0"          # non-public by convention
    __api_key = "demo-key"    # name-mangled

print(Configuration.app_name)                  # MyApp
print(Configuration._version)                  # 1.0
print(Configuration._Configuration__api_key)   # demo-key
```

- **Security warning:** double underscores do **not** protect credentials. Never hide passwords, API keys or secrets in source code behind name mangling; use proper credential management (environment variables, secret stores).

## 13. Single Underscore in Modules

A leading underscore also marks **module-level** names as internal.

```python
# utilities.py
PUBLIC_VALUE = 10
_INTERNAL_VALUE = 20

def display():
    print("Public function")

def _helper():
    print("Internal helper")
```

```python
from utilities import *

print(PUBLIC_VALUE)       # 10
print(_INTERNAL_VALUE)    # NameError: wildcard import skips _names
```

```python
from utilities import _INTERNAL_VALUE   # explicit import still works

print(_INTERNAL_VALUE)    # 20
```

- `from module import *` skips names starting with `_` **by default**.
- **Exception:** if the module defines `__all__`, wildcard import exports exactly those names, which may include `_names`.
- Again, the underscore is only a **convention**.

## 14. Getters and Setters

Access conventions alone don't **validate** state. **Getter** and **setter** methods control how an attribute is read and changed.

- **Getter** → returns the value.
- **Setter** → updates the value, usually after **validation**.

```python
class BankAccount:
    def __init__(self, balance):
        self.__balance = balance

    def get_balance(self):
        return self.__balance

    def set_balance(self, balance):
        if balance >= 0:
            self.__balance = balance
        else:
            print("Balance cannot be negative")


account = BankAccount(1000)
print(account.get_balance())
account.set_balance(2000)
print(account.get_balance())
account.set_balance(-500)          # rejected
print(account.get_balance())
```

```text
1000
2000
Balance cannot be negative
2000
```

- **Downside:** `account.get_balance()` is clunkier than `account.balance`. Python prefers **`@property`**: attribute-style syntax with the same control. Details also in [Topic 6: Encapsulation](6.%20Encapsulation.md).

## 15. The `@property` Decorator

`@property` turns methods into **controlled attribute access**: callers write `obj.salary`, but your getter/setter code runs. It's Python's standard tool for encapsulation.

```python
class Employee:
    def __init__(self, salary):
        self._salary = salary

    @property
    def salary(self):                  # runs on: employee.salary
        return self._salary

    @salary.setter
    def salary(self, value):           # runs on: employee.salary = value
        if value < 0:
            raise ValueError("Salary cannot be negative")
        self._salary = value


employee = Employee(50000)
print(employee.salary)        # 50000
employee.salary = 60000
print(employee.salary)        # 60000
employee.salary = -1000       # ValueError: Salary cannot be negative
```

- **Gap:** `__init__` sets `_salary` directly, so `Employee(-5)` is **not** validated. Fix below.

### 15.1 Validating the Initial Value Too

```python
class Employee:
    def __init__(self, salary):
        self.salary = salary           # goes through the setter

    @property
    def salary(self):
        return self._salary

    @salary.setter
    def salary(self, value):
        if value < 0:
            raise ValueError("Salary cannot be negative")
        self._salary = value


employee = Employee(50000)
print(employee.salary)        # 50000
```

- `self.salary = salary` in `__init__` calls the **setter**, so invalid initial values are rejected too.
- **Public interface:** `employee.salary`. **Implementation:** `employee._salary`.
- The class controls **normal** assignment, but outside code can still write `employee._salary` directly. Python's encapsulation is **cooperative**, not absolute.
- The setter must store into `_salary`, not `salary`, or it calls itself forever (`RecursionError`).

### 15.2 Read-Only Properties

Define a getter with **no setter** to allow reading but not assignment through the public name.

```python
class Circle:
    def __init__(self, radius):
        self._radius = radius

    @property
    def area(self):
        return 3.14 * self._radius ** 2


circle = Circle(5)
print(circle.area)        # 78.5
circle.area = 100         # AttributeError (no setter)
```

- Error text varies by version, e.g. `property 'area' of 'Circle' object has no setter` (3.11+) or `can't set attribute`.
- A read-only property does **not** make the object immutable: `circle._radius = 10` still changes the underlying state.
- If the property returns a **mutable** object (list, dict), callers can still mutate that object.

### 15.3 Property Deleters

```python
class Student:
    def __init__(self, name):
        self._name = name

    @property
    def name(self):
        return self._name

    @name.setter
    def name(self, value):
        self._name = value

    @name.deleter
    def name(self):
        print("Deleting name")
        del self._name


student = Student("Ali")
print(student.name)
student.name = "Sara"
print(student.name)
del student.name
```

```text
Ali
Sara
Deleting name
```

| Decorator | Purpose |
|---|---|
| `@property` | Getter |
| `@attribute.setter` | Setter |
| `@attribute.deleter` | Deleter |

- Define only the operations you need (e.g. getter only = read-only).

## 16. Real-World Example: Encapsulated Bank Account

Combines access conventions, a private attribute, a read-only property and validation.

```python
class BankAccount:
    def __init__(self, owner, initial_balance=0):
        if initial_balance < 0:
            raise ValueError("Initial balance cannot be negative")
        self.owner = owner                 # public
        self.__balance = initial_balance   # private-style

    @property
    def balance(self):                     # read-only: no setter
        return self.__balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Deposit amount must be positive")
        self.__balance += amount

    def withdraw(self, amount):
        if amount <= 0:
            raise ValueError("Withdrawal amount must be positive")
        if amount > self.__balance:
            raise ValueError("Insufficient funds")
        self.__balance -= amount


account = BankAccount("Ali", 1000)
print(account.balance)
account.deposit(500)
print(account.balance)
account.withdraw(300)
print(account.balance)
```

```text
1000
1500
1200
```

**Why this is good design:**

1. **Public attribute** `self.owner`: the holder's name is exposed directly.
2. **Private-style attribute** `self.__balance`: internal state, name-mangled.
3. **Read-only property** `balance`: readable, but no public setter.
4. **Controlled operations** `deposit()` / `withdraw()`: validate before changing the balance.

- **Limitation:** a determined caller can still use `account._BankAccount__balance`. This protects invariants during **normal use**; it is not a security boundary or a production-ready ledger.

## 17. Access Modifiers vs Encapsulation vs Abstraction

Closely related, not identical.

- **Access modifiers** communicate the intended accessibility of members: `self._balance`, `self.__balance`.
- **Encapsulation** bundles data with behavior and controls how state changes: `account.deposit(500)` instead of arbitrary balance edits. See [Topic 6: Encapsulation](6.%20Encapsulation.md).
- **Abstraction** exposes essential operations and hides implementation details: `payment.process_payment(500)` without knowing how the provider processes it. See [Topic 7: Abstraction](7.%20abstraction.md).

| Concept | Main focus |
|---|---|
| Access conventions | Which members are intended for external use |
| Encapsulation | Organizing and controlling object state |
| Abstraction | Exposing functionality while hiding complexity |

- **Connection:** naming conventions mark encapsulation boundaries; properties and methods enforce validation during normal access; abstraction decides which operations callers should depend on.

## 18. Common Mistakes / Gotchas

- **Believing `_name` is enforced protected access** → `obj._name` works from anywhere; Python doesn't restrict it to subclasses.
- **Believing `__name` gives absolute privacy** → `obj._ClassName__name` still reaches it.
- **Confusing `__name` with `__name__`** → only `__name` (no trailing double underscore) is mangled; dunders are special methods, not private ones.
- **Using `__` for every internal attribute** → unnecessary; `self._balance` is usually enough. Use `__` only when accidental subclass collisions are a real risk.
- **Assuming a read-only property makes the object immutable** → it only blocks assignment through that name; other attributes and mutable return values can still change.
- **Skipping validation where it's needed** → `self._age = -10` is still possible unless a setter/method validates it. Also route `__init__` through the setter.
- **Expecting a `__method` to be overridden normally** → the subclass's `__method` gets a different mangled name; use `_method` for extension points.
- **Assigning `obj.__value = x` outside the class** → creates a **new** plain `__value` attribute; the mangled `_ClassName__value` is unchanged (Practice Question 4).
- **Passing `"__value"` to `getattr()`** → strings aren't mangled; use `"_ClassName__value"`.
- **Treating access conventions as security** → no credential protection, authorization, or isolation from untrusted code.

## 19. Interview Questions

**Q1. What are access modifiers in Python?**
They describe the intended visibility of class members. Python uses naming conventions for public/protected members and name mangling for private ones; nothing is enforced like in Java or C++.

**Q2. How many types of access modifiers are commonly discussed in Python?**
Three: **public** (`name`), **protected** (`_name`), **private** (`__name`).

**Q3. Is there a `private` keyword in Python?**
No. Double-leading-underscore names trigger name mangling instead.

**Q4. What is name mangling?**
Rewriting a `__name` identifier inside a class definition to include the class name: `__balance` in `BankAccount` becomes `_BankAccount__balance`.

**Q5. Can protected attributes be accessed outside the class?**
Yes. A single underscore is only a naming convention.

**Q6. Can private attributes be accessed outside the class?**
Yes, through their mangled names (`obj._ClassName__name`). They are not strictly inaccessible.

**Q7. What is the difference between `_name` and `__name`?**
`_name` signals internal use (no renaming). `__name` triggers name mangling in class scope, which avoids accidental subclass collisions.

**Q8. Are private attributes inherited?**
They exist on subclass instances and inherited parent methods can use them. But `__name` written inside the child is mangled with the child's class name, so it's a different attribute.

**Q9. Can private methods be overridden?**
Not under the same `__name` spelling: the subclass version gets a different mangled name, so the parent still calls its own.

**Q10. What is the difference between `__init__` and `__value`?**
`__init__` is a special (dunder) method and is not mangled. `__value` is a private-style name and is mangled in class scope.

**Q11. What is the use of `@property`?**
It gives controlled, attribute-style access backed by methods: validation, computed values, and read-only interfaces.

**Q12. What happens if we define a property without a setter?**
Assigning through that property name raises `AttributeError`.

**Q13. Does Python support strict private variables?**
No, not through naming conventions or name mangling. Ordinary Python code can inspect or modify object internals.

**Q14. Why would we use `__name` instead of `_name`?**
To reduce accidental attribute or method name collisions in classes designed to be subclassed.

**Q15. Which naming style is more Pythonic for internal attributes?**
A single leading underscore. Use double underscores selectively when name mangling gives a concrete benefit.

</details>

**3. What does this print?**

```python
class Parent:
    def __show(self):
        print("Parent")

    def display(self):
        self.__show()

class Child(Parent):
    def __show(self):
        print("Child")

obj = Child()
obj.display()
```

(a) `Parent`  (b) `Child`  (c) `AttributeError`  (d) `Parent` then `Child`

<details><summary>Answer</summary>

**(a) `Parent`**: `display()` calls `self._Parent__show()`. The child's method is `_Child__show`, so it doesn't override.

</details>

**4. What does this print? (edge case)**

```python
class Demo:
    def __init__(self):
        self.__value = 100

obj = Demo()
obj.__value = 200
print(obj.__dict__)
```

(a) `{'_Demo__value': 200}`  (b) `{'_Demo__value': 100, '__value': 200}`  (c) `{'__value': 200}`  (d) `AttributeError`

<details><summary>Answer</summary>

**(b)**: inside the class, `self.__value` became `_Demo__value`. Outside the class, `obj.__value = 200` is **not** mangled, so it creates a separate attribute literally named `__value`. The private-style attribute is unchanged.

</details>

**5. Coding: Employee salary management.** Create an `Employee` class with a public `name`, a non-public `_department`, a private-style `__salary`, a read-only `salary` property, and a `give_raise(amount)` method. Salary can't be negative; the raise must be positive; external code should use only public methods/properties.

<details><summary>Answer</summary>

```python
class Employee:
    def __init__(self, name, department, salary):
        if salary < 0:
            raise ValueError("Salary cannot be negative")
        self.name = name
        self._department = department
        self.__salary = salary

    @property
    def salary(self):              # read-only: no setter
        return self.__salary

    def give_raise(self, amount):
        if amount <= 0:
            raise ValueError("Raise amount must be positive")
        self.__salary += amount


e = Employee("Ali", "IT", 50000)
e.give_raise(5000)
print(e.salary)    # 55000
```

</details>

**6. Coding: Student marks.** Create a `Student` class with a public `name`, a private-style `__marks`, a `marks` property whose setter validates 0-100, and a `calculate_grade()` method.

<details><summary>Answer</summary>

```python
class Student:
    def __init__(self, name, marks):
        self.name = name
        self.marks = marks             # validated by the setter

    @property
    def marks(self):
        return self.__marks

    @marks.setter
    def marks(self, value):
        if not 0 <= value <= 100:
            raise ValueError("Marks must be between 0 and 100")
        self.__marks = value

    def calculate_grade(self):
        if self.__marks >= 90:
            return "A"
        if self.__marks >= 75:
            return "B"
        if self.__marks >= 50:
            return "C"
        return "F"


s = Student("Sara", 82)
print(s.calculate_grade())   # B
```

</details>

**7. Coding: Inheritance and name mangling.** Starting from `class Parent: pass` and `class Child(Parent): pass`, define an attribute called `__value` in both classes, then inspect `obj.__dict__` to see how Python stores them.

<details><summary>Answer</summary>

```python
class Parent:
    def __init__(self):
        self.__value = "parent"


class Child(Parent):
    def __init__(self):
        super().__init__()
        self.__value = "child"


obj = Child()
print(obj.__dict__)   # {'_Parent__value': 'parent', '_Child__value': 'child'}
```

Two separate attributes: each class's `__value` is mangled with that class's name.

</details>

## Quick Recap

| Feature | Syntax | Access enforced? |
|---|---|---|
| Public attribute / method | `self.name`, `def show(self)` | No |
| Protected-style attribute / method | `self._name`, `def _show(self)` | No |
| Private-style attribute / method | `self.__name`, `def __show(self)` | No; name mangling only |
| Special (dunder) method | `def __str__(self)` | Not name-mangled |
| Property getter | `@property` | Controls ordinary access |
| Property setter | `@name.setter` | Controls ordinary assignment |
| Property deleter | `@name.deleter` | Controls ordinary deletion |

- Python has **no** access-modifier keywords; underscores signal intent.
- **Public** (`name`, no underscore) → meant for everyone.
- **Protected** (`_name`) → meant for internal and subclass use, but still accessible from outside.
- **Private** (`__name`) → **name-mangled** to `_ClassName__name` in class scope, mainly to avoid accidental subclass collisions.
- Mangling happens at **compile time** on identifiers, not on strings, not outside the class, not on dunders.
- `__method` in a subclass does **not override** the parent's `__method`; use `_method` for extension points.
- **Dunder** methods (`__init__`) are special methods, not private ones.
- Private-style members are still reachable via mangled names.
- **`@property`** gives controlled attribute-style access; validate in the setter and route `__init__` through it to protect invariants.
- **Never** rely on underscores for security.

> **Core idea:** access modifiers in Python are naming conventions plus name mangling. They communicate intended accessibility rather than enforce it; methods and properties are what keep object state valid.
